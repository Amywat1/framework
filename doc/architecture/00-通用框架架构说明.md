# 通用框架架构说明

## 1. 定位

`wash-device-framework` 是面向洗车设备的通用软件框架。它把稳定的设备业务能力沉淀到框架中，把项目差异留在 wiring、配置、绑定表和 provider 中。

框架当前覆盖：

- 运行时启动、线程注册、周期任务和事件总线。
- 命令网关、运行模式、洗车编排和状态投影。
- 洗车控制引擎、表达式、模板展开和 profile 查询接口。
- 报警注册、安全姿态、报警桥接和通用 detector helper。
- 设备控制通用模式，包括运动、旋转、互锁和流体路径。
- HAL、存储、云端的端口契约和部分通用适配器。

## 2. 架构原则

框架采用 DDD 分层、Ports & Adapters 和事件驱动运行时。

核心原则：

- 领域层表达业务规则，不依赖硬件、文件系统、云 SDK 或具体项目。
- 外部系统通过端口接入，具体实现由 adapter 或项目 provider 注册。
- 运行时负责启动和调度，不承载项目业务规则。
- 项目资产通过配置、绑定和 provider 注入，不修改框架核心逻辑。
- 通用能力必须跨项目可复用，项目专属表格和机型资产不进入框架。

## 3. 分层视图

```text
demo / project wiring / adapters
        ↓
ports / application
        ↓
domain
        ↓
common

runtime 负责启动、线程、事件分发和周期任务编排。
```

各层职责：

| 层 | 职责 |
|----|------|
| `common` | 错误码、日志、时间、事件类型、基础工具 |
| `runtime` | 启动编排、事件总线、线程注册、周期任务 |
| `domain` | 洗车、命令、安全、设备控制、状态快照等领域规则 |
| `application` | 领域模块之间的编排、桥接、投影和恢复处理 |
| `ports` | 入站、出站契约 |
| `adapters` | HAL、存储、云端、仿真和 runtime provider 实现 |
| `services` | 参数服务等共享服务 |
| `cloud` | 通用云点位模型、上下行转换和变化检测 |
| `observability` | 观测记录发布与故障黑匣子采样 |
| `demo` | 最小集成验证和项目接入示例 |

`observability` 是与业务无关的诊断设施：`core/observation` 提供非阻塞的观测记录
发布（事件、日志、状态、趋势、故障快照五类，普通与关键双队列），
`recorder/blackbox_recorder` 提供循环采样缓冲，故障发生时冻结现场供事后取回。
两者只依赖 `common`，不参与业务判定；记录如何落盘或外发由项目侧决定。

## 4. 设计边界

框架不包含具体机型的 IO 表、报警目录、云物模型表、水路拓扑表、真机 wiring 和洗车方案资产。这些内容由项目仓库或项目目录维护。

当项目能力具备跨项目复用价值时，应先抽象成端口、helper、通用模式或可配置模型，再进入框架。
