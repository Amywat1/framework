# 框架优化方向

## 1. 文档定位

本文档用于指导 `wash-device-framework` 后续优化方向。它不描述具体代码实现细节，而是记录当前通用框架在架构治理、项目接入、运行可靠性和可维护性上的改进重点。

优化原则：

- 优先增强通用框架能力，不迁入项目专属资产。
- 优先把文档约束转化为代码检查、启动期校验或测试。
- 优先补齐可观测性和接入可靠性，再扩展新业务能力。
- 对洗车机这类嵌入式项目，不以追求纯 DDD / 纯六边形为目标；可靠、可诊断、可接入、可复用优先。
- 对会显著增加抽象层、调用链和排查成本的改造，应先评估真实收益。
- 每项优化应同步更新 `module-design/` 中对应模块设计，并补充重新生成的单元测试。

## 2. 总体评价

当前框架方向是合理的，已经具备通用洗车机框架的主要骨架：

- 框架与项目资产边界清楚。
- DDD 分层和 Ports & Adapters 方向正确。
- 命令、运行模式、报警、安全姿态、方案引擎、事件总线和状态投影已经形成核心闭环。
- profile、detector、水路和模板能力的沉淀比较克制，未直接迁入具体机型表格。
- 文档已拆分为 `architecture/` 和 `module-design/`，具备方案评审和代码基线两种视角。

后续优化重点不是继续搬迁项目表格，而是让框架更可验证、更可接入、更难被项目代码污染。

## 3. 嵌入式项目性价比判断

洗车机软件具备嵌入式项目的典型特点：硬件链路长、现场问题复现困难、安全状态重要、项目接入差异多。对这类系统，架构优化应优先服务于启动期发现问题、运行期定位问题和安全行为可验证。

因此，当前不建议为了架构纯度做大规模重构。只要通用框架不依赖具体 adapter、SDK、项目资产和机型表格，当前工程化六边形架构已经具备继续演进的基础。

高性价比方向：

- 项目接入契约检查。
- 事件总线统计和诊断。
- 安全状态矩阵和命令允许矩阵。
- 依赖边界自动检查。
- 全局注册生命周期规范。

中等性价比方向：

- 错误模型统一。
- 配置与资产版本化。
- 状态投影一致性策略。
- HAL provider 边界收紧。

低性价比或暂不优先方向：

- 为了纯 DDD，把所有 domain event 都抽象一层再发布。
- 把所有 domain 使用的 port 都迁入 domain 内部。
- 把 application 对 event bus 的依赖完全端口化。
- 把当前框架全面改造成教科书式 Clean Architecture。

这些低性价比方向不是错误方向，但只有在测试隔离、事件系统替换、多运行时支持或模块复用边界出现真实痛点时才建议推进。

| 优先级 | 性价比 | 方向 | 实施策略 | 状态 |
|--------|--------|------|----------|------|

| P0 | 高 | 事件总线可观测性 | 增加统计、队列水位、失败计数和慢 handler 诊断 | 已完成 |
| P0 | 高 | 安全状态矩阵 | 明确报警、安全姿态、命令允许和恢复路径 | 未开始 |
| P1 | 高 | 依赖边界自动检查 | 用脚本防止 domain、ports、common 被 adapter 或项目语义污染 | 已完成 |
| P1 | 高 | 全局注册生命周期治理 | 统一 register/reset/reinit 语义，降低测试和重启风险 | 已完成（端口与线程表；domain 全局态、bootstrap 失败路径未覆盖） |
| P2 | 中 | 错误模型统一 | 在错误码开始分散前建立错误语义和处理策略 | 未开始 |

另有一轮针对并发缺陷与工程化护栏的修复，见第 15 节。

## 5. P0：项目接入契约检查

### 问题

当前项目接入已拆分为 register/configure/bind/validate/init/start 阶段，但缺失 port、provider、binding 或资产时，仍可能在运行到某条业务链路时才暴露问题。

### 优化目标

在 `project_validate()` 及框架侧校验点提供统一的启动期接入检查，使项目错误尽早失败。

建议检查项：

- 必需 port 是否已注册。
- `alarm catalog` 是否已加载。
- `cloud model` 是否通过校验。
- `engine_program_loader` 是否注册。
- `engine_io` 和 IO catalog 是否符合项目选择。
- HAL provider 和设备控制 binding 是否完成。
- 配置资产和 manifest 是否存在且版本匹配。

### 验收标准

- bootstrap 阶段能输出明确的接入检查结果。
- 任一必需能力缺失时返回明确错误，不进入运行线程启动。
- Demo 和单元测试覆盖至少一个缺失 port、一个缺失资产和一个非法 binding 场景。

## 6. P1：全局注册生命周期治理

### 问题

当前多个模块采用全局 singleton/register 模式。该模式适合嵌入式 C 框架，但需要统一生命周期语义，否则测试隔离、重复初始化和 bootstrap 失败恢复会变复杂。

### 优化目标

统一以下规则：

- 是否允许重复注册。
- 重复注册是覆盖、拒绝还是幂等成功。
- 是否提供 unregister 或 reset。
- 单元测试如何清理全局状态。
- bootstrap 失败后是否允许重新初始化。

### 建议方案

- 为测试提供 `*_reset_for_test()` 或统一 `framework_reset_for_test()`。
- 对运行期不允许重复注册的 port 返回明确错误。
- 对允许替换的 provider 在文档和 API 名称中表达清楚。
- 在 `module-design/` 中补充各模块注册生命周期表。

### 验收标准

- 单元测试不依赖测试执行顺序。
- 重复注册行为在所有 port/provider 中一致或有明确例外。
- bootstrap 失败路径不会留下不可预测的半初始化状态。

### 落地情况（部分完成）

已完成：端口注册语义统一，见 `ports/port_registry.h`。

- 13 个 `*_register()` 全部返回 `sw_err_t`，不再是 `void`。
  原先 `engine_program_loader_register` 校验失败后静默忽略，调用方无从得知。
- `ops == NULL` 明确为「解除注册」，返回 `SW_OK`。这是受支持的显式操作，
  测试与运行期降级均可使用。
- `ops != NULL` 但缺必填函数指针时返回 `SW_ERR_PARAM`，且**保持原注册不变**，
  不会被半个 ops 覆盖。必填字段只限调用方会无条件解引用的入口：

  | 端口 | 必填字段 | 依据 |
  |------|----------|------|
  | `param_store` | `load` / `save` / `get` / `set` | `svc_param` 只判 ops 非空即调用四者 |
  | `deploy_store` | `load` | bootstrap 只判 ops 非空即调 `load()` |
  | `device_command_port` | `submit` | 本端口唯一入口 |
  | `alarm_binding` | `trigger` / `clear` / `load_catalog` | 适配器无条件调用三者 |
  | `engine_program_loader` | `load` | 本端口唯一入口 |
  | HAL / `machine_ops` / cloud 各端口 | 无 | 调用方逐个判空，允许注册能力子集 |

- 重复注册合法函数表以最后一次为准（替换），返回 `SW_OK`。
- 按注册表分层提供复位：`port_registry_hal_reset()`、`port_registry_infra_reset()`、
  `port_registry_cloud_reset()`。分层而非单一入口，是为避免测试为了一个复位函数
  被迫链接全部三个注册表源文件。

单元测试：`tests/ports/test_cloud_ports.c` 覆盖合法注册、NULL 解除、缺必填字段被拒
且不覆盖原注册、重复注册替换、复位清空，并在 `setUp`/`tearDown` 调用复位消除用例
间顺序耦合。

安全端口后续由弱符号改为注册表绑定（`ports/port_registry_safety.c`），遵循同一套
语义并提供 `port_registry_safety_reset()`，四个注册表的复位入口统一在
`ports/port_registry.h` 声明。

线程登记表也已补 `thread_registry_reset_for_test()`。此前
`tests/runtime/test_scheduler.c` 多个用例硬编码「累加后」的期望值——
`test_register_arg_passes_context` 期望 count 为 2、
`test_periodic_task_register_and_scheduler_start` 依赖前序用例遗留的 one_shot
线程才能观察到执行——顺序耦合比原先记录的一处更普遍。现在 `setUp` 统一复位，
各用例自行注册所需线程；倒序执行全部用例同样通过。

该复位接口只允许测试调用：线程一经 `scheduler_start_all` 创建即 detach 且无法
回收，清空登记表不会停止已启动的线程，生产路径调用会造成登记与实际线程不一致。

仍未完成：

- domain 层全局态（`operational_mode`、`device_snapshot`）依赖各自 `init()` 复位，
  未提供统一 `framework_reset_for_test()`。
- bootstrap 失败路径的半初始化状态尚未系统梳理。

## 7. P0：事件总线可观测性

### 问题

事件总线是框架核心链路。真机问题常见于事件队列满、handler 执行慢、事件处理顺序不符合预期或关键事件被延迟。

### 优化目标

增强事件总线运行统计和诊断能力。

建议能力：

- 每类事件发布计数。
- 每类事件消费计数。
- 队列当前深度和高水位。
- 发布失败和队列满计数。
- handler 最大执行耗时。
- dispatch 线程 fatal 原因记录。

### 验收标准

- 测试可读取 event bus stats。
- 队列满场景有明确返回值和统计。
- 慢 handler 能被统计或告警。
- 安全关键事件的处理策略在文档中明确。

### 落地情况（已完成）

`event_bus_stats_t` 现含下列字段，测试可通过 `event_bus_get_stats()` 读取：

| 能力 | 字段 |
|------|------|
| 总量计数 | `published_count` / `dispatched_count` / `dropped_count` |
| 分类别计数 | `published_by_cat[]` / `dispatched_by_cat[]` / `dropped_by_cat[]`，下标为 `event_category_t` |
| 队列水位 | `queue_depth` / `queue_peak_depth` / `hi_queue_depth` / `hi_queue_peak_depth` |
| 失败计数 | `sem_post_fail_count` / `sem_wait_fail_count` |
| handler 耗时 | `handler_max_ms` / `handler_max_type` / `slow_handler_count` / `dispatch_max_ms` |

慢 handler 门限为 `EVENT_BUS_SLOW_HANDLER_MS`（50ms），超限同时计数并输出告警日志。

事件总线内部诊断已从 `printf` 改为 `sw_log`，队列满、丢事件、`sem_post` 失败等
关键记录会进入已注册的 sink 链（黑匣子、可观测服务），不再只打到 stdout。

dispatch 线程 fatal 原因通过 `event_bus_set_fatal_cb` 回调上报，bootstrap 注册
`system_panic_safe_stop` 置安全输出后 `abort()`。

单元测试：`tests/runtime/test_event_bus.c` 覆盖分类别计数、丢弃归集、慢 handler
识别与快 handler 不误判。

## 8. P0：安全状态矩阵

### 问题

报警、安全姿态、运行模式和命令网关已经形成链路，但安全行为需要更形式化，方便评审、测试和项目接入。

### 优化目标

形成统一安全矩阵：

- 报警响应策略到安全姿态的映射。
- `LOCKOUT` 下允许和拒绝的命令。
- 急停、暂停、停止、恢复、复位的状态转换。
- 安全输出失败时的兜底策略。
- ON_MOTION 重评估触发后的清除边界。

### 验收标准

- `architecture/` 有方案级安全矩阵说明。
- `module-design/` 有代码级状态表和测试映射。
- 单元测试覆盖关键命令在不同安全姿态下的裁决结果。

## 9. P1：依赖边界自动检查

### 问题

当前分层边界主要依靠文档和人工 review。随着项目接入增加，容易出现 domain include adapter、ports 暴露 SDK 类型、通用目录混入项目名等架构腐化。

### 优化目标

用脚本或 CI 检查约束依赖方向。

建议检查项：

- `domain/` 不 include `adapters/`。
- `ports/` 不 include provider 或 SDK 头。
- `common/` 不依赖上层目录。
- 通用框架目录不出现具体项目名、机型名、项目报警码表或 IO 点位表。
- `adapters/providers` 不出现项目工艺动作或报警码语义。

### 验收标准

- 新增 `scripts/check_arch_boundary.*` 或等价检查。
- CI 或本地验证能执行边界检查。
- 检查失败时输出具体文件和违规 include/关键词。

### 落地情况（已完成）

`scripts/check_arch_boundary.sh` 共 15 条规则，当前全部通过：

| 规则 | 约束 |
|------|------|
| R1 | `common/` 不依赖任何上层目录 |
| R2 | `domain/` 不依赖 `adapters/`、`application/` |
| R3 | `ports/` 不依赖 `adapters/`、`application/`、`runtime/` |
| R4 | `runtime/event_bus/` 不依赖业务层 |
| R5 | `runtime/scheduler/` 不依赖业务层 |
| R6 | 各框架层不引用项目专属头（`m8/` 前缀），按 8 个层分别检查 |
| R7 | 框架核心目录无项目机型前缀文件（`m8_*.c` / `m8_*.h`） |
| R8 | 全框架不使用 `../` 相对 include |

R8 是 R1~R6 的兜底：前六条依赖 `#include "<层>/` 的前缀匹配，若改用 `../` 形式
引用上层，依赖违规会绕过全部前缀规则。

`scripts/check_all.sh` 串联边界检查、格式检查（`format.sh --check`）与单元测试，
任一失败即整体失败，作为提交前门禁；无 cmake 环境时可用 `--skip-tests` 只做静态检查。

## 10. P2：错误模型统一

### 问题

框架已使用 `sw_err_t`，但不同模块对错误码语义的使用可能逐渐分散。

### 优化目标

统一错误分类和处理策略：

- 参数错误。
- 状态错误。
- 未注册或未初始化。
- 外设暂不可用。
- 存储损坏。
- 安全拒绝。
- 资源不足。
- 启动期致命错误。

### 验收标准

- 有统一错误语义说明。
- 关键模块错误返回与说明一致。
- 可重试和不可重试错误有明确边界。

## 11. P2：配置与资产版本化

### 问题

框架已有方案 manifest 校验，但项目接入涉及更多资产：云物模型、报警目录、HAL binding、水路拓扑和运行参数。这些资产需要版本和 schema 边界。

### 优化目标

为项目资产提供通用版本校验机制。

建议资产：

- engine program schema version。
- cloud model version。
- alarm catalog version。
- HAL binding version。
- fluid topology version。
- deploy config version。

### 验收标准

- 通用框架提供版本字段约定或校验 helper。
- 版本不兼容时启动期失败。
- 项目资产仍保留在项目侧，不迁入通用框架。

## 12. P2：HAL provider 边界收紧

### 问题

vendor provider 放在通用仓库中有实际价值，但长期维护中容易混入项目语义。

### 优化目标

明确 provider 只做协议和 SDK 适配。

禁止内容：

- 项目动作名。
- 报警码和报警等级。
- 工艺流程判断。
- 具体机型点位表。
- 云端产品字段。

### 验收标准

- provider 文档明确输入输出边界。
- provider API 只接收通用配置或项目传入的 binding。
- 架构边界检查覆盖 provider 目录。

## 13. P3：表达式与 profile 可控扩展

### 问题

方案引擎表达式和 profile 查询接口已经具备扩展基础。后续若不加约束，表达式可能演化成难以验证的脚本语言。

### 优化目标

表达式只用于条件和简单计算，不承担副作用。

建议规则：

- 表达式不得写 IO、触发报警或修改状态。
- 内建函数必须白名单注册。
- 函数签名在加载期校验。
- profile 扩展优先增加查询接口，不迁入具体扫描算法。

### 验收标准

- 表达式加载期能发现未知函数、参数数量错误和类型错误。
- profile provider 缺失或查询失败时行为明确。
- 单元测试覆盖 profile 查询失败和默认值路径。

## 14. P3：状态投影一致性策略

### 问题

状态投影为云端、CLI、UI 和诊断提供只读快照。需要明确快照与事实源之间的一致性关系。

### 优化目标

明确以下策略：

- 快照是否允许短暂滞后。
- 云端上报读取事实源还是投影。
- 投影初始化和重建方式。
- 事件丢失后如何重新同步。
- 多个投影之间是否要求同一时刻一致。

### 验收标准

- `module-design/domain/状态投影与设备上下文模块设计.md` 补充一致性等级。
- 测试覆盖投影初始化、事件更新和重建路径。
- 云端上报和诊断读取路径有明确数据来源。

## 15. 不建议优先推进的纯架构化改造

以下方向可提升架构纯度，但对当前洗车机嵌入式框架的短期收益有限，暂不建议优先投入：

| 方向 | 暂不优先原因 | 触发条件 |
|------|--------------|----------|
| domain event 完全解耦 event bus | 会增加事件中转层和排查链路 | 需要替换 event bus，或 domain 需要脱离 runtime 独立复用 |
| 所有 domain port 迁入 domain 内部 | 目录重构成本高，收益主要是架构纯度 | port 出现 SDK 泄漏，或多个运行时需要不同端口定义 |
| application event bus 端口化 | 当前 event bus 是框架基础设施，替换需求不强 | 需要多种事件实现，或测试隔离成本明显上升 |
| 全面 Clean Architecture 化 | 会增加抽象层、初始化复杂度和调试成本 | 框架需要作为跨产品 SDK 长期独立发布 |

这些方向可以作为长期演进选项，但不应阻塞当前更有价值的接入检查、运行诊断和安全矩阵建设。

## 16. 推荐实施顺序

建议按以下顺序推进：

1. 项目接入契约检查。
2. 事件总线可观测性。（已完成）
3. 安全状态矩阵。
4. 依赖边界自动检查。（已完成）
5. 全局注册生命周期治理。（端口层已完成，thread_registry 与 domain 全局态待补）
6. 错误模型统一。
7. 配置与资产版本化。
8. HAL provider 边界收紧。
9. 状态投影一致性策略。
10. 表达式与 profile 可控扩展。

其中 1 到 5 是框架可靠性和架构治理基础，应优先于新增业务能力。
下一步建议从第 1 项（项目接入契约检查）和第 3 项（安全状态矩阵）继续。

## 17. 并发缺陷与工程化护栏修复记录

本节记录一轮代码审查后的修复，不属于上表任何方向，但影响运行可靠性。

### 17.1 已修复的并发缺陷

**事件总线互斥量优先级反转。** 事件总线允许被实时线程调用——框架自带的急停轮询
适配器以 `SCHED_FIFO` 优先级 90 发布事件，项目也可能从自己的实时线程发布——而队列锁
同时被多个 `SCHED_OTHER` 周期任务竞争。原先两把锁是裸 `PTHREAD_MUTEX_INITIALIZER`，
普通优先级线程持锁期间被抢占会让实时线程阻塞且时长不受优先级保护，构成无界优先级反转。现改为运行期 `pthread_mutexattr_init` +
`PTHREAD_PRIO_INHERIT`，用 `pthread_once` 保证恰好初始化一次（`event_bus_init()`
允许被重复调用，对已初始化互斥量再次 `pthread_mutex_init` 是 POSIX 未定义行为）。
平台不支持优先级继承时退化为默认互斥量，功能不受影响。

**命令网关信号量残留计数。** `command_gateway_drain()` 原先在解锁后才 `sem_post`。
若 `gateway_submit` 正好在该窗口内超时并释放槽位，信号量计数会残留给下一任槽主，
使其 `sem_timedwait` 立即返回并读到占位 receipt——命令被静默丢弃、调用方却收到
`SW_ERR_BUSY`。现将 `sem_post` 移入持锁范围（`sem_post` 不阻塞，持锁开销可忽略），
并在抢到槽位时用 `sem_trywait` 排空残留计数作为双重保险。

同一函数另修两处：`sem_timedwait` 补 `EINTR` 重试（截止时间是绝对值，重试不延长
总等待时长），避免一个信号就把正常命令报成超时；新增 dispatch 线程重入防护——从
dispatch 线程自身调用 `submit` 必然自锁，原先要白等满超时才返回，现直接返回
`SW_ERR_STATE` 并记录错误。调用上下文约束已写入 `command_port.h`。

**告警注册表锁范围。** `find_def_index()` 原在锁外调用，而 `load_catalog` 持锁改写
`s_catalog` 与 `s_catalog_count`，读写保护不对称。现将查表纳入同一把锁。

**安全投影快照不一致。** `telemetry_projection` 原先分两次取锁（`copy_active_projection`
+ `safety_posture`），拿到的活动表与安全姿态可能来自不同时刻。新增
`alarm_registry_copy_safety_view()` 一次持锁读出四项；同时补订阅
`EVT_SAFETY_LOCKOUT` / `EVT_SAFETY_NOMINAL`，避免姿态切换后快照滞后。

### 17.2 已修复的容量与时序问题

**周期任务槽位耗尽。** `PERIODIC_TASK_MAX` 原为 9，而 M8 实测 sim 与 target 均已
注册满 9 个周期任务，零余量——下一个周期任务注册就会让 bootstrap 失败。现改为与
`THREAD_REGISTRY_MAX` 对齐（后者由 16 提升到 24），周期任务不再构成独立的第二道
容量上限，超限统一由 `thread_registry` 报错。并加编译期断言防止两者失配。
`thread_registry.h` 中记录了槽位构成的核算口径。

**周期任务累积漂移。** 原实现是「执行回调 → `usleep(period)`」，睡的是固定相对
时长，回调耗时会累加进周期（10ms 任务若回调耗 3ms，实际周期变 13ms）。现改用
`clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME)` 维护绝对下一拍；单次回调超过一个
周期时跳过已错过的拍而不追赶。9 个周期任务中有 5 个周期 ≤20ms，漂移会直接影响
传感器采样与水路判定的时间基准。

### 17.3 日志与诊断

- `sw_log` 增加运行期级别门限（`sw_log_set_level` / `sw_log_level_enabled`），
  过滤在格式化之前完成，被丢弃的日志不付出 `vsnprintf` 开销。
- 默认 sink 改为先整条组装进栈缓冲再单次 `fwrite`。原先用 `fprintf` + `vfprintf`
  + `fputc` 三次独立 stdio 调用，多线程并发时同一行会被其他线程输出插入。
- sink 表加锁保护，并在写日志时取快照后即释放锁，避免 sink 内部再写日志造成自锁。
- `level` 越界不再用于数组下标。

### 17.4 其他

- `util_fifo` 全部入口补判空；头文件明确「不含内部锁，多线程需调用方加锁」，
  并说明当前不可当作无锁 SPSC 队列使用的原因。
- `observation_context_t` 改为 `trace_context_t` 的别名。两者原本是同名同序的四个
  `uint64_t` 字段，重复定义会在各自演进后失同步。
- 云适配器的 `strcpy` 统一为 `snprintf`（原有长度校验本已到位，此处只统一风格）。
- `event_bus_dispatch_loop` 的 handler 快照数组补零：非法事件类型在 publish 侧已被
  拦截、理论不可达，但若不清零会保留上一轮 handler 并被重复调用。
- 补齐 `tests/stubs/mcc/motor_control_core_fake.c` 缺失的 `motor_pop_event` 桩。
  该缺失导致 `test_hal_motor_exec_mcc` 长期链接失败，而父工程从不构建 framework
  自带测试，因此一直未被发现。framework 独立测试现为 46/46 全通过。

## 18. 复用性与层归属整治记录

本节记录一轮架构评估后的结构性改动。这些改动不新增业务能力，目标是让框架能被
第二个项目干净接入，并让层边界从"文档约定"变为"脚本可判定"。

### 18.1 框架导出构建目标（原缺口：复用单位是源文件清单）

框架原先只为 5 个可选 vendor provider 建了 `add_library`，核心层一个目标都没有，
项目必须手抄 74 条 `framework/**/*.c` 路径。框架增删文件时项目要同步改列表，
第二个项目接入要把清单重抄一遍，编译选项与包含目录也无法传递。

现由 `cmake/wdf_targets.cmake` 导出分层目标，项目侧 `target_link_libraries` 即可。

选择 **INTERFACE 库而非 STATIC**：同一份框架源在不同目标下需要不同编译定义
（例如项目 smoke 目标为 `fluid_path.c` 定义 `FLUID_PATH_UNIT_TEST` 以剥离周期任务，
sim/真机不定义）。STATIC 只编译一次，无法同时满足；INTERFACE 传递源与包含目录，
由消费方按自己的宏编译，行为与手写源列表完全一致。

目标粒度按"可独立取用"划分而非按目录：`wdf_domain` 只含命令裁决、报警、遥测读模型，
设备控制模式与方案引擎各自独立（它们分别要求项目提供 motor provider / 方案资产，
最小接入并不需要）。`engine_session`、`report_scheduler`、方案 JSON 加载同理拆出。
验证方式是 demo 只链接最小集合仍能构建通过。

### 18.2 安全端口从弱符号改注册表（原缺口：最高风险处用了最松的绑定）

四个安全入口原为 `__attribute__((weak))` 空实现。弱符号是链接期绑定，项目漏实现
不会有任何提示——而空实现的 `safety_cutout_execute` 意味着急停不切断动力输出，
启动日志里也看不出异常。风险最高的四条路径用了整套端口机制里最松的方式。

现统一为 `safety_ops_t` 注册表：四字段全必填（缺任一都会让某条安全链路静默失效），
未注册时各入口首次被调用时报 ERROR（急停期间高频调用，故按路径各报一次而非每次），
并可由 `port_contract_validate(PORT_REQ_SAFETY)` 在启动期拦住漏注册。

改造过程中该机制立即暴露了两处此前被掩盖的真实缺陷：M8 smoke 在完成 wiring 前就
调用安全路径（弱符号时代是空操作，故一直"通过"）；急停 `cutout` 真正生效后会置位
水路 emergency 标志，影响后续水路时序断言。两处均已修正。

### 18.3 必需端口启动期校验（原缺口：漏注册与"不需要"无法区分）

`bootstrap` 原先对未注册端口一律 `return SW_OK` 跳过，于是漏注册能一路启动成功，
直到第一次业务调用才失败——现场表现为随机时刻功能不可用，而非启动失败。

现由项目在 `project_validate()` 声明必需端口位掩码，框架一次报出全部缺失项。
框架不内置"哪些端口必需"的判断：那取决于项目用到哪些能力，无云连接的项目本就
不该被要求注册 `cloud_link`。M8 sim 声明 10 项、target 13 项，demo 7 项。

### 18.4 层归属修正

| 原位置 | 现位置 | 理由 |
|--------|--------|------|
| `domain/program_engine/model/engine_program_manifest.*` | `adapters/outbound/storage/json/` | 做的全是文件读取 + SHA256 + JSON 解析，无领域规则；完整性校验改为 loader 端口的可选 ops，`application` 只依赖端口 |
| `domain` 内 `fluid_path` 自建周期任务 | 调用方注册 | 领域层不创建线程；`fluid_path_poll` 由条件编译的测试专用接口转为常规接口 |
| `runtime/platform/safety_thread.*` | `adapters/inbound/safety/estop_poll_thread.*` | 这是"如何采集急停"的一种实现，属入站适配器而非运行时核心。M8 有自己的 DI detector 采集通路，从未链接它 |
| `adapters/inbound/event/*_bridge.*` | `application/bridges/` | 四个 bridge 只依赖 domain + runtime，不适配任何外部系统；与已在 `application/orchestrators/` 的同性质协调器分处两层会让"adapters 是外部适配"失去可判定性 |
| `services/dev_ctx` | 删除，并入 `device_snapshot` | 该层只是把快照摊平再补一个 `cloud_connected`，无其他职责。`cloud_connected` 并入快照后读侧还获得了跨子域一致性 |

### 18.5 边界检查扩展（R9、R10）

原有 R1~R8 只看 include 路径，管不住"用标准库直接做本不属于该层的事"。新增：

- R9a~R9d：`domain/` 禁止文件 IO、序列化解析、线程注册、动态内存。
  方案引擎三文件按加载期一次性分配 + 显式 free 登记豁免，新增文件需显式登记。
- R10：`adapters/` 不得出现 `*_bridge` / `*_projection` / `*_coordinator`。

规则均以注入违规的方式验证过确实能捕获（而非写出永远通过的假规则）。

### 18.6 事件 param 编解码收口

三种不同位布局共用 `uint32_t param`，发布方与订阅方各自手写移位，改枚举顺序会
静默错位且编译器无法察觉。现统一为 `encode/decode` inline 函数，并补往返测试
锁定布局契约——两侧不同步时在 CI 阶段就失败。

### 18.7 跨线程读修正

`op_mode_*` 直读接口不加锁（其状态只在 event_dispatch 线程内修改），但
`m8_park_supervisor` 在自己的周期任务线程调用 `op_mode_get_current()`，构成无保护
跨线程读。已改用加锁的 `device_snapshot_get()`，并在头文件写明线程约束。
