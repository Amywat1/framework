# 框架优化方向

## 1. 文档定位

本文档用于指导 `wash-device-framework` 后续优化方向。它不描述具体代码实现细节，而是记录当前通用框架在架构治理、项目接入、运行可靠性和可维护性上的改进重点。

**本文档回答「还要做什么」。**已完成整治的决策理由记在 `../history/整治记录.md`，
代码现状记在 `../module-design/`，行为归属与验证级别记在 `../contract/行为契约.md`。

优化原则：

- 优先增强通用框架能力，不迁入项目专属资产。
- 优先把文档约束转化为代码检查、启动期校验或测试。
- 优先补齐可观测性和接入可靠性，再扩展新业务能力。
- 对洗车机这类嵌入式项目，不以追求纯 DDD / 纯六边形为目标；可靠、可诊断、可接入、可复用优先。
- 对会显著增加抽象层、调用链和排查成本的改造，应先评估真实收益。
- 每项优化应同步更新 `module-design/` 中对应模块设计，并补充重新生成的单元测试。

## 2. 总体评价

当前框架方向是合理的，已经具备通用洗车机框架的主要骨架：

- 框架与项目资产边界清楚。
- DDD 分层和 Ports & Adapters 方向正确。
- 命令、运行模式、报警、安全姿态、方案引擎、事件总线和状态投影已经形成核心闭环。
- profile、detector、水路和模板能力的沉淀比较克制，未直接迁入具体机型表格。
- 文档已拆分为 `architecture/` 和 `module-design/`，具备方案评审和代码基线两种视角。

后续优化重点不是继续搬迁项目表格，而是让框架更可验证、更可接入、更难被项目代码污染。

## 3. 嵌入式项目性价比判断

洗车机软件具备嵌入式项目的典型特点：硬件链路长、现场问题复现困难、安全状态重要、项目接入差异多。对这类系统，架构优化应优先服务于启动期发现问题、运行期定位问题和安全行为可验证。

因此，当前不建议为了架构纯度做大规模重构。只要通用框架不依赖具体 adapter、SDK、项目资产和机型表格，当前工程化六边形架构已经具备继续演进的基础。

高性价比方向：

- 项目接入契约检查。
- 事件总线统计和诊断。
- 安全状态矩阵和命令允许矩阵。
- 依赖边界自动检查。
- 全局注册生命周期规范。

中等性价比方向：

- 错误模型统一。
- 配置与资产版本化。
- 状态投影一致性策略。
- HAL provider 边界收紧。

低性价比或暂不优先方向：

- 为了纯 DDD，把所有 domain event 都抽象一层再发布。
- 把所有 domain 使用的 port 都迁入 domain 内部。
- 把 application 对 event bus 的依赖完全端口化。
- 把当前框架全面改造成教科书式 Clean Architecture。

这些低性价比方向不是错误方向，但只有在测试隔离、事件系统替换、多运行时支持或模块复用边界出现真实痛点时才建议推进。

## 5. P0：项目接入契约检查

### 问题

当前项目接入已拆分为 register/configure/bind/validate/init/start 阶段，但缺失 port、provider、binding 或资产时，仍可能在运行到某条业务链路时才暴露问题。

### 优化目标

在 `project_validate()` 及框架侧校验点提供统一的启动期接入检查，使项目错误尽早失败。

建议检查项：

- 必需 port 是否已注册。
- `alarm catalog` 是否已加载。
- `cloud model` 是否通过校验。
- `engine_program_loader` 是否注册。
- `engine_io` 和 IO catalog 是否符合项目选择。
- HAL provider 和机构控制 binding 是否完成。
- 配置资产和 manifest 是否存在且版本匹配。

### 验收标准

- bootstrap 阶段能输出明确的接入检查结果。
- 任一必需能力缺失时返回明确错误，不进入运行线程启动。
- Demo 和单元测试覆盖至少一个缺失 port、一个缺失资产和一个非法 binding 场景。

### 落地情况（已完成）

分两层：端口侧 `runtime/ports/port_contract.h`（14 个 `PORT_REQ_*` 位），资产侧
`application/asset_contract.h`（3 个 `ASSET_REQ_*` 位）。两者都由项目在
`project_validate()` 声明位掩码，框架一次报出全部缺失项而非首个即返回——接入调试
时一次看到完整清单，比反复启动逐个发现更省时间。

分工：**port_contract 答「函数表是否注册」，asset_contract 答「数据是否就位」。**
两者是同一问题的两面——端口注册了但资产没加载，业务链路同样在第一次真实调用才
失败，而启动日志一切正常。

资产侧补的是`history/整治记录.md` 第 5.1 节核查出的实际缺口：

| 验收项 | 核查时状态 | 现状 |
|--------|-----------|------|
| `alarm catalog` 是否已加载 | **全仓零处检查** | `ASSET_REQ_ALARM_CATALOG`，两侧 wiring 均声明 |
| `cloud model` 是否通过校验 | 仅 target 调 `cloud_model_validate()` | `ASSET_REQ_CLOUD_POINT_TABLE`（target 声明），先查就位再查内容 |
| `engine_io` 和 IO catalog | 只有三个 smoke 判非空 | `ASSET_REQ_ENGINE_IO_CATALOG`，两侧 wiring 均声明 |
| 测试覆盖缺失资产场景 | **不存在** | `tests/application/test_asset_contract.c` 13 个用例 |

报警目录这条是三者中现场代价最高的：目录为空时 `alarm_registry` 把任何报警码都
解析不到定义，`trigger` 静默失败——设备表现为**"从不报警"而非启动失败**，只能靠
触发一次真实故障才发现。

两处判据值得记录：

- **`engine_io` 目录已注册但 signal 与 axis 皆空，按缺失处理。** 空目录下方案加载期
  无法校验任何名称，非法 signal / axis 会一路通过到求值期，即洗车中途失败而非
  加载期拒绝——与目录未注册的后果相同，故不区分。
- **只答「有没有」，不答「对不对」。** 点位表的字段级校验仍由 `cloud_point_validate`
  负责，两者互补。target 侧 `project_validate` 先调 `asset_contract_validate`
  再调 `cloud_model_validate`：物模型未注册时后者返回 `NOT_INIT`，缺失原因不如
  前者点名清楚。

为此补了两个探测入口：`alarm_registry_catalog_count()` 与 `cloud_model_point_count()`。
`cloud_model` 另补 `cloud_model_reset_for_test()`——`cloud_model_register(NULL)` 是
参数错误而非解除注册，本模块也无 init 入口可复用，故按 `device_snapshot` 的先例
单独提供。

`asset_contract` 独立成 CMake 目标而非并入 `wdf_application`：它要探测报警目录、
云物模型与方案引擎 IO 目录三处资产，并入会让最小接入被迫链接 `cloud` 与
`program_engine`，与 `wdf_application` 刻意保持最小的粒度划分冲突。理由同
`wdf_report_scheduler` 的拆分。

已按`history/整治记录.md` 第 5.3 节的判据验证有生产调用方（接入项目 sim 与 target 两侧的 `project_validate`），
并注入「探测函数恒返回 true」确认检查确有约束力——两个用例立即失败。测试正序与
倒序执行均通过。

## 6. P1：全局注册生命周期治理

### 问题

当前多个模块采用全局 singleton/register 模式。该模式适合嵌入式 C 框架，但需要统一生命周期语义，否则测试隔离、重复初始化和 bootstrap 失败恢复会变复杂。

### 优化目标

统一以下规则：

- 是否允许重复注册。
- 重复注册是覆盖、拒绝还是幂等成功。
- 是否提供 unregister 或 reset。
- 单元测试如何清理全局状态。
- bootstrap 失败后是否允许重新初始化。

### 建议方案

- 为测试提供 `*_reset_for_test()` 或统一 `framework_reset_for_test()`。
- 对运行期不允许重复注册的 port 返回明确错误。
- 对允许替换的 provider 在文档和 API 名称中表达清楚。
- 在 `module-design/` 中补充各模块注册生命周期表。

### 验收标准

- 单元测试不依赖测试执行顺序。
- 重复注册行为在所有 port/provider 中一致或有明确例外。
- bootstrap 失败路径不会留下不可预测的半初始化状态。

### 落地情况（已完成）

已完成：端口注册语义统一，见 `runtime/ports/port_registry.h`。

- 13 个 `*_register()` 全部返回 `sw_err_t`，不再是 `void`。
  原先 `engine_program_loader_register` 校验失败后静默忽略，调用方无从得知。
- `ops == NULL` 明确为「解除注册」，返回 `SW_OK`。这是受支持的显式操作，
  测试与运行期降级均可使用。
- `ops != NULL` 但缺必填函数指针时返回 `SW_ERR_PARAM`，且**保持原注册不变**，
  不会被半个 ops 覆盖。必填字段只限调用方会无条件解引用的入口：

  | 端口 | 必填字段 | 依据 |
  |------|----------|------|
  | `param_store` | `load` / `save` / `get` / `set` | `svc_param` 只判 ops 非空即调用四者 |
  | `deploy_store` | `load` | bootstrap 只判 ops 非空即调 `load()` |
  | `device_command_port` | `submit_async` / `submit_sync` | 本端口唯一入口 |
  | `alarm_binding` | `trigger` / `clear` / `load_catalog` | 适配器无条件调用三者 |
  | `engine_program_loader` | `load` | 本端口唯一入口 |
  | HAL / `device_ops` / cloud 各端口 | 无 | 调用方逐个判空，允许注册能力子集 |

- 重复注册合法函数表以最后一次为准（替换），返回 `SW_OK`。
- 按注册表分层提供复位：`port_registry_hal_reset()`、`port_registry_infra_reset()`、
  `port_registry_cloud_reset()`。分层而非单一入口，是为避免测试为了一个复位函数
  被迫链接全部三个注册表源文件。

单元测试：`tests/ports/test_cloud_ports.c` 覆盖合法注册、NULL 解除、缺必填字段被拒
且不覆盖原注册、重复注册替换、复位清空，并在 `setUp`/`tearDown` 调用复位消除用例
间顺序耦合。

安全端口后续由弱符号改为注册表绑定（`runtime/ports/port_registry_safety.c`），遵循同一套
语义并提供 `port_registry_safety_reset()`，四个注册表的复位入口统一在
`runtime/ports/port_registry.h` 声明。

线程登记表也已补 `thread_registry_reset_for_test()`。此前
`tests/runtime/test_scheduler.c` 多个用例硬编码「累加后」的期望值——
`test_register_arg_passes_context` 期望 count 为 2、
`test_periodic_task_register_and_scheduler_start` 依赖前序用例遗留的 one_shot
线程才能观察到执行——顺序耦合比原先记录的一处更普遍。现在 `setUp` 统一复位，
各用例自行注册所需线程；倒序执行全部用例同样通过。

该复位接口只允许测试调用：线程一经 `scheduler_start_all` 创建即 detach 且无法
回收，清空登记表不会停止已启动的线程，生产路径调用会造成登记与实际线程不一致。

bootstrap 失败后的进程约束已写入 `runtime/bootstrap/bootstrap.h` 与
`architecture/04` 第 4.1 节：失败即必须终止进程，不得重试。不提供 teardown 是
有意取舍——为覆盖任意阶段失败而维护对称的反初始化路径，其自身正确性比
"失败即退出" 更难保证，而嵌入式设备由进程管理器重启即可回到确定状态。
文档同时写明了重复调用的具体后果（队列被重置、线程表累积重复条目）。

domain 层全局态也已补齐，但**没有采用**原方案里的统一 `framework_reset_for_test()`：
那样会让每个测试目标为了一个复位函数被迫链接全部 domain 模块，与端口注册表按层
拆分复位入口是同一个理由。改为按模块提供，并优先复用已有入口：

| 模块 | 复位方式 |
|------|----------|
| `operational_mode` | `operational_mode_init()` 本已复位三个字段，无需新增 |
| `alarm_registry` | `alarm_registry_init()` 补为清空目录、活动表、会话日志与待发事件 |
| `device_snapshot` | 新增 `device_snapshot_reset_for_test()`（本模块无 init 入口） |

`alarm_registry_init()` 选择改语义而非新增 `*_reset_for_test()`：多数相关测试文件
本就在 `setUp` 调用它并当它是复位，而它此前只注册 binding、不碰任何状态——
把实现对齐到既有调用方的预期，比再加一个入口更贴合现状。bootstrap 在 bind 阶段
于 `project_bind_alarm_catalog` 之前调用，故清空目录不会丢已加载资产。

该项立即暴露了一处真实的顺序耦合：`test_telemetry_projection` 倒序执行时
`test_operational_projection_syncs_current_context` 失败（期望 `OP_MODE_IDLE`
得到 `STOPPED` 且带阻塞旗标）——前序用例遗留的活动报警使开洗被拒、停机收敛。
该用例此前只在"报警用例不先执行"的顺序下成立。现 `setUp` 统一复位，正序与倒序
均通过。

## 7. P0：事件总线可观测性

### 问题

事件总线是框架核心链路。真机问题常见于事件队列满、handler 执行慢、事件处理顺序不符合预期或关键事件被延迟。

### 优化目标

增强事件总线运行统计和诊断能力。

建议能力：

- 每类事件发布计数。
- 每类事件消费计数。
- 队列当前深度和高水位。
- 发布失败和队列满计数。
- handler 最大执行耗时。
- dispatch 线程 fatal 原因记录。

### 验收标准

- 测试可读取 event bus stats。
- 队列满场景有明确返回值和统计。
- 慢 handler 能被统计或告警。
- 安全关键事件的处理策略在文档中明确。

### 落地情况（已完成）

`event_bus_stats_t` 现含下列字段，测试可通过 `event_bus_get_stats()` 读取：

| 能力 | 字段 |
|------|------|
| 总量计数 | `published_count` / `dispatched_count` / `dropped_count` |
| 分类别计数 | `published_by_cat[]` / `dispatched_by_cat[]` / `dropped_by_cat[]`，下标为 `event_category_t` |
| 队列水位 | `queue_depth` / `queue_peak_depth` / `hi_queue_depth` / `hi_queue_peak_depth` |
| 失败计数 | `sem_post_fail_count` / `sem_wait_fail_count` |
| handler 耗时 | `handler_max_ms` / `handler_max_type` / `slow_handler_count` / `dispatch_max_ms` |

慢 handler 门限为 `EVENT_BUS_SLOW_HANDLER_MS`（50ms），超限同时计数并输出告警日志。

事件总线内部诊断已从 `printf` 改为 `sw_log`，队列满、丢事件、`sem_post` 失败等
关键记录会进入已注册的 sink 链（黑匣子、可观测服务），不再只打到 stdout。

dispatch 线程 fatal 原因通过 `event_bus_set_fatal_cb` 回调上报，bootstrap 注册
`system_panic_safe_stop` 置安全输出后 `abort()`。

单元测试：`tests/runtime/test_event_bus.c` 覆盖分类别计数、丢弃归集、慢 handler
识别与快 handler 不误判。

## 8. P0：安全状态矩阵

### 问题

报警、安全姿态、运行模式和命令网关已经形成链路，但安全行为需要更形式化，方便评审、测试和项目接入。

### 优化目标

形成统一安全矩阵：

- 报警响应策略到安全姿态的映射。
- `LOCKOUT` 下允许和拒绝的命令。
- 急停、暂停、停止、恢复、复位的状态转换。
- 安全输出失败时的兜底策略。
- ON_MOTION 重评估触发后的清除边界。

### 验收标准

- `architecture/` 有方案级安全矩阵说明。
- `module-design/` 有代码级状态表和测试映射。
- 单元测试覆盖关键命令在不同安全姿态下的裁决结果。

### 落地情况（已完成）

等级与清除策略的语义原先散在判定点上：`level >= ALARM_LEVEL_MAJOR` 出现 3 处、
`level == CRITICAL` 出现 2 处、清除策略判定 3 处。每处都在重新表达"MAJOR 意味着
什么"，调整语义要逐个找齐，漏改无编译期提示。

现收口到 `domain/safety/model/safety_matrix.h`，以**行为属性**而非等级序号表达语义：

| 矩阵 | 维度 | 收口的判定点 |
|------|------|--------------|
| 等级行为 | 阻塞开洗 / 进入 LOCKOUT / 记会话日志 | `alarm_registry` 会话日志、blocking 判定、姿态推导（共 5 处） |
| 清除策略 | 条件消失即清 / 需运动重评估 / 允许手动复位 | `alarm_registry` 自动清除、重评估分组、手动复位（共 3 处） |

改为行为属性而非"序号比较"的原因：`level >= MAJOR` 隐含了「等级按严重度排序且
新等级只会追加在末尾」这一假设。若将来在 MINOR 与 MAJOR 之间插入一级，所有
`>=` 判定都会静默改变含义。查表则要求新等级显式声明自己的三个属性。

命令允许矩阵此前已是表驱动（`operational_mode.c` 的 `k_cmd_matrix`，现为 8×8 显式列出），
本轮未改动，只在文档中说明它与上面两张表的分工。

测试：`tests/domain/test_safety_matrix.c` 按格点逐一断言（3×3 两组共 18 格），
并校验「更高等级不得比更低等级宽松」的单调性不变量。已验证矩阵是行为的单一
来源——把 MAJOR 的 `blocks_wash_start` 改为 false 后，`test_safety_matrix`、
`test_alarm_registry`、`test_operational_mode` 三个测试同时失败。

安全输出失败的处置已补第一层——「可观测」，见`history/整治记录.md` 第 4.2 节。原先 `cutout` 返回
`void`，项目实现把每路 `safe_do_set` 的返回值全部 `(void)` 丢弃，切断失败时框架侧
完全无从知晓。现在失败会被逐层汇总、记录并计数。

失败后的姿态统一为「切断未确认」锁存：安全投影强制 `LOCKOUT`，开洗、手动动作、
自检和恢复均被拒绝，急停热路径不自动重试。项目可提供独立 `cutout_confirmed()`
反馈并调用 `safety_cutout_reconcile()` 解除；框架不猜测第二路继电器或硬件互锁状态。

## 9. P1：依赖边界自动检查

### 问题

当前分层边界主要依靠文档和人工 review。随着项目接入增加，容易出现 domain include adapter、ports 暴露 SDK 类型、通用目录混入项目名等架构腐化。

### 优化目标

用脚本或 CI 检查约束依赖方向。

建议检查项：

- `domain/` 不 include `adapters/`。
- `domain/ports` / `application/ports` 不 include provider 或 SDK 头。
- `common/` 不依赖上层目录。
- 通用框架目录不出现具体项目名、机型名、项目报警码表或 IO 点位表。
- `adapters/providers` 不出现项目工艺动作或报警码语义。

### 验收标准

- 新增 `scripts/check_arch_boundary.*` 或等价检查。
- CI 或本地验证能执行边界检查。
- 检查失败时输出具体文件和违规 include/关键词。

### 落地情况（已完成）

`scripts/check_arch_boundary.sh` 共 25 条规则，当前全部通过：

| 规则 | 约束 |
|------|------|
| R1 | `common/` 不依赖任何上层目录 |
| R2 | `domain/` 不依赖 `adapters/`、`application/`、`services/` |
| R3a/R3b | `domain/ports`、`application/ports` 不依赖 `adapters/` |
| R4 | `runtime/event_bus/` 不依赖业务层 |
| R5 | `runtime/scheduler/` 不依赖业务层 |
| R6 | 框架层引号 include 均可在框架树内解析（vendor 头限 `adapters/**/providers/`） |
| R7 | 框架层每个 `.c` 都已在框架构建清单中登记 |
| R8 | 全框架不使用 `../` 相对 include |
| R9a~R9d | `domain/` 不做文件 IO、序列化解析、线程注册、动态内存，详见`history/整治记录.md` 第 2.5 节 |
| R10 | `adapters/` 不含 `*_bridge` / `*_projection` / `*_coordinator`，详见`history/整治记录.md` 第 2.5 节 |

规则条数（25）多于表格行数：R9 拆为 4 条子规则，R16~R22 见后续章节。脚本
结尾输出的条数以实际执行的检查为准。

R8 是 R1~R5 的兜底：这些规则依赖 `#include "<层>/` 的前缀匹配，若改用 `../` 形式
引用上层，依赖违规会绕过全部前缀规则。R6 也拦不住这类——`../` 指向的是真实存在的
框架文件，在框架树内可解析，故 R8 必须独立存在。

#### R6 / R7 判据重做：从"名字像不像项目专属"到"能不能在框架树内解析"

两条规则原先都把「项目专属」绑定到写死的项目名：R6 grep `#include "m8/`，R7
`find -name 'm8_*.c'`。框架无从预知下一个接入项目叫什么，换个名字规则即完全失效。
实测确认：把 `#include "acme_robot/io_table.h"` 注入 `domain/op_mode/operational_mode.c`
后，全部规则仍报通过——一个领域层直接引用项目 IO 表的严重越界毫无反应。这不是
覆盖不全，是判据选错了对象：它检测「有没有叫某个名字的东西」，而要防的是
「有没有引用框架之外的东西」。

反过来立判据即可摆脱对项目命名的依赖——**框架不需要知道项目有什么，只需要知道
自己有什么**：

| 规则 | 新判据 |
|------|--------|
| R6 | 引号 include 须能以仓库根为基准解析，或在同目录内解析；否则即为框架外引用 |
| R7 | 框架层 `.c` 须出现在 `cmake/wdf_targets.cmake` 或根 `CMakeLists.txt` 中 |

R6 的例外只有 vendor SDK 头（`io_exp/`、`modbus/`）：其搜索路径由根 CMakeLists 的
provider 开关在编译期注入，确实不在框架树内。白名单逐项登记并附加位置约束——必须
位于 `adapters/**/providers/` 下，使 vendor 依赖无法渗入其它层。新增 vendor provider
须显式登记，这一步正是要让评审看见新的外部依赖。

R7 的例外是仅由 `demo/` 与 `tests/` 按路径直接装配、刻意不导出为公共目标的两个源文件
（`hw_estop_sim.c`、`safety_sim.c`），登记在脚本的 `UNEXPORTED_SOURCES` 中。
`estop_poll_thread.c` 已导出为可选目标 `wdf_estop_poll`。逐项登记而非按目录豁免，
每一项都是"为什么不导出"的显式决定。
该判据顺带能抓出框架自身的死代码：任何不被构建的框架文件都会在此暴露。

三个注入场景验证新判据确有约束力：任意命名的项目头（R6 报无法解析）、vendor 头出现在
`providers/` 之外（R6 报位置违规）、未登记的 `.c` 混入 `domain/`（R7 报未登记）。

`scripts/check_all.sh` 串联边界检查、行为契约、文档引用与单元测试，
任一失败即整体失败，作为提交前门禁；无 cmake 环境时可用 `--skip-tests` 只做静态检查。
代码格式由 `./scripts/format.sh` 按需手动执行，不纳入门禁。

### 落地情况续（门禁自动执行，已完成）

此前门禁**没有任何机制保证被执行**：`.github/` 不存在，`.git/hooks/` 无非样例钩子，
23 条静态规则与 126 条契约条目的约束力全都取决于提交者是否记得手动跑一次。

这个落差已经造成过实际后果：SAFE-01 的验证载体 `wdf_smoke` 曾长期以退出码 1 运行
且不在 `ctest` 内，那条「已验证」当时并不成立。对一个把「约束必须机器审计」当作
核心设计取向的框架，靠人自觉执行审计是最大的一处自相矛盾。

现补 `.github/workflows/gates.yml`：每次 push 与 PR 跑 `./scripts/check_all.sh`，
并无条件上传 `build-check/test-results/`（失败时报告是唯一排查依据）。
Unity 与 cJSON 随仓分发，CI 只需 cmake / gcc / python3；vendor provider 需外部 SDK，
默认 OFF，不在 CI 内构建。

### 落地情况续（规则集完整性对账，已完成）

第 9 节开头记的那个盲区（上层目录出向无人约束）后来**又以同一形态出现了一次**：
`cloud/` 迁入 `domain/cloud/` 后，ARCH-11 声明的三个禁止方向里 `services/` 一项在
脚本中始终没有实现，ARCH-12 的 `cloud/` 一项同样缺失，而两条条目都标着 `已验证`。
实测确认：注入 `#include "services/param/svc_param.h"` 到 `domain/cloud/cloud_model.c`，
当时 22 条规则全部通过。

**这说明「补一次规则」不解决问题——条目文字与规则实参是两处独立维护的清单，必然
失同步。**故补的不是第三条规则，而是对账机制：`check_behaviour_contract.sh` 新增
C10，要求每条 L0 结构条目在「条目 → 保证规则」映射表中声明由哪条规则保证，且条目
文字里出现的每个禁止路径都必须出现在该规则的实参中。

同时把缺口本身补上：R2 增加 `services/` 实参（`cloud` 已在 domain 锥内，故 ARCH-11
由 R2 一并覆盖，不再立同义规则），R13 增加 `domain/cloud/` 实参。

已注入验证 C10 确有约束力：把 R2 回退为两实参后，C10 点名报出 ARCH-02 与 ARCH-11
两条与规则失同步。

### 落地情况续（L0 结构门禁补全，已完成）

C10 原先只认 `ARCH-NN`。PROJ-03、ERRM-02 两条 L0 结构条目没有对应规则，ENGN-04
虽已有 R17 也不在对账范围内。补 R21（快照写边界）与 R22（错误分类 helper），
并把映射表扩到全部 ARCH L0 与 L0 结构条目。规则条数 23 → 25。

这两条都是结构性质：领域模块一旦直接写快照、调用点再手写 `BUSY || TIMEOUT`，
运行期测试不一定看得到，静态规则可以穷举。

### 落地情况续（急停延迟预算，已完成切断路径约束）

原先把 `drv_modbus_link.c` 按「项目 cutout 可能直写寄存器」登记为 RT 可达，
于是持 `bus_lock` 的 100ms 超时进入了急停预算。RS-485 同时只能发一帧，把收发
移出总线锁并不能让切断插队。

已改为契约禁止：`safety_port.h` 要求 cutout 不得调用 Modbus / UART 同步收发，
停机只用数字输出。该文件改登记为非 RT；失败后的 `modbus_connect` 也不再在
持锁时进行。R20 现在只盯仍在切断路径上的 vendor 阻塞（`io_exp` 锁外 DO，
预算 300ms）。现场标定仍属 L5。

## 10. P2：错误模型统一

### 问题

框架已使用 `sw_err_t`，但不同模块对错误码语义的使用可能逐渐分散。

### 优化目标

统一错误分类和处理策略：

- 参数错误。
- 状态错误。
- 未注册或未初始化。
- 外设暂不可用。
- 存储损坏。
- 安全拒绝。
- 资源不足。
- 启动期致命错误。

### 验收标准

- 有统一错误语义说明。
- 关键模块错误返回与说明一致。
- 可重试和不可重试错误有明确边界。

### 落地情况（已完成）

语义与边界定义见 `common/sw_error.h`：三个判定 helper（`sw_err_is_transient` /
`_caller_fault` / `_missing_binding`）划分瞬时可重试、调用方缺陷、接入缺失三类，
`tests/common/test_sw_error.c` 断言三类互斥且覆盖全部错误码。

`history/整治记录.md` 第 5 节核查时这三个 helper 尚无生产调用方——语义已定义但对运行时行为没有任何
约束力。现已接入 `report_scheduler` 的两处上报路径：

原先写法是 `(ret != SW_OK) && (ret != SW_ERR_COMM)`，手工挑出 COMM 一个码当作
"可以不告警"。但上报按周期重来，`SW_ERR_BUSY` 与 `SW_ERR_TIMEOUT` 同样是等下一拍
即可的情形，为它们打 WARN 只会淹没真正需要看的错误。改用 `sw_err_is_transient()`
后三个瞬时码一致处理，日志同时改用 `sw_err_name()` 输出可读名而非裸数字。

**刻意没有全局替换**：`drv_voice` 与 `hal_vfd_manager` 里的 `ret == SW_ERR_COMM`
判断保持原样。那两处用 COMM 驱动通信丢失/恢复状态机，语义就是"通信断了"，
把 `SW_ERR_BUSY` 也算作通信丢失会误报 COMM_LOST 事件。helper 表达的是"该不该重试"，
不能替代"具体哪种故障"——凡是错误码本身参与状态判定的地方，都应保留具体码。

这条区分也是 helper 的使用边界：适用于「按类别决定处置」（是否重试、是否告警、
是否致命），不适用于「按具体故障决定行为」。

## 11. P2：配置与资产版本化

### 问题

框架已有方案 manifest 校验，但项目接入涉及更多资产：云物模型、报警目录、HAL binding、水路拓扑和运行参数。这些资产需要版本和 schema 边界。

### 优化目标

为项目资产提供通用版本校验机制。

建议资产：

- engine program schema version。
- cloud model version。
- alarm catalog version。
- HAL binding version。
- fluid topology version。
- deploy config version。

### 验收标准

- 通用框架提供版本字段约定或校验 helper。
- 版本不兼容时启动期失败。
- 项目资产仍保留在项目侧，不迁入通用框架。

### 落地情况（已完成）

上面「建议资产」六项里，只有两项是运行期从文件读入的，也只有这两项需要版本校验：

| 资产 | 载入形态 | 版本校验 |
|------|----------|----------|
| engine program | 运行期读 JSON | 已接入（`ENGINE_PROGRAM_SCHEMA_SUPPORTED`）|
| deploy config | 运行期读 JSON | 已接入（`DEPLOY_CONFIG_SCHEMA_SUPPORTED`）|
| cloud model | 编译期 `cloud_model_bundle_t` 结构体 | **不适用** |
| alarm catalog | 编译期 `alarm_def_t` 数组，项目侧合并各分表后 `load_catalog` | **不适用** |
| HAL binding | 编译期 X-macro 展开自项目 IO 表头文件 | **不适用** |
| fluid topology | 编译期项目水路拓扑数组 | **不适用** |

后四项标「不适用」而非「待接入」：它们与框架编译进同一个二进制，不存在版本漂移的
可能——结构体定义变了，编译期就失败，这比运行期比对版本串更强。给一个编译期数组
配版本串只是仪式，读它的代码和写它的代码本来就是同一次编译的产物。

原「建议资产」清单把这六项并列，隐含了「都需要版本校验」的判断，是不成立的。
判据应当是**资产能否独立于框架二进制变化**：能，才需要版本；不能，编译器已经保证。

deploy config 的接入要点：

- JSON 必须声明 `schemaVersion`，缺失即拒绝加载。不按"缺失视为最早版本"处理，
  是因为该文件承载设备身份与云端主题，静默接受一份不声明版本的配置，等于让
  字段含义的任何变更都无从被发现。
- 两种失败分开返回：版本串缺失或无法解析返回 `SW_ERR_PARAM`（资产本身不合契约），
  可解析但不兼容返回 `SW_ERR_STATE`（资产合法、只是与本框架不配）。
- 版本不合时整份丢弃新配置，但**保留上一次加载成功的内容**。`deploy_load` 也用于
  重新加载，运行期推来一份版本不对的配置时，清空会连设备身份与云端主题一起丢掉，
  故障面反而更大；首次加载失败则由 bootstrap 的 `BOOT_CHECK` 终止启动，不存在
  "带着空配置运行"。

测试：`tests/adapters/test_json_deploy_store.c` 覆盖缺字段、主版本不符、次版本更高、
带修订号后缀被接受、拒绝后旧配置仍可读五个场景。已用真机路径验证端到端行为——
接入项目的 sim 目标在版本 `2.0` 时退出码 1 并输出「版本不兼容，资产 2.0.0 框架支持 1.0.x」，
删除字段时退出码 1 并输出「缺少 schemaVersion 字段」，恢复后正常启动。

## 12. P2：HAL provider 边界收紧

### 问题

vendor provider 放在通用仓库中有实际价值，但长期维护中容易混入项目语义。

### 优化目标

明确 provider 只做协议和 SDK 适配。

禁止内容：

- 项目动作名。
- 报警码和报警等级。
- 工艺流程判断。
- 具体机型点位表。
- 云端产品字段。

### 验收标准

- provider 文档明确输入输出边界。
- provider API 只接收通用配置或项目传入的 binding。
- 架构边界检查覆盖 provider 目录。

### 落地情况（部分完成）

R19 已把 provider 对象布局收成通用静态边界：`adapters/**/providers/<vendor>/` 下的
`*_internal.h` 只允许被该 vendor 目录内的生产代码 include；同目录公共头只保留不透明
类型，不得重新出现对应 `struct` 定义。对象存储仍由该 vendor 的组合层持有，不在框架层
新增第二套实例池。测试 fake 可使用私有头替代 vendor SDK，但不形成生产依赖。

本方向仍是“部分完成”：provider 不得承载项目动作名、报警码、工艺判断、机型点位表和
云字段，目前主要由目录职责与 review 约束，尚未形成可靠的通用静态判据。仓内仍可保留
可选 vendor 源码，但门禁不再点名某一家厂商。

## 13. P3：表达式与 profile 可控扩展

### 问题

方案引擎表达式和 profile 查询接口已经具备扩展基础。后续若不加约束，表达式可能演化成难以验证的脚本语言。

### 优化目标

表达式只用于条件和简单计算，不承担副作用。

建议规则：

- 表达式不得写 IO、触发报警或修改状态。
- 内建函数必须白名单注册。
- 函数签名在加载期校验。
- profile 扩展优先增加查询接口，不迁入具体扫描算法。

### 验收标准

- 表达式加载期能发现未知函数、参数数量错误和类型错误。
- profile provider 缺失或查询失败时行为明确。
- 单元测试覆盖 profile 查询失败和默认值路径。

### 落地情况（部分完成：白名单与加载期校验）

四条建议规则里第二、三条已落地，第一、四条本轮未动（见下文「未做」）。

`engine_expr.c` 内新增 `k_builtins[]` 白名单表，`engine_expr_compile` 在语法解析
成功后递归全树校验每个 `NODE_FUNC`，三类错误在加载期拒绝并点名函数：

| 错误 | 原先 | 现在 |
|------|------|------|
| 未知函数名 | 求值期 `*ok = false`，无名称信息 | `未知函数 'body_containz'` |
| 参数个数不符 | 同上 | `函数 'body_contains' 需要 3 个参数，实际 2 个` |
| `profile.in_zone` 首参非字符串字面量 | 同上 | `函数 'profile.in_zone' 首参必须是字符串字面量` |

**为何值得做**：方案是部署时下发的资产。写错一个函数名，原先要洗到用到该表达式
的那一步才失败——车在机器里中途停机；现在部署即拒绝，方案不生效。这与本轮资产
契约是同一条思路：把「运行到某一步才失败」提前到「加载期拒绝」。

首参类型这条只能在加载期查：字符串在求值期一律置 `*ok = false`，`profile.in_zone`
的区域名是唯一合法的字符串位置，求值期无从区分「该位置本应是字符串」与「表达式
里误用了字符串」。

**求值侧的 arity 检查保留未删。** `engine_expr_clone` 可以绕过 `compile` 直接得到
AST，删掉会让克隆路径失去保护。两处检查读同一张白名单表，语义不会分叉。

**防漂移**：`test_engine_expr_whitelist_all_evaluable` 逐个实际求值白名单里的每个
函数，而不只是判「能编译」——表里加了名字而 `eval_node` 漏加分支时，加载期会放过
而求值期落到兜底的 `*ok = false`，只判能编译是抓不到这种漏分支的。已注入验证：
白名单加一个无求值分支的 `ghost_fn` 后该用例立即失败。

同样注入验证了校验本身有约束力——跳过 `check_functions` 调用后 4 个用例失败。

**本轮未做**：
- 「表达式不得写 IO、触发报警或修改状态」：当前 4 个内建函数全是纯查询，无副作用
  入口，该约束**事实成立但无机制保证**。要真正约束需在白名单表加「是否纯函数」
  标记并在注册期拒绝副作用函数——等真有扩展需求时再加，现在加是为假想未来预支。
- 「profile 扩展优先增加查询接口」：属评审判据而非可自动检查项，维持文档约束。
- 类型校验只覆盖了字符串字面量位置。数值 / 布尔位置的类型在本表达式语言里都是
  double，没有可校验的差异。

接入项目现有方案未用到任何内建函数，故本项在项目侧无行为
变化，价值全在框架侧——下一个用到 `profile.*` 的方案会在部署期就得到反馈。

## 14. P3：状态投影一致性策略

### 问题

状态投影为云端、CLI、UI 和诊断提供只读快照。需要明确快照与事实源之间的一致性关系。

### 优化目标

明确以下策略：

- 快照是否允许短暂滞后。
- 云端上报读取事实源还是投影。
- 投影初始化和重建方式。
- 事件丢失后如何重新同步。
- 多个投影之间是否要求同一时刻一致。

### 验收标准

- `module-design/domain/状态投影与设备快照模块设计.md` 补充一致性等级。
- 测试覆盖投影初始化、事件更新和重建路径。
- 云端上报和诊断读取路径有明确数据来源。

## 15. 不建议优先推进的纯架构化改造

以下方向可提升架构纯度，但对当前洗车机嵌入式框架的短期收益有限，暂不建议优先投入：

| 方向 | 暂不优先原因 | 触发条件 |
|------|--------------|----------|
| domain event 完全解耦 event bus | 会增加事件中转层和排查链路 | 需要替换 event bus，或 domain 需要脱离 runtime 独立复用 |
| 所有 domain port 迁入 domain 内部 | 目录重构成本高，收益主要是架构纯度 | port 出现 SDK 泄漏，或多个运行时需要不同端口定义 |
| application event bus 端口化 | 当前 event bus 是框架基础设施，替换需求不强 | 需要多种事件实现，或测试隔离成本明显上升 |
| 全面 Clean Architecture 化 | 会增加抽象层、初始化复杂度和调试成本 | 框架需要作为跨产品 SDK 长期独立发布 |

这些方向可以作为长期演进选项，但不应阻塞当前更有价值的接入检查、运行诊断和安全矩阵建设。

## 16. 推荐实施顺序

表内 P0/P1 基础项已完成。后续按收益而不是按架构纯度推进：

1. HAL provider 语义边界随第二个厂商接入再加静态判据。
2. 周期任务跳拍 / 回调耗时 / 唤醒滞后 / 越过量已由 `periodic_task_get_stats()` 落地；合并线程仍等有现场数据再议。

不要优先做：domain event 再抽象、application 对 event bus 端口化、全面 Clean
Architecture、编译期资产加版本串、表达式纯函数机制、启动 teardown。
