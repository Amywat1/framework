# 作业核与机型无关运行

## 1. 文档定位

本文记录洗车控制器的作业运行核：把整机运营态、云端订单簿和在洗作业占用拆开，使单车机型与连续多车机型共用同一套命令网关与放行规则。机型差异只出现在 `machine_profile_t` 容量数字和项目 `device_ops` 实现中。

配套：产品叙述与项目声明清单见 `10-通用洗车运营模型.md`。分层边界见 `01-分层架构与依赖边界.md`，命令链路见 `02-核心业务链路说明.md`，资产边界见 `03-通用能力与项目资产边界.md`。

## 2. 三层模型

| 层 | 模块 | 职责 | 不问的事 |
|----|------|------|----------|
| 整机运营 | `operational_mode` | 停机 / 就绪 / 作业中 / 清障 / 占位 / 自检 / 恢复 | 几辆车、套餐、输送还是往复 |
| 订单簿 | `order_book` | 内存 FIFO：入队、取消、取队首、清空 | 何时放行、如何执行工艺 |
| 在洗占用 | `active_jobs` | 已放行未结束的作业 0..N | 车在哪一站、刷头怎么动 |

`command_gateway` 的 4 槽队列只是 `cmd_control` 线程的命令串行槽，不是业务订单簿。二者不得混用。

放行核 `job_admit` 位于 application，不是 domain 状态机。唯一规则：

```text
总开关开 且 无急停 且 切断已确认 且 无阻塞报警
且 整机允许放行（STANDBY 或 ACTIVE）
且 active_count < max_active_jobs
且 订单簿非空（队首过期先淘汰）
且 device_ops.is_admit_ready()
    → 计入 active_jobs → start_job(job) → 成功则移出订单簿
```

放行只走 `START_WASH` → `job_admit_start()`。入簿、作业结束、场区清空、恢复完成都不自动放行。一次启动只放队首一单。洗着能否再放，由占用上限和 `is_admit_ready` 决定，不另禁「洗中启动」。空簿、未准入、占用满、HOLD/停机均失败，已入队单保留。准入后不会因早先的启动自动开洗。过期队首由周期扫描清掉，入簿和放行前再扫一次；已开洗作业不在簿中，不受有效期约束。

订单簿与占用表的写入只经 `job_admit`，下单、启动、取消、过期淘汰、`STOP_ALL`、`CLEAR_MACHINE`、关总开关清簿和放行共用一把锁，`start_job` 在锁内调用。这样全停或清障不会与进行中的放行交错，漏掉裁决后才启动的作业。`start_job` 因此只能启动异步流程，不得同步回调任何 `job_admit_*`。

`start_job` 返回 `SW_ERR_PARAM` 视为永久失败，丢弃该单；其它错误保留在队首。同一 `order_id` 已在簿或在洗时，重复下单幂等成功。

## 3. 整机态语义

| 模式 | 含义 |
|------|------|
| `STOPPED` | 未运营或待恢复 |
| `STANDBY` | 可接单、可放行 |
| `ACTIVE` | 至少一单在洗；允许继续入簿和放行 |
| `CLEARING` | 整机清障/排空，停止放行 |
| `HOLD` | 可选占位，等场区清空后再回 `STANDBY` |
| `SELF_CHECK` / `RECOVERING` | 自检 / 恢复 |

占用数以 `active_jobs` 为准，不靠模式枚举表达车数。最后一单结束时：`hold_after_last_job` 为真则进 `HOLD`，否则回 `STANDBY`。

## 4. 命令词汇

入簿成功即命令完成，网关不等待开洗。`START_WASH` 放行成功才算命令完成；条件不够则失败，已入队的单保留。

| 命令 | 行为 |
|------|------|
| `SUBMIT_ORDER` | 总开关开且非 `INIT`、切断已确认即可入簿；急停拒新单；不放行 |
| `START_WASH` | 请求开洗队首；条件不够则失败 |
| `CANCEL_ORDER` | 按 `order_id` 取消未放行订单 |
| `SET_SERVICE` | 关总开关拒新单；默认保留已入簿订单 |
| `STOP_ALL_OUTPUTS` | 切 `STOPPED`、切断输出、清空订单簿、中止在洗作业 |
| `CLEAR_MACHINE` | 停放行、中止在洗、进 `CLEARING`，项目 `clear_machine()` |
| `RECOVER` / `MANUAL` / `SELF_CHECK` | 仍作用在整机层 |

## 5. 机型 profile

项目在 bind 阶段注册 `machine_profile_t`：

- `max_active_jobs`：同时在洗上限
- `max_queued_orders`：内存簿上限，满则入簿失败
- `hold_after_last_job`：最后一单结束后是否进入 `HOLD`
- `clear_on_service_off`：关总开关时是否清簿，默认 false
- `clear_on_job_abort`：单车工艺中止后是否整机清障；单车机型为 true（默认），连续多车为 false
- `max_order_age_ms`：入簿有效期，过期单由周期扫描淘汰，入簿和放行前再扫一次；0 表示不淘汰，默认 30 分钟

框架不出现具体机型枚举。

## 6. 与项目的边界

框架提供作业描述、放行核和整机态。项目提供：

- `is_admit_ready`：下一辆能否进场
- `start_job`：异步启动一单工艺
- `abort_jobs` / `clear_machine` / `home_device`
- 作业开始/结束事件：`EVT_JOB_STARTED` / `EVT_JOB_COMPLETED` / `EVT_JOB_ABORTED`；后两者 param 为框架分配的 `job_id`
- 场区清空：`EVT_JOB_AREA_CLEARED`（仅 `hold_after_last_job` 机型需要）

`EVT_JOB_ABORTED` 只撤对应 `job_id` 的占用；`clear_on_job_abort` 为真时整机进入 `CLEARING`，由项目 `clear_machine()` 收尾。急停、LOCKOUT、`STOP_ALL`、`CLEAR_MACHINE` 会先撤掉全部占用，其后到达的 `EVT_JOB_ABORTED` 找不到对应作业，直接忽略。

输送工位表、停车锁止、仿形算法留在项目仓。

## 7. 掉电与急停

订单只在内存，掉电丢弃。急停拒绝新单、保留已入簿订单、中止在洗作业。`STOP_ALL` 清空订单簿。
