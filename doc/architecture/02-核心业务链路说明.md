# 核心业务链路说明

## 1. 命令链路

外部命令统一进入设备命令端口，经命令网关裁决后再产生副作用。

```text
Cloud / CLI / Sim
        ↓
device_command_port
        ↓
command_gateway
        ↓
operational_mode
        ↓
side_effect_router
        ↓
device_ops（项目实现）/ safety action
```

命令网关负责判断当前运行模式、安全状态和命令是否合法。`SUBMIT_ORDER` 入队成功即返回，
不在网关内等待开洗。具体工艺由项目 `device_ops.start_job` 在放行核调用时启动。

## 2. 作业链路

云端启动先入队，设备逻辑决定何时放行：

```text
SUBMIT_ORDER
        ↓
order_book（内存 FIFO）
        ↓
job_admit（占用未满 且 is_admit_ready 且次数授权允许）
        ↓
device_ops.start_job（项目编排）
        ↓
engine_session / 产品工位表
        ↓
HAL adapter / project machine
```

框架负责解释方案、表达式求值、tick 推进和通用联锁，并提供
`application/engine_session/` 作为通用会话。

**框架不提供机型工艺编排器。**选哪个方案、车在哪一站、如何驱动机构属于项目职责。
放行核只保证 FIFO 取队首，并遵守 `machine_profile_t` 的同时在洗上限与次数授权（见 `10-通用洗车运营模型.md` §3.1）。

## 3. 事件与状态链路

业务事实通过事件总线传播，投影模块生成只读快照：

```text
domain event
        ↓
event_bus
        ↓
application projection / bridge
        ↓
device_snapshot（单锁四子域只读视图）
        ↓
cloud report / CLI / UI / diagnostics
```

写侧事实源仍归领域模块维护，读侧通过 snapshot 降低跨模块查询耦合。快照合并为单一
结构而非按子域分设，是为让读侧一次取到跨子域一致的视图——分多次取会拿到不同时刻
的状态，安全姿态与活动报警不一致过就是这么来的。

## 4. 安全链路

硬件急停、报警触发和运行模式共同形成安全闭环：

```text
HAL / detector / project binding
        ↓
alarm binding or safety event
        ↓
alarm_registry / alarm_bridge
        ↓
operational_mode / command_gateway
        ↓
safety output / command deny / deferred stop
```

项目负责 detector 表、报警目录和安全 IO；框架负责报警状态机、安全姿态聚合和命令拦截。
