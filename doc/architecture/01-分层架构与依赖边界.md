# 分层架构与依赖边界

## 1. 分层目标

分层的目标是隔离变化：业务规则稳定，硬件、云端、存储格式、项目绑定和部署配置变化频繁。框架通过依赖方向约束保证业务模块可以复用。

## 2. 依赖方向与调用方向

端口契约按所有权落在 `domain/ports`、`application/ports`；`runtime/ports` 只做
注册表与契约校验（装配）。**不再存在顶层 `ports/` 业务层。**

依赖方向（谁 `#include` 谁）与调用方向（运行时谁调用谁）必须分开看。

### 2.1 依赖方向（include）

```text
adapters / demo / 项目 wiring
        │
        ▼
application
        │
        ├──► application/ports/outbound/cloud
        ▼
     domain ──► domain/ports/outbound
        │
        ▼
     common

runtime/bootstrap 与 runtime/ports 作为装配器可依赖各层契约。
event_bus / scheduler 只依赖 common。
```

禁止方向：

- `domain` 依赖 `adapters` 或 `application`（含 `application/ports`）。
- `domain` 直接访问文件系统、云 SDK、Modbus 地址或 IO 编号。
- `domain` 自建线程或周期任务；时序推进由调用方驱动 tick。
- `domain` 使用动态内存（方案引擎按加载期一次性分配登记豁免）。
- `domain/ports`、`application/ports` 暴露具体 SDK 类型或依赖 `adapters`。
- `adapters` 承载跨领域编排（bridge / projection / coordinator 属于 `application`）。
- 通用框架目录引用框架树之外的头文件（vendor SDK 头限 `adapters/**/providers/`），
  或存在未被框架构建清单登记的 `.c`。
- `application` 依赖 `adapters`。
- `observability` 依赖 `common` 之外的任何层。
- 不得再设立 `services/` 层。

以上各条由 `scripts/check_arch_boundary.sh` 自动检查。

### 2.2 调用方向（运行时）

入站（driving）：

```text
Cloud / CLI / UI / Sim / Test
        ↓
adapters/inbound
        ↓
application/ports/inbound
        ↓
application（含 alarm_bridge 等）
        ↓
domain
```

出站（driven，依赖倒置）：

```text
application / domain
        ↓
domain/ports/outbound 或 application/ports/outbound/cloud
        ↓
adapters/outbound
        ↓
HAL / Storage / Cloud SDK / Project Machine
```

### 2.3 端口所有权（物理路径）

C 用 include 路径前缀当可见性：内部层合法的出站必须挂在 `domain/` 下，
内部层禁止消费的契约必须挂在 `application/` 下。判定只看「内部层将来可不可以
消费」，不看今天谁 include。

新端口放哪：

1. 外部驱动用例 → `application/ports/inbound`
2. 云传输 → `application/ports/outbound/cloud`（领域禁止碰传输）
3. 注册表 / 启动校验 → `runtime/ports`
4. 其余出站（外面实现、里面调用）→ `domain/ports/outbound/<能力域>`

`domain/ports/outbound` 只放真 driven port。领域自己实现的 API 不进这棵树：
`motor_exec.h` 在 `domain/mechanism/motor/`，`safety_output_hold` 在 `domain/safety/`。

| 路径 | 语义所有权 | 说明 |
|------|------------|------|
| `domain/ports/outbound/hal/` | 设备能力 | IO / sensor / VFD / voice；adapters、runtime 装配 |
| `domain/ports/outbound/motor/motor_hw_port.h` | 电机硬件 | 驱动器 / 编码器 / 限位；`motor_types.h` 是共用词汇 |
| `domain/ports/outbound/safety/safety_port.h` | 安全切断与急停输入 | 注册时绑定 `safety_output_hold` 的 DI |
| `domain/ports/outbound/storage/` | 存储出站 | 参数 / 部署 / 方案加载；`param_kv` 是同目录便利层 |
| `domain/ports/outbound/device/` | 项目机型动作 | `device_ops` |
| `domain/ports/outbound/program_engine/` | 引擎环境 | provider 句柄 |
| `application/ports/inbound/**` | 入站用例 | command、alarm_binding |
| `application/ports/outbound/cloud/**` | 应用层云出站 | 链路、属性上报、下行 recv |
| `runtime/ports/**` | 装配 | port_registry、port_contract |

HAL、storage 即使当前没有 domain 源文件 include，也留在 domain 锥：内部层必须
有权消费设备能力与存储。拒绝再立顶层「共享 ports」——会回到旧的模糊外层。

门禁：R24 拦截出站头声明、领域内部定义的假 port；R25 要求 `domain/ports/outbound`
下每个 `.c` 登记为 `register_stub` 或 `helper`；R26 要求端口源文件落在上表能力域。
登记表与注入自检在 `scripts/check_port_placement.py`。

出站契约可引用领域类型（契约使用领域语言）。适配器实现契约，领域不依赖适配器。

### 2.4 各层允许的出向依赖

| 层 | 允许依赖 |
|----|----------|
| `common` | 无 |
| `domain` | `common`、`domain/ports/outbound`、`runtime`（仅 event_bus） |
| `application` | `common`、`domain`、`application/ports`、`runtime` |
| `runtime` | `common`（event_bus/scheduler）；bootstrap 与 `runtime/ports` 可装配各层 |
| `adapters` | 以上各层 |
| `observability` | `common` |

云端物模型位于 `domain/cloud/`；属性 JSON 编解码在 `adapters/outbound/cloud/`。

## 3. Ports & Adapters

六边形关系：业务依赖出站契约而非适配器；外部经入站契约驱动应用层。
入站跟 application；内部层合法的出站挂在 domain 锥。打开目录能区分入站/出站/装配。

## 4. 项目接入边界

项目侧通过以下方式接入：

- `wiring()` 注册 HAL、storage、cloud、engine loader 等 provider。
- `project_hooks` 填充项目生命周期逻辑。
- binding 表描述 IO、报警、设备实例、云点位等项目资产。
- 配置文件提供部署参数、运行参数和洗车方案。

框架侧只依赖这些接入后的通用端口。
