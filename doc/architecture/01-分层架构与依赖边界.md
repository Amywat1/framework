# 分层架构与依赖边界

## 1. 分层目标

分层的目标是隔离变化：业务规则稳定，硬件、云端、存储格式、项目绑定和部署配置变化频繁。框架通过依赖方向约束保证业务模块可以复用。

## 2. 依赖方向与调用方向

端口契约按所有权落在 `domain/ports`、`application/ports`；`runtime/ports` 只做
注册表与契约校验（装配）。**不再存在顶层 `ports/` 业务层。**

依赖方向（谁 `#include` 谁）与调用方向（运行时谁调用谁）必须分开看。

### 2.1 依赖方向（include）

```text
adapters / demo / 项目 wiring
        │
        ▼
application / services
        │
        ├──► application/ports/outbound/cloud
        ▼
     domain ──► domain/ports/outbound
        │
        ▼
     common

runtime/bootstrap 与 runtime/ports 作为装配器可依赖各层契约。
event_bus / scheduler 只依赖 common。
```

禁止方向：

- `domain` 依赖 `adapters` 或 `application`（含 `application/ports`）。
- `domain` 直接访问文件系统、云 SDK、Modbus 地址或 IO 编号。
- `domain` 自建线程或周期任务；时序推进由调用方驱动 tick。
- `domain` 使用动态内存（方案引擎按加载期一次性分配登记豁免）。
- `domain/ports`、`application/ports` 暴露具体 SDK 类型或依赖 `adapters`。
- `adapters` 承载跨领域编排（bridge / projection / coordinator 属于 `application`）。
- 通用框架目录引用框架树之外的头文件（vendor SDK 头限 `adapters/**/providers/`），
  或存在未被框架构建清单登记的 `.c`。
- `application` 依赖 `adapters` 或 `services`。
- `services` 依赖 `adapters` 或 `application`。
- `observability` 依赖 `common` 之外的任何层。

以上各条由 `scripts/check_arch_boundary.sh` 自动检查。

### 2.2 调用方向（运行时）

入站（driving）：

```text
Cloud / CLI / UI / Sim / Test
        ↓
adapters/inbound
        ↓
application/ports/inbound
        ↓
application（含 alarm_binding_bridge 等）
        ↓
domain
```

出站（driven，依赖倒置）：

```text
application / domain
        ↓
domain/ports/outbound 或 application/ports/outbound/cloud
        ↓
adapters/outbound
        ↓
HAL / Storage / Cloud SDK / Project Machine
```

### 2.3 端口所有权（物理路径）

| 路径 | 语义所有权 | 说明 |
|------|------------|------|
| `domain/ports/outbound/**` | 出站契约树（挂在 domain 依赖锥） | 见下表：并非「每个头都被 domain 代码 include」 |
| `application/ports/inbound/**` | 入站用例边界 | command、alarm_binding |
| `application/ports/outbound/cloud/**` | 应用层云出站 | 单一 `cloud_link_port`（含属性上报与下行 recv） |
| `runtime/ports/**` | 装配 | port_registry、port_contract |
| `application/bridges/alarm_binding_bridge.*` | 入站→领域 | 注册 alarm_binding，转调 `alarm_registry_*` |

`domain/ports/outbound` 内按**契约能力域与形态**再分（不以「谁 include」嵌套路径）：

| 子树 | 契约形态 | domain 是否 include | 主要调用方 | 为何仍放在此树 |
|------|----------|---------------------|------------|----------------|
| `machine/`、`motor/` | 领域直接消费的执行抽象（machine：ops 注册；motor：轴会话 + 硬件端口类型） | 是 | domain；接线填硬件端口；业务走 `motor_axis` | 领域规则直接消费；硬件端口只在 bind 时由 composition root 填入 |
| `safety/` | 安全域出站 | 否 | application、runtime | 与其它非云出站同树，避免按调用方再拆第三套路径 |
| `hal/`（io/sensor/vfd/voice） | register/get_ops 设备能力 | 否 | adapters、runtime | 设备能力边界的稳定契约；adapters/runtime 装配，不经 application |
| `storage/` | 存储出站 | 否（loader 例外：application 用） | services、runtime、adapters | **services 不得依赖 application**，共享出站只能落在 domain 锥内 |

因此目录名表示「出站契约的能力域与形态」，不是「domain 源文件的 include 清单」。拒绝再立顶层「共享 ports」——那会回到旧的模糊外层。

出站契约可引用领域类型（契约使用领域语言）。适配器实现契约，领域不依赖适配器。

### 2.4 各层允许的出向依赖

| 层 | 允许依赖 |
|----|----------|
| `common` | 无 |
| `domain` | `common`、`domain/ports/outbound`、`runtime`（仅 event_bus） |
| `application` | `common`、`domain`、`application/ports`、`runtime` |
| `runtime` | `common`（event_bus/scheduler）；bootstrap 与 `runtime/ports` 可装配各层 |
| `services` | `common`、`domain`（含 `domain/ports/outbound/storage`） |
| `adapters` | 以上各层 |
| `observability` | `common` |

云端物模型位于 `domain/cloud/`；属性 JSON 编解码在 `adapters/outbound/cloud/`。

## 3. Ports & Adapters

六边形关系：业务依赖出站契约而非适配器；外部经入站契约驱动应用层。
入站跟 application；出站树挂在 domain 依赖锥（含上表共享出站）。打开目录能区分入站/出站/装配，共享出站的真实调用方以上表为准。

## 4. 项目接入边界

项目侧通过以下方式接入：

- `wiring()` 注册 HAL、storage、cloud、engine loader 等 provider。
- `project_hooks` 填充项目生命周期逻辑。
- binding 表描述 IO、报警、设备实例、云点位等项目资产。
- 配置文件提供部署参数、运行参数和洗车方案。

框架侧只依赖这些接入后的通用端口。
