# 检索层

本目录供快速定位代码，不讲设计意图。三份文件分工：

| 文件 | 内容 | 维护方式 |
|------|------|----------|
| `符号索引.md` | 事件全表（含发布/订阅点）、端口全表、错误码、容量常量 | **自动生成** |
| `代码地图.md` | 目录 → CMake 目标 → 设计文档 | **自动生成** |
| `任务索引.md` | 常见改动 → 必须一起改的位置 | 手工维护 |

前两份由 `scripts/gen_doc_index.py` 从代码抽取，文件头有「请勿手工编辑」标记。
`check_all.sh` 会以 `--check` 校验它们与代码一致，代码改了而索引没重生成即门禁失败——
索引因此不可能落后于代码。

```bash
./scripts/gen_doc_index.py            # 重新生成
./scripts/gen_doc_index.py --check    # 只校验是否最新
```

第三份手工维护，因为它记的是判断（"改这个必须同时改那个"）而非可抽取的数据。

## 为什么这一类要生成

`architecture/` 与 `module-design/` 都是手写散文，失效速度相同。本仓的实际教训是
"机器能算、人在手抄"的信息必然失同步：一次核查在 24 篇文档里查出 6 处不存在的路径
与 3 处不存在的符号，其中 `../module-design/ports-adapters/CloudModel模块设计.md`
的文件清单把 JSON 编解码写成
`domain/` 侧职责——而那次改动的全部目的正是把编解码移出 `domain`。同类事故还有
`tests/reports/` 的手写覆盖表声称 event_bus 8 例而实际 13 例。

所以检索层若也手写，只会成为第四份失同步副本。同一论证见 `../contract/行为契约.md` 第 5 节。

## 与其他文档的关系

| 想知道 | 去哪 |
|--------|------|
| 某个符号在哪 | 本目录 `符号索引.md` |
| 改动要动哪些文件 | 本目录 `任务索引.md` |
| 为什么这样设计 | `../architecture/` |
| 代码具体怎么实现契约 | `../module-design/` |
| 某条行为由谁保证、在哪验证 | `../contract/行为契约.md` |
