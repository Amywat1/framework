# 文档入口

本文档目录按用途分为三类。分类依据是**谁消费、多久失效一次**，不是抽象层次高低——
三类各有不同的维护机制，混在一起会一起烂掉。

| 目录 | 定位 | 主要读者 | 内容边界 | 维护机制 |
|------|------|----------|----------|----------|
| `architecture/` | 架构说明 | 方案评审、项目负责人、接入方 | 说明通用框架的设计目标、模块协作、边界和落地范围，不展开代码细节 | 手写，只在设计决策变化时改 |
| `module-design/` | 模块设计基线 | 开发、维护、测试、项目适配人员 | 对齐当前代码实现，说明模块文件、接口契约、数据模型、行为和测试覆盖 | 手写，代码变更影响模块契约时改 |
| `ai/` | 检索层 | AI 与需要快速定位代码的人 | 符号索引、代码地图、任务索引，只答「在哪」不答「为什么」 | 前两份**自动生成**，任务索引手写 |

`contract/行为契约.md` 是第四种东西——它不描述设计也不描述实现，而是回答「每条行为由谁保证、
在哪一层验证」，是测试方案的事实源，由 `scripts/check_behaviour_contract.sh` 校验结构。

## 推荐阅读路径

| 目标 | 推荐文档 |
|------|----------|
| 快速理解通用框架 | `architecture/00-通用框架架构说明.md` |
| 判断框架与项目边界 | `architecture/03-通用能力与项目资产边界.md` |
| 理解运行链路 | `architecture/02-核心业务链路说明.md` |
| 接入新项目 | `architecture/06-项目接入架构.md`、`module-design/integration/Demo与项目接入模块设计.md` |
| 规划后续优化 | `architecture/08-框架优化方向.md` |
| 维护具体代码 | `module-design/README.md` 后按模块进入对应文档 |
| 定位某个符号 | `ai/符号索引.md` |
| 知道一处改动要连带改哪些文件 | `ai/任务索引.md` |
| 查某条行为的归属与验证级别 | `contract/行为契约.md` |

## 构建与门禁

```bash
./scripts/check_all.sh              # 五项门禁：架构边界 / 行为契约 / 文档引用 / 格式 / 测试
./scripts/check_all.sh --skip-tests # 无 cmake 环境时只做静态检查
```

报告在 `build-check/test-results/report.html`。

## 文档维护原则

- `architecture/` 只描述方案和设计判断，避免结构体字段、完整 API 表和测试细节。
- `module-design/` 必须和当前代码实现保持一致，代码变更影响模块契约时同步更新。
- `ai/符号索引.md` 与 `ai/代码地图.md` 由 `scripts/gen_doc_index.py` 生成，
  **不得手工编辑**；改代码后须重新生成，否则 D4 门禁失败。
- 文档引用的代码路径与函数名必须真实存在（D1/D2），文档间链接必须可解析（D3）。
  记录已删除的符号或路径需在 `scripts/check_doc_refs.sh` 的白名单登记并写理由。
- 项目专属资产不写入通用框架设计，包括具体 IO 表、报警目录、云物模型表、水路拓扑表和洗车方案资产。
- 当项目能力确认具备跨项目复用价值后，先沉淀为通用接口或 helper，再补充对应模块设计。
