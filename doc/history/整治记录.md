# 框架整治记录

本文档记录不属于 `architecture/08-框架优化方向.md` 优先级表任何方向的整治工作。
它们的共同点是：从代码审查或架构评估中发现，改动横跨多个模块，且**决策理由值得留存**——
"当时为什么这么选、放弃了什么替代方案、代价是什么"。

与其他文档的分工：

| 文档 | 回答 |
|------|------|
| `architecture/08-框架优化方向.md` | 还要做什么，各方向当前状态 |
| 本文档 | 已经做过什么，当时为什么这么决定 |
| `../module-design/` | 代码现在是什么样 |
| git 历史 | 具体改了哪些行 |

**本文档只留决策，不留过程。**改动清单在 git 历史里，重述一遍只会失同步。若某条记录
读起来像变更日志而非决策依据，应当删掉或改写成决策。

各节按整治轮次排序，编号与时间顺序一致。

## 1. 并发缺陷与工程化护栏修复记录

本节记录一轮代码审查后的修复，不属于优先级表任何方向，但影响运行可靠性。

### 1.1 已修复的并发缺陷

**事件总线互斥量优先级反转。** 事件总线允许被实时线程调用——框架自带的急停轮询
适配器以 `SCHED_FIFO` 优先级 90 发布事件，项目也可能从自己的实时线程发布——而队列锁
同时被多个 `SCHED_OTHER` 周期任务竞争。原先两把锁是裸 `PTHREAD_MUTEX_INITIALIZER`，
普通优先级线程持锁期间被抢占会让实时线程阻塞且时长不受优先级保护，构成无界优先级反转。现改为运行期 `pthread_mutexattr_init` +
`PTHREAD_PRIO_INHERIT`，用 `pthread_once` 保证恰好初始化一次（`event_bus_init()`
允许被重复调用，对已初始化互斥量再次 `pthread_mutex_init` 是 POSIX 未定义行为）。
平台不支持优先级继承时退化为默认互斥量，功能不受影响。

**命令网关信号量残留计数。** `command_gateway_drain()` 原先在解锁后才 `sem_post`。
若 `gateway_submit` 正好在该窗口内超时并释放槽位，信号量计数会残留给下一任槽主，
使其 `sem_timedwait` 立即返回并读到占位 receipt——命令被静默丢弃、调用方却收到
`SW_ERR_BUSY`。现将 `sem_post` 移入持锁范围（`sem_post` 不阻塞，持锁开销可忽略），
并在抢到槽位时用 `sem_trywait` 排空残留计数作为双重保险。

同一函数另修两处：`sem_timedwait` 补 `EINTR` 重试（截止时间是绝对值，重试不延长
总等待时长），避免一个信号就把正常命令报成超时；新增 dispatch 线程重入防护——从
dispatch 线程自身调用 `submit` 必然自锁，原先要白等满超时才返回，现直接返回
`SW_ERR_STATE` 并记录错误。调用上下文约束已写入 `command_port.h`。

**告警注册表锁范围。** `find_def_index()` 原在锁外调用，而 `load_catalog` 持锁改写
`s_catalog` 与 `s_catalog_count`，读写保护不对称。现将查表纳入同一把锁。

**安全投影快照不一致。** `telemetry_projection` 原先分两次取锁（`copy_active_projection`
+ `safety_posture`），拿到的活动表与安全姿态可能来自不同时刻。新增
`alarm_registry_copy_safety_view()` 一次持锁读出四项；同时补订阅
`EVT_SAFETY_LOCKOUT` / `EVT_SAFETY_NOMINAL`，避免姿态切换后快照滞后。

### 1.2 已修复的容量与时序问题

**周期任务槽位耗尽。** `PERIODIC_TASK_MAX` 原为 9，而接入项目实测 sim 与 target 均已
注册满 9 个周期任务，零余量——下一个周期任务注册就会让 bootstrap 失败。现改为与
`THREAD_REGISTRY_MAX` 对齐（后者由 16 提升到 24），周期任务不再构成独立的第二道
容量上限，超限统一由 `thread_registry` 报错。并加编译期断言防止两者失配。
`thread_registry.h` 中记录了槽位构成的核算口径。

**周期任务累积漂移。** 原实现是「执行回调 → `usleep(period)`」，睡的是固定相对
时长，回调耗时会累加进周期（10ms 任务若回调耗 3ms，实际周期变 13ms）。现改用
`clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME)` 维护绝对下一拍；单次回调超过一个
周期时跳过已错过的拍而不追赶。9 个周期任务中有 5 个周期 ≤20ms，漂移会直接影响
传感器采样与水路判定的时间基准。

### 1.3 日志与诊断

- `sw_log` 增加运行期级别门限（`sw_log_set_level` / `sw_log_level_enabled`），
  过滤在格式化之前完成，被丢弃的日志不付出 `vsnprintf` 开销。
- 默认 sink 改为先整条组装进栈缓冲再单次 `fwrite`。原先用 `fprintf` + `vfprintf`
  + `fputc` 三次独立 stdio 调用，多线程并发时同一行会被其他线程输出插入。
- sink 表加锁保护，并在写日志时取快照后即释放锁，避免 sink 内部再写日志造成自锁。
- `level` 越界不再用于数组下标。

### 1.4 其他

- `util_fifo` 全部入口补判空；头文件明确「不含内部锁，多线程需调用方加锁」，
  并说明当前不可当作无锁 SPSC 队列使用的原因。
- `observation_context_t` 改为 `trace_context_t` 的别名。两者原本是同名同序的四个
  `uint64_t` 字段，重复定义会在各自演进后失同步。
- 云适配器的 `strcpy` 统一为 `snprintf`（原有长度校验本已到位，此处只统一风格）。
- `event_bus_dispatch_loop` 的 handler 快照数组补零：非法事件类型在 publish 侧已被
  拦截、理论不可达，但若不清零会保留上一轮 handler 并被重复调用。
- 补齐 电机执行器测试桩（路径已随组合件整治移除） 缺失的 `motor_pop_event` 桩。
  该缺失导致 `test_motor_exec_port` 长期链接失败，而父工程从不构建 framework
  自带测试，因此一直未被发现。framework 独立测试现为 46/46 全通过。

## 2. 复用性与层归属整治记录

本节记录一轮架构评估后的结构性改动。这些改动不新增业务能力，目标是让框架能被
第二个项目干净接入，并让层边界从"文档约定"变为"脚本可判定"。

### 2.1 框架导出构建目标（原缺口：复用单位是源文件清单）

框架原先只为 5 个可选 vendor provider 建了 `add_library`，核心层一个目标都没有，
项目必须手抄 74 条 `framework/**/*.c` 路径。框架增删文件时项目要同步改列表，
第二个项目接入要把清单重抄一遍，编译选项与包含目录也无法传递。

现由 `cmake/wdf_targets.cmake` 导出分层目标，项目侧 `target_link_libraries` 即可。

选择 **INTERFACE 库而非 STATIC**：同一份框架源在不同目标下需要不同编译定义
（例如测试目标为 `hal_io_sim.c` 定义 `HAL_IO_SIM_UNIT_TEST` 以暴露测试复位入口，
sim/真机不定义）。STATIC 只编译一次，无法同时满足；INTERFACE 传递源与包含目录，
由消费方按自己的宏编译，行为与手写源列表完全一致。

目标粒度按"可独立取用"划分而非按目录：`wdf_domain` 只含命令裁决、报警、遥测读模型，
机构控制模式与方案引擎各自独立（它们分别要求项目提供 motor provider / 方案资产，
最小接入并不需要）。`engine_session`、`report_scheduler`、方案 JSON 加载同理拆出。
验证方式是 demo 只链接最小集合仍能构建通过。

### 2.2 安全端口从弱符号改注册表（原缺口：最高风险处用了最松的绑定）

四个安全入口原为 `__attribute__((weak))` 空实现。弱符号是链接期绑定，项目漏实现
不会有任何提示——而空实现的 `safety_cutout_execute` 意味着急停不切断动力输出，
启动日志里也看不出异常。风险最高的四条路径用了整套端口机制里最松的方式。

现统一为 `safety_ops_t` 注册表：四字段全必填（缺任一都会让某条安全链路静默失效），
未注册时各入口首次被调用时报 ERROR（急停期间高频调用，故按路径各报一次而非每次），
并可由 `port_contract_validate(PORT_REQ_SAFETY)` 在启动期拦住漏注册。

改造过程中该机制立即暴露了两处此前被掩盖的真实缺陷：项目 smoke 在完成 wiring 前就
调用安全路径（弱符号时代是空操作，故一直"通过"）；急停 `cutout` 真正生效后会置位
水路 emergency 标志，影响后续水路时序断言。两处均已修正。

### 2.3 必需端口启动期校验（原缺口：漏注册与"不需要"无法区分）

`bootstrap` 原先对未注册端口一律 `return SW_OK` 跳过，于是漏注册能一路启动成功，
直到第一次业务调用才失败——现场表现为随机时刻功能不可用，而非启动失败。

现由项目在 `project_validate()` 声明必需端口位掩码，框架一次报出全部缺失项。
框架不内置"哪些端口必需"的判断：那取决于项目用到哪些能力，无云连接的项目本就
不该被要求注册 `cloud_link`。接入项目 sim 声明 10 项、target 13 项，框架 demo 7 项。

### 2.4 层归属修正

| 原位置 | 现位置 | 理由 |
|--------|--------|------|
| `domain/program_engine/model/engine_program_manifest.*` | `adapters/outbound/storage/json/` | 做的全是文件读取 + SHA256 + JSON 解析，无领域规则；完整性校验改为 loader 端口的可选 ops，`application` 只依赖端口 |
| `domain` 内 `fluid_path` 自建周期任务 | 调用方注册 | 领域层不创建线程；`fluid_path_poll` 由条件编译的测试专用接口转为常规接口 |
| `runtime/platform/safety_thread.*` | `adapters/inbound/safety/estop_poll_thread.*` | 这是"如何采集急停"的一种实现，属入站适配器而非运行时核心。已接入项目有自己的 DI detector 采集通路，从未链接它 |
| `adapters/inbound/event/*_bridge.*` | `application/bridges/` | 四个 bridge 只依赖 domain + runtime，不适配任何外部系统；与已在 `application/orchestrators/` 的同性质协调器分处两层会让"adapters 是外部适配"失去可判定性 |
| `services/dev_ctx` | 删除，并入 `device_snapshot` | 该层只是把快照摊平再补一个 `cloud_connected`，无其他职责。`cloud_connected` 并入快照后读侧还获得了跨子域一致性 |

### 2.5 边界检查扩展（R9、R10）

原有 R1~R8 只看 include 路径，管不住"用标准库直接做本不属于该层的事"。新增：

- R9a~R9d：`domain/` 禁止文件 IO、序列化解析、线程注册、动态内存。
  方案引擎三文件按加载期一次性分配 + 显式 free 登记豁免，新增文件需显式登记。
- R10：`adapters/` 不得出现 `*_bridge` / `*_projection` / `*_coordinator`。

规则均以注入违规的方式验证过确实能捕获（而非写出永远通过的假规则）。

### 2.6 事件 param 编解码收口

三种不同位布局共用 `uint32_t param`，发布方与订阅方各自手写移位，改枚举顺序会
静默错位且编译器无法察觉。现统一为 `encode/decode` inline 函数，并补往返测试
锁定布局契约——两侧不同步时在 CI 阶段就失败。

### 2.7 跨线程读修正

`op_mode_*` 直读接口不加锁（其状态只在 event_dispatch 线程内修改），但
项目侧一个监管模块在自己的周期任务线程调用 `op_mode_get_current()`，构成无保护
跨线程读。已改用加锁的 `device_snapshot_get()`，并在头文件写明线程约束。

## 3. 安全形式化与运行可靠性记录

本节记录第二轮评估后的改动。上一轮（第 2 节）解决的是复用性与层归属，本轮
聚焦安全行为形式化、容量依据与错误语义。

### 3.1 安全矩阵（P0 收尾）

三个 P0 方向中最后一个未动的项。详见 `architecture/08-框架优化方向.md` 第 8 节「落地情况」。要点：等级与清除策略
的语义从散落在 8 处判定点收口到 `domain/safety/model/safety_matrix.h`，以行为属性
（阻塞开洗 / 进入 LOCKOUT / 记会话日志）而非等级序号表达。

选择行为属性而非序号比较的原因：`level >= MAJOR` 隐含「等级按严重度排序且新等级
只追加在末尾」的假设，若将来在 MINOR 与 MAJOR 之间插入一级，所有 `>=` 判定都会
静默改变含义。

### 3.2 零覆盖模块补测试

核对了 12 个无独立测试文件的模块，其中 11 个被其他测试间接链接覆盖，只有
`alarm_bridge` 完全零覆盖。它虽只有 30 行，但决定 session journal 何时
开关，而 journal 决定洗完后哪些 MAJOR 报警把设备推入 STOPPED——错了的现场表现
是"洗完车该停机却没停"。

`tests/application/test_alarm_event_bridge.c` 覆盖 9 个场景，含会话未开始不记
日志、新会话清空上轮、MINOR 不记录、重复触发去重、清除后仍保留。已验证漏订阅
`EVT_WASH_DONE` 会导致测试失败。

### 3.3 容量常量补实测依据

原先 `EVENT_BUS_QUEUE_SIZE` 等是拍定的数。`tests/runtime/test_event_bus_capacity.c`
按已接入项目最密的 10ms 周期档压测，实测：

| 项目 | 实测峰值 | 容量 | 余量 |
|------|----------|------|------|
| 普通队列稳态 | 9 | 64 | 86% |
| 高优先级稳态 | 0 | 16 | 100% |
| 单事件订阅者 | 4 | 8 | 50% |

设计预留（非压测结论，勿与上表「实测峰值」混读）：

| 项目 | 依据 | 容量 |
|------|------|------|
| 电机执行器逻辑轴/驱动/互锁（`MOTOR_MAX_*`） | 覆盖当前多轴接入余量并控制静态 RAM | 16 |
| 电机每轴事件槽（`MOTOR_EVENT_SLOT_CAP`） | 每轴每拍通常至多 1 条终止事件，偶发 WARNING+FAULT；满时只丢该轴最旧事件 | 4 |

另外验证了两个设计前提确实成立：慢 handler 阻塞期间普通队列能完整填到 64 才开始
拒绝（有效容量等于标称容量，不是提前失效），且此时高优先级队列仍能完整接受 16 个
安全事件（双队列隔离有效）。

依据已写入 `event_bus_config.h`、`alarm_types.h` 与电机执行器头注释；调整容量时需同步
更新表格与测试断言门限。

### 3.4 错误语义分类

`SW_ERR_PARAM` 占全部返回的约一半（192 处），被当作通用失败码，调用方无法据此
判断该重试、降级还是终止。现在 `common/sw_error.h` 提供三类判定 helper
（瞬时可重试 / 调用方缺陷 / 接入缺失），并说明 `SW_ERR_PARAM` 应收窄到"入参本身
不合契约"。

两个从未使用的枚举（`SW_ERR_UPGRADE` = -11、`SW_ERR_NOT_SUPPORT` = -13）**未删除**：
错误码数值经 protobuf 跨进程传给观测进程（`observation.proto` 的 `effect_error`），
删除中间值会让后续值前移，观测侧解读出的错误原因全部错位。现改为保留数值并标注
废弃，`tests/common/test_sw_error.c` 断言全部数值不变以拦住这类改动。

### 3.5 资产版本校验

原先只有方案与观测记录有 schema version，且方案用 `strcmp("1.0")` 精确匹配——
`"1.0.1"` 这类合法资产会被拒，也无法表达"接受同主版本的较低次版本"。

`common/asset_version.h` 提供通用语义化版本解析与兼容判定（主版本不同不兼容、
资产次版本高于框架不兼容、修订号不参与判定），方案加载器已改用它。云物模型、
报警目录、HAL binding、水路拓扑可按同一 helper 逐步接入，资产本身仍留项目侧。

刻意不做"未知字段自动忽略"：对报警目录、水路拓扑这类安全相关资产，静默忽略
未识别字段等于让缺失的约束通过校验。

## 4. 急停热路径整治记录

本节记录第三轮评估后的改动。上两轮分别解决复用性/层归属（第 2 节）与安全形式化
（第 3 节），本轮只针对一条链路：硬件急停触发后的切断路径。

选这条链路的原因是它同时命中两类此前未查透的缺陷，而且都在同一段代码里：
第 1 节修优先级反转时只追到 `event_bus` 与 `log`，没追到 cutout 往下的 HAL 层；
第 3 节做安全矩阵时形式化了"报警等级到姿态"的映射，但没管"切断本身失败了怎么办"。

### 4.1 切断路径上残余的优先级反转

`estop_poll_thread` 以 `SCHED_FIFO` / `THD_SAFETY_THREAD_PRIO` 运行，
`safety_cutout_execute()` 往下会取三处**裸 `PTHREAD_MUTEX_INITIALIZER`**：

| 锁 | 位置 | 竞争方 |
|----|------|--------|
| `s_output_mutex` / `s_input_mutex` | `io_exp_driver.c`（真机 DO 写） | CAN 刷新、输入采样周期任务 |
| `s_do_mutex` / `s_di_mutex` | `hal_io_sim.c`（sim DO 写） | 同上 |
| `s_vfd_lock` / `s_control_lock` | `hal_vfd_manager.c`（电机 cutoff） | 变频器轮询、通信保活 |

六把锁全部改为优先级继承。`fluid_path_emergency_off` 已核查为纯原子写，不涉及锁，
不在此列。

同时把第 1 节各自手写的初始化收口为 `common/sw_mutex.h` 的
`sw_mutex_init_prio_inherit()`。原先 `event_bus`（两把）与 `log`（一把）各有一份
约 20 行的相同代码，本轮再加六把会变成五份副本，任何一份漏掉
`setprotocol` 失败分支都不会有编译期提示。

不提供"带静态初始化的包装类型"：静态初始化出来的互斥量已经可用，再对它调用
`pthread_mutex_init` 是 POSIX 未定义行为，因此无法"先静态初始化、事后升级为
优先级继承"。三个 HAL 模块都没有可靠的集中初始化时机（`hal_io_sim` 与
`hal_vfd_manager` 根本没有 init 入口，`io_exp_driver` 的 getter 允许在
`drv_io_init` 之前被调用），故沿用 `pthread_once` 在首次上锁前初始化。

已用独立探针确认本平台确实启用了继承而非走退化分支（`helper_applied=1`）。

### 4.2 切断失败不可见（`architecture/08-框架优化方向.md` 第 8 节遗留验收项）

原先 `safety_ops_t.cutout` 返回 `void`，项目侧的切断实现把每一路 `safe_do_set` 的
返回值都 `(void)` 丢弃，安全输出兜底实现同样丢弃。
后果是急停切断失败时：无日志、无计数、无报警，框架侧完全无从知晓——而这正是
最需要留下现场证据的时刻。

现改为逐层汇总：

| 层 | 变化 |
|----|------|
| `safety_ops_t.cutout` | 返回 `sw_err_t`；契约要求「尽力做完全部切断动作再返回」，不得在首个失败处提前返回 |
| `safety_cutout_execute` | 返回错误码，失败即记 ERROR 并累加 `safety_cutout_failure_count()` |
| 项目 `safety_ops_t.cutout` 实现 | 汇总各路 DO 写失败，返回首个错误码并记录失败路数 |
| 项目 `assert_safe_outputs` 实现 | 同上，且纳入输出立即下发的失败 |
| 项目上电安全态初始化 | 上电置安全态失败改为**拒绝启动**（原先无条件返回 `SW_OK`） |

三条设计取舍：

- **不在急停热路径重试。** 重试会延长动力输出未确认切断的窗口，且失败原因通常在
  硬件链路本身（总线离线、板卡无响应），重试无从改变。
- **切断失败不阻断后续事件发布。** `EVT_HW_ESTOP_ON` 必须照常送出，否则领域层不会
  进入急停态，故障会同时丢掉切断与状态收敛两条路径。这条性质由
  `test_cutout_failure_still_publishes_event` 锁定，已注入「失败即 return」的
  回归验证过该用例确实会失败。
- **失败计数不做首次节流。** 与"未注册"的 `warn_once` 不同：未注册是接入错误，
  一次就够；切断失败是运行期硬件故障，每一条都是判因证据。未注册导致的"未执行"
  返回 `SW_ERR_NOT_INIT` 且**不计入**失败计数，两者语义分开。

上电安全态初始化改为可拒绝启动是行为变更：上电无法把输出置安全态说明 IO
链路本身不可信，继续启动会让设备带着未知输出状态进入运行，且后续所有安全动作都
建立在同一条不可信链路上。bootstrap 的 `BOOT_CHECK` 会据此终止进程。

## 6. 目录环与命名一致性整治记录

本节记录第四轮评估后的改动。前几轮聚焦运行可靠性与安全形式化，本轮针对的是
**分层与命名的可判定性**：让"目录能否单独提取"和"保护宏是否跟得上目录"这两件事
从人工 review 转为脚本判定。

### 6.1 安全端口五头合一

`domain/ports/outbound/safety/` 下曾有 5 个头文件表达同一组能力：`safety_port.h` 是注册
入口（`safety_ops_t` 四字段全必填），另 4 个（`safety_cutout_port.h`、
`safety_deferred_stop.h`、`hw_estop_port.h`、`op_mode_alarm_port.h`）各只声明一个
包装函数，且全部由 `port_registry_safety.c` 实现。

这是弱符号时代的残留：那时它们确实是 4 个独立的链接期可替换符号，第 2.2 节改为
注册表后就只剩 4 个转发。消费者也印证了这一点——除注册表与测试外，每个头各只有
1 个真实调用点。

现合并进 `safety_port.h`（含 `safety_cutout_failure_count`），5 个头减为 1 个。

合并同时修掉两处**已经失实**的注释：`hw_estop_port.h` 与 `op_mode_alarm_port.h`
都还写着「项目层提供强符号实现；框架默认弱符号返回 false」，而弱符号早已不存在。
这类注释比缺注释更危险——它会让读者按已废弃的机制去接入。同样过时的表述在
`module-design/runtime/Runtime模块设计.md` 与 `module-design/domain/报警系统模块设计.md`
中各有一处，一并改正。

代价是 `op_mode_bridge.c` 只需 `alarm_is_estop` 却会看到整个 `safety_ops_t`。
可接受：该头只依赖 `sw_error.h` + `stdbool` + `stdint`，无传递性负担。

### 6.2 cloud 与 application 的目录环

**问题**：`cloud/` 与 `application/` 互相依赖——

```
cloud/cloud_model.h            → application/orchestrators/report_scheduler.h
application/orchestrators/report_scheduler.c → cloud/cloud_point_watcher.h
```

不是编译单元环（两个 `.o` 不互相依赖），但是**目录级双向依赖**：两个目录谁都无法
单独提取。而当时 R1~R10 全部通过，原因见 22.3。

**方向判定**：`cloud/` 位于 `application/` 之下。依据是 `cloud/` 只提供点位模型与
编解码能力，不订阅事件、不注册周期任务；而 `report_scheduler` 两者都做，属编排。
故保留 `application → cloud`，砍掉反向。

**做法**：把上报策略从物模型注册包摘出，由项目直接注册到调度器。

| 改动 | 说明 |
|------|------|
| `cloud_model_bundle_t` 删 `report_policies` / `policy_count` | 策略是调度器的输入格式，不属物模型 |
| 删 `cloud_model_register_scheduler()` / `cloud_model_request_resync()` | 两者合计仅三行转发 |
| 内部 `model_point_id_by_index` 提为公开 `cloud_model_point_id_by_index()` | 项目注册 resolver 时需要 |

`report_policy_entry_t` **未搬家**：它是调度器的输入格式，留在
`application/orchestrators/report_scheduler.h` 是正确归属。为三行转发让整个 `cloud/`
反向依赖 `application/`，代价与收益不成比例。

**未采用的替代方案**：把 `report_scheduler.c` 整体搬进 `cloud/`。同样能断环且更
"云内聚"，但会让 `cloud/` 变成含编排的层，与 R10 的判据（bridge / projection /
coordinator 属 application）自相矛盾，且 `cloud/` 就不再位于 application 之下。

CMake 侧同一处失真也已修正：`wdf_cloud` 原声明 `DEPENDS wdf_common wdf_ports`，
但 `cloud_point.h` 需要 `domain/`、`cloud_point_watcher.c` 需要 `runtime/`。因为
include 根是仓库根，**缺失的依赖声明不会报错**——目标声明此前不是可信的依赖描述。

### 6.3 上层出向依赖规则（R11~R14）

上一节那个环能长期存在的根因：R1~R10 **只约束 `common`/`domain`/`ports`/`runtime`
的出向依赖**。`application`、`cloud`、`services`、`observability` 的出向没有任何
规则，它们只作为"禁止被引用的上层"出现在别人的规则里。

补四条，允许集按实际需要确定，不做超出现状的收紧：

| 规则 | 约束 |
|------|------|
| R11 | `application/` 不依赖 `adapters/`、`services/` |
| R12 | `cloud/` 不依赖 `adapters/`、`application/`、`services/` |
| R13 | `services/` 不依赖 `adapters/`、`application/`、`cloud/` |
| R14 | `observability/` 只依赖 `common/` |

R14 最严是有依据的：`architecture/01` 称 `observability` 为旁路设施——任何层都可
向它发布记录、它不回调任何层、因此不构成环。这条性质**只有在它除 `common` 之外
什么都不依赖时才成立**，所以规则逐一排除其余各层。

四条规则均以注入违规的方式验证过确实能捕获。R12 尤其做了针对性验证：把
`cloud_model.h` 对 `report_scheduler.h` 的 include 加回去，R12 立即失败并指到
`cloud/cloud_model.h:15`。

### 6.4 保护宏与路径一致（R15）

核对发现 **67 个头文件**的保护宏与路径不符，分三类：

| 类型 | 例子 | 后果 |
|------|------|------|
| 撞名风险 | `DRV_VFD_H`、`TIME_UTIL_H`、`SW_ERROR_H`、`UTIL_FIFO_H` | vendor SDK 出现同名宏时，后包含的头被静默跳过，报"类型未定义"而非重复定义，排查成本远高于改名成本 |
| 路径失同步 | `CORE_BOOTSTRAP_BOOTSTRAP_H`（`core/` 是旧目录名）、`CONFIG_THREADING_THREAD_CONFIG_H`（目录从未叫 `threading`） | 读者据宏名找不到对应目录 |
| 层级缺失 | `ADAPTERS_HAL_SIM_HW_HAL_IO_SIM_H` 缺 `OUTBOUND`、多余 `HW_`；`DOMAIN_MODEL_ALARM_TYPES_H` 缺 `SAFETY` | 同名文件在不同层时可能撞名 |

`DRV_VFD_H` 这类尤其值得注意——变频器 SDK 里出现同名宏完全不意外。

改写前先确认了两件事：全部保护宏只被自身 `#ifndef` 引用，无 `#ifdef`/`defined()`
形式的条件编译依赖，故重命名安全；绝大多数头文件是 CRLF 行尾，改写须保留行尾，
否则会产生全文件 diff 掩盖真实改动。

**这项的主要产出是 R15 而非改名本身。** 67 处不一致全是"目录搬过、宏没跟"的遗留；
只改一次而不加规则，下次搬目录同样不会跟，等于把同一笔债重新记一遍。

R15 的判据设计：只取文件中第一个 `#ifndef`，且要求其后紧跟同名 `#define`。这样
`#ifndef TRUE`（`sw_types.h`）与 `#ifndef SW_LOG_COMPONENT`（`log.h`）这类条件定义
不会被误判为保护宏——已验证这两个文件不出现在违规列表里。

同时修正 `runtime/config/thread_config.h` 注释里同样过时的 `core/scheduler` 表述。

| `application/` 其余扁平与子目录混排 | `recovery_service` 已迁入 `orchestrators/`；其余（如 `adapters/runtime/snack/` 命名）仍攒批处理 |
| `adapters/runtime/snack/` 改名（与顶层 `runtime/` 撞概念） | 同上 |
| `op_mode` / `operational_mode` 命名统一、`svc_` 前缀 | 同上 |
| 框架统一 `wdf_` 符号前缀（当前 `wdf_` 只在 CMake 目标名上，C 符号是裸名） | 波及全部公开符号，收益只在接第二个项目时兑现 |
| 线程模型（每周期任务一线程，约 13 个） | 仍无实测抖动或 CPU 痛点，与前三轮判断一致 |

### 6.6 遗留观察

两处定位问题本轮只记录、未处理，它们需要的是决策而非改代码：

- **`cloud/` 顶层定位可疑。** 它不是一个层，是按"云"这个话题横切出的包。
  要么拆开，要么在文档里明确它是话题包而非层。

  > **本条的职责划分判断有误，且已在第 7 节处理。** 原文称
  > 「`cloud_point_dispatch.c` 做 JSON 编解码、`cloud_point_validate.c` 是纯逻辑、
  > `cloud_model.c` 是注册入口」——三层职责。实读代码后：编解码在
  > `common/point_table/`，`cloud_point_dispatch.c` 只是转调，自己用 cJSON 仅为
  > 遍历顶层 key；它的真实职责是**语义分派**（按 semantic 路由到设备命令 /
  > 云服务 / set，并拒绝只读点位），属领域逻辑。故实际是两层而非三层，且两层
  > 都归 domain。「顶层定位可疑」的结论成立，但依据不是原文写的那个。
- **`observability/` 框架生产路径零接入。** `runtime/`、`application/`、`demo/` 无任何
  引用，只有自身与测试在用；而项目侧有 10+ 文件在用。当前它是"框架提供、框架不用、
  项目在用"的库，其正确性只由单测保证，框架自身链路从未验证过它（`blackbox_recorder`
  尤其如此）。定位要么明确写成旁路库，要么框架自己接入一条链路。

  > **已在第 8 节处理**：选了"框架自己接入一条链路"，新增
  > `application/bridges/observation_event_bridge.c` 桥接 13 类事件。
  > `blackbox_recorder` 仍未被框架侧接入——它需要触发策略决策（何时录、录多久），
  > 那是项目语义，不宜由框架代定。

## 7. 序列化分层与云子域归位

本节记录第五轮改动。前几轮解决可靠性、安全形式化与命名一致性，本轮针对一条
贯穿三层的耦合：**最底层绑定了一种序列化格式**。

### 7.1 问题的实际形状

第 6.6 节把 `cloud/` 记为"混了三层职责"，实读后不成立（该条已就地更正）。真正
的问题在更下面一层：

`common/point_table/point_table.h` 自己 include cJSON，而 R1 特批 `common/` 依赖
`third_party/`。这意味着最底层绑定了 JSON，上面每一层都能传递性地碰到它——于是
「domain 不解析序列化格式」（R9b）变成一条**孤立的禁令**：禁 domain，却不禁
domain 所依赖的 common。

`cloud/` 之所以无法干净归位，也是这条耦合的下游表现：它要用点位表，就必然连上
cJSON；而 R9b 禁止 domain 用 cJSON，所以它只能留在顶层。

### 7.2 三步拆解

**第一步：point_table 拆模型与编解码。**

| 位置 | 内容 |
|------|------|
| `common/point_table/point_table.h` + `.c` | 点位表模型、结果汇总、查表。零外部依赖 |
| `adapters/outbound/serialization/json/point_table_json.*` | JSON 编解码 |

`point_apply_result_init` / `record_error` / `find_entry_at` / `find_entry` 四个
函数与 JSON 无关，原先却在 `point_table_from_json.c` 里——若随编解码一起搬走，
`common/` 就会声明一批只有 `adapters/` 才提供的符号。故新建 `point_table.c` 承载。

CMake 侧 `wdf_common` 不再传递 `wdf_cjson`，编解码独立为 `wdf_point_table_json`。
副作用是**不接云、不用 JSON 存储的项目现在可以完全不链接 cJSON**。

**第二步：物模型的 JSON 门面移出 domain。**

`cloud_point_dispatch.c` 原先一身两职：JSON 出入口 + 语义分派。现拆为

| 文件 | 层 | 职责 |
|------|----|------|
| `domain/cloud/cloud_point_dispatch.c` | domain | `cloud_point_apply_value()`：按 semantic 分派已解析的值，拒绝只读点位 |
| `adapters/outbound/cloud/cloud_point_json.c` | adapters | 属性 JSON 构建 / 解析，解析后逐个交给上面那个函数 |
| `adapters/outbound/cloud/cloud_model_json.c` | adapters | `property_port` 安装 + 全量/增量属性构建 |

**`property_port` 的安装从 `cloud_model_register()` 移到 `cloud_model_json_install()`** ——
该端口的契约参数是 JSON 载荷字符串，实现它必须解析 JSON，因此安装动作属适配层。
这是一处行为变更：注册物模型后须另调 install 才有属性下行，单元测试与项目 wiring
均已同步。`cloud_model_bundle_t` 也因此去掉 `property_reply` 字段。

`cloud_model_json.c` 不持有点位表，运行期从 `cloud_model_entries()` 取——避免与
`cloud_model.c` 出现两份可能不一致的引用。

**未改端口签名。** 原计划把 `on_property_set` 从收 JSON 字符串改为收已解析值。
放弃的理由：改完后每个 cloud provider 都要各自解析属性载荷，JSON 结构会在多个
provider 间分叉，而现在两端（snack inbound 调用、`cloud_model_json` 实现）都在
adapters，domain 已完全不参与序列化，目标已经达成。

**第三步：`cloud/` 迁入 `domain/cloud/`。**

前两步做完后 `cloud/` 零 cJSON、出向只剩 `common` / `domain` / `runtime`，完全在
domain 的许可集内，搬迁没有阻碍。顶层目录从 9 个减为 8 个。

### 7.3 收益：约束从目录名巧合变为层归属决定

搬迁的实质价值不是目录整齐，而是 **R9b 现在自动覆盖云子域**。已注入验证：往
`domain/cloud/cloud_point_dispatch.c` 加一行 `#include cJSON`，R9b 立即失败并指到
该文件。此前同样的代码放在顶层 `cloud/`，任何规则都不会拦。

R12（"cloud/ 不依赖 adapters/application/services"）随之退役——它约束的目录已并入
`domain/`，由 R2 覆盖。R13 去掉 `cloud/` 前缀。**编号不重排**：R12 作为已废止编号
留空，避免历史记录里的规则编号与当前脚本对不上。本项使规则数减一（当前总数以
脚本结尾输出为准，其间另有他轮新增规则）。

### 7.4 一处判断修正

第 6.5 节曾把"拆散 `cloud/`"列为不做，理由是「打散成三层只为架构纯度，且要动
项目侧 include 与 CMake」。这个判断在当时的信息下是合理的，但它假设了拆分只有
纯度收益。实际做完后发现有两个实质收益：R9b 覆盖范围扩大（见 23.3），以及
`common/` 摆脱 cJSON 使最小接入不必链接 JSON 库。

代价也确实如当时估计：项目侧改了 4 个文件的 include 与 CMake 目标清单。判断失误
不在代价估算，而在收益识别——**当时没有意识到 `common/` 的 cJSON 依赖是同一个
问题的根因**，只看到了 `cloud/` 这个下游表现。

## 8. 可观测设施的框架侧接入

本节记录第六轮改动，处理 22.6 节的第二条遗留：`observability/` 框架生产路径零接入。

### 8.1 问题：框架提供、框架不用、项目在用

核查确认 `runtime/`、`application/`、`domain/`、`adapters/`、`ports/`、`common/`、
`services/`、`demo/` 对 `observability/` **零引用**，而接入项目侧有 5 个文件在用。

这种形状的问题不是"少了个调用"。它意味着框架无法证明自己提供的设施可用：
`observability` 的正确性只由它自己的单测保证，框架链路从未验证过它。真正的缺陷
要到项目集成时才暴露，而那时责任归属已经模糊。

### 8.2 为何用桥接而非在各层直接调 `observation_publish()`

散布调用有两个硬问题：

- `event_bus` 按 R4 必须对业务层无知，`domain` 也不应依赖旁路设施。散布调用会让
  核心基础设施反向依赖 `observability`。
- 每加一处记录点都要改一个与观测无关的模块。"哪些事件值得记录"这个决策会散落
  在十几个文件里，无法整体审查。

故新增 `application/bridges/observation_event_bridge.c`，订阅已有 event_bus 事件并
转为观测记录。各层只管发事件，决策集中在一张表里。

### 8.3 选事件的判据

判据是「事后复盘需要这条时间线」，不是「事件重要」。共 13 类：安全姿态与急停、
报警触发/清除、IO 掉线/恢复、洗车中止、命令被拒、恢复请求/完成、云连接断开。

明确不记录三类：`EVT_CLOUD_POINT_DIRTY`（每次点位变化都发，量级远高于其余事件，
会淹没队列）、`EVT_OP_MODE_CONTEXT_SYNC`（周期同步，无事件语义）、
`EVT_WASH_CHECKPOINT_REACHED`（正常流程进度，非异常线索）。

载荷只放 `evt->param` 且不解释它——解释需要各域的编码知识（报警码、拒绝原因、
点位索引各不相同），那属于消费侧（导出/分析）的事。

### 8.4 接入点：`observation_is_ready()` 而非无条件挂接

可观测是旁路设施，项目可以选择不启用。已接入项目在 `project_init_adapters()` 内调
`observation_init()`，而 bootstrap 的桥接初始化必须在其之后——故新增
`observation_is_ready()`，bootstrap 在 `init_adapters` 之后按就绪状态决定是否挂接。

不启用观测的项目（如框架自带 demo）会走 else 分支记一条 INFO 并跳过。这比"无条件
挂接、记录全部被 `NOT_INIT` 丢弃"要好：后者会静默积累 `dropped` 计数，看起来像
观测在工作。

链接侧仍沿用 bootstrap 的既有模式：不制造 `wdf_runtime` → `wdf_observation_bridge`
的目标依赖（那会与 architecture/01 的依赖方向冲突），由消费方一并链接。

### 8.5 验证

- 框架 57 项测试全通过；边界脚本当时的 27 条规则无违规（R6 判据重做后合并为 20 条，见 `architecture/08-框架优化方向.md` 第 9 节）。
- **注入验证（桥接侧）**：把 `observation_publish` 换成 `(void)spec`，6 个用例中 5 个
  失败，`test_unlisted_event_produces_no_record` 仍通过（它断言"不产生记录"，符合预期）。
- **注入验证（接入侧）**：把 `observation_is_ready()` 换成 `true`，demo 强行挂接后
  启动行为改变，还原后恢复。
- 项目侧 28 项测试全通过，其 sim 目标启动日志确认「已桥接 13 类事件」，且项目观测服务
  周期任务在消费队列——端到端链路完整，不只是订阅成功。

### 8.6 过程中修掉的两处测试自身缺陷

**测试挂死掩盖失败。** 首次注入验证时进程挂死而非失败。原因是 Unity 断言失败会
直接跳出用例函数，写在用例末尾的 `pthread_join` 不再执行，分发线程留着不退出。
后果比"测试没写好"严重：**失败信息永远看不到**。改为把线程句柄放静态变量、收尾
放 `tearDown`（无论用例成败都执行）。

这个缺陷只有注入验证能发现——正常路径下所有断言都通过，join 照常执行。

**测试前提不成立。** 原先想用"灌满观测队列"验证不阻塞分发，但 event_bus 普通队列
容量 64 远小于观测队列的 256，事件在到达桥接之前就已在 event_bus 侧被丢弃，观测
队列根本填不满。改为验证可观察的性质：积压期间旁路探针订阅者仍被调用、分发线程
能正常 join。

## 9. 端口所有权与分层图对齐

**问题。** 架构文档曾用一张「adapter → port → domain」竖线图同时表达 include
依赖与运行时调用，读者会把「领域依赖出站契约」误读成「领域依赖外层」。

**决策。** 拆依赖方向 / 调用方向双图，并写明端口物理路径的所有权表。曾评估过

## 10. 端口物理归属迁移

**问题。** 顶层 `ports/` 仍像「外层业务」，且 `alarm_registry_init` 注册入站端口
迫使 domain include inbound。

**决策。**

1. 删除顶层 `ports/`：出站迁入 `domain/ports/outbound`（含 HAL/storage 等共享
   出站——services 不能依赖 application，故共享契约挂在 domain 锥；详见
   `architecture/01` §2.3），入站与云出站迁入 `application/ports`，注册表/契约
   迁入 `runtime/ports`。
2. 新增 `application/bridges/alarm_binding_bridge`：bootstrap 在
   `alarm_registry_init` 之后调用 `alarm_binding_bridge_bind()`；domain 不再
   include 任何 application 端口（由 R2 保证）。
3. 门禁将契约目录拆为 R3a（`domain/ports`）/ R3b（`application/ports`），
   禁止依赖 adapters。

**拒绝。** 继续用文档解释顶层 `ports/`——目录与所有权长期不一致，认知成本高于
一次搬迁。亦拒绝再立顶层「共享 ports」目录——会回到旧的模糊外层。

## 11. 取消 OP_MODE_EXCEPTION（故障与模式正交）

**问题。** `EXCEPTION` 同时表达「有故障」与「曾出过事须 RECOVER 才摘标」，使
`STOP_ALL_OUTPUTS` 无法干净落点；空 EXCEPTION 与急停粘性互相打架。

**决策。** 删除 `OP_MODE_EXCEPTION`（9 态）。故障只读 `estop_active` / blocking /
LOCKOUT。急停与手动全停均收敛到 `STOPPED`；`STOP_ALL` 切断 + `abort_wash(STOP_ALL)`
且不清障。自检仅拒急停（LOCKOUT/blocking 可开）。`RECOVERY_RESULT_EXCEPTION` 改名为
`RECOVERY_RESULT_FAILED`。

**拒绝。** 保留独立故障模式再用派生落点函数同步——仍是派生状态同步税。

同轮清理：删除从未进入的 `OP_MODE_HOMING`（运营归位仅 `RECOVERING`，清障仅 `ABORT_HOMING`）。

后续收口：`recovery_service` 订阅 `EVT_OP_MODE_CHANGED` 离开 RECOVERING 自取消，
并守卫迟到 `HOME_COMPLETED`；`STOP_ALL` 按前态分切断 / 切断+abort 两档 effect；
删除死路径 `DEV_CMD_EFFECT_HOME_DEVICE` 与 `op_mode_on_home_done` 无用参数；MODE-01
补 8×8 穷举断言。

## 12. 代码格式移出门禁

**问题。** `check_all.sh` 曾串联 `format.sh --check`。Windows/`core.autocrlf` 与
WSL 上不同版本的 `clang-format` 会使同一棵树在不同机器上「格式不符」结果不一致，
门禁误伤真实逻辑改动；全库 format 还会制造与本次无关的 diff 噪声。

**决策。** 格式检查退出统一门禁。`scripts/format.sh` / `format.ps1` 保留，按需手动
执行（或日后挂 pre-commit），不作为提交阻断项。门禁现为四项：架构边界、行为契约、
文档引用、自动化测试。另加 `.gitattributes` 固定 `*.sh` 为 LF，避免脚本行尾空 diff。

**拒绝。** 继续把 format 留在门禁并靠统一 CI 镜像「压死」版本差异——开发机仍会与
CI 打架，本地体验成本高于收益。

## 13. 运行对象的存储所有权收口

**问题。** `engine_session` 虽声明内部字段不可访问，仍要求调用方按字节数准备缓冲区；
Snack Modbus 三个驱动则直接在公共头公开完整结构体。两种方式都把实现布局、同步原语
和后续字段演进泄漏给组合根之外的调用方，也无法从类型系统阻止直接访问内部状态。

**决策。** 对“自身拥有完整生命周期和容量上限”的 `engine_session`，采用模块静态槽池
与不透明句柄：项目只在启动装配期用稳定 `slot_id` 绑定一次，运行期保存句柄。对已经由
VFD/voice provider 组合层持有、生命周期从属于组合层的底层驱动，不再建立重复槽池；仅
将布局移入 provider 私有头，公共 API 接受不透明指针。两者都消除外部静态分配权限，
但不强行统一不同所有权模型。

**拒绝。** 为所有驱动机械增加全局实例池——这会让 VFD manager 容量、provider 槽位和
底层驱动槽位三处同时管理同一批实例，增加 ID 同步和失败回滚路径，并不提升封装性。
也拒绝保留 `size()` + 字节缓冲兼容接口；它仍允许任意调用方拥有对象存储，且把对象
大小变成公共 ABI。R19 将 Snack Modbus 私有头范围固化为自动门禁。

## 14. 切断禁总线与事件同步排空

**问题。** 两件独立的事被捆在一起：急停预算把 `drv_modbus_link.c` 算进 RT 路径，
只因「项目 cutout 可能写寄存器」；事件测试则普遍 `publish → sleep → 断言`。

**决策。**

1. 切断禁止走 Modbus / UART。RS-485 同时只能发一帧，把 IO 移出 `bus_lock`
   并不能让急停插队。Snack VFD 的 `stop_outputs` 本来就只拉 DO。将该链路文件
   改为非 RT，失败重连改到下一次业务读写，不再持锁 `modbus_connect`。
2. 增加 `event_bus_drain()`，与 `dispatch_loop` 共用出队和 handler 快照。
   dispatch 运行中调用返回 `SW_ERR_STATE`。生产路径不调用。
3. 项目未用的启动阶段填 `project_hook_noop` / `project_hook_noop_void`，
   15 个钩子仍然全必填。

## 15. 投影写边界与错误分类的静态门禁

**问题。** PROJ-03 与 ERRM-02 都是 L0 结构条目，却长期停在待验证。缺少门禁时，

**拒绝。** 用运行期测试代替这两条——结构性质静态可穷举，运行期只能抽样。

## 20. 报警域：静默丢事件与目录零校验

**问题一：待发事件队列静默丢弃。** `alarm_types.h` 的容量依据里写着「报警丢失比
报警溢出更危险」，活跃池满确实硬失败返回 `SW_ERR_OVERFLOW`；但同一份状态的另一个
出口 `enqueue_event_locked` 队列满时只打一条 WARN 就 return，两个调用方都不看返回值。
后果不是丢一条日志：`op_mode_bridge` 的阻塞报警收敛和 `telemetry_projection` 的安全
快照都按 `EVT_ALARM_*` 边沿驱动，丢掉当批唯一的 TRIGGERED 就意味着模式不收敛、快照
停在旧值，要等下一次报警变位才恢复。门槛不高——pending 与 active 都是 32，一个 50ms
drain 周期内 32 条报警各变位一次就是 64 条事件。

**决策。** 清除路径是批量操作（`reevaluate_group` / `reset_all`），没有可以返回错误的
单一调用方，不能照抄活跃池的硬失败。改为累计丢弃条数，由 `pull_events` 的
`dropped_out` 与本批事件同锁交出后清零——分两次取会让中间新产生的丢弃被当成已上报
而清掉。`alarm_bridge` 拿到非 0 即发 `EVT_ALARM_RESYNC`，两个订阅者重读 registry 全量
状态。可以丢事件，不能让消费者不知道自己漏了。同时给 drain 的排空循环加轮次上限：
原先 `while (n == MAX)` 无上界，与 R18「所有等待有界」的取向不一致。

**问题二：`load_catalog` 只校验指针与条数。** 报警目录是项目手写资产，四类配置错误在
运行期都不报错：非法码绕开 6 位编码约定；重复码让 `find_def_index` 永远命中第一条、
后一条的等级与清除策略静默失效（配了 CRITICAL 却不停机就是这么来的）；未定义等级或
策略落进行为矩阵的最严格兜底分支，而那个兜底本意是纵深防御、不该是常态入口；
`ON_MOTION` 缺分组则永远进不了任何重评估批次。`alarm_code_is_valid()` 早就写好了，
却从未在唯一装载入口用过。

**决策。** 装载期逐条校验，任一条不合法即整表拒绝、不做部分装载。顺带修正装载时的
复位范围——原先只清活动表与 pending，会话日志里会留着新目录已不存在的码；现与 `init`
共用 `reset_runtime_state_locked()`，两条复位路径覆盖范围一致。这次修正暴露出两个既有
测试目录本身就配错了：`test_asset_contract` 的 `0x00010101`（大类解析为 0）和
`test_recovery_emergency` 的 `ON_MOTION` + `GROUP_NONE`。校验刚上线就抓到两条，说明
这类错误确实不会自己暴露。

**顺带的重复表达清理。** `alarm_instance_t` 插入时已缓存 `level` / `clear`，但
`clear` / `reset_all` / `reevaluate_group` 仍回查 catalog；后两者还都是「先扫一遍收集
`codes[]`、再第二趟按码找下标删」的两趟结构，唯一理由是删除的 memmove 会打乱索引——
倒序单趟扫描天然没这个问题。把 `reeval_group` 也缓存进实例后，三处的 catalog 查找全部
消失：`reevaluate_group` 从 O(active × catalog) = 2048 次比较降到 O(active) = 32，两个
`uint32_t codes[32]` 临时数组和两个函数各约一半的代码一起删掉。`has_blocking_active`
与 `safety_posture` 改为复用 `copy_safety_view_locked` 的同一次扫描，「MAJOR 阻塞开洗」
「CRITICAL 进 LOCKOUT」这两句判定在实现里各只剩一处。

**拒绝。** 不给丢弃的事件做重放缓冲——那是把队列容量问题换成更大的队列。RESYNC 让
下游重读当前状态，比补发历史事件简单且不会重复触发副作用。`copy_active_projection`
删掉是因为生产代码零调用、唯一的测试还在证明「它和 copy_safety_view 一致」。也不在
本轮补 registry 的并发测试：它确实缺（R16 已登记该文件由报警采集线程驱动，而测试无
一处 pthread_create），但那是独立一项工作，不混在本轮里。

## 21. 报警桥并发、端口姿势统一与并发契约补验证

承接第 20 节末尾列出的三项遗留。

**桥内 `s_posture` 无保护，且已经在并发。** 原以为这是「项目将来可能从别的线程调
`drain`」的假设风险，查调用面后发现现在就在发生：`demo/app/demo_main.c` 从主线程调
`alarm_bridge_drain()` 做同步验证，而 `alarm_bridge_init` 注册的 50ms 周期任务此刻正在
跑，两者并发进入 `publish_posture_edge` 的读-比较-改写。逐码事件不受影响
（`pull_events` 自身持锁），受损的只有姿态边沿：可能重复发 `EVT_SAFETY_LOCKOUT`，或
两个线程各自看到「没变化」而双双漏发。

**决策。** 加桥内互斥量 `s_drain_mutex`，串行化整个 `drain`。不选「只锁边沿判定、锁外
发布」：那样两个线程仍可能以相反顺序发布 LOCKOUT/NOMINAL，对安全事件而言顺序倒置比多
发一次更糟。整体串行化后边沿判定天然只有一个赢家。锁序 bridge → event_bus，没有任何
handler 回调 drain，不成环；`event_publish` 是非阻塞入队，持锁跨发布的代价有界。
`alarm_bridge_init` 里对 `s_posture` 的复位也纳入同一把锁。按 R16 登记为非 RT 可达，
依据「drain 串行化；急停切断不取此锁」。

也没有采纳「把 `drain` 约束成仅测试用」这条更省事的路：demo 用它在触发后立刻确认链路
通、不靠 sleep 猜，是合理用法。为回避加锁而砍掉一项正当能力，方向是反的。

**目录装载绕过端口。** `demo_main.c` 的 `trigger` 本来就走 `alarm_binding_get_ops()`，
只有 `demo_alarm_catalog_load()` 直接调 `alarm_registry_load_catalog`。同一个 demo 里
两种姿势并存，比单纯「绕过端口」更糟——它示范了不一致，而 demo 的作用正是当接入范本。

**决策。** 改为经端口装载，取不到 ops 返回 `SW_ERR_NOT_INIT`。启动顺序上没有障碍：
bind 阶段先 `alarm_binding_bridge_bind()` 注册 ops，再 `project_bind_alarm_catalog()`。
反方向（把 `load_catalog` 从 `alarm_binding_ops_t` 摘掉）没选：`port_registry_infra` 要求
三个成员全非空、`asset_contract` 有 `ASSET_REQ_ALARM_CATALOG` 在跟踪装载状态，摘掉要动
的面更大，且项目若要替换 registry 实现，目录装载同样需要这层间接。

**并发测试从缺到有，并用变异验证它真的有效。** `alarm_registry.c` 在 R16 里登记为「由
报警采集线程驱动」，本就是多线程共享聚合，但此前所有 registry 与桥接测试都是单线程的。
`copy_safety_view` 当初引入的全部理由是「四项数据必须来自同一次持锁」，而那条主张只有
单线程断言支撑——单线程下任何实现都成立，包括分多次取锁的退化实现。

新增 `test_alarm_registry_concurrent`，断言的不是「并发跑一遍没崩」，而是投影内部的逻辑
蕴含：blocking 为真 ⇔ 表内存在阻塞等级条目；posture 为 LOCKOUT ⇔ 表内存在 CRITICAL；
表非空则最高码必在表内；LOCKOUT 蕴含 blocking。读线程只累加不一致计数、不在非主线程调
Unity 断言（那会 longjmp 出线程，属未定义行为）。

**这里有一个值得记的过程。** 第一版测试写完后原实现 8/8 通过，但把
`copy_safety_view` 变异成分两次取锁后只有 2/10 检出——撕裂只在「两次取锁之间 CRITICAL
恰好变位」时才可观测，4000 次迭代下这个窗口太窄。若就此收下，等于加了一条 25% 命中率
的门禁，比没有更糟：它会让人以为这块已经验过了。遂把迭代提到 20 万，并让 0 号写线程
专门紧凑翻动 CRITICAL 的进出（trigger → clear → reset_all 三步循环），检出率做到
10/10，还原后 10/10 通过，耗时 1.6 秒。

**拒绝。** 不用 sleep 或 sched_yield 去「制造」竞争窗口——那测的是特定时序而非不变量。
不把并发测试并进 `test_alarm_registry`：并发用例耗时和失败特征都和单元用例不同，混在
一起会让单元测试的失败定位变模糊。

## 22. 报告门禁的假失败，与它掩盖的真段错误

**问题一：WDFSPEC 行被 stdout 缓冲截断。** `测试报告生成` 一直失败，报
`test_operational_mode/test_cmd_matrix_exhaustive_64` 未填写测试目的——但那条
`WDF_RUN_TEST` 明明填了中文摘要。实际原因是输出错乱：`WDF_RUN_TEST` 用无缓冲的
`write(STDERR_FILENO, ...)` 一次写出 WDFSPEC 行，而 Unity 的 `RUN_TEST` 走带缓冲的
stdout。两者重定向到同一管道时，stdout 要攒满 4096 字节才刷出，刷出点正好落在
WDFSPEC 行中间，把它截成 `/mnt/c/Us` + `WDFSPEC\t...`，生成器的 `^WDFSPEC` 锚点随即
匹配不上。截断位置用 `head -c 4110 | tail -c 20` 核实过，正是缓冲区边界。

**决策。** 写 stderr 前先 `fflush(stdout)`。一行改动。这也解释了为何症状是「固定某一条
用例出问题」而非随机失败——用例数刚好让缓冲区在那条用例处填满。

**问题二：门禁一放行，真缺陷就露出来了。** 报告门禁修好后，全量套件开始间歇失败，
`test_scheduler` 段错误。此前我核对过它「与本轮改动无关」（它只链接 scheduler /
thread_registry / periodic_task / log / sw_mutex，不含任何报警代码），当时单跑 6 次
全过便判为偶发。这个判断下得太轻：换成裸跑 30 次是 10 次段错误。6 次全过只是运气。

ASan 一次就定位到位置：`SEGV on unknown address 0x0 (pc 0x0)`，线程由
`scheduler_start_all` 创建——跳到空函数指针，不是我起初猜的「退出期析构竞争」。

**根因。** `test_periodic_task_register_and_scheduler_start` 启动了一个 10ms 周期任务，
而周期线程以 `pthread_detach` 创建、不可 join，用例结束后它继续在跑。下一个用例的
`setUp` 调 `periodic_task_reset_for_test()`，`memset` 把整张槽表清零，其中包括
`slot->fn`。仍在循环里的线程随即 `slot->fn(slot->ctx)` 跳到空指针。

`periodic_task.h` 的头注释早写明「清空登记表不会停止已启动的线程」，但只有注释、
没有机制。tick 循环逐字段无锁读 `fn` / `ctx` / `period_ms` / `name`，而清表持锁改写
它们——又是一处读写保护不对称，和第 1.1 节里 `find_def_index` 那条同一个形状。

**决策。** 每拍在锁内取一次槽位快照（`periodic_task_take_tick_view`），槽位已清空即
干净退出、不再触碰 slot。入口处原有的三项无锁判空一并删掉：有效性判定收口到快照里
一处，不留第二个无锁读点。不加 `scheduler_stop`——detach 不可 join 是刻意的设计
（头注释写了「进程退出即随之终止」），加停止接口是另一个决策，不在本轮范围。

修后 ASan 20/20 干净（修前 6/6 全报），裸跑 40/40 无段错误，全量套件连跑 8 轮
63/63。这是本轮第一次四项门禁全绿。

**教训记在这里。** 一条失败的门禁把另一条真缺陷挡在了视野外：报告生成失败时套件被判
「失败」，`test_scheduler` 那次段错误就淹没在同一个失败结论里。更关键的是我对偶发的
判断——「单跑 6 次全过」不足以支撑「偶发、与本轮无关」这个结论，前半句（不含相关代码）
成立，后半句（可以不管）不成立。并发缺陷的复现率要用足够样本量去测，6 次不是样本量。

## 23. ALRM-19 可失败断言，与 home_dir 不再与正向共用 0

**ALRM-19。** 锁已落地但长期待验证：黑盒边沿计数在去掉互斥量后仍 10/10 通过，因为
`pull_events` 的 registry 锁形成 happens-before，且一条域事件只能被一个线程取走。
不以边沿总数当门禁。改为在 drain 临界区内注入停留钩子，观测「已有线程在内」的
重叠计数——有锁则恒为 0，去掉锁后停留把窗口拉到可检出。这测的是互斥本身：它是
「边沿不重复、LOCKOUT/NOMINAL 顺序不倒置」的实现，互斥被破坏则主张不成立。

**home_dir。** `MOTOR_DIR_FORWARD` 曾是 0，未填配置与正向无法区分，于是 `home()`
把正向也改写成反向，正向回原无法表达。现正向=1、反向=2，未指定=0；装载期只接受
正向或反向。未填在 bind 失败，而不是静默当反向。反向回原由配置显式填写
`MOTOR_HOME_DEFAULT_DIR`（或 `REVERSE`）。

**拒绝。** 不为 drain 互斥量做测试期开关——生产路径不得被测试关掉。也不保留
「零值默认反向」：那仍是零值等于反向，只是换了说法。

## 24. 电机与流体共用输出抑制

原先流体用 `emergency_off` 脉冲、电机 tick 读绑定表里的 `estop->active()`，两套
语义还不一样：流体第一拍消费后 `set()` 可以再开，电机按钮松开后仍锁存直到
`reset_estop`。急停热路径又不能进领域锁。

现把「还能否写输出」收成 `safety_output_hold`：电平 = 急停 DI 或软件锁存，
`safety_output_hold_request` 无锁。采样到 DI 会锁存，松开后仍抑制，直到显式释放且 DI 已无效。
电机 tick / 命令与流体 poll / set 都读这一句。流体不再提供 `fluid_path_emergency_off()`：
它只是 `hold_request` 的包装，电机也没有对等入口。能量切断仍只走 `safety_cutout_execute()`；急停确认按下
后额外 `safety_output_hold_request()`，以免短脉冲在下一拍采样前丢失。

复位急停只有 `safety_output_hold_release()`。电机本地 `ESTOP` 相位在下一拍 tick
或下一条命令跟随解除；不再提供 `motor_executor_reset_estop()`。看门狗安全态仍是
`motor_executor_reset_watchdog()`，不是急停。

电机绑定表不再带独立急停口，避免与安全端口各绑一根 DI。

**拒绝。** 不在 cutout 里调 `motor_exec_stop()` / `fluid_path_all_off()`——那两
条要拿领域锁或走总线。也不把 hold 塞进 `mechanism_bridge`，没挂桥的执行器会漏。
也不把 `reset_estop` 做成 `hold_release` 的包装——调用方会以为复位的是电机。
也不保留流体侧 `emergency_off` 去调 `hold_request`——置位急停抑制不是水路的职责。
