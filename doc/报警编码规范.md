## 0. 本版假设与待确认项（重要）

本规范第 6 章的目录是**首版草案**。以下内容依据现有清单与常识推定，**必须经电气图与现场接线确认**后才能定稿，请重点红线：

- 每条报警的**等级**（Critical/Major/Minor）是按「对洗车流程/安全的影响」推定的，非最终判定。
- 每条报警的**故障性质**取了「最主要的一种」；同一部件可有多种性质（如限位既可「信号异常」也可「动作超时」），其余按需另编。
- **DI 极性**（高/低电平有效）一律待现场确认，本规范不涉及极性，只定码与策略。
- `风机报警反馈`、`接触器辅助触点`、`高度测距雷达接口` 等的**信号物理来源**尚未确证，归类标注了「待确认」。
- Major 的「本次洗车结束后仍在则停机」语义**当前实现未落地**（现 MAJOR 仅上报），属后续工作。

## 1. 编码结构

报警码为 **6 位十进制整数**，按位划分三个字段：

```
            大类(1位)  具体编号(3位)  故障性质(2位)
报警码  =  [ M ]      [ N N N ]      [ K K ]
```

| 字段 | 位宽 | 取值 | 含义 |
|------|------|------|------|
| 大类 M | 1 位 | 1–9 | 信号**物理来源**所属的硬件大类 |
| 具体编号 N | 3 位 | 000–999 | 大类内的部件/信号登记号 |
| 故障性质 K | 2 位 | 00–99 | 故障的性质（过载/通讯/超时…） |

**等级不进码值**：报警码只表达「是谁、什么性质的故障」，是稳定身份；严重程度（等级）、清除方式由第 6 章目录单独赋予，是策略。重新定级时改目录、不改码，历史数据不断裂。

### 1.1 编解码公式（落地时集中实现，禁止散落 magic 运算）

```c
/* 约束：具体编号 ∈ [0,999]，故障性质 ∈ [0,99]；uint32_t 足够（最大 999999） */
code  = major * 100000u + index * 100u + nature;

major  = code / 100000u;          /* 大类 */
index  = (code / 100u) % 1000u;   /* 具体编号 */
nature = code % 100u;             /* 故障性质 */
```

> 现有上报字段 `cloud_report_payload_t.alarm_code`（`uint32_t`）与 dev_ctx 字段结构**无需改动**，只是取值从十六进制（`0x0xxxxx`）改为本规范的十进制 6 位；云端/HMI 的解码规则需同步更新。

## 2. 编码铁律（消除二义性）

**按信号的物理来源编码，而非按「被它影响的部件」编码。**

理由与边界（来自评审结论）：很多执行元件（电机、气缸）本身无反馈信号，其异常是外接器件检出的——例如侧刷电机只是执行件，「侧刷过载」是外接过载检测器件产生的 DI。因此：

1. **同一物理故障若有多个信号来源，是不同的码**。如「电机过流」：
   - 外接过载继电器检出 → 归**感知硬件(2)**；
   - 变频器内部保护上报 → 归**控制硬件(4)**。
   两者排查入口不同，故为两条独立报警。
2. **无自身反馈的纯执行元件（大类1 电机 / 大类3 气缸接触器）默认不分配报警码**；其故障由对应的感知(2)或控制(4)信号承载。仅当该元件确有自身信号（如电机热保 DI、接触器辅助触点反馈）接入时，才在其大类下分配码。
3. **统计口径提示（仅针对保护/监视型信号）**：多数信号是「自报型」——报出信号的器件就是失效器件，此时大类统计即等于根因分布（如限位粘连 `200204`、变频器通讯丢失 `400102`、急停 `201709`）。**唯一例外**是「一个传感器监视另一个执行件」的保护型信号（典型为外接过载继电器）：侧刷电机过载报 `201101`（大类2 感知硬件），但失效器件是侧刷电机（大类1 动力硬件）——对这类码，大类指向的是「监视器件」而非「失效器件」，单看大类做统计会把电机故障误计入感知硬件。
   - 但根因信息并未丢失：故障性质 `01 过载` 出现在大类2 的码上，本身即表明「某动力件过载」而非传感器坏；`desc`（如「侧刷电机过载」）也写明根因部件。**用「大类+性质」或带 desc 的统计可拿到正确根因；只有「单看大类」会误判。**
   - 若将来需要按根因部件精确出报表，再为这类码补一个可选「根因部件」字段（如 `201101` 关联 `1-004 侧刷电机`），本版不做。

## 3. 等级模型

| 等级 | 枚举 | 含义 | 上报 | 停机策略 | 对应安全态 |
|------|------|------|------|----------|------------|
| **Critical 紧急** | `ALARM_LEVEL_CRITICAL` | 危及安全/无法继续，需立刻停机 | 立即 | **立即停机**（LOCKOUT） | LOCKOUT |
| **Major 重要** | `ALARM_LEVEL_MAJOR` | 影响设备性能/洗车质量 | 立即 | **本次洗车结束后仍在则停机**（`blocks_next_service`，待实现） | WARNING |
| **Minor 轻微** | `ALARM_LEVEL_MINOR` | 不影响运行 | 上报 | 不停机 | OK |

聚合：整机安全态取所有活跃报警的最高等级派生（CRITICAL→LOCKOUT，MAJOR→WARNING，MINOR/无→OK）。聚合语义收口在 `safety_fsm`，与本规范一致。

## 4. 故障性质字典

| 性质码 | 含义 | 典型场景 | 默认清除方式 |
|--------|------|----------|--------------|
| `00` | 其他/指令 | 用户主动停止等非故障事件 | AUTO_STATIC |
| `01` | 过载/过流 | 电机堵转、泵阻力大、电流超标 | **LATCHED** |
| `02` | 通讯丢失 | 变频器连不上、信号线断 | **LATCHED** |
| `03` | 硬件故障 | 设备内部损坏、变频器报错、电源坏 | **LATCHED** |
| `04` | 信号异常 | 传感器误报、光电遮挡、码盘无脉冲 | AUTO_STATIC |
| `05` | 动作超时 | 气缸没伸出、限位没碰到、动作太慢 | **LATCHED** |
| `06` | 压力异常 | 水压低、气压低 | AUTO_STATIC |
| `07` | 液位异常 | 缺水、缺蜡、缺泡沫 | AUTO_STATIC |
| `09` | 安全触发 | 急停按下、防撞条/杆碰到 | AUTO_STATIC |

> `08` 暂空缺（预留）。「默认清除方式」是按性质给的缺省值，个别条目可在目录中覆盖并注明理由。

## 5. 清除方式（扩展点 2）

当前实现仅有 `ALARM_CLEAR_AUTO_STATIC`。本规范要求扩展为两类（落地时改 `alarm_code.h`）：

```c
typedef enum {
    ALARM_CLEAR_AUTO_STATIC = 0,  /* 条件消失即自动清除（电平类：急停、限位、液位、防撞…） */
    ALARM_CLEAR_LATCHED,          /* 锁存，须 CMD_RESET_FAULT 人工复位（通讯、硬件故障、过载、超时…） */
} alarm_clear_t;
```

- **AUTO_STATIC**：DI 复位 / 物理量恢复即自动清除。适用于本就期望自恢复的状态（碰撞解除、补液后液位恢复）。
- **LATCHED**：触发后保持，即使触发条件消失也不自动清，必须人工复位。适用于需查因后才允许恢复运行的故障（过载、通讯丢失、硬件故障、动作超时），避免「故障闪一下自愈、根因没查就继续跑」。

**落地说明（本期未启用强制锁存，待校准）**：当前唯一的人工复位入口是 `CMD_RESET_FAULT`，而 `application/command_guard.c` 把它限定为**仅 `DEV_STATE_FAULT` 可用**，且设备只在 CRITICAL（LOCKOUT）时进入 FAULT。因此 **MAJOR/MINOR 级的锁存报警目前没有复位通路**——若现在就对侧刷过载（MAJOR）启用 LATCHED，其 DI 复位后报警将永远清不掉。

据此，最小实现暂作如下处理：

1. `alarm_clear_t` 已加入 `ALARM_CLEAR_LATCHED`（类型就位，供目录与后续使用）；
2. `alarm_core` **暂不**按清除方式分流，已接入的三条报警仍走 AUTO_STATIC；
3. 启用 LATCHED 的前置条件（后续校准项）：补一个**不依赖 FAULT 态**的「报警确认/复位」入口（或放宽 `command_guard` 对 WARNING 态的 `RESET_FAULT` 许可），再让 `alarm_core` 对 LATCHED 报警拦截自动清除、改由该入口复位。

## 7. 与现有实现的对照（迁移影响）

现有 `alarm_code.h` 用十六进制模块前缀编码，迁移到本规范后取值变化如下：

| 现有码（hex） | 现有等级/清除 | 部件 | 新码（十进制） | 新等级/清除 | 变化点 |
|---------------|---------------|------|----------------|-------------|--------|
| `0x040001` ESTOP | CRITICAL / AUTO | 急停 | `201709` | Critical / AUTO | 归入感知硬件(2)，不再单列「安全模块」前缀 |
| `0x020001` SIDE_BRUSH_OVERLOAD | MAJOR / AUTO | 侧刷过载 | `201101` | Major / AUTO（目标 LATCHED） | 码值变更；清除方式目标为 LATCHED，本期未启用（见 §5） |
| `0x020002` FAN_FAULT | MINOR / AUTO | 风机报警反馈 | `400303` | Minor / AUTO | 归入风机变频器(4-003)；来源**待确认** |

> 已实现并 sim 验证的最小集就是这三条：`201709` / `201101` / `400303`，运行时清除方式当前均为 AUTO_STATIC。`safety_fsm` 聚合逻辑与执行机构反应未改动。

要点：
- 旧设计里「安全 = 0x04 模块前缀」的语义**取消**；安全态完全由**等级**派生，与码值无关（符合「等级不进码」原则）。
- 三条示例码的码值都会变；上报字段类型不变，仅取值变，云端/HMI 解码规则需同步。

## 8. 配置来源与加载（数据驱动）

报警**定义**是数据，不是代码，已收敛到单一来源；检测逻辑仍在机型层（方案乙）。三层职责：

| 关注点 | 位置 | 内容 |
|--------|------|------|
| **报警定义**（唯一来源） | `doc/m8_alarm_catalog.json` | 每条 `code/level/clear/desc`，机型无关；增删改报警在此一处 |
| **检测/绑定**（何时触发） | `adapters/machine/m8/m8_alarm_adapt.c` | 「信号/逻辑 → 报警码」，简单的为电平/边沿，组合的为判定函数；引用码用本地常量 `M8_ALM_*`（标识值，与 JSON 靠 code 数值对齐） |
| **滤波** | `config/machine/m8_signal_table` | 仅 DI 防抖，**不含报警语义** |

**加载链**（`core/bootstrap/bootstrap.c`）：
```
alarm_core_init()                         → 先装内置兜底目录（仅 CRITICAL，见下）
alarm_catalog_load_json_file(PATH,...)    → adapters/storage/json：cJSON 解析 JSON → alarm_def_t[]
alarm_core_load(defs, count)              → 整表替换兜底目录
  加载失败 → LOG_ERROR + 保留兜底目录（不中止启动）
```

**内置兜底（D1，故障安全）**：`alarm_core.c` 的 `s_fallback_defs[]` 编译进固件，仅含安全必需项（当前为急停 `201709`/CRITICAL）。JSON 缺失/损坏时退回兜底，保证急停等安全报警链不失效；普通报警（MAJOR/MINOR）此时降级为「不报」，强于「整表为空连急停也不报」。**长期兜底表只增 CRITICAL 安全项，不堆全量报警。**

**类型层瘦身**：`domain/model/alarm_code.h` 只保留 `ALARM_CODE_NONE` 哨兵 + `ALARM_CODE_MAKE` 宏 + 类型（等级/清除/`alarm_def_t`），不再罗列具体码；`alarm_def_t.desc` 为定长 `char[ALARM_DESC_MAX]`，免堆便于加载。

**路径**：sim 由 CMake 注入 `M8_ALARM_CONFIG_PATH=<src>/doc/m8_alarm_catalog.json`；真机默认 `/etc/m8/m8_alarm_catalog.json`（部署路径与引擎 JSON 同属待统一问题，已占位）。

## 9. 扩展指引

- **新增/修改报警定义**：编辑 `doc/m8_alarm_catalog.json` 加一条 `{code, level, clear, desc}` 即可（增删改的唯一处）。`code` 按 §1.1：确定信号来源 → 定大类 → 登记编号 → 选性质 → 公式得码。
- **新增报警的检测**：若该报警由机型信号/逻辑触发，在 `m8_alarm_adapt.c` 加「检测 → 码」绑定（电平直检型加进 `s_alarm_map[]` + 一条 `M8_ALM_*`；组合/流程/心跳型写对应判定）。纯靠其它模块 `event` 触发的可不动适配器。
- **同部件多性质**：直接换性质码即可（如限位 `2002**04**` 信号异常 vs `2002**05**` 动作超时），二者是独立报警。
- **容量**：目录上限 `ALARM_CATALOG_MAX`（当前 64），超出 `alarm_core_load` 返回 `SW_ERR_OVERFLOW`。
- **不需要动**：`safety_fsm` 聚合逻辑、执行机构反应、`safety_supervisor` 投影——它们只认等级/安全态，与具体码无关。
