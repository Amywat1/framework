## 0. 本版假设与待确认项（重要）

本规范第 6 章的目录是**首版草案**。以下内容依据现有清单与常识推定，**必须经电气图与现场接线确认**后才能定稿，请重点红线：

- 每条报警的**等级**（Critical/Major/Minor）是按「对洗车流程/安全的影响」推定的，非最终判定。
- 每条报警的**故障性质**取了「最主要的一种」；同一部件可有多种性质（如限位既可「信号异常」也可「动作超时」），其余按需另编。
- **DI 极性**（高/低电平有效）一律待现场确认，本规范不涉及极性，只定码与策略。
- `风机报警反馈`、`接触器辅助触点`、`高度测距雷达接口` 等的**信号物理来源**尚未确证，归类标注了「待确认」。
- MAJOR「会话结束后仍 active 则拒单」语义见 `报警系统设计说明.md` v4.0 §6（PostWash）；不再使用 per-alarm `blocks_next_service` 字段。

## 1. 编码结构

报警码为 **6 位十进制整数**，按位划分三个字段：

```
            大类(1位)  具体编号(3位)  故障性质(2位)
报警码  =  [ M ]      [ N N N ]      [ K K ]
```

| 字段 | 位宽 | 取值 | 含义 |
|------|------|------|------|
| 大类 M | 1 位 | 1–9 | 信号**物理来源**所属的硬件大类 |
| 具体编号 N | 3 位 | 000–999 | 大类内的部件/信号登记号 |
| 故障性质 K | 2 位 | 00–99 | 故障的性质（过载/通讯/超时…） |

**等级不进码值**：报警码只表达「是谁、什么性质的故障」，是稳定身份；严重程度（等级）、清除方式由第 6 章目录单独赋予，是策略。重新定级时改目录、不改码，历史数据不断裂。

### 1.1 编解码公式（落地时集中实现，禁止散落 magic 运算）

```c
/* 约束：具体编号 ∈ [0,999]，故障性质 ∈ [0,99]；uint32_t 足够（最大 999999） */
code  = major * 100000u + index * 100u + nature;

major  = code / 100000u;          /* 大类 */
index  = (code / 100u) % 1000u;   /* 具体编号 */
nature = code % 100u;             /* 故障性质 */
```

> 报警码经 `safety_snapshot` / `dev_ctx.top_alarm_code` 投影，再由项目点位表 getter（如 `sts_dev_warning`）序列化上报；字段类型仍为 `uint32_t`，只是取值从十六进制（`0x0xxxxx`）改为本规范的十进制 6 位；云端/HMI 的解码规则需同步更新。

## 2. 编码铁律（消除二义性）

**按信号的物理来源编码，而非按「被它影响的部件」编码。**

理由与边界（来自评审结论）：很多执行元件（电机、气缸）本身无反馈信号，其异常是外接器件检出的——例如侧刷电机只是执行件，「侧刷过载」是外接过载检测器件产生的 DI。因此：

1. **同一物理故障若有多个信号来源，是不同的码**。如「电机过流」：
   - 外接过载继电器检出 → 归**感知硬件(2)**；
   - 变频器内部保护上报 → 归**控制硬件(4)**。
   两者排查入口不同，故为两条独立报警。
2. **无自身反馈的纯执行元件（大类1 电机 / 大类3 气缸接触器）默认不分配报警码**；其故障由对应的感知(2)或控制(4)信号承载。仅当该元件确有自身信号（如电机热保 DI、接触器辅助触点反馈）接入时，才在其大类下分配码。
3. **统计口径提示（仅针对保护/监视型信号）**：多数信号是「自报型」——报出信号的器件就是失效器件，此时大类统计即等于根因分布（如限位粘连 `200204`、变频器通讯丢失 `400102`、急停 `201709`）。**唯一例外**是「一个传感器监视另一个执行件」的保护型信号（典型为外接过载继电器）：侧刷电机过载报 `201101`（大类2 感知硬件），但失效器件是侧刷电机（大类1 动力硬件）——对这类码，大类指向的是「监视器件」而非「失效器件」，单看大类做统计会把电机故障误计入感知硬件。
   - 但根因信息并未丢失：故障性质 `01 过载` 出现在大类2 的码上，本身即表明「某动力件过载」而非传感器坏；`desc`（如「侧刷电机过载」）也写明根因部件。**用「大类+性质」或带 desc 的统计可拿到正确根因；只有「单看大类」会误判。**
   - 若将来需要按根因部件精确出报表，再为这类码补一个可选「根因部件」字段（如 `201101` 关联 `1-004 侧刷电机`），本版不做。

## 3. 等级与响应策略

等级用于**上报/统计**；本单即时行为由 **响应策略** `response_strategy_t` 决定（见 `报警系统设计说明.md` v4.0 §3.2）。

| 等级 | 枚举 | 缺省 response_strategy | 本单行为 | 会话边界（仍 active） |
|------|------|------------------------|----------|------------------------|
| **Critical** | `ALARM_LEVEL_CRITICAL` | `RESP_STOP_IMMEDIATELY` | 立即 abort | → EXCEPTION |
| **Major** | `ALARM_LEVEL_MAJOR` | `RESP_COMPLETE_THEN_ASSESS` | 继续完成本单 | → EXCEPTION |
| **Minor** | `ALARM_LEVEL_MINOR` | `RESP_LOG_ONLY` | 不干预 | 不拒单 |

**安全姿态**（`safety_posture_t`）仅两态：`NOMINAL` / `LOCKOUT`。  
`LOCKOUT ⇔ 存在 response==RESP_STOP_IMMEDIATELY 的活跃报警`。MAJOR **不**映射全局 WARNING。

## 4. 故障性质字典

| 性质码 | 含义 | 典型场景 | 默认清除方式 |
|--------|------|----------|--------------|
| `00` | 其他/指令 | 用户主动停止等非故障事件 | AUTO_STATIC |
| `01` | 过载/过流 | 电机堵转、泵阻力大、电流超标 | **MANUAL_RESET** |
| `02` | 通讯丢失 | 变频器连不上、信号线断 | **MANUAL_RESET** |
| `03` | 硬件故障 | 设备内部损坏、变频器报错、电源坏 | **MANUAL_RESET** |
| `04` | 信号异常 | 传感器误报、光电遮挡、码盘无脉冲 | AUTO_STATIC 或 **ON_MOTION**（流程类） |
| `05` | 动作超时 | 气缸没伸出、限位没碰到、动作太慢 | **ON_MOTION** 或 **MANUAL_RESET** |
| `06` | 压力异常 | 水压低、气压低 | AUTO_STATIC |
| `07` | 液位异常 | 缺水、缺蜡、缺泡沫 | AUTO_STATIC |
| `09` | 安全触发 | 急停按下、防撞条/杆碰到 | AUTO_STATIC |

> `08` 暂空缺（预留）。「默认清除方式」是按性质给的缺省值，个别条目可在目录中覆盖并注明理由。

## 5. 清除方式

v4.0 清除方式为三类（见 `alarm_types.h` / `报警系统设计说明.md` v4.0 §3.3）：

```c
typedef enum {
    ALARM_CLEAR_AUTO_STATIC = 0,  /* 条件消失即自动清除 */
    ALARM_CLEAR_ON_MOTION,        /* 检查点到达后 reevaluate；Recover 强制清 */
    ALARM_CLEAR_MANUAL_RESET,     /* 须 Recover / ResetFault 强制清 */
} alarm_clear_t;
```

| 清除方式 | 自动 clear | Recover |
|----------|------------|---------|
| AUTO_STATIC | 条件恢复即清 | 可强制清 |
| ON_MOTION | 仅 `reevaluate_group` / Recover 可清 | Recover **强制清** |
| MANUAL_RESET | 忽略 | **强制清** |

急停报警由硬件信号决定，Recover **不得**强制清除。

**MANUAL_RESET 典型流程**：侧刷过载 DI 释放 → `alarm_registry_clear()` 忽略 → 操作员 Recover → `alarm_registry_recover_all()` 强制清除 → 安全姿态重聚合。

> v2.0 的 `ALARM_CLEAR_LATCHED` 在 v3.0 中拆分为 `ON_MOTION` 与 `MANUAL_RESET`，按触发源在目录中分别配置。

## 7. 与现有实现的对照（迁移影响）

现有 `alarm_code.h` 用十六进制模块前缀编码，迁移到本规范后取值变化如下：

| 现有码（hex） | 现有等级/清除 | 部件 | 新码（十进制） | 新等级/清除 | 变化点 |
|---------------|---------------|------|----------------|-------------|--------|
| `0x040001` ESTOP | CRITICAL / AUTO | 急停 | `201709` | Critical / AUTO_STATIC | 归入感知硬件(2) |
| `0x020001` SIDE_BRUSH_OVERLOAD | MAJOR / AUTO | 侧刷过载 | `201101` | Major / MANUAL_RESET | 码值变更；清除方式为 MANUAL_RESET |
| `0x020002` FAN_FAULT | MINOR / AUTO | 风机报警反馈 | `400303` | Minor / AUTO_STATIC | 归入控制硬件(4-003) |

> 已实现并 sim 验证的最小 DI 集：`201709` / `201101` / `400303` / `202301`（水泵过载）。运行时已迁移至 `alarm_registry` + 两态 `safety_posture`；历史对照见设计说明 §16。

要点：
- 旧设计里「安全 = 0x04 模块前缀」的语义**取消**；即时安全姿态由 `response_strategy` 派生（两态 NOMINAL/LOCKOUT），与码值无关。
- 三条示例码的码值都会变；上报字段类型不变，仅取值变，云端/HMI 解码规则需同步。
