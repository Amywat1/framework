# 云端通信规格说明

版本：v3.4  
适用范围：跨机型洗车机控制软件的云端物模型通信  
架构基线：`doc/软件设计框架说明.md` §8.3、§14

---

## 1. 概述

### 1.1 设计目标

本文档定义云端物模型通信的领域契约，实现：

- **链路、调度、内容三者分离**：MQTT 传输、上报时机、物模型字段互不耦合
- **路由横切编解码与业务**：下行 JSON 按 `semantic` 分流，上行 JSON 由点位表统一构建
- **一次注册**：项目物模型表、上报策略、下行应答在同一 `bundle` 中注入，无转发层
- **传输无关编解码**：`point_table` 可被云端、CLI 等场景复用，不感知 MQTT 与语义

### 1.2 适用场景

本规格适用于满足以下特征的控制需求：

**属性型物模型**  
云端以 `id → 值` 的 JSON 属性集与设备交互；每个属性有类型（bool / int / string）、访问权限与业务语义。

**周期 + 事件混合上报**  
设备需周期全量同步、重连补发、报警/变更增量上报。**何时上报**由调度策略表决定；**上报哪些 key** 由全量/增量构建规则决定。

**下行命令与服务**  
云端可写属性触发设备命令、云端服务回调或手动机构动作；设备可选回显当前值。

**不适用**：离线消息队列、框架级 publish 重试、desired/reported 双通道、云端直接在 port 层定义业务载荷。

### 1.3 核心概念一览

```text
物模型点位（cloud_point_entry_t）
  ├── 基础编解码（id / type / get / set）
  ├── 访问权限（access）
  ├── 路由语义（semantic）
  └── 点位上报标记（report_policy）

物模型注册包（cloud_model_bundle_t）
  ├── 点位表（entries）
  ├── 调度策略表（report_policies）
  └── 下行应答（property_reply，可选）

上报调度（report_scheduler + report_policy_entry_t）
  ├── 触发源（周期 / 事件）
  └── 上报形态（full / delta）

链路（cloud_link_port）
  └── 传输 + 连接边沿
```

## 2. 映射层

云端通信分四层职责，各层只回答一类问题：

| 层次 | 载体 | 内容 |
|------|------|------|
| **概念层** | `framework/cloud/` | 点位元模型、语义路由、注册入口、变更检测 |
| **编解码层** | `framework/common/point_table/` | id ↔ 值 ↔ JSON（传输无关）；查找、解析、结果记录公共 API |
| **端口层** | `framework/ports/.../cloud/` | 链路、上行 publish、下行 property 契约 |
| **配置层** | `projects/<project>/adapters/cloud/` | X-macro 物模型单表、调度策略、handler |
| **适配层** | `framework/adapters/.../cloud/` | 云平台 provider（如 Snack MQTT） |

**依赖禁令**（不得违反）：

- `point_table` 不感知 `semantic`、MQTT、`command_port`
- `cloud_point` 不含具体 `sts_*` / `cmd_*` 业务含义
- `report_scheduler` 不含物模型 id 列表（由 `delta_ids` 或事件 param 解析）
- inbound/outbound adapter 不得各自 init MQTT（唯一 owner：link adapter）
- port 层不得定义业务上报载荷

## 3. 物模型点位

### 3.1 语义

物模型点位是云端与设备之间的**最小属性契约单元**。项目以 X-macro 单表登记，每行展开为一个 `cloud_point_entry_t`。

### 3.2 登记语法

```text
SEM  ACCESS  POLICY  ID  TYPE  GET  SET  CMD  SERVICE
```

| 列 | 填入字段 | 说明 |
|----|----------|------|
| `GET` / `SET` | `base.get` / `base.set` | 编解码回调 |
| `CMD` | `cmd_type` | 仅 `DEVICE_CMD` 使用 |
| `SERVICE` | `service` | 仅 `CLOUD_SERVICE` 使用 |

### 3.3 类型定义

```c
typedef struct {
    point_table_entry_t      base;        /* id / type / get / set */
    cloud_point_access_t     access;
    cloud_point_semantic_t   semantic;
    cloud_report_policy_t    report_policy;
    cmd_type_t               cmd_type;    /* DEVICE_CMD 专用 */
    cloud_service_fn_t       service;     /* CLOUD_SERVICE 专用 */
} cloud_point_entry_t;
```

`base` 作为首成员嵌入 `point_table_entry_t`：

- **下行查找**：通过 `point_table_find_entry_at(entries, count, sizeof(cloud_point_entry_t), id)` 按 id 定位 `base`，再按 `semantic` 路由
- **上行序列化**：因 `cloud_point_entry_t[]` 与 `point_table_entry_t[]` 步长不同，须先将 `get != NULL` 的 `base` 展开到长度不超过 `CLOUD_POINT_TABLE_MAX` 的临时表，再委托 `point_table_to_json_*`
- **JSON 值解析**：下行与通用点表共用 `point_table_parse_cjson_value()`；结果记录共用 `point_apply_result_record_error()`

### 3.4 访问权限（access）

| 值 | 含义 | 约束 |
|----|------|------|
| `CLOUD_POINT_ACCESS_RO` | 只读遥测 | 必须有 `get`，`set` 必须为 `NULL` |
| `CLOUD_POINT_ACCESS_WO` | 只写命令 | `semantic` 不得为 `TELEMETRY`；`get` 可选（回显） |
| `CLOUD_POINT_ACCESS_RW` | 读写 | 类型存在；当前项目层未使用 |

### 3.5 数据类型（type）

| 值 | JSON 形态 | 说明 |
|----|-----------|------|
| `POINT_TYPE_BOOL` | `true` / `false` | 布尔属性 |
| `POINT_TYPE_INT` | number | 整型；三态枚举命令用 -1 / 0 / 1 |
| `POINT_TYPE_STRING` | string | 最大 `POINT_STR_MAX`（32 字节含 `\0`） |
| `POINT_TYPE_FLOAT` | number | 浮点遥测 |

### 3.6 登记校验

上电 `cloud_point_validate()` 校验：

- `id` 非空、不重复
- `TELEMETRY` 必有 `get`
- `DEVICE_CMD` 必有 `cmd_type`
- `CLOUD_SERVICE` 必有 `service`
- `MANUAL_ACT` 必有 `set`
- `RO` 不得有 `set`

## 4. 点位语义（semantic）

### 4.1 语义

`semantic` 决定下行 JSON 的**路由行为**：框架按语义选择处理入口，项目 handler 不得绕过此路由。

| semantic | 下行入口 | 行为 |
|----------|----------|------|
| `TELEMETRY` | 拒绝 | `access==RO` 或 `semantic==TELEMETRY` 均拒绝写 |
| `DEVICE_CMD` | `cmd_type` | 写 `true` → `command_port.inject()`；写 `false` 忽略（仅 bool 型有效） |
| `CLOUD_SERVICE` | `service` | 调用 `entry->service(val)`，不使用 `base.set` |
| `MANUAL_ACT` | `base.set` | 调用 `entry->base.set(val)` |

### 4.2 选型约束

| 场景 | 应选 semantic | 原因 |
|------|---------------|------|
| 映射 `command_port` 标准命令 | `DEVICE_CMD` | 框架代为 `inject`，只需填 `cmd_type` |
| 需自定义载荷或副作用 | `CLOUD_SERVICE` | 走 `service` 回调 |
| 机构/水路/配置开关等直接 set | `MANUAL_ACT` | 走 `base.set` |

> **示例（M8，仅供参考）**
>
> | semantic | 典型点位 |
> |----------|----------|
> | `DEVICE_CMD` | `cmd_home` |
> | `CLOUD_SERVICE` | `cmd_safe_home`、`cmd_start_wash`、`cmd_custom_stop`、`cmd_sync`、`cmd_open_data_minitor`、`cmd_communication_test` |
> | `MANUAL_ACT` | `cmd_stop`、水路/机构/配置/强制动作类 `cmd_*` |
> | `TELEMETRY` | 全部 `sts_*` |

## 5. 下行处理

### 5.1 语义

云端下发属性 JSON 后，框架逐 key 解析、路由并统计处理结果。下行应答与属性回显是两个独立通道。

### 5.2 处理结果

```c
typedef struct {
    size_t    total_keys;
    size_t    applied;
    size_t    rejected;
    size_t    skipped_get;
    sw_err_t  first_error;
    char      first_error_id[POINT_ID_MAX];
} point_apply_result_t;
```

| 情形 | 结果 |
|------|------|
| 未知 id | `rejected++`，记录 `first_error` |
| 只读点位 | `rejected++` |
| 类型不匹配 | `rejected++` |
| 路由成功 | `applied++` |

### 5.3 下行应答（可选）

- `property_reply` 由 `cloud_model_bundle_t` 注入
- deploy 配置 `topicPropertyReply`；未配置则静默跳过
- 应答 JSON：`{"applied":N,"rejected":M}`，不含属性值

### 5.4 连接状态

- `dev_ctx_snapshot().cloud_connected` 读穿 `cloud_link_port.is_online()`，无本地副本
- link adapter `poll()` 检测边沿，发布 `EVT_CLOUD_CONNECTED` / `EVT_CLOUD_DISCONNECTED`

## 6. 回显

### 6.1 语义

可写点位的 `get` 用于向云端回显**当前值**，与下行应答（`applied`/`rejected`）无关。回显值参与上行 JSON 构建，是否触发增量上报由 `report_policy` 与调度策略共同决定。

### 6.2 回显类型

| 类型 | get 实现 | 典型 `report_policy` | 说明 |
|------|----------|---------------------|------|
| 脉冲命令 | `cloud_point_get_echo_idle`（恒定 false） | `NEVER` | `DEVICE_CMD`、强制动作 |
| 持续命令 | 读运行态（bool） | `ON_CHANGE` | 水路、风机、照明 |
| 三态枚举 | 读机构状态（-1/0/1） | `ON_CHANGE` | 龙门、升降、刷具、轮锁 |
| 配置开关 | 读项目运行时保存值 | `ON_CHANGE` | 功能按钮、传感器检测开关 |
| 无回显 | `get = NULL` | `NEVER` | 不参与上行序列化 |

持续型/三态命令须在机构停止后 `get` 才复位；`ON_CHANGE` watcher 检测变化后触发单点增量上报。

> **示例（M8，仅供参考）**
>
> - `cmd_communication_test`：`get = NULL`，由 `sts_communication_test` 单独遥测回显
> - `cmd_open_data_minitor`：`CLOUD_SERVICE` 写配置 + 状态型 `get` 回显

## 7. 上报机制

上报分**两个正交维度**，登记与实现时不得混用：

| 维度 | 载体 | 决定什么 |
|------|------|----------|
| **调度策略** | `report_policy_entry_t` | **何时**触发 full / delta |
| **点位上报标记** | `cloud_report_policy_t` | 是否纳入 **ON_CHANGE** 变更检测 |

### 7.1 调度策略（report_policy_entry_t）

由项目在 `cloud_model_bundle_t.report_policies` 注入，`report_scheduler` 消费。

```c
typedef struct {
    report_trigger_kind_t kind;           /* PERIODIC / EVENT */
    uint32_t              period_ms;
    uint32_t              event_id;
    bool                  full;           /* true=全量，false=增量 */
    bool                  use_event_param_as_point_index;
    const char *const    *delta_ids;
    size_t                delta_id_count;
} report_policy_entry_t;
```

| 触发方式 | 典型配置 | 上报动作 |
|----------|----------|----------|
| `REPORT_TRIGGER_PERIODIC` | `period_ms = THD_CLOUD_REPORT_PERIOD_MS`, `full=true` | 全量 `publish_properties()` |
| `REPORT_TRIGGER_EVENT` + `EVT_CLOUD_CONNECTED` | `full=true` | 重连全量 |
| `REPORT_TRIGGER_EVENT` + `EVT_ALARM_*` | `full=false`, `delta_ids={...}` | 报警增量 |
| `REPORT_TRIGGER_EVENT` + `EVT_CLOUD_POINT_DIRTY` | `use_event_param_as_point_index=true` | 单点增量 |

周期任务 `cloud_report` 同时执行：`cloud_link_port.poll()`、`cloud_point_watcher_poll()`、周期策略触发。

显式同步（如 `cmd_sync` 服务回调调用 `report_scheduler_request_resync()`）直接触发一次全量上报。

### 7.2 点位上报标记（cloud_report_policy_t）

```c
typedef enum {
    CLOUD_REPORT_PERIODIC = 0,
    CLOUD_REPORT_ON_CHANGE,
    CLOUD_REPORT_RESYNC_ONLY,
    CLOUD_REPORT_NEVER,
} cloud_report_policy_t;
```

**框架实际行为**：

| 值 | 行为 |
|----|------|
| `CLOUD_REPORT_ON_CHANGE` | 纳入 `cloud_point_watcher`；变更时发 `EVT_CLOUD_POINT_DIRTY` |
| 其他值 | 不参与 watcher 变更检测 |

**上行 JSON 构建规则**（`cloud_point_to_json`）：

- 凡 `get != NULL` 的点位均可被序列化
- **不按** `cloud_report_policy_t` 过滤全量内容
- 全量上报包含所有可读点位；增量按传入 id 列表过滤
- `RESYNC_ONLY` / `NEVER` 目前仅为**项目登记意图**，框架未据此裁剪全量 JSON

### 7.3 变更检测（ON_CHANGE）

- 仅 `report_policy == CLOUD_REPORT_ON_CHANGE` 且 `get != NULL` 的点位纳入 watcher
- shadow 按**点位表索引**存储
- 点位表总数不得超过 `CLOUD_POINT_TABLE_MAX`（96）
- 首次 poll 建立 shadow 时也会发一次 `EVT_CLOUD_POINT_DIRTY`

### 7.4 get 失败策略

上行 `get()` 失败时（`cloud_point_set_get_fail_policy`）：

| 策略 | 行为 |
|------|------|
| `CLOUD_POINT_GET_FAIL_OMIT`（默认） | 跳过该 key |
| `CLOUD_POINT_GET_FAIL_ABORT` | 整包构建失败 |
| `CLOUD_POINT_GET_FAIL_NULL` | 写入 `"key": null` |

### 7.5 规模约束

| 常量 | 值 | 含义 |
|------|-----|------|
| `CLOUD_REPORT_JSON_MAX` | 4096 | 单次上报 JSON 缓冲上限 |
| `CLOUD_POINT_TABLE_MAX` | 96 | 点位表最大条目数；watcher shadow 与 `cloud_point_to_json` 临时表共用此上限 |

## 8. 物模型注册包

### 8.1 语义

项目以 `cloud_model_bundle_t` 一次性注入物模型表、调度策略与下行应答，框架保存指针并安装 `property_port`，不在此阶段启动调度器或建立 MQTT 连接。

### 8.2 类型定义

```c
typedef struct {
    const cloud_point_entry_t    *entries;
    size_t                        count;
    const report_policy_entry_t  *report_policies;
    size_t                        policy_count;
    cloud_property_reply_fn_t     property_reply;  /* 可选 */
} cloud_model_bundle_t;
```

### 8.3 启动阶段约束

| 阶段 | 动作 | 约束 |
|------|------|------|
| `wiring()` | adapter 注册 + `cloud_model_register()` | 保存点位表与策略指针；安装 `property_port` |
| `bootstrap_init_application()` | `cloud_model_start_scheduler()` | 注册点位索引解析器；启动 `report_scheduler` |
| `bootstrap_init_adapters()` | `cloud_model_validate_and_watch()` | 校验点位表；初始化 watcher |
| `bootstrap_init_adapters()` | `cloud_link_port.init()` | MQTT 连接；失败仅告警，不阻断启动 |

`cloud_model_register()` **不得**在此阶段启动调度器、校验点位表或 init MQTT。

## 10. 实现职责边界

配置文件声明"要什么"，框架负责"怎么协调"。以下逻辑固化在实现中：

| 实现职责 | 说明 |
|----------|------|
| JSON 编解码 | `point_table` 序列化/反序列化；公共查找 `point_table_find_entry` / `point_table_find_entry_at`；公共解析 `point_table_parse_cjson_value` |
| semantic 路由 | 按 `semantic` 分流下行写操作 |
| 登记校验 | `cloud_point_validate` |
| ON_CHANGE 检测 | `cloud_point_watcher`（`is_watched_entry` 过滤 `ON_CHANGE` 且 `get!=NULL`） |
| 一次注册 | `cloud_model_register` 保存 bundle 并安装 `property_port` |
| 上报调度 | `report_scheduler` 消费 `report_policy_entry_t` |
| 链路契约 | `cloud_link_port` 传输与连接边沿 |

以下行为由配置 / 项目层决定，实现不得硬编码：

- 物模型 id 列表与 handler 实现
- `report_policy_entry_t` 触发源与 delta id 列表
- 点位 `report_policy` 标记（当前仅 `ON_CHANGE` 影响 watcher）
- semantic 选型（`DEVICE_CMD` / `CLOUD_SERVICE` / `MANUAL_ACT`）
- 遥测与 DI/领域状态绑定
- 云平台 provider 与 deploy topic 配置

实现不得硬编码机型名或具体物模型字段；同一逻辑只依赖 bundle 声明的点位表与调度策略。

**代码落位**（简要）：概念层 `framework/cloud/`；编解码 `framework/common/point_table/`；端口 `framework/ports/.../cloud/`；项目配置 `projects/<project>/adapters/cloud/`；provider `framework/adapters/.../cloud/`。

## 附录 B：扩展与衔接

### B.1 新增物模型点位

1. 在 `*_cloud_points.h` 增加 X-macro 行
2. 按 §4.2 选择 `semantic`
3. 实现 `get` / `set` / `service`；脉冲命令用 `cloud_point_get_echo_idle`
4. 设置 `report_policy`：需要 watcher 增量时选 `ON_CHANGE`
5. 在 `*_cloud_register.c` 补充调度策略（若需新触发源）
6. 上电 `cloud_model_validate_and_watch()` 自动校验

### B.2 新增云平台 provider

实现 `cloud_link_ops_t` + property adapter + report adapter；项目提供 `*_cloud_register()` bundle。
