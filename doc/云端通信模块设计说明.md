# 云端通信模块设计说明

本文档说明框架中 **cloud 模块** 的分层思路、职责边界与扩展方式。  
描述以通用架构为主；文中出现的 M8 文件名与点位 id 仅作**示例**，不代表其它机型必须照搬。

---

## 1. 设计目标

云端通信模块要解决三类问题，且彼此解耦：

| 问题 | 归属 | 说明 |
|------|------|------|
| **传什么** | 项目层点位表 | 物模型字段 id、读写语义、与业务逻辑的映射 |
| **怎么编解码** | `common/point_table` | 标识符 ↔ JSON，与 MQTT/云平台无关 |
| **怎么收发** | 框架 inbound/outbound 适配器 | MQTT 连接、Topic、SDK 调用 |

设计原则：

1. **按数据流方向拆分**：下行（Cloud → 设备）与上行（设备 → Cloud）各自独立目录与适配器。
2. **传输与语义分离**：JSON 点位表引擎不依赖任何云 SDK；云适配器不嵌入业务规则。
3. **项目可替换**：换云平台 provider 或换机型，只改对应层，不牵动 application/domain。
4. **下行语义分流**：并非所有云端写入都是「设备生命周期命令」；按语义走不同链路，避免全部塞进 `command_port`。

---

## 2. 总体分层

```text
┌─────────────────────────────────────────────────────────────┐
│  application（report_aggregator、device_fsm 等）             │
│  只感知 port，不感知 MQTT / 物模型字段名                      │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  ports                                                       │
│  outbound/cloud/report   — 上行抽象（cloud_report_ops）       │
│  inbound/command         — 设备生命周期命令（部分下行经此注入）│
└───────────────────────────┬─────────────────────────────────┘
                            │
        ┌───────────────────┴───────────────────┐
        │                                       │
┌───────▼────────┐                   ┌──────────▼─────────┐
│ framework      │                   │ projects/<机型>/    │
│ adapters       │                   │ adapters/cloud/     │
│                │                   │ adapters/manual/    │
│ inbound/cloud  │  MQTT 下行接收     │                     │
│ outbound/cloud │  MQTT 上行发送     │ 点位表 + 绑定层     │
│ runtime/snack  │  SDK 传输          │ 业务 handler 实现   │
└───────┬────────┘                   └──────────┬─────────┘
        │                                       │
        └───────────────────┬───────────────────┘
                            │
                ┌───────────▼───────────┐
                │ common/point_table    │
                │ JSON 编解码（通用）    │
                └───────────────────────┘
```

**框架层**负责「能连上、能发能收」；**项目层**负责「连上之后读写字段代表什么」；**common 层**负责「字段如何变成 JSON」。

## 3. 目录与职责

### 3.1 框架通用（`framework/`）

| 路径 | 职责 |
|------|------|
| `common/point_table/` | 点位表类型、`point_table_to_json` / `point_table_from_json` |
| `ports/outbound/cloud/report/` | 上行 port：`cloud_report_ops_t` |
| `adapters/inbound/cloud/providers/<provider>/` | 云平台下行：连接、注册 recv 回调 |
| `adapters/outbound/cloud/providers/<provider>/` | 云平台上行：实现 `cloud_report_ops`，调用注入的 JSON 构建器 |
| `adapters/runtime/<provider>/` | SDK 级传输（MQTT 连接、Topic 读写） |
| `application/orchestrators/report_aggregator.c` | 周期聚合 `dev_ctx` 快照，调用 `cloud_report_ops.report()` |

当前仓库中 provider 示例为 `snack`（Snack MQTT）。新增阿里云原生 SDK、华为云等时，在 `providers/` 下增加并列实现，**不修改** `common/point_table` 与 application。

### 3.2 项目专属（`projects/<机型>/adapters/cloud/`）

项目层按**职责域**拆分文件，而不是把所有 handler 堆进单文件。推荐结构（名称可带机型前缀）：

| 文件（示例） | 职责 |
|--------------|------|
| `<proj>_cloud_bind.*` | 对接框架 inbound/outbound 适配器的**唯一绑定入口**（上报构建、属性下发分发） |
| `<proj>_cloud_model.*` | 组装完整 `point_table_entry_t[]`，登记所有点位 id |
| `<proj>_cloud_telemetry.*` | 只读遥测：`sts_*` 类点位的 get handler |
| `<proj>_cloud_device_cmd.*` | 设备生命周期命令：映射到 `command_port` |
| `<proj>_cloud_service.*` | 云端服务类操作：同步、通信测试等，**不进 device_fsm** |
| `<proj>_cloud_manual_cmd.*` | 手动机构动作点位的 set handler（若物模型包含） |
| `<proj>_cloud_common.*` | 多个点位共用的辅助函数（如脉冲命令的统一 get 回显） |

与 cloud 平行的 **`adapters/manual/`**（示例：`manual_guard`、`manual_action`）承载手动点动的**业务入口与准入守卫**；云端 manual 点位、CLI、仿真控制台应共用该模块，而不是在 cloud handler 里直接调机构驱动。

## 4. 点位表引擎（`common/point_table`）

点位表是传输无关的核心抽象：

```c
typedef struct {
    const char     *id;      /* 物模型属性标识符，如 "sts_standby" */
    point_type_t    type;    /* BOOL / INT / STRING */
    point_get_fn_t  get;     /* 上行：读当前值；NULL 表示不可读 */
    point_set_fn_t  set;     /* 下行：执行写操作；NULL 表示只读 */
} point_table_entry_t;
```

约定：

- **只读点位**：`set = NULL`，上行序列化时调用 `get`。
- **脉冲命令点位**：云端写 `1` 触发、`0` 无操作；设备侧通常**不保存状态**，上行 `get` 可统一返回恒定值（示例：公共函数 `get_cmd_pulse` 恒返回 `false`）。
- **未知 id / 类型不匹配 / 写只读点位**：记录告警，**同一条 JSON 内其它属性继续处理**。

该引擎可被云端、CLI 调试、本地 HTTP 等非 MQTT 场景复用，因此**不得**放入 `adapters/cloud/`。

## 5. 上行数据流（设备 → Cloud）

```text
dev_ctx 快照
  → report_aggregator.build_payload()
  → cloud_report_ops.report(payload)          [port]
  → <provider>_cloud_report_adapter           [框架 outbound]
       └─ 调用项目注入的 report_builder
  → <proj>_cloud_on_report()                  [项目 bind]
       └─ point_table_to_json(model, ...)     [common]
  → MQTT publish
```

要点：

1. **`cloud_report_payload_t` 是框架聚合快照**，供需要结构化载荷的上报路径使用；若项目 JSON **完全由点位表各 `get()` 驱动**（当前 M8 即如此），builder 可忽略 payload，仅遍历点表。
2. 字段名、类型、是否上报某 DI 状态，全部由**项目点位表**决定，框架不硬编码物模型。
3. 离线时 `report_aggregator` 静默跳过，不产生无意义错误风暴。

## 6. 下行数据流（Cloud → 设备）

```text
MQTT JSON（可含多个属性）
  → <provider>_cloud_command_adapter          [框架 inbound]
  → <proj>_cloud_on_property_set(json)        [项目 bind]
  → point_table_from_json(model, ...)         [common]
  → 各 entry.set() 按语义分流：
       ├─ device_cmd   → command_port.inject → command_handler → event_bus
       ├─ cloud_service → report_aggregator / 其它 application 接口
       └─ manual_act   → manual_action → manual_guard → 机构驱动
```

### 6.1 三类下行语义

扩展物模型时，必须先归类，再选链路：

| 类型 | 典型点位命名 | 行为特征 | 推荐链路 |
|------|--------------|----------|----------|
| **设备生命周期命令** | `cmd_home`、`cmd_custom_stop` | 改变 device_fsm 状态，需 command_guard | `command_port` → `device_fsm` |
| **云端服务** | `cmd_sync`、`cmd_communication_test` | 触发同步/调试，不改变洗车主状态机 | application 编排器或项目 service handler |
| **手动机构动作** | `cmd_gantry_fwd`、`cmd_brush_side` | 点动/脉冲，需独立准入规则 | `manual_action` + `manual_guard` → 机构 API |

**反模式**：把所有 `cmd_*` 一律 `inject` 进 `command_port`，会导致手动点动与设备状态机耦合、守卫规则难以表达。

### 6.2 脉冲命令约定

- 写 `true` / `1`：执行一次。
- 写 `false` / `0`：无操作（便于云端复位属性）。
- 不要求设备持久化命令位状态；上行回显统一为「未触发」即可。

## 7. 绑定层（`<proj>_cloud_bind`）

绑定层是项目与框架 cloud 适配器之间的**薄胶水**，只做两件事：

1. **上行**：接收 `cloud_report_payload_t` + 缓冲区，调用 `point_table_to_json`。
2. **下行**：接收 JSON 字符串，调用 `point_table_from_json`。

注册时机（示例）：

- `wiring()`：`snack_cloud_report_adapter_register(<proj>_cloud_on_report)`
- `project_adapters_init()`：`snack_cloud_command_adapter_init(<proj>_cloud_on_property_set)`

绑定层**不应**包含具体点位的业务逻辑；handler 实现在各域源文件中，由 `*_cloud_model.c` 汇总登记。

---

## 8. 与 `command_port` 的边界

| 场景 | 是否走 command_port |
|------|---------------------|
| 启动洗车、停止洗车、回零、复位故障 | 是 |
| 请求全量属性同步 | 否（cloud_service） |
| 龙门/刷子点动 | 否（manual_action） |
| 通信测试标志位 | 否（cloud_service / 项目内存） |

`command_port` 承载的是**框架已定义的 `cmd_type_t` 设备命令**，经 `command_handler` 校验与 `command_guard` 状态检查后发布事件。云端 device_cmd handler 的职责仅是：**把物模型 bool 脉冲翻译成一次 `inject()`**。

---

## 9. 手动点动与 cloud 的关系

手动机构动作若出现在物模型中，cloud 层只做**协议适配**：

```text
cmd_gantry_fwd (云端 bool)
  → cloud_manual_cmd.set()
  → manual_gantry_fwd()
  → manual_guard_allow_motion()   /* 项目规则：device_state + 急停等 */
  → gantry_move_fwd()
```

守卫规则放在 `adapters/manual/`，**不**放在 `command_guard` 或 `safety_state` 中，除非业务明确要求统一。这样 CLI 与云端共用同一套准入逻辑。

## 10. 命名约定

| 前缀/模块 | 层级 | 含义 |
|-----------|------|------|
| `point_table_*` | framework common | 通用引擎类型与 API |
| `snack_cloud_*_adapter` | framework provider | Snack MQTT 收发 |
| `<proj>_cloud_*` | project | 项目云端点位与绑定 |
| `<proj>_manual_*` | project | 手动动作与守卫 |
| `sts_*` | 物模型 id（示例） | 只读状态 / 遥测 |
| `cmd_*` | 物模型 id（示例） | 可写命令或脉冲 |

新增点位时：**id 与云平台控制台一致**；C 函数名按域命名（`get_sts_*` / `set_cmd_*`），在 model 表中登记一行。

## 11. 扩展指南

### 11.1 新增云平台 provider

1. 在 `adapters/inbound/cloud/providers/<name>/` 实现下行适配（连接 + dispatch 回调注入）。
2. 在 `adapters/outbound/cloud/providers/<name>/` 实现 `cloud_report_ops`（发送 + builder 回调注入）。
3. 项目层 `*_cloud_bind` 接口保持不变，仅 wiring 改注册目标。

### 11.2 新增机型

1. 复制 cloud 目录结构模板，实现各域 handler。
2. 在 `*_cloud_model.c` 登记点位表。
3. 在 wiring / project_hooks 注册 bind 函数。
4. 手动类点位复用或实现 `<proj>_manual_*`。

### 11.3 新增物模型点位

1. 确定语义类型（telemetry / device_cmd / cloud_service / manual_act）。
2. 在对应域文件实现 `get` / `set`。
3. 在 `*_cloud_model.c` 增加一行 `{ id, type, get, set }`。
4. 若为脉冲命令且需统一回显，复用 common 中的共享 getter。

### 11.4 仿真构建

仿真可链接 `common/point_table` 与项目 cloud 源文件做 JSON 单元测试，**无需**拉入 inbound/outbound provider（无 MQTT SDK）。`report_aggregator` 在未注册 `cloud_report_ops` 时自动跳过上报。

## 12. 示例对照（M8，仅供参考）

以下为当前 M8 实现的映射关系，其它机型可不同：

| 概念 | M8 示例 |
|------|---------|
| 绑定入口 | `m8_cloud_on_report` / `m8_cloud_on_property_set` |
| 点位表 | `m8_cloud_model()` |
| 脉冲 get 复用 | `m8_cloud_get_cmd_pulse()` |
| 设备命令 | `m8_device_cmd_submit(CMD_HOME_DEVICE)` |
| 云端同步 | `report_aggregator_request_resync()` |
| 点动 | `m8_manual_gantry_fwd()` |

M8 上行 JSON **以点位表 getter 为准**，`cloud_report_payload_t` 在 builder 中可忽略——这是项目层策略，不是框架强制要求。

## 14. 一句话总结

Cloud 模块采用 **「common 编解码 + framework 传输 + project 语义」** 三层结构，上下行按方向拆分；下行按 **telemetry / device_cmd / cloud_service / manual_act** 分流，避免把物模型、MQTT 与设备状态机焊死在同一文件里。
