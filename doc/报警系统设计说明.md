# 报警系统设计说明

**版本**：v4.0  
**状态**：v4.0 核心已落地（`alarm_registry`、`motion_reeval_group`、龙门 `motion_completed` 桥接）；顶刷/侧刷/流程检查点事件发布待补齐  
**适用范围**：嵌入式控制软件报警/安全域（framework 通用；M8 为首个落地机型示例）  
**架构基线**：`软件设计框架说明.md` §2.1/§12、`运行模式状态机设计说明.md` v2.0  
**配套文档**：`报警编码规范.md`（码值与目录配置）  
**关键词**：AlarmRegistry、响应策略、PostWash 评估、motion_reeval_group、reeval_binding、完整活跃列表、ON_MOTION、Comm 硬切断

## 1. 设计目标

报警系统把硬件/流程/通讯异常转化为**可分级、可清除、可上报**的报警实例，在**最大服务完成原则**约束下驱动即时安全反应与会话边界决策，并对外提供完整活跃列表。

### 1.1 业务北极星：最大服务完成原则

> 在安全许可的前提下，系统优先保障**当前洗车会话**完整完成；**是否允许开始下一单**，在会话结束边界统一决策。

据此确立两条时间尺度：

| 时间尺度 | 决策问题 | 典型输入 |
|----------|----------|----------|
| **会话内（WASHING）** | 本条故障是否须**立即**中止本单？ | `response_strategy` |
| **会话边界（Completed/Aborted）** | 本单结束后是否仍须**停机拒单**？ | 活跃 MAJOR+ 是否存在 |

**已确认产品规则**：

1. 当前订单执行中：MAJOR 允许继续完成本单；CRITICAL 立即中止。
2. 当前订单结束后：若仍存在未清除的 **MAJOR 或 CRITICAL** 活跃报警，整机进入 EXCEPTION，**不得**带报警承接下一单。
3. MINOR 活跃报警不阻断下一单（仅上报提示）。

### 1.2 四条独立轴（禁止合并枚举）

| 轴 | 回答问题 | 权威模块 |
|----|----------|----------|
| **报警等级** `alarm_level_t` | 统计/上报严重度 | AlarmDefinition（静态） |
| **响应策略** `response_strategy_t` | 本单是否立即停 | AlarmDefinition（静态） |
| **安全姿态** `safety_posture_t` | 是否须立即切断/abort | SafetyPosture 聚合 |
| **运行模式** `operational_mode_t` | 允许哪些外部命令 | OperationalMode |

等级 **不得** 单独驱动全部下游行为；消费者应优先读 `response_strategy` 与查询接口，而非硬编码 level 分支。

## 2. 分层架构

```text
                    ┌──────────────────────────────────────┐
  safety_thread     │ EStop → safety_cutout_execute()      │
  (SCHED_FIFO)      │       → EVT_HW_ESTOP_ON/OFF          │
                    └──────────────────────────────────────┘
                                    │
  detectors (adapters)              │
  ┌──────────────┬──────────────┬──────────────┐
  │ LevelDetector│ CommWatchdog │ ProcessEval  │ CallSiteReporter
  │ (DI 轮询)    │ (心跳超时)   │ (流程 guard) │ (HAL/领域调用)
  └──────┬───────┴──────┬───────┴──────┬───────┘
         │ immediate_cutout? (Comm CRITICAL 配置项)
         └──────────────┼──────────────┘
                        ▼
              ┌─────────────────────┐
              │    AlarmRegistry    │  ← 报警唯一事实源
              │  definitions[]      │
              │  active_list[]      │
              │  session_journal[]  │
              │  recent_journal[]   │
              └─────────┬───────────┘
                        │ AlarmTriggered / AlarmCleared
                        │ PostWashAssessmentCompleted
         ┌──────────────┼──────────────┬──────────────┐
         ▼              ▼              ▼              ▼
  SafetyPosture   WashOrchestrator  OpModeBridge   SafetySupervisor
  (NOMINAL/       (abort/journal)   (PostWash/     → dev_ctx / 云端
   LOCKOUT)                         EXCEPTION)

  机构 / 流程（projects/*/domain/mechanism、wash）
         │  motion_completed / checkpoint_reached（领域事件，不含报警类型）
         ▼
  projects/*/wiring/alarm_reeval_bridge
         │  lookup reeval_binding → alarm_registry_reevaluate_group()
         ▼
              AlarmRegistry（ON_MOTION 批量清除）
```

**依赖方向**：

- `projects/*/adapters` 只依赖 `ports/inbound/safety/alarm_binding_port` 与 `domain/safety/model/*`（**不含** `reevaluate_group`）。
- `projects/*/domain/mechanism` **不得**依赖 `domain/safety/*`；动作完成时只发布机构/流程生命周期事件。
- `projects/*/wiring/alarm_reeval_bridge` 订阅生命周期事件，查 binding 表后调用 `alarm_registry_reevaluate_group()`。
- `domain/safety/alarm_registry` 不依赖任何 adapter 或项目配置。
- Registry **不订阅** event_bus；由 application 喂入 sensor / session_ended / recover，再 pull 领域事件发布。

## 3. 数据模型

### 3.1 报警等级（上报/统计）

```c
typedef enum
{
    ALARM_LEVEL_MINOR = 0,
    ALARM_LEVEL_MAJOR,
    ALARM_LEVEL_CRITICAL,
} alarm_level_t;
```

### 3.2 响应策略（本单即时行为）

```c
typedef enum
{
    RESP_LOG_ONLY = 0,           /**< 仅记录上报，不干预本单 */
    RESP_COMPLETE_THEN_ASSESS,   /**< 本单继续；会话边界再评估（MAJOR） */
    RESP_STOP_IMMEDIATELY,       /**< 立即 abort + LOCKOUT（CRITICAL） */
} response_strategy_t;
```

**缺省映射**（目录可覆盖并注明理由）：

| level | 缺省 response_strategy |
|-------|--------------------------|
| MINOR | RESP_LOG_ONLY |
| MAJOR | RESP_COMPLETE_THEN_ASSESS |
| CRITICAL | RESP_STOP_IMMEDIATELY |

### 3.3 清除方式

```c
typedef enum
{
    ALARM_CLEAR_AUTO_STATIC = 0,  /**< 条件消失即自动清除（电平类 DI、液位等） */
    ALARM_CLEAR_ON_MOTION,        /**< 静止无法评估；检查点到达后 reevaluate，条件满足则清除 */
    ALARM_CLEAR_MANUAL_RESET,     /**< 条件消失也不自动清；Recover / ResetFault 强制清除 */
} alarm_clear_t;
```

| 清除方式 | 自动 clear 请求 | Recover 批量清除 | 典型场景 |
|----------|-----------------|------------------|----------|
| AUTO_STATIC | 条件恢复即清 | 可强制清 | 急停、防撞、液位 |
| ON_MOTION | 仅 `reevaluate_group` / Recover 可清 | Recover **强制清** | 限位超时、码盘无脉冲 |
| MANUAL_RESET | 忽略 | **强制清** | 过载、通讯丢失、硬件故障 |

**已确认**：Recover 时对 ON_MOTION 报警**强制清除**，不要求机构再走一遍验证。

急停报警（`M8_ALARM_CODE_ESTOP`）由硬件信号决定，Recover **不得**强制清除。

### 3.4 报警定义（静态目录）

#### 3.4.1 Framework 通用类型

定义于 `framework/domain/safety/model/alarm_types.h`：

```c
typedef enum
{
    ALARM_SOURCE_LEVEL   = 0,
    ALARM_SOURCE_COMM,
    ALARM_SOURCE_PROCESS,
    ALARM_SOURCE_CALLSITE,
} alarm_source_kind_t;

/** @brief ON_MOTION 重评估分组 ID；framework 只定义 NONE，具体取值由项目配置 */
#define ALARM_REEVAL_GROUP_NONE  0U
typedef uint16_t motion_reeval_group_id_t;

typedef struct
{
    uint32_t                  code;
    alarm_level_t             level;
    response_strategy_t       response;
    alarm_clear_t             clear;
    alarm_source_kind_t       source_kind;
    motion_reeval_group_id_t  reeval_group;   /**< ON_MOTION 必填；其余填 NONE */
    bool                      immediate_cutout;
    char                      desc[ALARM_DESC_MAX];
} alarm_def_t;
```

**设计约束**：

- `motion_reeval_group_id_t` 对 Registry 是**不透明等值键**；framework **不得**枚举 `GANTRY`、`TOP_BRUSH` 等项目语义。
- `reeval_group` 只表达「该 ON_MOTION 报警属于哪个重评估分组」，不表达触发源本身。
- v2.0 的 `alarm_def_t` 仅含 `level + clear(LATCHED)`；v3.0 引入 `response + clear(三分) + immediate_cutout`；v4.0 以 `reeval_group` 替代 v3.x 的 `alarm_scope_t` 枚举，实现 framework/项目分离。

#### 3.4.2 项目分组命名空间（M8 示例）

定义于 `projects/m8/config/m8_motion_reeval_groups.h`：

```c
typedef enum

    M8_REEVAL_GROUP_SIDE_BRUSH,       /**< 侧刷切换 */
```

#### 3.4.4 ON_MOTION 触发桥接（项目 wiring）

ON_MOTION 清除的**触发源**（机构动作完成、流程检查点到达）与**分组 ID**（目录 `reeval_group`）解耦，由项目 wiring 显式绑定。

**Framework 生命周期事件契约**（`framework/domain/device_control/model/actuator_events.h`）：

```c
typedef uint16_t actuator_id_t;
typedef uint16_t wash_checkpoint_id_t;

void actuator_publish_motion_completed(actuator_id_t id);
void wash_publish_checkpoint_reached(wash_checkpoint_id_t cp);
```

- `actuator_id_t`、`wash_checkpoint_id_t` 均为不透明 ID，具体取值由项目定义。
- 机构/流程代码**只发布事件**，不 `#include` 报警头文件。

**项目 binding 表**（`projects/m8/wiring/m8_alarm_reeval_bindings.h`）：

```c
typedef enum
{
    REEVAL_TRIGGER_ACTUATOR = 0,
    REEVAL_TRIGGER_PROCESS,

typedef struct
{
    reeval_trigger_kind_t     kind;
    uint16_t                  trigger_id;   /* M8_ACTUATOR_* 或 M8_CHECKPOINT_* */

```

**桥接模块**（`projects/m8/wiring/m8_alarm_reeval_bridge.c`）：

```text

  → lookup binding(trigger_kind, trigger_id)
```


### 3.6 安全姿态（即时安全，两态）

```c
typedef enum
{
    SAFETY_POSTURE_NOMINAL = 0,
    SAFETY_POSTURE_LOCKOUT,
} safety_posture_t;
```

聚合规则：

```text
LOCKOUT ⇔ ∃ active instance WHERE response == RESP_STOP_IMMEDIATELY
NOMINAL ⇔ 否则
```

**不再使用** v2.0 的 `SAFETY_STATE_WARNING`。MAJOR 不抬升全局安全姿态；拒单由 PostWash 与会话边界查询驱动。

## 4. AlarmRegistry 聚合

### 4.1 职责

AlarmRegistry 是安全管理上下文的**聚合根**，负责：

- 持有报警定义目录（启动时 load，只读）
- 管理活跃实例列表 `active_list[]`
- 维护当前 WashSession 的 MAJOR journal（去重 append）
- 维护 recent_journal（Trigger/Clear 环形缓冲，仅 RAM）
- 执行 PostWashAssessment
- 响应 Recover 批量强制清除（急停除外）
- 提供查询：top_code、active_list、blocking_active、posture 推导

### 4.2 内部结构

```text
AlarmRegistry
├── definitions[ALARM_CATALOG_MAX]
├── definition_count
├── active[ALARM_ACTIVE_MAX]
├── active_count
├── session_major_journal[ALARM_SESSION_JOURNAL_MAX]
├── session_journal_count
├── recent_journal[ALARM_RECENT_JOURNAL_MAX]   /* 环形缓冲 */
├── recent_head
└── mutex
```

### 4.3 对外接口

```c
/* --- 生命周期 --- */
sw_err_t alarm_registry_init(void);
sw_err_t alarm_registry_load_catalog(const alarm_def_t *defs, unsigned count);

/* --- 检测器 / 适配器写入（经 alarm_binding_port 转发）--- */
sw_err_t alarm_registry_trigger(uint32_t code);
sw_err_t alarm_registry_clear(uint32_t code);

/**
 * @brief  按重评估分组清除 ON_MOTION 活跃报警
 * @param  group  项目定义的 motion_reeval_group_id_t
 * @note   **调用方契约**：须在触发源侧已自行验证故障条件已恢复（如龙门完成
 *         一次完整行走且限位/码盘正常）后，方可调用本函数。
 *         Registry **无 hook 注册机制**；内部扫描 definitions[]，对
 *         clear==ON_MOTION && reeval_group 匹配 && 当前 ACTIVE 的条目执行强制 clear。
 *         常规路径由 projects/*/wiring/alarm_reeval_bridge 调用；机构/流程代码
 *         **不得**直接调用本函数，也不得枚举具体 ON_MOTION 报警码。
 */
sw_err_t alarm_registry_reevaluate_group(motion_reeval_group_id_t group);

/* --- 应用层喂入 --- */
void alarm_registry_on_wash_session_started(void);
void alarm_registry_on_wash_session_ended(void);
sw_err_t alarm_registry_recover_all(void);        /* 强制清；跳过 ESTOP */

/* --- 查询 --- */
bool     alarm_registry_is_active(uint32_t code);
bool     alarm_registry_has_blocking_active(void); /* 任意 active level >= MAJOR */
bool     alarm_registry_is_estop_active(void);
uint32_t alarm_registry_top_code(void);
unsigned alarm_registry_get_active_list(alarm_instance_t *buf, unsigned max);
safety_posture_t alarm_registry_safety_posture(void);

/* --- 领域事件（application pull 后发布到 event_bus）--- */
unsigned alarm_registry_pull_events(alarm_domain_event_t *buf, unsigned max);
```

### 4.4 trigger / clear 语义

**trigger(code)**：

1. 查定义；未知码 → `SW_ERR_PARAM`。
2. 已 ACTIVE → 幂等返回 `SW_OK`。
3. `active_count >= ALARM_ACTIVE_MAX` → overflow 策略（见 §4.6）。
4. 插入 active，写 `triggered_at_ms`，append recent_journal。
5. 若 level >= MAJOR 且会话进行中 → append session_major_journal（去重）。
6. 产出 `AlarmTriggered` 领域事件（含 level/response/clear/triggered_at）。

**clear(code)**：

1. 未 ACTIVE → 幂等返回。
2. 若 `clear == MANUAL_RESET` 或 `ON_MOTION` → **忽略**自动 clear（返回 `SW_OK`）。
3. AUTO_STATIC：移除 active，产出 `AlarmCleared`。

**recover_all()**：

- 清除所有 ACTIVE 实例，**跳过** `M8_ALARM_CODE_ESTOP`。
- ON_MOTION / MANUAL_RESET **一律强制清**。
- 每个清除产出 `AlarmCleared`；最后产出一次 `AlarmBatchCleared`（param=NONE）供 SafetyPosture 重聚合。

### 4.5 ON_MOTION 按分组清除（无 hook）

**语义（解读 B，本期采用）**：`reevaluate_group()` **不是**「Registry 主动查询传感器再判定是否恢复」。  
触发源（机构/流程）在动作完成或检查点到达边界**已自行验证** guard 通过后，经 wiring 桥接调用本函数；Registry 仅按 `reeval_group` 批量清除匹配的 ON_MOTION 活跃报警。

**设计约束**：

- 机构/流程代码 **不得**硬编码 ON_MOTION 报警码列表，**不得**直接调用 Registry。
- 清除入口统一为 wiring 层的 `alarm_registry_reevaluate_group()`。
- inbound `alarm_binding_port` **不包含** `reevaluate_group`（ON_MOTION 清除不是检测器入站写入路径）。

**Registry 内部流程**（无 hook 注册、无回调表）：

```text
reevaluate_group(group):
  for each def in definitions[]:
    if def.clear == ON_MOTION AND def.reeval_group == group AND is_active(def.code):
        force_clear_on_motion(def.code)   /* 内部路径，产出 AlarmCleared */
```

> 公开 API `alarm_registry_clear(code)` 对 ON_MOTION 仍忽略（§4.4）；  
> `force_clear_on_motion` 为 Registry 内部函数，仅供 `reevaluate_group` 与 `recover_all` 使用。

**调用示例**（龙门完成一次行走且限位/码盘校验通过后）：

```c
/* projects/m8/domain/mechanism/gantry.c — 不含报警头文件 */
actuator_publish_motion_completed(M8_ACTUATOR_GANTRY);

/* projects/m8/wiring/m8_alarm_reeval_bridge.c */
(void)alarm_registry_reevaluate_group(M8_REEVAL_GROUP_GANTRY);
```

**不采用解读 A 的理由**：限位超时/码盘丢失/切换异常等 ON_MOTION 场景，guard 判定逻辑已在机构/流程模块内；由 Registry 再挂 hook 重复判定，增加注册/调度复杂度且无额外收益。

### 4.6 活跃池 overflow 与可观测性

`active_count >= ALARM_ACTIVE_MAX` 时：

| 新报警类型 | 策略 |
|------------|------|
| CRITICAL / RESP_STOP_IMMEDIATELY | 挤掉 active 中**最低 level** 的 MINOR（若有）；仍满则 LOG_ERROR 拒绝新实例 |
| 其他 | LOG_WARN 拒绝新 MINOR |

**元报警（可观测性）**：任一 overflow 处理分支执行后（挤掉或拒绝），Registry **同步 trigger** 内置软件报警：

```text
ALARM_CODE_ACTIVE_POOL_OVERFLOW  (= 900200)
  level=MINOR, response=RESP_LOG_ONLY, clear=AUTO_STATIC
  desc="活跃报警池已满"
```

- 该码在 `alarm_registry_init()` 时注入 definitions[]（不占项目 X-macro 行）。
- `active_count` 回落到 `ALARM_ACTIVE_MAX - 1` 以下时 AUTO 清除元报警。
- 确保 overflow 边界在无持久化日志环境下仍可通过 dev_ctx / 云端 / CLI 追溯。

## 5. 检测器模型

每条 `AlarmDefinition` 通过 `source_kind` 绑定检测实现；配置仍使用 X-macro 编译期单表（见 `报警编码规范.md` §8）。

| source_kind | 配置表 | 实现模块 | 触发机制 |
|-------------|--------|----------|----------|
| LEVEL | `m8_alarm_table.h` | `m8_alarm_adapt.c` | DI 轮询 + 独立防抖 + 边沿 |
| COMM | `m8_alarm_comm_table.h` | `m8_comm_watchdog.c` | 心跳超时 trigger；恢复 heartbeat clear |
| PROCESS | `m8_alarm_sw_table.h` + 流程绑定 | `projects/m8/domain/mechanism` + `bindings/m8_mechanism_fault.c` | guard 满足时 trigger/clear；电机 fault 经 lifecycle opts 回调 |
| CALLSITE | `m8_sw_alarm_table.h` | HAL / 业务 | 显式 trigger/clear |

### 5.1 Process 类报警（guard 必填）

流程报警不得与 DI 边沿检测混用同一 poll 路径。示例：

```text
200205 龙门前限位超时：
  reeval_group: M8_REEVAL_GROUP_GANTRY
  guard: gantry.state == MOVING_FWD && expecting_fwd_limit
  trigger: 超时未到位
  clear: ON_MOTION（按目录）
```

机构动作完成且**本地 guard 已通过**后，`gantry.c` 发布 `actuator_publish_motion_completed(M8_ACTUATOR_GANTRY)`；wiring 桥接查 binding 后调用 `alarm_registry_reevaluate_group(M8_REEVAL_GROUP_GANTRY)`。顶刷/侧刷/流程检查点同理，分别走 actuator 或 checkpoint 事件路径。

### 5.2 Comm CRITICAL 硬切断（混合路径）

对 `immediate_cutout == true` 的通讯/HW CRITICAL 报警，watchdog 超时回调顺序：

```text
1. safety_cutout_execute()     /* 与急停同级项目 binding；仅 cutout，不做 mode/abort */
2. alarm_registry_trigger(code)
3. （不在 watchdog 线程做 wash abort / OperationalMode 切换）
```

**推荐配置**：

| 报警码 | immediate_cutout | 理由 |
|--------|------------------|------|
| 400402 IO 子板通讯丢失 | true | 全部 IO 盲控 |
| 400102 龙门行走变频器通讯丢失 | true | 失控行走风险 |
| 400202 毛刷变频器通讯丢失 | false | MAJOR，本单可完成 |
| 400302 风机变频器通讯丢失 | false | MINOR |
| 400502 语音模块 | false | MINOR |

评估结论：纯软路径（仅 event_bus）对 Comm CRITICAL 延迟过大；纯硬路径（仅 cutout）丢失可观测性。**硬 cutout + Registry 记录**为最优。

## 10. 线程模型与事件 drain

### 10.1 线程职责

| 线程 | 职责 |
|------|------|
| **safety_thread** (SCHED_FIFO) | 急停 DI；`safety_cutout_execute`；`EVT_HW_ESTOP_*` |
| **io_poll** (~30ms) | LevelDetector；CommWatchdog（cutout 同步调用）；**每轮末尾 drain Registry 事件** |
| **event_dispatch** | 消费 EVT_ALARM_* / EVT_SAFETY_*；SafetyPosture；OpMode；PostWash；Recover |
| **command_gateway** | `CMD_RESET_FAULT` / Recover → `alarm_registry_recover_all` |

- Registry 内部 mutex 保护 active_list 与 pending 事件队列。
- SafetyPosture / OperationalMode 仅在 dispatch 线程写入，无需 mutex。

### 10.2 pull_events 驱动者与频率

Registry 的 `trigger/clear/recover` **只写内部 pending 队列，不直接 publish**（safety_thread 急停事件除外）。

| pull 点 | 线程 | 时机 | 说明 |
|---------|------|------|------|
| **主 drain** | io_poll | 每轮 poll **末尾**一次 | `m8_alarm_adapt_poll()` → `m8_comm_watchdog_poll()` → **`alarm_event_bridge_drain()`** |
| **辅 drain** | event_dispatch | Recover / PostWash / recover_all 返回后 | 若 `pull_events` 仍有 pending，再 drain 一次，避免同步路径遗漏 |

`alarm_event_bridge_drain()` 伪代码：

```c
void alarm_event_bridge_drain(void)
{
    alarm_domain_event_t batch[8];
    unsigned n;
    while ((n = alarm_registry_pull_events(batch, 8)) > 0) {
        for (unsigned i = 0; i < n; ++i) {
            event_publish(batch[i].type, &batch[i].payload);
        }
    }
}
```

**频率**：主 drain 与 io_poll 同周期，**约 30ms/次**。

`alarm_event_bridge_init()`（§13）在 `project_alarm_poll_start()` 之前完成：向 io_poll 注册末尾钩子，确保首轮 poll 产生的事件可被 drain。

### 10.3 端到端最坏延迟（CRITICAL）

| 路径 | 物理切断（动力） | SafetyPosture → abort / EXCEPTION |
|------|------------------|-----------------------------------|
| **硬件急停** | ≤5ms（safety_thread，与 pull 无关） | ≤5ms + T_dispatch |
| **Comm + immediate_cutout** | 同步于 io_poll 内 watchdog（≤30ms） | **≤30ms + T_dispatch** |
| **DI CRITICAL（无 cutout）** | 无独立硬切断；靠 abort | **≤30ms + T_dispatch** |
| **MAJOR** | 不 abort 本单 | PostWash 边界评估 |

其中 `T_dispatch` = event_dispatch 高优先级队列排空时间，典型 <10ms，最坏取决于当时队列深度。

**可接受性说明**：

- **人身/失控类**（急停、子板盲控、行走变频器失联）：物理切断必须在硬路径完成（急停 ≤5ms；immediate_cutout 在 watchdog 回调同步执行），**不得**依赖 pull/dispatch 才切断动力。
- **软反应**（SafetyPosture、wash abort、模式转 EXCEPTION、云端上报）允许 30ms + T_dispatch；对非急停 CRITICAL，这是「检测 → 编排停机的软件延迟」，与急停硬路径分工一致。
- 若未来某 DI CRITICAL 也需 ≤5ms 切断，应将该路信号提升到 `safety_thread` 或配置 `immediate_cutout`，而非缩短 poll 周期 alone。

## 11. Recover 与 ResetFault

### 11.1 Recover（`CMD_RECOVER` / RecoveryProcedure）

```text
1. guard: !estop_active
2. alarm_registry_recover_all()   /* 含 ON_MOTION 强制清；跳过 ESTOP */
3. 并行驱动机构到安全位置（应用服务）
4. RecoveryCompleted → IDLE | EXCEPTION
```

### 11.2 ResetFault（遗留 `CMD_RESET_FAULT`）

语义收敛为 Recover 的子集或别名：强制清除可清除报警 + 安全姿态重聚合。  
放行条件：`EXCEPTION` 或 `IDLE && has_blocking_active`。

## 17. 测试要点

1. **多报警并存**：MINOR + MAJOR + CRITICAL 同时 active；active_list 与 top_code 正确。
2. **PostWash**：WASHING 中 MAJOR 继续；结束后仍 active → EXCEPTION；已清除 → IDLE。
3. **ON_MOTION**：自动 clear 拒绝；Recover 强制清。
4. **MANUAL_RESET**：DI 释放不 clear；Recover 清除。
5. **Comm cutout**：`immediate_cutout=true` 超时同步 cutout + Registry 记录。
6. **overflow**：active 满时 CRITICAL 挤 MINOR；`ALARM_CODE_ACTIVE_POOL_OVERFLOW` 被 trigger 且可上报。
7. **ON_MOTION 分组清除**：gantry 本地 guard 通过后发布 `motion_completed`；wiring 调 `reevaluate_group(GANTRY)`，Registry 强制清该分组下 ON_MOTION 活跃项（无 hook）；机构代码不含报警头文件。
8. **binding 完整性**：每个 ON_MOTION 目录行的 `reeval_group` 均有对应 binding 条目；缺失 binding 时事件不产生清除（可测试断言）。
9. **pull 延迟**：DI CRITICAL 触发到 EVT_SAFETY_LOCKOUT 最坏 ≤30ms + T_dispatch；immediate_cutout 动力切断不依赖 dispatch。
10. **急停**：Recover 跳过 ESTOP；硬件 off 后 AUTO 清除报警实例。
