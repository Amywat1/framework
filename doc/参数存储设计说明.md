# 参数存储设计说明

**版本**：v1.1  
**状态**：已落地（端口 + JSON 适配器 + `svc_param` 业务层）  
**适用范围**：`wash-device-framework/`、`Project/framework/framework/ports/outbound/storage/`、`Project/framework/framework/adapters/outbound/storage/json/`  
**架构基线**：Ports & Adapters（六边形）+ 依赖注入（`wiring`）  
**关键词**：param_store、json_param_store、KV 持久化、部署配置、端口注册

---

## 1. 设计目标与核心理念

参数存储为框架提供**运行期可读写、可持久化**的键值配置能力，屏蔽底层 JSON 文件（或未来 SQLite 等）细节。

### 1.1 设计目标

- **端口抽象**：业务通过 `param_store_ops_t` 访问，不直接依赖 cJSON 或文件路径。
- **显式持久化**：内存修改与落盘分离——`set` 只改内存，须调用 `save` 才写入文件。
- **字符串统一接口**：`get` / `set` 均以字符串形式交换，数值键在适配器内转换。
- **路径编译期注入**：JSON 文件路径由项目 CMake 通过宏注入，适配器不硬编码部署路径。
- **线程安全**：适配器内部互斥锁保护内存树，支持多线程并发读写的基本安全。

### 1.2 核心理念

| 原则 | 规定 |
|------|------|
| 两层分离 | **param_store**（原始 KV）→ **svc_param**（带业务语义的参数访问，完整框架中位于 `services/param/`） |
| 与部署存储分离 | **param_store** 运行期可写；**deploy_store** 出厂只读（见 §2.4） |
| 适配器可替换 | 仿真/真机/不同介质通过 `wiring` 注册不同 `ops` 实现 |
| 失败可感知 | 文件缺失、解析失败、键不存在均返回明确 `sw_err_t`，由调用方决定默认值策略 |

### 1.3 存储类型对比

```text
运行期参数（param_store）          部署期配置（deploy_store）
  ├── load / save / get / set        ├── load / get（只读）
  ├── 用户/业务可修改                 ├── 出厂写入，运行期不改
  ├── params.json 等                 ├── device.json 等
  └── 典型：模式、计数、校准值        └── 典型：SN、MQTT 地址、Topic
```

## 2. 分层归属与依赖方向

### 2.1 模块落位

| 层次 | 路径 | 职责 |
|------|------|------|
| **端口契约** | `ports/outbound/storage/param_store.h` | `param_store_ops_t`、register/get |
| **端口注册** | `ports/port_registry.c` | `param_store_register()` / `param_store_get_ops()` |
| **JSON 适配器** | `adapters/outbound/storage/json/json_param_store.{h,c}` | 基于 cJSON + 文件的实现 |
| **依赖注入** | `demo/wiring/wiring_sim.c`（或产品 `wiring.c`） | 启动时 `json_param_store_register()` |
| **业务封装** | `services/param/svc_param.*` | 具名参数 API，内部调用 `param_store_get_ops()` |
| **第三方** | `third_party/cJSON/` | JSON 解析与序列化 |

### 2.2 依赖方向

```text
application / services (svc_param)
        │ param_store_get_ops()->get/set/load/save
        ▼
   ports/outbound/storage/param_store.h
        ▲
        │ param_store_register(ops)
   adapters/outbound/storage/json/json_param_store.c
        │
        ▼
   third_party/cJSON + 标准 C 库（stdio / pthread）
```

**依赖禁令**：

- `ports/` 不得 include 适配器或 cJSON 头文件。
- `json_param_store` 不得依赖 `domain/`、`application/` 业务头文件。
- 业务模块不得直接 `fopen` 参数 JSON 路径，须通过端口访问。

### 2.3 启动顺序契约

```text
wiring()
    ├── json_param_store_register()   // 注册 ops，不自动 load
    └── ...
业务 init()
    └── param_store_get_ops()->load()   // 启动时加载一次
         └── 失败时由业务层决定默认值 / 告警策略
```

`wash-device-framework` Demo 当前仅完成 **register**，未调用 `load()`；产品启动代码须在业务 init 中显式 `load()`。

### 2.4 与 deploy_store 的关系

| 维度 | param_store | deploy_store |
|------|-------------|--------------|
| 端口头文件 | `param_store.h` | `deploy_store.h` |
| 适配器 | `json_param_store.c` | `json_deploy_store.c` |
| 编译宏 | `PARAM_STORE_JSON_FILE_PATH` | `DEPLOY_STORE_JSON_FILE_PATH` |
| 写接口 | `set` + `save` | 无 |
| 典型时机 | 运行中多次 load/save | 启动时 load 一次 |

两者在 `wiring` 中并列注册，共用 `port_registry.c` 注册机制，彼此独立。

## 4. 数据模型

### 4.1 端口操作表

```c
typedef struct {
    sw_err_t (*load)(void);
    sw_err_t (*save)(void);
    sw_err_t (*get)(const char *key, char *buf, size_t buf_size);
    sw_err_t (*set)(const char *key, const char *val);
} param_store_ops_t;
```

### 4.2 内存模型（json_param_store 实现）

```text
静态状态
  ├── s_root      : cJSON 对象树（键值对根节点）
  └── s_mutex     : pthread 互斥锁

键值类型
  ├── 字符串      : cJSON_String，get 原样返回
  ├── 数值        : cJSON_Number，get 转为 "%g" 字符串
  └── 新键 set    : 统一以 cJSON_String 写入
```

### 4.3 JSON 文件形态

文件为**扁平 JSON 对象**，键为参数名，值为字符串或数值：

```json
{
    "deviceName": "M8-001",
    "maxSpeed": 120,
    "mode": "auto"
}
```

- 不支持嵌套对象作为 KV 值（当前实现仅处理顶层键）。
- 数组、布尔等类型：`get` 时非 String/Number 视为键不存在（返回 `SW_ERR_PARAM`）。

### 4.4 路径注入

适配器编译期要求定义宏：

```c
#ifndef PARAM_STORE_JSON_FILE_PATH
#error "PARAM_STORE_JSON_FILE_PATH must be supplied by the project build"
#endif
```

Demo 示例（`demo/CMakeLists.txt`）：

```cmake
add_compile_definitions(
    PARAM_STORE_JSON_FILE_PATH="/tmp/demo/params.json"
)
```

产品项目应在 `projects/<product>/config/` 或对应 CMake 目标中注入实际部署路径。

## 5. API 行为契约

以下行为以 **`json_param_store.c` 当前实现** 为准。

### 5.1 load

| 条件 | 行为 | 返回值 |
|------|------|--------|
| 每次调用 | 释放旧 `s_root`，创建新的空对象后再尝试读文件 | — |
| 文件不存在 | 打 WARN 日志，内存保留空对象 | `SW_ERR_STORAGE` |
| 文件存在且 JSON 合法 | 解析替换 `s_root` | `SW_OK` |
| 文件存在但 JSON 非法 | 内存保留空对象 | `SW_ERR_STORAGE` |
| 文件为空（len=0） | 内存保留空对象 | `SW_ERR_STORAGE` |

> **注意**：头文件注释曾写「文件不存在返回 SW_OK」；实现为 `SW_ERR_STORAGE`。调用方应以实现为准，在业务层处理默认值。

### 5.2 save

| 条件 | 行为 | 返回值 |
|------|------|--------|
| `s_root == NULL` | 无法序列化 | `SW_ERR_STORAGE` |
| `s_root` 为空对象 `{}` | 写出 `"{}"` | `SW_OK` |
| 文件不可写 | 打 ERROR 日志 | `SW_ERR_STORAGE` |
| 正常 | `cJSON_PrintUnformatted` 后写入 | `SW_OK` |

`save` 不持有锁跨越文件 I/O 的完整过程：仅在取 JSON 字符串时持锁，写文件在锁外进行。

### 5.3 get

| 条件 | 返回值 |
|------|--------|
| `key` / `buf` 为 NULL，或 `buf_size == 0` | `SW_ERR_PARAM` |
| `s_root == NULL` | `SW_ERR_PARAM` |
| 键不存在 | `SW_ERR_PARAM` |
| 键为 String | `SW_OK`，内容拷贝至 `buf`（截断并保证 `\0`） |
| 键为 Number | `SW_OK`，`snprintf(buf, "%g", ...)` |

### 5.4 set

| 条件 | 行为 | 返回值 |
|------|------|--------|
| `key` / `val` 为 NULL | — | `SW_ERR_PARAM` |
| `s_root == NULL`（未 load） | 静默无操作 | `SW_OK` |
| 键不存在 | 新增 String 键 | `SW_OK` |
| 键已存在且为 Number | `atof(val)` 更新数值 | `SW_OK` |
| 键已存在且为 String | `strdup` 更新字符串 | `SW_OK` |

`set` **不会**自动调用 `save`；掉电前须由业务显式持久化。

## 6. 线程安全与并发

| 操作 | 锁范围 |
|------|--------|
| `load` | 全程持 `s_mutex`（含文件读与树重建） |
| `save` | 持锁取 JSON 字符串；写文件在锁外 |
| `get` / `set` | 持锁访问 `s_root` |

- 允许并发 `get`；`set` 与 `load` 互斥。
- 业务层应避免在持其他全局锁时调用 `load`（可能阻塞较久）。
- 当前为**进程内单例**；不支持多进程同时写同一 JSON 文件。

## 7. 典型用法（仅供参考）

### 7.1 启动加载

```c
const param_store_ops_t *ps = param_store_get_ops();
if (ps == NULL || ps->load == NULL) {
    /* 端口未注册 */
    return SW_ERR_NOT_INIT;
}
if (ps->load() != SW_OK) {
    /* 文件缺失或损坏：业务层写入默认值或告警 */
}
```

### 7.2 读写与持久化

```c
char buf[64];

if (ps->get("mode", buf, sizeof(buf)) == SW_OK) {
    /* 使用 buf */
}
if (ps->set("mode", "auto") == SW_OK) {
    (void)ps->save();
}
```

### 7.3 通过 wiring 注册（Demo）

```c
sw_err_t wiring(void)
{
    json_param_store_register();
    /* ... */
    return SW_OK;
}
```

## 8. 职责边界

### 8.1 框架层负责

| 职责 | 说明 |
|------|------|
| KV 读写与 JSON 序列化 | `json_param_store.c` |
| 线程安全 | 互斥锁保护 `s_root` |
| 端口 register/get | `port_registry.c` |
| 路径编译期注入 | 项目 CMake |

### 8.2 业务 / 项目层负责

| 职责 | 说明 |
|------|------|
| 何时 load / save | 启动 load；参数变更后 save |
| 默认值策略 | `load` 失败时的兜底值 |
| 键名语义 | 如 `"maxSpeed"`、`"washCount"` 的含义 |
| 具名参数 API | `svc_param` 封装（待迁入） |
| JSON 文件初始内容 | 出厂或首次启动写入 |

实现**不得**在 `json_param_store.c` 内硬编码业务键名或机型分支。

| 场景 | 错误码 | 日志级别 |
|------|--------|----------|
| 文件不存在 | `SW_ERR_STORAGE` | WARN |

| 文件不可写 | `SW_ERR_STORAGE` | ERROR |
| 键不存在 / 参数非法 | `SW_ERR_PARAM` | 无 |
| 加载成功 | `SW_OK` | INFO |
| 保存成功 | `SW_OK` | INFO |
| 注册完成 | — | INFO |

## 10. 扩展指南

### 10.1 替换存储后端

1. 新建适配器（如 `sqlite_param_store.c`），实现相同 `param_store_ops_t` 四接口。
2. 在对应 `wiring.c` 中调用 `xxx_param_store_register()` 替代 JSON 版本。
3. 端口与业务层代码无需修改。

### 10.2 新增业务参数

1. 在 `svc_param`（或业务模块）定义具名 getter/setter。
2. 内部调用 `param_store_get_ops()->get/set`。
3. 在参数变更流程末尾调用 `save()`。
4. **不要**在 `json_param_store.c` 增加键名常量。

### 10.3 与完整框架对齐

完整 `Project/framework` 中：

- `services/param/svc_param.c` 封装常用参数，业务优先依赖 `svc_param.h` 而非直接 `param_store`。
- 产品 `wiring.c` 在 bootstrap 阶段注册 `json_param_store_register()`。
- 参数 JSON 样例位于 `projects/<product>/config/`。

迁入 `wash-device-framework` 时，**端口 + JSON 适配器 + 测试**先行，`svc_param` 随 services 层一并迁入。

### 10.4 禁止的扩展方式

- 在业务代码中直接读写 JSON 文件路径。
- 在 `set` 内隐式自动 `save`（破坏批量写入与性能控制）。
- 通过 param_store 存储大二进制或嵌套结构（应使用专用存储或文件端口）。
- 与 deploy_store 混用同一 JSON 文件。
