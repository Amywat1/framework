# 软件设计框架说明

## 1. 文档定位

本文档定义一套面向多项目复用的嵌入式控制软件框架。该框架以 DDD 分层思想和六边形架构为主线，同时结合嵌入式控制系统对安全、线程、周期任务、仿真和硬件适配的要求。

本文档描述的是目标框架设计，不绑定某一个具体项目或机型。具体项目资产应放在 `projects/<project_name>/` 下，框架公共能力应放在 `framework/` 下。

框架的核心目标是：

- 业务规则与硬件、云端、存储、UI、仿真环境解耦。
- 同一套领域能力可以复用于多个项目和机型。
- 真机和仿真通过适配器替换，而不是修改领域逻辑。
- 洗车流程、安全、报警、设备控制和上报模型具有清晰边界。
- 项目扩展时优先新增项目配置、绑定和适配器，不复制框架核心逻辑。

## 2. 架构原则

### 2.1 框架与项目分离

`framework/` 只放跨项目复用能力，不能依赖任何具体项目。

`projects/` 放项目落地资产，包括入口、接线、配置、机型绑定、项目专属适配器、工艺程序和项目测试。

基本规则：

- `framework/` 不允许依赖 `projects/`。
- `framework/domain/` 不允许出现项目名、机型名、IO 点位、设备地址和云端项目字段。
- `projects/<project>/wiring/` 负责把框架端口连接到项目选择的适配器。
- 项目新增能力时，先放在项目目录；确认可跨项目复用后，再沉淀到 `framework/`。

### 2.2 DDD 分层

框架采用 DDD 的分层思想：

```text
application     应用层：用例、流程编排、状态协调
domain          领域层：业务模型、领域规则、领域服务
ports           端口层：系统边界契约
adapters        适配器层：外部世界接入
runtime         运行时层：启动、事件、线程、生命周期
services        共享服务层：参数、状态快照、命令路由等纯软件服务
common          公共基础层：错误码、类型、日志、时间、工具
```

领域规则应尽量进入 `domain/`，业务流程协调进入 `application/`，外部实现进入 `adapters/`，运行骨架进入 `runtime/`。

### 2.3 六边形架构

框架采用六边形架构区分入站和出站边界。

入站方向表示外部如何驱动系统：

```text
云端命令 / CLI / 本地 UI / 仿真控制台 / 测试脚本
    ↓
adapters/inbound
    ↓
ports/inbound
    ↓
application
```

出站方向表示系统如何访问外部资源：

```text
application / domain
    ↓
ports/outbound
    ↓
adapters/outbound
    ↓
硬件 / 存储 / 云端 / 外部 SDK
```

端口只定义契约，不包含协议解析、硬件 SDK 类型、项目点位或项目字段。适配器负责协议转换、SDK 调用和外部资源访问。

### 2.4 稳定逻辑与变化因素分离

稳定逻辑包括：

- 洗车流程模型
- 控制引擎模型
- 设备机构动作语义
- 报警和安全状态模型
- 应用编排规则
- 事件分发和线程调度机制

变化因素包括：

- IO 点位
- 信号极性
- VFD 参数
- 机型尺寸
- 云端物模型
- 硬件 SDK
- 部署参数
- 洗车工艺程序

变化因素应收敛到 `projects/<project>/config/`、`projects/<project>/bindings/`、`projects/<project>/adapters/` 和 `projects/<project>/programs/`。

## 4. 框架目录说明

### 4.1 `framework/common/`

`common/` 放跨层共用的基础能力，只包含与业务无关的通用内容。

适合放入：

- 基础类型
- 统一错误码
- 日志接口
- 时间工具
- CRC、FIFO 等纯工具
- 全局事件类型定义

不适合放入：

- 设备业务规则
- 项目配置
- 硬件点位
- 云端项目字段

### 4.2 `framework/runtime/`

`runtime/` 是框架运行骨架，负责系统如何启动、如何调度、如何分发事件、如何管理生命周期。

推荐结构：

```text
framework/runtime/
  bootstrap/
  lifecycle/
  event_bus/
  scheduler/
  thread_registry/
```

职责：

- 初始化顺序编排
- 生命周期状态管理
- 事件总线
- 线程注册和统一启动
- 致命错误回调
- 运行时统计

`runtime/` 不承载设备业务语义，不直接包含项目 wiring，不直接依赖项目适配器。

### 4.3 `framework/services/`

`services/` 放纯软件共享服务。它们不是领域规则本身，但会被多个应用编排器或适配器使用。

推荐结构：

```text
framework/services/
  dev_ctx/
  param/
  command_router/
```

职责：

- `dev_ctx/`：统一设备状态快照，供上报、CLI、测试和仿真读取。
- `param/`：带业务语义的参数服务，对上屏蔽存储端口细节。
- `command_router/`：将外部命令转换为应用层可处理的命令请求。

约束：

- `services/` 不依赖硬件驱动。
- `services/` 不直接依赖项目适配器。
- 领域规则不应堆到 `services/` 中。
- `dev_ctx` 是状态投影，不是业务流程驱动器。

## 5. 领域层设计

领域层按限界上下文组织。每个上下文拥有自己的模型、规则和领域服务，跨上下文协作由应用层编排。

推荐结构：

```text
framework/domain/
  wash/
    model/
    engine/
    program/

  device_control/
    model/
    mechanism/
    actuator/

  safety/
    model/
    alarm/
    interlock/
    safety_fsm/

  telemetry/
    model/
    snapshot/
```

### 5.1 `domain/wash/`

`wash/` 是洗车流程上下文，负责表达洗车程序、阶段、步骤、条件、动作和控制引擎规则。

核心概念：

- Program：洗车程序
- Phase：阶段
- Lane：并行通道
- Step：步骤
- Condition：条件表达式
- Action：动作原语
- Axis / Marker：位置抽象
- Interlock：流程联锁

设计原则：

- 洗车流程不硬编码为固定动作序列。
- 控制引擎理解通用流程抽象，不理解具体 IO 点位。
- 不同项目通过 `programs/` 提供流程配置。
- 机型动作由项目 bindings 或出站端口承接。

### 5.2 `domain/device_control/`

`device_control/` 是设备机构控制上下文，负责表达设备动作语义。

典型机构：

- 龙门
- 刷子
- 水路
- 风机
- 升降机构
- 门锁
- 执行器

设计原则：

- 上层使用机构动作语义，不直接操作 IO。
- 关键机构使用显式状态机。
- 执行器统一处理启动、停止、限位、超时、故障和安全输出。
- 具体硬件输出通过出站 HAL 端口完成。

### 5.3 `domain/safety/`

`safety/` 是安全和报警上下文，负责维护报警事实、聚合安全状态和表达安全规则。

核心概念：

- Alarm：报警事实
- Alarm Catalog：报警目录
- Alarm Level：报警等级
- Safety State：安全状态
- Interlock：安全互锁
- Reset Policy：复位策略

设计原则：

- 报警负责记录事实。
- 安全状态负责表达整机运行姿态。
- 应用层根据安全状态执行停机、降级、复位和上报。
- 机构控制不直接感知所有报警码，只消费安全状态或互锁结果。

### 5.4 `domain/telemetry/`

`telemetry/` 是状态投影和上报模型上下文，负责定义对外可观测状态。

职责：

- 定义设备快照模型。
- 定义上报字段的领域含义。
- 定义状态聚合口径。

约束：

- 不直接调用云端 SDK。
- 不直接读取硬件。
- 云端协议转换由出站适配器完成。

## 6. 应用层设计

`framework/application/` 负责用例和编排。它不实现底层硬件细节，也不承载复杂领域规则。

推荐结构：

```text
framework/application/
  usecases/
    start_wash/
    stop_wash/
    reset_fault/
    home_device/

  orchestrators/
    device_fsm/
    wash_orchestrator/
    safety_supervisor/
    emergency_handler/
    report_aggregator/
```

职责：

- 消费入站命令。
- 校验当前设备状态是否允许执行命令。
- 调用领域能力完成业务目标。
- 订阅领域事件和安全事件。
- 更新状态快照。
- 触发出站端口完成硬件动作、存储或上报。

`usecases/` 和 `orchestrators/` 的建议分工：

- `usecases/`：短生命周期命令入口，负责参数校验和业务意图表达。
- `orchestrators/`：长期运行流程、状态机和周期任务编排。

## 7. 端口设计

### 7.1 入站端口

入站端口定义外部如何驱动系统。

推荐结构：

```text
framework/ports/inbound/
  command/
  diagnostic/
  simulation_control/
```

典型能力：

- 启动洗车
- 停止洗车
- 暂停和恢复
- 故障复位
- 设备归位
- 参数查询
- 诊断命令
- 仿真信号注入

入站端口不解析 MQTT、CLI 字符串、HTTP 请求或私有协议；这些解析属于入站适配器。

### 7.2 出站端口

出站端口定义系统如何访问外部资源。

推荐结构：

```text
framework/ports/outbound/
  hal/
    io/
    motor/
    sensor/
    vfd/
    voice/
    do_group/

  cloud/
    report/
    connection/

  storage/
    param_store/
    deploy_store/
    program_store/

  safety/
    safety_action/
```

典型能力：

- 读取输入信号。
- 设置输出。
- 控制电机、VFD、语音和 DO 组。
- 读取和保存参数。
- 加载部署配置。
- 加载洗车程序。
- 上报设备状态。
- 执行项目特定安全动作。

出站端口不包含具体 SDK 类型、Modbus 地址、IO 点位或云端 Topic。

## 8. 适配器设计

### 8.1 入站适配器

入站适配器接收外部输入，转换为框架命令或用例调用。

推荐结构：

```text
framework/adapters/inbound/
  cli/
  cloud_command/
  local_ui/
  simulator/
```

职责：

- 解析外部协议。
- 做基础格式校验。
- 转换为入站端口命令。
- 调用应用层用例或命令入口。

入站适配器不做设备状态决策，不实现洗车流程，不直接操作 HAL。

### 8.2 出站适配器

出站适配器实现出站端口，封装外部资源。

推荐结构：

```text
framework/adapters/outbound/
  hal/
    linux_hw/
    sim_hw/
    generic/

  cloud/
    aliyun/
    tsl/

  storage/
    json/
```

职责：

- 调用硬件 SDK。
- 封装仿真硬件。
- 实现云端上报协议。
- 实现 JSON 或其他存储方式。
- 将框架状态转换为外部协议数据。

可跨项目复用的适配器放入 `framework/adapters/`；项目专属点表、项目专属协议和项目专属硬件映射放入 `projects/<project>/adapters/`。

## 9. 项目目录设计

每个项目放在 `projects/<project_name>/` 下。

推荐结构：

```text
projects/
  m8/
    app/
    wiring/
    config/
    bindings/
    adapters/
    programs/
    tests/
```

### 9.1 `app/`

项目入口目录，负责接入具体运行环境并启动框架。

适合放入：

- 真机入口
- 仿真入口
- 项目启动参数
- 与运行时框架对接的入口文件

### 9.2 `wiring/`

项目装配目录，负责把框架端口连接到具体适配器。

职责：

- 注册入站适配器。
- 注册出站适配器。
- 选择真机或仿真实现。
- 注入项目 bindings。
- 完成项目级启动接线。

`wiring/` 是项目依赖框架的关键位置，框架不应反向依赖它。

### 9.3 `config/`

项目配置目录，放编译期或部署期的项目配置。

适合放入：

- IO 映射
- 信号表
- VFD 表
- 电机参数
- 水路参数
- 报警目录
- 线程参数
- 设备部署配置
- 云端点表配置

### 9.4 `bindings/`

项目绑定目录，负责把通用领域能力绑定到具体机型资源。

典型绑定：

- 控制引擎动作绑定到具体机构。
- 领域机构 ID 绑定到电机和 IO。
- 报警源绑定到项目报警目录。
- 上报模型绑定到项目点表。

`bindings/` 表达“通用框架如何落到这个项目上”，不应放入通用领域规则。

### 9.5 `adapters/`

项目专属适配器目录。

适合放入：

- 项目专属云端点表转换。
- 项目专属 CLI 命令。
- 项目专属硬件初始化。
- 无法跨项目复用的外部协议适配。

### 9.6 `programs/`

项目洗车程序和工艺配置目录。

适合放入：

- 标准洗程序
- 快洗程序
- 调试程序
- 不同工艺版本配置

### 9.7 `tests/`

项目级测试目录。

适合放入：

- 项目场景测试
- 项目仿真测试
- 项目点表测试
- 项目 wiring 测试

## 10. 依赖规则

推荐依赖方向：

```text
projects/<project>
    ↓
framework/application
    ↓
framework/domain

framework/application → framework/ports + framework/services + framework/runtime + framework/common
framework/domain      → framework/ports/outbound + framework/runtime/event_bus + framework/common
framework/services    → framework/ports/outbound + framework/runtime + framework/common
framework/adapters    → framework/ports + framework/runtime + framework/common
framework/runtime     → framework/common
framework/ports       → framework/common
```

严格禁止：

- `framework/` 依赖 `projects/`。
- `domain/` 直接包含适配器头文件。
- `domain/` 直接使用硬件 SDK、云 SDK、文件系统路径或项目点位。
- `application/` 直接操作驱动、串口、Modbus 或 IO 板。
- `adapters/` 实现业务状态机。
- `services/` 承载领域规则。
- 用事件总线替代所有同步接口。

## 11. 运行模型

系统启动流程：

```text
项目入口
    ↓
runtime/bootstrap
    ↓
初始化 common 基础能力
    ↓
初始化 event_bus / scheduler / lifecycle
    ↓
项目 wiring 注册端口实现
    ↓
初始化 services
    ↓
初始化 domain
    ↓
初始化 application
    ↓
启动线程和周期任务
```

运行期由三类机制协作：

- 周期任务：传感器扫描、报警扫描、执行器调度、流程 tick、状态上报。
- 事件总线：命令、安全、报警、流程结果、云连接状态等异步通知。
- 状态机：设备状态、安全状态、执行器状态、洗车流程状态。

事件总线适合：

- 外部异步输入。
- 跨模块广播。
- 状态变化通知。
- 流程完成或中止通知。

事件总线不适合：

- 同一用例内部的顺序步骤。
- 简单即时动作。
- 局部状态查询。
- 需要明确返回结果的同步调用。

## 12. 安全与报警设计

安全和报警是独立限界上下文。

基本流向：

```text
硬件异常 / 通讯异常 / 软件异常
    ↓
项目报警适配
    ↓
报警核心记录活跃报警
    ↓
安全状态机聚合安全状态
    ↓
应用层执行停机、降级、复位和上报
```

设计原则：

- 报警核心维护报警事实。
- 安全状态机输出整机安全姿态。
- 应用层负责根据安全状态采取动作。
- 项目专属安全输出通过出站安全动作端口完成。
- 机构控制不直接关心所有报警码。

## 13. 洗车流程设计

洗车流程采用配置驱动的通用控制引擎。

流程模型：

```text
Program
  ├── axes
  ├── markers
  ├── interlocks
  ├── templates
  └── phases
        └── lanes
              └── steps
```

设计原则：

- 程序描述工艺，代码实现引擎。
- 阶段顺序执行，阶段内部允许多通道并行。
- 位置、标记、信号和表达式共同决定动作触发。
- 安全联锁独立于普通业务步骤。
- 动作原语不直接暴露 IO 点位。
- 项目 bindings 将动作原语连接到具体机构。

示例：

```yaml
phases:
  - id: pre_rinse
    name: 预冲洗
    enter_when: "vehicle.detected == true"
    exit_when: "position.gantry >= vehicle.rear + 300"
    lanes:
      - id: gantry_move
        steps:
          - type: control
            action: gantry.forward
            speed: low
            active_when: "safety.state == OK"

      - id: water_spray
        steps:
          - type: control
            action: water.open
            channel: pre_rinse
            active_when: "position.gantry >= vehicle.front - 200 and position.gantry <= vehicle.rear + 200"
```

## 14. 状态上报设计

状态上报不由各模块直接调用云端接口，而是先形成统一状态快照，再由上报聚合器输出。

```text
洗车流程状态
报警状态
安全状态
设备状态
云连接状态
    ↓
services/dev_ctx
    ↓
application/report_aggregator
    ↓
ports/outbound/cloud/report
    ↓
adapters/outbound/cloud
```

设计原则：

- `dev_ctx` 是统一状态投影。
- `domain/` 不直接写云端。
- `adapters/` 不直接修改业务状态。
- 上报适配器只处理协议转换和发送。

## 15. 真机与仿真设计

真机和仿真共享领域层、应用层和端口层，只替换适配器和项目 wiring。

真机路径：

```text
ports/outbound/hal
    ↓
adapters/outbound/hal/linux_hw
    ↓
硬件 SDK / IO 板 / VFD / 传感器
```

仿真路径：

```text
ports/outbound/hal
    ↓
adapters/outbound/hal/sim_hw
    ↓
内存状态 / 模拟编码器 / 模拟传感器
```

仿真设计要求：

- 可注入输入信号。
- 可观测输出状态。
- 可运行完整洗车场景。
- 可验证安全联锁和报警流程。
- 不依赖真实硬件 SDK。

## 18. 总结

本框架采用 DDD 分层和六边形架构组织多项目嵌入式控制软件。

核心结构是：

```text
framework/
  common
  runtime
  services
  domain
  application
  ports
  adapters

projects/
  <project>
```

关键设计取舍是：

- 用 `framework/` 与 `projects/` 分离通用能力和项目资产。
- 用限界上下文组织领域层。
- 用 `ports/inbound` 和 `ports/outbound` 表达系统边界方向。
- 用 `adapters/inbound` 和 `adapters/outbound` 隔离外部世界。
- 用 `runtime/` 管理启动、事件、线程和生命周期。
- 用 `services/` 承载纯软件共享服务。
- 用 `bindings/` 将通用能力连接到具体项目资源。

该设计适合持续扩展不同项目、不同机型、不同硬件平台和不同洗车工艺，同时保持核心控制逻辑稳定可测。
