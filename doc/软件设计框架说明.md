# 软件设计框架说明

## 1. 文档定位

本文档定义一套面向多项目复用的嵌入式控制软件框架。该框架以 DDD 分层思想和六边形架构为主线，同时结合嵌入式控制系统对安全、线程、周期任务、仿真和硬件适配的要求。

本文档描述的是目标框架设计，不绑定某一个具体项目或机型。具体项目资产应放在 `projects/<project_name>/` 下，框架公共能力应放在 `framework/` 下。

框架的核心目标是：

- 业务规则与硬件、云端、存储、UI、仿真环境解耦。
- 同一套领域能力可以复用于多个项目和机型。
- 真机和仿真通过适配器替换，而不是修改领域逻辑。
- 洗车流程、安全、报警、设备控制和上报模型具有清晰边界。
- 项目扩展时优先新增项目配置、绑定和适配器，不复制框架核心逻辑。

## 2. 架构原则

### 2.1 框架与项目分离

`framework/` 只放跨项目复用能力，不能依赖任何具体项目。

`projects/` 放项目落地资产，包括入口、接线、配置、机型绑定、项目专属适配器、工艺程序和项目测试。

基本规则：

- `framework/` 不允许依赖 `projects/`。
- `framework/domain/` 不允许出现项目名、机型名、IO 点位、设备地址和云端项目字段。
- `projects/<project>/wiring/` 负责把框架端口连接到项目选择的适配器。
- 项目新增能力时，先放在项目目录；确认可跨项目复用后，再沉淀到 `framework/`。

### 2.2 DDD 分层

框架采用 DDD 的分层思想：

```text
application     应用层：用例、流程编排、状态协调
domain          领域层：业务模型、领域规则、领域服务
ports           端口层：系统边界契约
adapters        适配器层：外部世界接入
runtime         运行时层：启动、事件、线程、生命周期
services        共享服务层：参数、状态快照、命令路由等纯软件服务
common          公共基础层：错误码、类型、日志、时间、工具
```

领域规则应尽量进入 `domain/`，业务流程协调进入 `application/`，外部实现进入 `adapters/`，运行骨架进入 `runtime/`。

### 2.3 六边形架构

框架采用六边形架构区分入站和出站边界。

入站方向表示外部如何驱动系统：

```text
云端命令 / CLI / 本地 UI / 仿真控制台 / 测试脚本
    ↓
adapters/inbound
    ↓
ports/inbound
    ↓
application
```

出站方向表示系统如何访问外部资源：

```text
application / domain
    ↓
ports/outbound
    ↓
adapters/outbound
    ↓
硬件 / 存储 / 云端 / 外部 SDK
```

端口只定义契约，不包含协议解析、硬件 SDK 类型、项目点位或项目字段。适配器负责协议转换、SDK 调用和外部资源访问。

### 2.4 稳定逻辑与变化因素分离

稳定逻辑包括：

- 洗车流程模型
- 控制引擎模型
- 设备机构动作语义
- 报警和安全状态模型
- 应用编排规则
- 事件分发和线程调度机制

变化因素包括：

- IO 点位
- 信号极性
- VFD 参数
- 机型尺寸
- 云端物模型
- 硬件 SDK
- 部署参数
- 洗车工艺程序

变化因素应收敛到 `projects/<project>/config/`、`projects/<project>/bindings/`、`projects/<project>/adapters/` 和 `projects/<project>/programs/`。

### 2.5 领域语言与核心原则

框架文档、代码命名、测试用例和项目配置应尽量使用一致的领域语言。以下术语作为当前基线：

| 中文 | 领域术语 | 说明 |
|---|---|---|
| 洗车程序 | `WashProgram` | 一套可配置的洗车工艺定义，描述阶段、动作、条件和参数 |
| 洗车会话 | `WashSession` | 一次洗车过程的运行实例，拥有独立生命周期、状态和运行期数据 |
| 车辆画像 | `VehicleProfile` | 当前会话识别出的车辆前后边界、长度、轮廓、宽高类别和置信度 |
| 运行时计划 | `RuntimeWashPlan` | 基于洗车程序和车辆画像生成的本次会话执行计划 |
| 执行机构 | `Actuator` | 接受控制指令的物理机构，如刷子、风机、水泵、升降和门锁 |
| 接触性执行机构 | `ContactActuator` | 需要接触或贴近车身的高风险机构，如侧刷、顶刷 |
| 运行模式 | `OperationalMode` | 设备当前工作模式，同一时刻只能处于一种模式 |
| 报警定义 | `AlarmDefinition` | 报警静态配置，定义等级、清除方式、处置策略和是否阻断下次服务 |
| 报警实例 | `AlarmInstance` | 一次活跃报警事实，由报警核心或报警注册表维护 |
| 服务完成评估 | `PostWashAssessment` | 会话结束后评估活跃报警是否阻断下次服务 |
| 安全状态 | `SafeState` | 龙门保持当前位置，其余机构到达安全位置，泵、阀、风机关闭 |
| 恢复操作 | `Recover` | 操作员触发的恢复流程，清除可清除报警并驱动机构到安全位置 |

核心服务原则：

- 在安全许可的前提下，系统优先保障当前洗车会话完整完成。
- `CRITICAL` 报警立即停机并进入异常态。
- `MAJOR` 报警默认记录并上报，洗车会话可继续完成；会话结束后执行服务完成评估。
- `MINOR` 报警只记录和上报，不干预运行模式。
- 程序参数和部署配置的修改只影响后续会话，不应改变已经创建的会话快照。
- 依赖车辆相对位置、车辆比例或轮廓置信度的高风险动作，必须在车辆画像达到要求状态后才允许执行。

## 4. 框架目录说明

### 4.1 `framework/common/`

`common/` 放跨层共用的基础能力，只包含与业务无关的通用内容。

适合放入：

- 基础类型
- 统一错误码
- 日志接口
- 时间工具
- CRC、FIFO 等纯工具
- 标识符点位表 JSON 编解码（`common/point_table/`）
- 全局事件类型定义

不适合放入：

- 设备业务规则
- 项目配置
- 硬件点位
- 云端项目字段

### 4.2 `framework/runtime/`

`runtime/` 是框架运行骨架，负责系统如何启动、如何调度、如何分发事件、如何管理生命周期。

推荐结构：

```text
framework/runtime/
  bootstrap/
  lifecycle/
  event_bus/
  scheduler/
    scheduler.*
    thread_registry.*
    periodic_task.*
```

职责：

- 初始化顺序编排
- 生命周期状态管理
- 事件总线
- 线程注册、周期任务注册和统一启动
- 致命错误回调
- 运行时统计

`runtime/` 不承载设备业务语义，不直接包含项目 wiring，不直接依赖项目适配器。

`scheduler/` 是运行时线程治理的归口目录。`thread_registry` 只负责登记线程入口、
入口参数、调度策略、优先级和栈大小；`periodic_task` 是基于 `thread_registry`
的周期线程注册辅助接口，只负责把固定周期回调包装成 scheduler 管理的线程。
`periodic_task` 不替代 scheduler，不承载业务语义，也不拥有项目实例。

### 4.3 `framework/services/`

`services/` 放纯软件共享服务。它们不是领域规则本身，但会被多个应用编排器或适配器使用。

推荐结构：

```text
framework/services/
  dev_ctx/
  param/
```

职责：

- `dev_ctx/`：统一设备状态快照，供上报、CLI、测试和仿真读取。
- `param/`：带业务语义的参数服务，对上屏蔽存储端口细节。

> **注**：外部命令入口已迁至 `application/command_gateway`（注册 `command_port`），不再使用 `services/command_router/`。

约束：

- `services/` 不依赖硬件驱动。
- `services/` 不直接依赖项目适配器。
- 领域规则不应堆到 `services/` 中。
- `dev_ctx` 是状态投影，不是业务流程驱动器。

## 5. 领域层设计

领域层按限界上下文组织。每个上下文拥有自己的模型、规则和领域服务，跨上下文协作由应用层编排。

推荐结构：

```text
framework/domain/
  wash/
    model/
    engine/
    program/

  device_control/
    model/
    mechanism/
    actuator/

  safety/
    model/
    alarm/
    interlock/
    safety_fsm/

  telemetry/
    model/
    snapshot/
```

### 5.1 `domain/wash/`

`wash/` 是洗车流程上下文，负责表达洗车程序、阶段、步骤、条件、动作和控制引擎规则。

核心概念：

- Program：洗车程序
- Phase：阶段
- Lane：并行通道
- Step：步骤
- Condition：条件表达式
- Action：动作原语
- Axis / Marker：位置抽象
- Interlock：流程联锁

设计原则：

- 洗车流程不硬编码为固定动作序列。
- 控制引擎理解通用流程抽象，不理解具体 IO 点位。
- 不同项目通过 `programs/` 提供流程配置。
- 机型动作由项目 bindings 或出站端口承接。

### 5.2 `domain/device_control/`

`device_control/` 是设备机构控制上下文，负责表达设备动作语义。

典型机构：

- 龙门
- 刷子
- 水路
- 风机
- 升降机构
- 门锁
- 执行器

设计原则：

- 上层使用机构动作语义，不直接操作 IO。
- 关键机构使用显式状态机。
- 执行器统一处理启动、停止、限位、超时、故障和安全输出。
- 具体硬件输出通过出站 HAL 端口完成。

### 5.3 `domain/safety/`

`safety/` 是安全和报警上下文，负责维护报警事实、聚合安全状态和表达安全规则。

核心概念：

- Alarm：报警事实
- Alarm Catalog：报警目录
- Alarm Level：报警等级
- Safety State：安全状态
- Interlock：安全互锁
- Reset Policy：复位策略

设计原则：

- 报警负责记录事实。
- 安全状态负责表达整机运行姿态。
- 应用层根据安全状态执行停机、降级、复位和上报。
- 机构控制不直接感知所有报警码，只消费安全状态或互锁结果。

### 5.4 `domain/telemetry/`

`telemetry/` 是状态投影和上报模型上下文，负责定义对外可观测状态。

职责：

- 定义设备快照模型。
- 定义上报字段的领域含义。
- 定义状态聚合口径。

约束：

- 不直接调用云端 SDK。
- 不直接读取硬件。
- 云端协议转换由出站适配器完成。

## 6. 应用层设计

`framework/application/` 负责用例和编排。它不实现底层硬件细节，也不承载复杂领域规则。

推荐结构：

```text
framework/application/
  command_gateway/
  op_mode_bridge/
  mode_projection/
  recovery_service/
  self_check_service/
  safety_deferred_stop/
  orchestrators/
    wash_orchestrator/
    emergency_handler/
    safety_supervisor/
    report_scheduler/
```

职责：

- 消费入站命令（经 `command_port.inject` → `command_gateway`）。
- 由 `OperationalMode` 聚合校验命令权限与模式转移。
- 调用领域能力完成业务目标。
- 订阅领域事件和安全事件（`op_mode_bridge` 喂入聚合）。
- 更新状态快照（`mode_projection`）。
- 触发出站端口完成硬件动作、存储或上报。

## 7. 端口设计

### 7.1 入站端口

入站端口定义外部如何驱动系统。

推荐结构：

```text
framework/ports/inbound/
  command/
  diagnostic/
  simulation_control/
```

典型能力：

- 启动洗车
- 停止洗车
- 暂停和恢复
- 故障复位
- 设备归位
- 参数查询
- 诊断命令
- 仿真信号注入

入站端口不解析 MQTT、CLI 字符串、HTTP 请求或私有协议；这些解析属于入站适配器。

### 7.2 出站端口

出站端口定义系统如何访问外部资源。

推荐结构：

```text
framework/ports/outbound/
  hal/
    io/
    motor/
    sensor/
    vfd/
    voice/
    do_group/

  cloud/
    report/
    connection/

  storage/
    param_store/
    deploy_store/
    program_store/

  safety/
    safety_action/
```

典型能力：

- 读取输入信号。
- 设置输出。
- 控制电机、VFD、语音和 DO 组。
- 读取和保存参数。
- 加载部署配置。
- 加载洗车程序。
- 查询云端连接状态（`connection` port）。
- 触发属性上报（`report` port，内容由项目 builder 决定）。
- 执行项目特定安全动作。

出站端口不包含具体 SDK 类型、Modbus 地址、IO 点位或云端 Topic。

## 8. 适配器设计

### 8.1 入站适配器

入站适配器接收外部输入，转换为框架命令或用例调用。

推荐结构：

```text
framework/adapters/inbound/
  cloud/
    providers/
      snack/
        snack_cloud_command_adapter.*
  cli/
  local_ui/
  simulator/
```

云端下行由 `inbound/cloud/` 接收 MQTT 消息，经项目点位表解析后注入 `ports/inbound/command`；JSON 编解码本身由 `common/point_table/` 提供，不属于入站适配器。

职责：

- 解析外部协议。
- 做基础格式校验。
- 转换为入站端口命令。
- 调用应用层用例或命令入口。

入站适配器不做设备状态决策，不实现洗车流程，不直接操作 HAL。

### 8.2 出站适配器

出站适配器实现出站端口，封装外部资源。

推荐结构：

```text
framework/adapters/outbound/
  hal/
    components/
    providers/
    sim/

  cloud/
    providers/
      snack/
        snack_cloud_link_adapter.*
        snack_cloud_report_adapter.*

  storage/
    json/
```

`common/point_table/` 不放在 `adapters/outbound/cloud/` 下：它是传输无关的 JSON 点位表工具，云端、CLI 或其它协议均可复用。

职责：

- 调用硬件 SDK。
- 封装仿真硬件。
- 实现云端上报协议。
- 实现 JSON 或其他存储方式。
- 将框架状态转换为外部协议数据。

可跨项目复用的适配器放入 `framework/adapters/`；项目专属点位表、项目专属协议和项目专属硬件映射放入 `projects/<project>/adapters/`。

### 8.3 云端通信与点位表

云端通信按**数据流方向**拆分入站/出站适配器；点位表 JSON 编解码作为通用工具放在 `common/point_table/`。

```text
framework/common/point_table/              通用 JSON 点位表引擎（传输无关）
  point_table.h
  point_table_to_json.c       （全量与按 id 过滤序列化）
  point_table_from_json.c

framework/cloud/                           物模型元模型 + 一次注册
  cloud_point.*
  cloud_model.*

framework/ports/outbound/cloud/link/       链路 port（传输 + 连接边沿）
  cloud_link_port.h

framework/adapters/inbound/cloud/          MQTT 下行
  providers/snack/snack_cloud_command_adapter.*

framework/adapters/outbound/cloud/         MQTT 上行 + 链路
  providers/snack/snack_cloud_link_adapter.*
  providers/snack/snack_cloud_report_adapter.*

projects/<project>/adapters/cloud/         项目云端点位登记
  m8_cloud_register.*                      一次注册 bundle + report_policy
  m8_cloud_model.*                         点位表组装
  m8_cloud_telemetry.*                     只读遥测
  m8_cloud_service.*                       云端服务
  m8_cloud_manual_cmd.*                    手动机构动作点位

projects/<project>/adapters/manual/        手动机构动作（云端/CLI 共用）
  m8_manual_action.*
```

**下行（Cloud → 设备）**

```text
MQTT JSON
  → snack_cloud_command_adapter（inbound）
  → cloud_property_port.on_property_set
  → cloud_point_apply_json（framework/cloud）
  → 按 semantic 分流：
      device_cmd → command_port.inject
      cloud_service → entry->service
      manual_act → entry->base.set → m8_manual_action（运动类先 inject CMD_MANUAL_ACTUATOR）
  → property_port.reply_property_set（可选 ack）
```

**上行（设备 → Cloud）**

```text
report_scheduler（周期 / 重连 / 报警 / ON_CHANGE 事件调度）
  → cloud_link_port.is_online()              [离线则跳过]
  → cloud_report_ops.publish_properties()    [port，无业务载荷]
  → snack_cloud_report_adapter               [框架 outbound]
       └─ cloud_model_build_properties / _delta
  → cloud_point_to_json                      [framework/cloud]
  → cloud_link_port.publish                  [MQTT 发送]

snack_cloud_link_adapter                     [链路唯一 owner]
  → init / online / publish / recv
  → poll 边沿 → EVT_CLOUD_CONNECTED / DISCONNECTED
  → dev_ctx_snapshot() 读穿 is_online()
```

命名约定：

| 模块 | 类型 | 示例 |
|------|------|------|
| `point_table_*` | 框架通用 | `point_table_entry_t`、`point_table_to_json()` |
| `cloud_model_*` | 框架物模型 | `cloud_model_register()`、`cloud_model_build_properties()` |
| `m8_cloud_*` | 项目云端 | `m8_cloud_model()`、`m8_cloud_register()` |
| `snack_cloud_link_adapter_*` | 云平台 provider | `snack_cloud_link_adapter_register()` |
| `m8_manual_*` | 项目手动 | `m8_manual_gantry_fwd()`（内部经 `CMD_MANUAL_ACTUATOR` 仲裁） |
| `snack_cloud_*_adapter` | 云平台 provider | `snack_cloud_command_adapter_register()` |

## 9. 项目目录设计

每个项目放在 `projects/<project_name>/` 下。

推荐结构：

```text
projects/
  m8/
    app/
    wiring/
    config/
    bindings/
    adapters/
    programs/
    tests/
```

### 9.1 `app/`

项目入口目录，负责接入具体运行环境并启动框架。

适合放入：

- 真机入口
- 仿真入口
- 项目启动参数
- 与运行时框架对接的入口文件

### 9.2 `wiring/`

项目装配目录，负责把框架端口连接到具体适配器。

职责：

- 注册入站适配器。
- 注册出站适配器。
- 选择真机或仿真实现。
- 注入项目 bindings。
- 完成项目级启动接线。

`wiring/` 是项目依赖框架的关键位置，框架不应反向依赖它。

`wiring/` 负责选择并注册具体 adapter/provider；`bindings/` 负责把项目配置表、
机型资源和领域/端口抽象绑定起来。`bindings/` 不应依赖 `wiring/` 选择的
具体 adapter 实现头文件；若项目绑定确需调用绑定能力，该能力应由端口层、
专门的绑定端口，或 framework 明确标注为公共绑定 API 的头文件提供。

### 9.3 `config/`

项目配置目录，放编译期或部署期的项目配置。

适合放入：

- IO 映射
- 信号表
- VFD 表
- 电机参数
- 水路参数
- 报警目录
- 线程参数
- 设备部署配置
- 云端点表配置

### 9.4 `bindings/`

项目绑定目录，负责把通用领域能力绑定到具体机型资源。

典型绑定：

- 控制引擎动作绑定到具体机构。
- 领域机构 ID 绑定到电机和 IO。
- 报警源绑定到项目报警目录。
- 上报模型绑定到项目点表。

`bindings/` 表达“通用框架如何落到这个项目上”，不应放入通用领域规则。

`bindings/` 可以为项目绑定出的具体硬件实例注册或创建项目专属周期任务，
例如绑定具体第三方 SDK 实例后的 tick、项目报警扫描或项目机型专属轮询。
此类任务应只服务于项目实例，不应沉淀跨项目通用运行逻辑。当某个周期逻辑
不再依赖项目点位、项目配置、第三方 SDK 实例或机型策略时，才考虑上移到
`framework/`。

### 9.5 `adapters/`

项目专属适配器目录。

适合放入：

- 项目专属云端点位表（如 `m8_cloud_model.*`）与手动动作模块（如 `m8_manual_*`）。
- 项目专属 CLI 命令。
- 项目专属硬件初始化。
- 无法跨项目复用的外部协议适配。

### 9.6 `programs/`

项目洗车程序和工艺配置目录。

适合放入：

- 标准洗程序
- 快洗程序
- 调试程序
- 不同工艺版本配置

### 9.7 `tests/`

项目级测试目录。

适合放入：

- 项目场景测试
- 项目仿真测试
- 项目点表测试
- 项目 wiring 测试

## 10. 依赖规则

推荐依赖方向：

```text
projects/<project>
    ↓
framework/application
    ↓
framework/domain

framework/application → framework/ports + framework/services + framework/runtime + framework/common
framework/domain      → framework/ports/outbound + framework/runtime/event_bus + framework/common
framework/services    → framework/ports/outbound + framework/runtime + framework/common
framework/adapters    → framework/ports + framework/runtime + framework/common
framework/runtime     → framework/common
framework/ports       → framework/common
```

严格禁止：

- `framework/` 依赖 `projects/`。
- `domain/` 直接包含适配器头文件。
- `domain/` 直接使用硬件 SDK、云 SDK、文件系统路径或项目点位。
- `application/` 直接操作驱动、串口、Modbus 或 IO 板。
- `adapters/` 实现业务状态机。
- `services/` 承载领域规则。
- 用事件总线替代所有同步接口。

## 11. 运行模型

系统启动流程：

```text
项目入口
    ↓
runtime/bootstrap
    ↓
初始化 common 基础能力
    ↓
初始化 event_bus / scheduler / lifecycle
    ↓
项目 wiring 注册端口实现
    ↓
初始化 services
    ↓
初始化 domain
    ↓
初始化 application
    ↓
启动线程和周期任务
```

运行期由三类机制协作：

- 周期任务：传感器扫描、报警扫描、执行器调度、流程 tick、状态上报。
- 事件总线：命令、安全、报警、流程结果、云连接状态等异步通知。
- 状态机：设备状态、安全状态、执行器状态、洗车流程状态。

周期任务归属按职责判定：

- 如果任务只推进 framework 通用状态机或通用 HAL 组合层，且不依赖项目点位、
  项目 SDK 实例或项目策略，应归入 `framework/`。
- 如果任务推进的是项目绑定出的具体实例，依赖项目配置、机型资源或第三方 SDK
  运行模型，应归入 `projects/<project>/`。
- 如果任务属于外部 SDK/provider 的内部资源维护逻辑，应归入对应 provider，
  由 provider 提供清晰的初始化和启动边界。

并发约束：

- 模块内部状态若可能被多个线程访问，模块必须自行提供互斥、原子变量或明确的
  单线程调用约束。
- 若模块声明单线程调用约束，调用方必须在 wiring/bootstrap 中保证 tick、命令
  和查询处于同一执行上下文。
- 周期 tick 与同步查询/命令并发访问同一状态时，不能依赖调用时序假设。
- 第三方 SDK 未明确声明线程安全时，provider 或项目绑定层必须将其视为非线程安全，
  并在边界处串行化访问。

事件总线适合：

- 外部异步输入。
- 跨模块广播。
- 状态变化通知。
- 流程完成或中止通知。

事件总线不适合：

- 同一用例内部的顺序步骤。
- 简单即时动作。
- 局部状态查询。
- 需要明确返回结果的同步调用。

### 11.1 运行模式仲裁

所有外部命令必须经过统一运行模式仲裁，不允许 CLI、云端、仿真控制台或调试接口绕过应用层直接驱动编排器或 HAL。

推荐运行模式：

| 模式 | 说明 |
|---|---|
| `IDLE` | 待机，可接受启动洗车、自检、进入手动等命令 |
| `WASHING` | 洗车会话执行中，只允许洗车相关中止或安全干预 |
| `MANUAL` | 手动维护模式，允许单机构调试和 Recover |
| `SELF_CHECK` | 自检模式，主动驱动机构验证状态 |
| `EXCEPTION` | 异常停机模式，等待维护；急停清除后可 Recover |
| `RECOVERING` | 恢复过渡状态，拒绝外部命令直到恢复完成 |

命令权限基线：

| 命令 | IDLE | WASHING | MANUAL | SELF_CHECK | EXCEPTION | RECOVERING |
|---|---|---|---|---|---|---|
| `StartWash` | 允许 | 拒绝 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| `StartSelfCheck` | 允许 | 拒绝 | 拒绝 | 拒绝 | 急停未激活时允许 | 拒绝 |
| `EnterManual` | 允许 | 拒绝 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| `ManualActuator` | 拒绝 | 拒绝 | 允许 | 拒绝 | 允许 | 拒绝 |
| `AbortWash` | 拒绝 | 允许 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| `Recover` | 拒绝 | 拒绝 | 急停未激活时允许 | 拒绝 | 急停未激活时允许 | 拒绝 |

设计原则：

- 运行模式由 `domain/command_gateway/operational_mode` 聚合唯一持有，`mode_projection` 投影到 `dev_ctx`。
- 命令合法性应优先表驱动，避免分散在多个适配器和编排器中。
- 被拒绝的命令应产生命令拒绝结果，供 CLI、云端和测试场景观测。
- `Recover` 是应用层跨模块用例，负责协调报警清除和机构归安全位，不属于单个领域对象的内部动作。

### 11.2 Recover 语义

`Recover` 用于将设备从 `MANUAL` 或 `EXCEPTION` 恢复到可服务状态。

前置条件：

- 当前模式为 `MANUAL` 或 `EXCEPTION`。
- 急停报警未激活。
- 没有正在执行的洗车会话或自检任务。

执行规则：

- 清除可清除报警；急停报警由硬件信号决定，不由 Recover 强制清除。
- 龙门保持当前位置不动。
- 并行驱动刷子、升降、风机、水路、门锁等机构到安全位置。
- 所有机构到位且无活跃 `CRITICAL` 报警时进入 `IDLE`。
- 超时、机构未到位或恢复过程中出现 `CRITICAL` 报警时进入 `EXCEPTION`。

## 12. 安全与报警设计

安全和报警是独立限界上下文。

基本流向：

```text
硬件异常 / 通讯异常 / 软件异常
    ↓
项目报警适配
    ↓
报警核心记录活跃报警
    ↓
安全状态机聚合安全状态
    ↓
应用层执行停机、降级、复位和上报
```

设计原则：

- 报警核心维护报警事实。
- 安全状态机输出整机安全姿态。
- 应用层负责根据安全状态采取动作。
- 项目专属安全输出通过出站安全动作端口完成。
- 机构控制不直接关心所有报警码。

### 12.1 报警等级和处置策略

| 等级 | 处置策略 | 对服务的影响 |
|---|---|---|
| `CRITICAL` | 立即停止所有执行机构，进入 `EXCEPTION` | 完全阻断，须维护或 Recover 后恢复 |
| `MAJOR` | 记录、上报，当前会话可继续；会话结束后评估 | 可能阻断下次服务 |
| `MINOR` | 记录和上报 | 不影响运行模式 |

`MAJOR` 报警遵循最大服务完成原则：只要安全状态允许，当前洗车会话继续完成。是否阻断下一次服务，由服务完成评估决定。

### 12.2 报警清除方式

报警定义应声明清除方式：

| 清除方式 | 说明 |
|---|---|
| `AUTO_STATIC` | 检测条件可持续监测，条件恢复后自动清除 |
| `ON_MOTION` | 静止时无法持续评估，相关机构再次运动时重评估并自动清除 |
| `RECOVER_CLEAR` | Recover 流程中批量清除的可清除报警 |

约束：

- 同一报警码同一时刻只允许一个活跃实例。
- 重复触发同一活跃报警应幂等处理。
- `AlarmCleared` 后活跃实例从内存事实源移除，历史记录由日志或存储系统承担。
- 急停报警由硬件信号决定，不应被普通 Recover 强制清除。

### 12.3 服务完成评估

服务完成评估用于决定本次会话结束后是否允许继续提供下一次服务。

推荐流程：

```text
MAJOR 报警触发
    ↓
当前 WashSession 记录 alarm_code 到会话 journal
    ↓
会话继续执行
    ↓
WashSessionCompleted / WashSessionAborted
    ↓
PostWashAssessment
    ↓
交叉查询：会话 journal 中出现过 + 当前仍活跃 + blocks_next_service = true
    ↓
存在阻断报警 → 进入 EXCEPTION
不存在阻断报警 → 保持或回到 IDLE
```

分工：

- `WashSession` 只记录本会话出现过的 `MAJOR` 报警 journal，不负责报警事实判断。
- 报警核心或报警注册表是活跃报警事实源。
- 服务完成评估由应用层在会话结束后触发。
- 上报流水线和服务评估流水线相互独立；报警触发后应立即上报，不等待会话结束。

### 12.4 急停快速通道

急停应采用快速同步通道和普通事件通道并行的设计。

快速通道：

- 立即停止所有执行机构。
- 同步更新运行模式或安全状态，使设备进入 `EXCEPTION`。
- 更新急停激活标志，影响 `Recover` 命令合法性。

普通事件通道：

- 记录急停报警实例。
- 发布报警事件。
- 触发云端上报、日志记录和状态快照更新。

允许存在极短窗口期：快速通道已更新运行模式，但普通事件通道尚未完成报警实例记录。该窗口期内，`Recover` 合法性应以快速通道维护的急停状态为准。

## 13. 洗车流程设计

洗车流程采用配置驱动的通用控制引擎。

流程模型：

```text
Program
  ├── axes
  ├── markers
  ├── interlocks
  ├── templates
  └── phases
        └── lanes
              └── steps
```

设计原则：

- 程序描述工艺，代码实现引擎。
- 阶段顺序执行，阶段内部允许多通道并行。
- 位置、标记、信号和表达式共同决定动作触发。
- 安全联锁独立于普通业务步骤。
- 动作原语不直接暴露 IO 点位。
- 项目 bindings 将动作原语连接到具体机构。

### 13.1 WashSession 会话语义

`WashSession` 是一次洗车过程的运行实例，位于应用编排和通用控制引擎之上，用于表达会话级语义。

职责：

- 持有本次会话的程序快照。
- 记录会话状态、开始时间、结束时间和中止原因。
- 跟踪当前执行进度。
- 记录本次会话期间出现过的 `MAJOR` 报警 journal。
- 在会话完成或中止时触发服务完成评估。

状态基线：

```text
CREATED → RUNNING → COMPLETING → COMPLETED
                  ↘ ABORTING  → ABORTED
```

设计约束：

- 同一时刻只能有一个活跃洗车会话。
- 洗车程序在会话创建时形成快照，运行中的会话不受后续配置修改影响。
- `CRITICAL` 报警使会话进入中止路径。
- `MAJOR` 报警只追加到 journal，不因清除而从 journal 中删除。
- `WashSession` 不直接上报云端，也不直接维护报警活跃事实。

### 13.2 车辆画像和运行时计划

后续支持车辆自适应洗车时，可在现有控制引擎基础上引入车辆画像和运行时计划。

`VehicleProfile` 建议包含：

- 车辆前边界、后边界和车长。
- 车顶或车身轮廓采样。
- 宽高类别。
- 识别状态：`UNKNOWN`、`ACQUIRING`、`PARTIAL_LOCKED`、`FULL_LOCKED`、`FAILED`。
- 识别置信度。

`RuntimeWashPlan` 建议由 `WashProgram` 快照和 `VehicleProfile` 生成：

- 车辆画像未知时，只允许低风险动作。
- 依赖车辆相对位置或车辆比例的动作，必须等画像达到要求状态。
- 接触性执行机构在 `VehicleProfile` 未锁定前默认禁止激活，除非程序显式配置保守 fallback。
- 画像识别失败时，按 `FallbackPolicy` 选择安全降级、退回通用窗口、跳过高风险动作或中止会话。
- 同一会话内运行时计划可随画像状态升级而增量更新，但已经执行的动作不回滚。

示例：

```yaml
phases:
  - id: pre_rinse
    name: 预冲洗
    enter_when: "vehicle.detected == true"
    exit_when: "position.gantry >= vehicle.rear + 300"
    lanes:
      - id: gantry_move
        steps:
          - type: control
            action: gantry.forward
            speed: low
            active_when: "safety.state == OK"

      - id: water_spray
        steps:
          - type: control
            action: water.open
            channel: pre_rinse
            active_when: "position.gantry >= vehicle.front - 200 and position.gantry <= vehicle.rear + 200"
```

## 14. 状态上报设计

状态上报不由各模块直接调用云端接口。业务状态先投影到 `dev_ctx`，上报调度由 `report_scheduler` 负责，JSON 内容由 `cloud_model` + `cloud_point` 构建。

```text
洗车流程 / 报警 / 安全 / 设备状态
    ↓
services/dev_ctx（cloud_connected 读穿 cloud_link_port）
    ↓
application/report_scheduler（周期全量 + 重连 resync + 报警/ON_CHANGE 增量）
    ↓
ports/outbound/cloud/link（在线检查 + publish）
ports/outbound/cloud/report（publish_properties / publish_properties_delta）
    ↓
adapters/outbound/cloud/providers/snack（MQTT 发送）
    ↓
framework/cloud/cloud_model（builder → cloud_point → point_table → JSON）
```

连接边沿由 `snack_cloud_link_adapter` 唯一发布 `EVT_CLOUD_CONNECTED` / `DISCONNECTED`；`report_scheduler` 订阅连接与报警事件，不维护连接状态副本。

云端下行命令不走 `report_port`，而是经 `adapters/inbound/cloud` 接收 MQTT 消息后，由项目点位表解析并注入 `ports/inbound/command`。详见 §8.3。

设计原则：

- `dev_ctx` 是统一状态投影；`cloud_connected` 读穿 connection port，不本地同步写入。
- `domain/` 不直接写云端。
- `adapters/` 不直接修改业务状态。
- report port 不含业务载荷；JSON 构建由 `common/point_table` + 项目点位表完成。
- `common/point_table` 不依赖 cloud adapter，可被非云端场景复用。

## 15. 真机与仿真设计

真机和仿真共享领域层、应用层和端口层，只替换适配器和项目 wiring。

真机路径：

```text
ports/outbound/hal
    ↓
adapters/outbound/hal/linux_hw
    ↓
硬件 SDK / IO 板 / VFD / 传感器
```

仿真路径：

```text
ports/outbound/hal
    ↓
adapters/outbound/hal/sim_hw
    ↓
内存状态 / 模拟编码器 / 模拟传感器
```

仿真设计要求：

- 可注入输入信号。
- 可观测输出状态。
- 可运行完整洗车场景。
- 可验证安全联锁和报警流程。
- 不依赖真实硬件 SDK。

```text
    bindings/
    adapters/
    programs/
    tests/
```

根目录旧版框架说明中的 `src/`、`apps/`、`core/`、`service/`、`config/` 目录基线不再作为后续演进依据。后续设计和实现以本文档中的 `framework/ + projects/<project>/` 结构为准。

已确认值得继续沿用的方向：

- `framework/` 与 `projects/` 分离，不将项目资产放回框架目录。
- `runtime/` 作为启动、事件、线程和生命周期骨架，不再使用 `core/` 命名。
- `services/` 作为纯软件共享服务层，不再使用单数 `service/` 命名。
- 洗车流程继续沿用配置驱动的 `domain/wash/engine`，不回退到硬编码 recipe/step_engine。
- 项目机型落地继续放在 `projects/<project>/config`、`bindings`、`adapters`、`programs`，不放入 `framework/adapters/machine/<project>`。

## 18. 持续推进事项

以下事项是当前代码继续向目标架构推进时的优先方向。

### 18.1 补齐应用用例层

### 18.1 命令网关与运行模式（已落地）

`framework/application/command_gateway` + `domain/command_gateway/operational_mode` 已替代原 `device_fsm` / `command_guard` / `usecases/` 分层。

目标分工：

- `OperationalMode` 负责命令矩阵、模式转移和门控变量（`estop_active` / `service_enabled`）。
- `command_gateway` 负责 `command_port.inject` 入队、同步回执和副作用分发。
- `op_mode_bridge` 负责将 `EVT_WASH_*` / `EVT_HW_ESTOP_*` / `EVT_SAFETY_LOCKOUT` 等事件喂入聚合。
- `wash_orchestrator` 负责长期洗车流程、工作线程和流程状态通知。
- `emergency_handler` 负责 LOCKOUT 归位与急停延后完备停机。
- `safety_supervisor` 负责安全状态驱动的 dev_ctx 投影。

约束：

- 外部命令统一经 `command_port.inject`，不直接调用 `wash_orchestrator`。
- 手动点动经 `CMD_MANUAL_ACTUATOR` 仲裁，不维护平行准入判断模块。
- 应用层不直接操作 HAL、驱动、串口或 Modbus（机构动作经 domain/mechanism）。

### 18.2 统一线程治理

统一线程治理的适用范围按职责区分。`framework` 通用模块自身创建或要求的线程/
周期任务，应优先通过 `runtime/scheduler`、`thread_registry` 或
`scheduler/periodic_task`
注册和启动。`projects/<project>` 中绑定具体机型、第三方 SDK 实例、项目点位或
项目策略的线程，可以由项目层自行创建或注册。provider 内部用于维护外部资源的
基础设施线程，可以由 provider 自治，但必须有清晰的 init/start 接口和故障边界。

建议优先收敛：

- framework 通用 HAL 组合层 tick 线程。
- framework 通用传感器 poll 线程。
- 洗车流程 worker 线程。
- 状态上报周期线程。

不应为了统一线程治理，把项目点位、第三方 SDK 类型、项目策略或具体机型资源带入
`framework/`。项目专属线程只要职责局限于项目落地、不反向污染 framework，
可以保留在项目目录中。

端口接口的可见性必须和线程归属一致。若某个周期推进入口属于 framework 通用能力
自管，例如通用传感器滤波采样，则该入口不应作为项目业务可见的 `tick` 暴露在
port ops 中。业务可见 port 不承载项目点位或 provider 绑定；绑定应由组件装配接口
或项目 bindings 完成，port 只保留初始化、读取稳定结果，以及明确限定为启动阶段的
预热接口。VFD manager 这类通用 HAL 组合层可由项目层绑定实例和 provider，但其
运行期周期推进属于 framework 组件自管能力，不应通过项目业务可见 port 暴露。
项目相关周期任务只有在绑定具体机型流程、第三方 SDK 实例或项目策略时，才由项目层
通过 `scheduler/periodic_task` 注册，且不得反向把项目实例、第三方 SDK 类型或项目
策略带入 framework 通用组件。

适配器或 provider 内部确需自治的基础设施线程，应满足以下条件：

- 线程职责局限于外部资源维护或底层轮询。
- 不直接承载业务状态机。
- 启停接口清晰，由项目启动流程显式调用。
- 线程参数来源可配置，避免硬编码散落。

目标收益：

- 线程创建、命名、栈大小、优先级和启动顺序可统一治理。
- 仿真、测试和真机路径的线程行为更一致。
- 后续可扩展运行时诊断、停机和线程健康检查。

### 18.3 补齐安全动作出站端口

安全和报警上下文已经通过报警绑定端口接收项目报警目录和硬件报警源。后续应补齐 `ports/outbound/safety/safety_action` 或等价端口，用于承接项目特定安全动作。

典型动作：

- 断开或恢复安全输出。
- 急停复位相关输出。
- 机型专属故障恢复动作。
- 安全降级时的项目专属执行策略。

约束：

- `domain/safety` 不直接调用安全动作端口。
- `application/safety_supervisor` 根据安全状态决定是否触发安全动作。
- `projects/<project>/adapters` 或 `projects/<project>/bindings` 实现具体动作。
- 项目安全动作不得反向修改安全状态事实源。

### 18.4 明确 bindings 层边界

`projects/<project>/bindings/` 是当前结构中的关键项目落地层，应作为正式架构层维护。

允许职责：

- 将控制引擎动作原语绑定到项目机构。
- 将机构 ID 绑定到项目电机、IO、VFD、传感器和参数表。
- 将项目报警目录、信号表和机型配置注入框架。
- 将项目点表字段映射到框架状态快照。
- 为项目绑定出的具体硬件实例注册或创建项目专属周期任务。

禁止职责：

- 不沉淀跨项目通用领域规则。
- 不实现云端协议解析。
- 不直接承载应用状态机。
- 不绕过端口访问可替换的外部资源。
- 不为了调用绑定能力而包含 `framework/adapters/` 下具体实现头文件。

当某个 binding 逻辑已经不再依赖 M8 点位、M8 机构表或 M8 云端字段时，才考虑沉淀到 `framework/`。

### 18.5 持续检查端口方向和依赖

后续新增模块时应持续检查以下边界：

- `framework/` 不依赖 `projects/`。
- `domain/` 不包含适配器头文件、SDK 类型、文件系统路径和项目点位。
- `application/` 不直接操作驱动、串口、Modbus 或 IO 板。
- `services/` 不承载领域规则，不依赖项目适配器。
- `ports/` 不暴露具体 SDK 类型、Modbus 地址、IO 点位或云端 Topic。
- `adapters/` 不实现业务状态机。
- `projects/<project>/bindings/` 不包含具体 adapter 实现头文件；项目绑定所需接口
  应来自端口、绑定端口或 framework 明确公开的绑定 API。

端口头文件可以引用必要的领域模型类型，但不得引用领域实现头文件。

第三方 SDK provider 属于 framework 对外部资源的适配实现，不代表该 SDK 的运行模型
就是 framework 通用能力。当某个 SDK 实例的生命周期、tick 周期、配置和资源绑定依赖
具体项目时，应由项目层负责实例化和调度；framework provider 只负责协议转换、类型隔离
和必要的线程安全封装。

### 18.6 事件录制与回放

为提升现场问题定位和场景测试能力，后续可补充事件录制与回放工具。

建议能力：

- 记录事件 ID、时间戳、载荷和来源。
- 支持从文件重放命令、安全、报警和流程事件。
- 支持仿真环境加载回放文件。
- 支持对比回放后的状态快照和预期结果。

约束：

- 回放工具不应改变生产运行路径。
- 事件载荷需要稳定的序列化格式。
- 涉及隐私、设备标识或云端凭据的字段应脱敏。

## 19. 总结

本框架采用 DDD 分层和六边形架构组织多项目嵌入式控制软件。

核心结构是：

```text
framework/
  common
  runtime
  services
  domain
  application
  ports
  adapters

projects/
  <project>
```

关键设计取舍是：

- 用 `framework/` 与 `projects/` 分离通用能力和项目资产。
- 用限界上下文组织领域层。
- 用 `ports/inbound` 和 `ports/outbound` 表达系统边界方向。
- 用 `adapters/inbound` 和 `adapters/outbound` 隔离外部世界。
- 用 `runtime/` 管理启动、事件、线程和生命周期。
- 用 `services/` 承载纯软件共享服务。
- 用 `bindings/` 将通用能力连接到具体项目资源。

该设计适合持续扩展不同项目、不同机型、不同硬件平台和不同洗车工艺，同时保持核心控制逻辑稳定可测。
