## 第一阶段详细：需求探索 + 规格生成（OpenSpec）

### 方式一：简单功能（直接 propose）

你只需描述几句话：

```
/opsx:propose 我需要一个 VFD 管理器，管理多个变频器实例，
能监测通信状态，连续几次失败就报警，能复位故障，
挡位和频率控制不能同时用
```

AI 会自动在 `openspec/changes/<name>/` 下生成：
- proposal.md（为什么做、影响范围）
- specs/\<capability\>/spec.md（行为场景 + 不变量 + 状态机 + 时序约束）
- design.md（技术方案）
- tasks.md（实现步骤）

### 方式二：复杂功能（先 explore 再 propose）

如果你还没完全想清楚：

```
/opsx:explore 我想给框架加一个异步 IO 管理器，但不确定该怎么跟现有调度器配合
```

explore 模式下 AI 会：
- 读你的代码，了解现有架构
- 问你澄清问题
- 画架构图，比较方案
- **不写任何代码**

聊清楚后：

```
/opsx:propose async-io-manager
```

### 你审规格的方法（10 分钟）

打开 `openspec/changes/<name>/specs/<capability>/spec.md`，逐条扫描：

| 标记 | 含义 | 你的动作 |
|------|------|----------|
| ✓ | 行为正确 | 不动 |
| ✗ | 行为错误 | 告诉 AI 正确的应该是什么 |
| ? | 遗漏了场景 | 补一句话描述缺失的行为 |

**你不需要关心措辞是否精确**——你只判断行为对不对。措辞和格式由 AI 打磨。

规格中标了 [待确认] 的条目优先看——那是 AI 不确定的地方。

### 迭代修改

规格不满意？直接在同一对话里说：

```
"连续 3 次太少了，改成 5 次"
"漏了一个场景：通信恢复后如果故障码还在，不应该清故障状态"
"状态机缺一个 SELF_CHECK 状态"
```

AI 会更新对应的 spec 文件。OpenSpec 的核心优势就在这里——
**artifact 文件就是上下文**，多轮修改不会丢失，换对话也能继续。

### 审核的关注点

你是领域专家，重点看这些：

- [ ] 时序数字对不对？（3 次失败？200ms 脉冲？2000ms 采样周期？）
- [ ] 故障场景覆盖够不够？（断电？总线冲突？传感器异常？）
- [ ] 不变量完整吗？（什么不能同时发生？什么必须被保护？）
- [ ] 状态机有没有遗漏的转换或死状态？

**核心原则：如果你看到一条场景描述，觉得"这就是设备应该的行为"，就 ✓。
觉得"不对/不够"，就标出来。**

### 这比审代码容易在哪

```
审代码：
  if ((slot->comm_fail_count >= VFD_COMM_FAIL_NOTIFY) && slot->comm_ok) {
      slot->comm_ok = false;
      lost          = true;
  }
  → 你需要理解：这段逻辑正确地实现了"连续 N 次失败后报警"吗？
    需要追踪 comm_fail_count 在哪里加、在哪里清零、有没有竞态...

审规格：
  "连续 3 次 Modbus read 失败 → 上报 COMM_LOST 事件一次"
  → 你只需要判断：3 次对不对？这个行为是我想要的吗？
```

差别是一个数量级的认知负担。

## 第二阶段详细：AI 实现（/opsx:apply）

### 操作步骤

规格审核通过后：

```
/opsx:apply
```

AI 会按 change 目录下的 tasks 逐步实现，并在完成后自动：
1. 输出自证清单（每条 spec 映射到保证它的代码位置）
2. 跑 `./scripts/check_all.sh --skip-tests` 验证架构边界
3. 标注无法被现有测试覆盖的规格条目

### 审自证清单的要点（5 分钟）

- 每条规格都有对应条目？（漏了说明 AI 跳过了）
- "保证机制"是否合理？（"靠调用者保证"= 没有保证）
- 有没有条目指向同一行代码？（一行代码不可能同时保证多条不相关的行为）

## 第三阶段详细：对抗式验证

### 操作步骤

在新对话中执行：

```
/opsx:adversarial <change-name>
```

AI 会自动：
1. 读取 change 的行为规格和公开头文件
2. 以「破坏者」视角生成 ≥10 个攻击性测试用例（覆盖 7 个攻击方向中的 ≥5 个）
3. 输出可编译的 Unity 测试 `.c` 文件到 `tests/<layer>/`
4. 注册到 CMake 并运行 `ctest`
5. 中文汇报结果（通过/失败及暴露的缺陷）

手动模板仍可用（见 `doc/spec/_adversarial.md`），但通常不再需要。

### 为什么建议在新对话中执行

同一对话中的 AI 已经"知道"自己是怎么实现的，会无意识地避开自己代码的弱点。
新对话的 AI 只看到接口和规格，没有实现偏见。

## 第五阶段详细：自动化抽查（门禁规则）

原人工抽查的三类问题已全部纳入 `scripts/check_arch_boundary.sh` 自动检查：

| 抽查类别 | 自动化规则 | 检查方式 |
|----------|-----------|----------|
| 状态机转换 | R21: 快照写接口仅投影可写 | 注册表 + 写入点扫描 |
| 并发保护 | R22: 错误分类判定必须走 helper | AST 级别语句扫描 |
| 硬件时序 | R23: HAL 超时覆盖分类 | 注册表 + 附加验证（文件存在 / SW_ERR_TIMEOUT） |

新增 HAL 文件、新增 s_ 变量写入点、新增状态枚举 switch 站点时，若未在对应注册表
中登记分类，门禁自动 FAIL——开发者必须显式表态后才能通过。

无需人工操作，随 `./scripts/check_all.sh` 自动执行。

## 第六阶段详细：合入与归档

### 提交

```bash
git add src/<module>/ tests/<layer>/test_<feature>*.c openspec/changes/<name>/
git commit -m "[feat]: <中文描述>"
```

### OpenSpec 归档

```
/opsx:archive
```

这会自动：
- 将 spec delta（ADDED/MODIFIED/REMOVED）合入 `openspec/specs/` 主目录
- 将 change 文件夹移到 `openspec/changes/archive/<date>-<name>/`
- `openspec/specs/` 始终反映系统当前行为的完整真相

### 行为契约同步

归档后，人工判断哪些不变量需要提升到框架契约级别：

1. 从归档的 specs 中提取框架级不变量 → 追加到 `doc/contract/行为契约.md`
2. 提取模块内部约束 → 追加到对应 `doc/module-design/` 文件
3. 如果新增了门禁可检查的规则 → 更新 `scripts/check_arch_boundary.sh`

## 时间预算

| 阶段 | 你的时间 | 机器时间 |
|------|----------|----------|
| 写需求描述 | 2 分钟 | 0 |
| 审 AI 生成的规格 | 10 分钟 | AI 生成规格 |
| 审自证清单 | 5 分钟 | AI 实现时间 |
| 对抗测试（/opsx:adversarial） | 2 分钟（审结果） | AI 生成+运行 |
| 自动化验证 | 0 | 构建+测试时间 |
| 自动化抽查（R21-R23） | 0 | 随门禁执行 |
| 合入 | 3 分钟 | 0 |
| **总计** | **~22 分钟** | |

对比逐行审代码：同规模功能通常需要 2-3 小时审核。

**为什么审规格比审代码快**：你作为领域专家，判断"连续 3 次失败后报警"
是否正确只需要 5 秒；但审实现这个行为的 50 行含锁、计数器、状态标志的代码
需要 10 分钟。规格是以你的思维粒度表达的，代码不是。

---

## 何时跳过某阶段

| 情况 | 可跳过 |
|------|--------|
| 纯重构（行为不变） | 跳过第一、三阶段，只跑门禁 |
| 修 bug（已有失败测试） | 跳过第一阶段，从修复开始 |
| 改配置/常量 | 跳过第三、五阶段，只跑门禁 |
| 新增安全相关功能 | 不跳过任何阶段 |
