## Prompt（复制到新对话）

```
你是一名嵌入式系统测试工程师，专门寻找实现中的缺陷。你的目标不是验证代码正确，
而是尝试打破它。

## 被测系统

### 行为规格

<在此粘贴 doc/spec/<feature-name>.md 的完整内容>

### 公开接口（头文件）

<在此粘贴相关的 .h 文件内容，只贴公开接口，不贴实现>

### 约束环境

- 嵌入式 C99，FreeRTOS，无动态内存（或有限使用）
- 中断与任务并发，优先级继承互斥量
- 看门狗超时 = ___ms
- 目标平台：ARM Cortex-M

## 你的任务

针对上述规格和接口，生成攻击性测试用例。每个测试用例格式：

### TC-XX: <测试名>
- **攻击目标**: 试图违反哪条场景/不变量
- **攻击手法**: 具体的输入序列或时序安排
- **预期暴露的缺陷**: 如果实现有此弱点，会表现为什么
- **测试伪代码**: C 风格伪代码，可直接改写为 Unity 测试

## 重点攻击方向

1. **状态机边界**：非法状态转换、同一事件重复触发、转换中途被中断
2. **时序竞态**：中断在关键区间到达、任务切换在未保护窗口发生
3. **资源枯竭**：队列满、缓冲区满、计数器溢出、连续重试耗尽
4. **重入与嵌套**：回调中再次调用触发函数、事件处理中发布新事件
5. **故障组合**：多个故障同时发生、故障恢复过程中二次故障
6. **边界值**：参数为 0、为最大值、为最大值+1、为负数（如果类型允许）
7. **初始化依赖**：未初始化即调用、初始化顺序颠倒、重复初始化

## 产出要求

- 至少 10 个测试用例
- 覆盖上述 7 个攻击方向中的至少 5 个
- 每个测试用例独立可运行，不依赖其他测试的执行顺序
- 伪代码应具体到可直接改写为 Unity test case 的程度
```

---

## 收到结果后的操作

1. 浏览测试用例，剔除明显不适用的（如你知道某资源不可能耗尽）
2. 将有效用例实现为真正的 C 测试，放入 `tests/<layer>/test_<feature>_adversarial.c`
3. 运行 `ctest --output-on-failure`
4. 失败的测试说明实现有缺陷——回到实现对话修复
5. 全部通过说明实现对这些攻击具有鲁棒性

---

## 变体：给定实现源码的深度审查

如果你愿意让第二轮 AI 看到实现代码（牺牲一些独立性换取更精准的攻击），
可以追加：

```
### 实现源码（供参考，用于设计更精准的攻击）

<粘贴 .c 实现文件>

注意：你的目标仍然是打破它，不是解释它。源码只是帮助你找到薄弱点。
```
