# 洗车机通用控制引擎规格说明

版本：1.0  
适用范围：各类洗车机控制系统

---

## 1. 概述

### 1.1 设计目标

本文档定义一套**通用控制引擎模型**，通过加载配置文件驱动洗车机各机构动作，实现：

- 程序固定不变，修改洗车流程只需修改配置文件
- 同一套引擎支持不同机械结构的洗车机，无需为每种机型单独开发控制程序
- 配置文件能够清晰、完整地表达动作序列、约束条件与错误策略

### 1.2 适用场景

本引擎适用于满足以下特征的洗车机控制需求：

**多阶段串行执行**  
洗车流程由若干阶段组成，阶段间严格按顺序执行（如归位、去程刷洗、回程刷洗、吹风）。每个阶段有明确的进入条件和退出条件。

**多机构并行控制**  
同一阶段内，多个机构（水泵、刷具、水阀、风机等）各自独立地根据传感器信号或位置条件启停，互不阻塞。

**通用位置建模**
控制引擎不按“龙门式 / 隧道式”等机型进入不同分支，而是按配置声明的位置来源、事件和表达式统一调度。

| 抽象 | 作用 | 典型用途 |
|---|---|---|
| **物理轴**（physical axis） | 直接读取编码器并换算为工程单位 | 龙门位置、输送带位置、升降机构位置 |
| **追踪轴**（tracked axis） | 某事件后沿物理轴累计位移，并维护有效性 | 入口光电触发后推算车头 / 车尾当前位置 |
| **锁存标记**（latched marker） | 某事件发生瞬间记录指定轴当前位置 | 龙门移动扫描时记录车头 / 车尾坐标 |
| **派生位置**（derived） | 通过表达式组合轴、标记和信号 | 相对位置、车身覆盖区间、工艺坐标 |

不同机械结构的差异应体现在配置文件中：配置声明有哪些轴、哪些传感器事件、事件如何生成车辆位置或工艺坐标；引擎只执行这些通用抽象。

**轮廓自适应控制**  
扫描阶段采集车辆外形数据（高度、分区），后续阶段可根据轮廓数据动态调整机构动作。在数据尚不可用时，配置可指定默认行为，实现自动降级。

**安全联锁独立管理**  
急停、防撞等安全条件独立于业务步骤，由引擎以最高优先级持续监控，任何阶段均有效。

### 1.3 核心概念一览

```
Program（方案）
  ├── 坐标轴定义（axes）
  ├── 位置标记定义（markers）
  ├── 联锁层（interlocks）
  ├── 模板库（templates）
  └── 阶段列表（phases）[有序]
        └── Phase（阶段）
              └── Lane（通道）[并行]
                    └── Step（步骤）[各自独立触发]
                          ├── event 型：触发一次，执行动作列表
                          └── control 型：持续激活，实时映射输出
```

## 2. 硬件映射层

### 2.1 分层原则

硬件映射分为两层，各司其职：

| 层次 | 载体 | 内容 |
|---|---|---|
| **硬件层**（C 代码） | 项目自定义的 IO 注册实现 | IO 通道号、信号去抖滤波、编码器计数、RS485 驱动 |
| **配置层**（YAML） | 方案配置文件 | 坐标轴类型与业务参数；表达式与动作直接引用硬件层注册的枚举名 |

配置文件中**不出现**通道号（`DI_04`）或设备地址（`0x01`）。引擎启动时由硬件层批量注册所有 IO 枚举名，使其在表达式中可直接引用。硬件层的具体实现方式（文件名、注册机制）由各项目自行决定，只要在引擎初始化前完成注册即可。

### 2.2 坐标轴（axes）

坐标轴抽象连续变化的位置数据，支持三种类型。`encoder` 字段引用硬件层已注册的编码器枚举名；`driven_by` 字段引用同一配置中已定义的物理轴 ID。

#### 2.2.1 物理轴（physical）

直接读取编码器原始脉冲并换算为工程单位。适用于可直接测量位置的运动源，例如龙门编码器、输送带编码器或升降机构编码器。

```yaml
axes:
  gantry:
    type: physical
    encoder: GANTRY_ENCODER_PULSE   # 引用硬件层注册的编码器枚举名
    unit: mm
    pulse_per_mm: 10.5              # 脉冲换算系数（机械参数）
    direction: 1                    # 1=正向，-1=反向（可选，默认 1）
```

#### 2.2.2 追踪轴（tracked）

记录某个事件触发后物理轴的累计增量。引擎在 `zero_on` 事件发生时将该轴清零，此后跟随 `driven_by` 指向的物理轴累计工程位移，追踪轴有一个 `valid` 标志，清零前值为无效。

适用于目标位置无法直接测量、需要通过事件和某个物理轴增量推算的场景。典型例子是入口光电触发后，用输送带轴推算车头 / 车尾当前位置：

```yaml
axes:
  conveyor:
    type: physical
    encoder: CONVEYOR_ENCODER_PULSE
    unit: mm
    pulse_per_mm: 8.0

  car_front:
    type: tracked
    driven_by: conveyor                 # 跟随哪个物理轴累计
    zero_on:                            # 清零触发事件：车头遮断入口光电
      signal: ENTRY_BEAM
      edge: falling
    valid_after: zero_on

  car_rear:
    type: tracked
    driven_by: conveyor
    zero_on:                            # 清零触发事件：车尾离开入口光电
      signal: ENTRY_BEAM
      edge: rising
    valid_after: zero_on
```

追踪轴属性：

| 属性 | 说明 |
|---|---|
| `axes.<id>.position` | 当前累计位置，单位继承 `driven_by` 指向的物理轴 |
| `axes.<id>.valid` | 是否已完成首次清零 |

#### 2.2.3 派生轴（derived）

由表达式从其他轴或信号计算得出。

```yaml
axes:
  car_speed:
    type: derived
    expr: "axes.conveyor.speed * $speed_ratio"
```

### 2.3 位置标记（markers）

位置标记用于记录离散事件对应的位置点。它不是连续变化的轴，而是在事件触发时锁存某个轴的当前位置，并提供 `position` / `valid` 给表达式使用。

#### 2.3.1 锁存标记（latch）

`latch` 在 `on` 事件发生时读取指定 `axis` 的当前位置并保存。适用于龙门移动扫描车辆时，通过龙门架对射光电捕获车头和车尾坐标：

```yaml
markers:
  car_front:
    type: latch
    axis: gantry
    on: {signal: GANTRY_BEAM, edge: falling}

  car_rear:
    type: latch
    axis: gantry
    on: {signal: GANTRY_BEAM, edge: rising}
```

锁存标记属性：

| 属性 | 说明 |
|---|---|
| `markers.<id>.position` | 事件触发瞬间锁存的轴位置（mm） |
| `markers.<id>.valid` | 是否已经完成首次锁存 |

锁存行为规则：

- 标记在**首次锁存后，后续同一触发事件不再更新** `position`（写一次保护），防止多趟往返时标记被反向行程覆盖
- 程序（Program）实例启动时，所有标记自动清零（`position = 0`，`valid = false`）
- 如需在程序运行中显式重置，使用 `reset_marker` 动作原语（见第 6.5 节）

#### 2.3.2 标记与追踪轴的选择原则

| 场景 | 建议抽象 |
|---|---|
| 事件发生时只需要记录一个坐标点，之后该点不随时间变化 | `marker: latch` |
| 事件发生后目标继续相对机构移动，需要持续更新当前位置 | `axis: tracked` |
| 位置可由编码器直接读取 | `axis: physical` |
| 位置由其他轴、标记、参数组合计算 | `axis: derived` 或表达式函数 |

### 2.4 IO 枚举名使用规则

- **DI 信号**：在表达式中以枚举名作为布尔/整数值直接引用，如 `ESTOP == 1`、`GANTRY_FWD_LIMIT == 1`
- **DO 输出**：在动作原语的 `channel` 字段中直接填写枚举名，如 `GANTRY_FWD`、`SIDE_BRUSH_FWD`
- 枚举名由各项目的硬件层在引擎初始化时注册，具体命名和实现方式由项目自行决定

## 3. 联锁层（interlocks）

联锁条件独立于业务步骤，由引擎在最高优先级持续监控。联锁触发时直接执行对应动作，不受当前阶段或步骤状态影响。

```yaml
interlocks:
  - id: estop
    condition: "ESTOP == 1"
    action: halt_all
    priority: 0               # 数值越小优先级越高
    reset_condition: "ESTOP == 0"
    auto_reset: false         # false=需手动确认复位；true=条件消除自动恢复

  - id: bumper_hit
    condition: "BUMPER_LEFT == 1 OR BUMPER_RIGHT == 1"
    action: halt_all
    priority: 1
    reset_condition: "BUMPER_LEFT == 0 AND BUMPER_RIGHT == 0"
    auto_reset: false

  - id: top_brush_overload
    condition: "TOP_BRUSH_OVERLOAD == 1"
    action: halt_phase
    priority: 2
    reset_condition: "TOP_BRUSH_OVERLOAD == 0"
    auto_reset: true
```

联锁动作类型：

| 动作 | 说明 |
|---|---|
| `halt_all` | 立即停止所有执行器，程序终止，**不执行** `on_exit` |
| `halt_phase` | 停止当前阶段，执行 `on_exit`，等待恢复指令 |
| `custom_action` | 执行指定动作列表（见第 6 节） |

## 4. 模板库（templates）

模板定义可复用的步骤结构，在 Lane 中通过 `use` 引用并实例化。

### 4.1 字段优先级规则

实例上直接写的字段**优先于**模板定义，无需额外包装。优先级从高到低：

1. 实例自身字段（直接写在步骤上）
2. 模板定义字段

`output` 字段在实例上必须填写，模板中不定义。

```yaml
templates:
  # 示例：适用于已测车身区间的侧刷避让控制
  side_brush_avoidance:
    type: control
    active_while: "body_contains(axes.gantry.position, markers.car_front, markers.car_rear)"
    value_expr: >
      profile.in_zone('mirror', axes.gantry.position, default=false) ? 0 : 1

  # 示例：适用于追踪轴车身覆盖判断的通用机构激活模板
  tunnel_ctrl:
    type: control
    value_expr: "1"
```

### 4.2 引用示例

```yaml
steps:
  # 完整继承模板，只绑定执行器
  - id: brush_left_ctrl
    use: side_brush_avoidance
    output: SIDE_BRUSH_FWD
    on_error: degrade             # 模板中没有此字段，直接追加

  # 覆盖 value_expr，其余继承模板
  - id: brush_right_ctrl
    use: side_brush_avoidance
    output: SIDE_BRUSH_FWD
    value_expr: >                 # 直接写即覆盖
      profile.in_zone('mirror_right', axes.gantry.position, default=false) ? 0 : 1
    on_error: degrade

  # 覆盖 active_while，value_expr 继承
  - id: foam_ctrl
    use: tunnel_ctrl
    active_while: "body_covers($foam_pos, axes.car_front, axes.car_rear)"
    output: FOAM_VALVE
```

## 5. 阶段（Phase）

阶段是一个并行通道的集合，阶段之间按列表顺序串行执行。

```yaml
phases:
  - id: pass2_main_wash
    name: 第二趟-主刷
    direction: backward           # 仅对有方向概念的阶段有意义，无方向流程填 none
    entry_guard: "axes.gantry.position >= $gantry_length - 50"
    exit_guard:  "axes.gantry.position <= 50"
    timeout_ms: 90000
    on_timeout: halt_phase
    on_enter:                     # 进入阶段后、步骤开始前执行一次（可选）
      - io_set: {channel: WATER_BRUSH, value: 1}
    on_exit:                      # 阶段结束时执行（正常退出和 halt_phase 均触发，可选）
      - io_set: {channel: GANTRY_FWD,     value: 0}
      - io_set: {channel: GANTRY_REV,     value: 0}
      - io_set: {channel: SIDE_BRUSH_FWD, value: 0}
      - io_set: {channel: WATER_BRUSH,    value: 0}
    lanes: [...]
```

### 5.1 Phase 字段说明

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一标识 |
| `direction` | enum | `forward` / `backward` / `none`，表达当前阶段的工艺行进方向语义 |
| `entry_guard` | Expression | 前一阶段退出后，满足此条件才进入本阶段 |
| `exit_guard` | Expression | 持续求值，满足后本阶段结束 |
| `timeout_ms` | int | 阶段超时时间 |
| `on_timeout` | ErrorStrategy | 超时策略（见第 6.6 节） |
| `on_enter` | Action[] | 进入阶段时执行一次的动作列表（可选） |
| `on_exit` | Action[] | 阶段结束时执行的动作列表，正常退出和 `halt_phase` 均触发，`halt_all` 不触发（可选） |
| `lanes` | Lane[] | 并行通道列表 |

### 5.2 Phase 退出规则

当 `exit_guard` 满足、超时或 `halt_phase` 联锁触发时，引擎按以下顺序执行：

1. 停止该阶段所有 `control` 步骤的输出（置 0）
2. 执行 `on_exit` 动作列表
3. 进入下一阶段（或等待恢复）

`event` 步骤通过 `actions` 已置位的 DO，引擎**不自动复位**，需在 `on_exit` 中显式清零。

### 5.3 归位阶段

方案配置文件通常将第一个 Phase 设为归位阶段，确保洗车开始前机构处于已知状态。归位阶段的 `entry_guard` 设为 `"true"`（立即进入），`exit_guard` 设为所有归位到位条件的组合。

## 6. 通道与步骤（Lane / Step）

### 6.1 通道（Lane）

通道将同一机构的所有步骤组织在一起，通道之间并行运行。

```yaml
lanes:
  - id: brush_left_lane
    steps: [...]
```

### 6.2 步骤：事件型（event）

触发一次，执行动作列表，等待完成条件。

```yaml
- id: retract_top_brush
  type: event
  trigger:                        # 激活触发器
    type: signal
    signal: TOP_BRUSH_PRESSURE_HIGH
    edge: rising
  guard: "axes.gantry.position > 100"   # 可选守卫，触发后再判断
  actions:
    - io_set: {channel: TOP_BRUSH_ACT, value: 0}
    - wait_signal: {signal: LIFT_UP_LIMIT, state: 1, timeout_ms: 5000}
  done:
    type: signal
    signal: LIFT_UP_LIMIT
    state: 1
  on_error: halt_phase
  after: [stop_side_brush]        # 可选：等待指定步骤完成后才开始监听触发器
```

触发器类型：

| 类型 | 字段 | 说明 |
|---|---|---|
| `position` | `axis`, `range: [start, end]` | 编码器进入指定范围 |
| `signal` | `signal`, `edge: rising/falling/high/low` | 信号边沿或电平 |
| `condition` | `expr: Expression` | 通用布尔表达式触发 |

`position` 触发器仅适用于 `physical` 和 `tracked` 轴。`markers.<id>` 是事件锁存值，不是实时变化的位置源；如需基于标记值触发，使用 `condition` 触发器配合表达式。

完成条件类型：

| 类型 | 说明 |
|---|---|
| `trigger_exit` | 触发器条件失活时完成 |
| `signal` | 等待指定信号达到目标状态 |
| `timeout` | 经过指定时长后完成 |
| `actions_complete` | 动作列表全部执行完毕 |

### 6.3 `after` 字段语义

`after: [step_id, ...]` 指定前置步骤，完整规则如下：

| 问题 | 规则 |
|---|---|
| 作用范围 | 被引用步骤必须在**同一阶段内**，可以在不同通道 |
| 前置步骤从未激活 | 当前步骤同样不激活（前置触发器未触发视为前置未完成） |
| 前置步骤出错 | 若前置步骤 `on_error` 为 `halt_phase`/`stop`，当前步骤随之停止；若为 `skip`/`degrade`，当前步骤正常启动 |
| 多个前置步骤 | 所有前置步骤均完成后，当前步骤才开始监听触发器 |

### 6.4 步骤：控制型（control）

持续激活期间实时求值，将结果输出到执行器。适用于需要随传感器或位置变化连续控制输出的场景。

```yaml
- id: top_brush_follow
  type: control
  active_while: "TOP_BRUSH_CONTACT == 1 AND LIFT_UP_LIMIT == 0"
  output: TOP_BRUSH_ACT
  value_expr: >
    TOP_BRUSH_OVERLOAD == 1 ? 0 : 1
  on_error: halt_phase
```

### 6.5 动作原语（Action）

事件型步骤的 `actions` 列表以及 `on_enter` / `on_exit` 均由以下原语组成：

| 原语 | 参数 | 说明 |
|---|---|---|
| `io_set` | `channel`（DO 枚举名）, `value` | 设置数字量输出 |
| `io_pwm` | `channel`, `duty`, `duration_ms` | PWM 输出 |
| `rs485_cmd` | `device_id`, `cmd`, `params` | 485 指令 |
| `move_to` | `axis`, `position`, `speed` | 驱动轴到指定位置 |
| `set_speed` | `axis`, `speed` | 设置轴速度 |
| `wait_time` | `ms` | 等待指定时间 |
| `wait_signal` | `signal`（DI 枚举名）, `state`, `timeout_ms` | 等待信号，超时报错 |
| `reset_marker` | `marker`（标记名） | 将指定标记清零（position = 0，valid = false），使其可重新锁存 |

`move_to` 和 `set_speed` 仅适用于可被执行器驱动的 `physical` 轴。`tracked` / `derived` 轴以及 `markers.<id>` 是计算或锁存得到的位置引用，只能用于表达式读取，不能作为运动控制目标。

### 6.6 错误策略（ErrorStrategy）

| 策略 | 说明 |
|---|---|
| `stop` | 急停整机，程序终止 |
| `halt_phase` | 停止当前阶段，执行 `on_exit`，等待恢复指令 |
| `skip` | 跳过当前步骤，继续后续步骤 |
| `degrade` | 执行降级动作后继续 |

## 7. 表达式语言

配置文件中 `guard`、`active_while`、`entry_guard`、`exit_guard`、`value_expr`、`condition` 等字段均为表达式，由引擎运行时求值。

### 7.1 运算符

| 类别 | 运算符 |
|---|---|
| 算术 | `+` `-` `*` `/` |
| 比较 | `>` `<` `>=` `<=` `==` `!=` |
| 逻辑 | `AND` `OR` `NOT` |
| 三目 | `condition ? true_val : false_val` |

### 7.2 可引用上下文

```
$param_name                               方案级全局参数
<ENUM_NAME>                               DI 信号实时值（硬件层注册的枚举名，示例：ESTOP、WATER_PRESSURE_OK）
axes.<id>.position                        编码器当前位置
axes.<id>.speed                           编码器当前速度
axes.<id>.valid                           轴位置是否有效（追踪轴清零前为 false；物理轴通常为 true）
markers.<id>.position                     标记锁存的位置
markers.<id>.valid                        标记是否已经完成首次锁存
phase.elapsed_ms                          当前阶段已运行时间
phase.direction                           当前阶段行进方向
```

### 7.3 轮廓查询函数

轮廓数据在扫描阶段由引擎自动构建，后续阶段可通过以下函数查询。所有函数均支持 `default` 参数，在数据尚不可用时返回默认值，实现同一配置在有无轮廓数据时均能正常运行。

| 函数 | 说明 | 可用时机 |
|---|---|---|
| `profile.current_height` | 当前检测高度（实时） | 始终 |
| `profile.height_at(pos, default=0)` | 指定位置高度 | 机构扫过该位置后 |
| `profile.in_zone(name, pos, default=false)` | 是否在命名分区内 | 扫描阶段结束后 |
| `profile.zone_start(name)` | 分区起始位置 | 扫描阶段结束后 |
| `profile.zone_end(name)` | 分区结束位置 | 扫描阶段结束后 |
| `profile.car_length` | 车身长度 | 扫描阶段结束后 |
| `profile.zones_ready` | 分区计算是否完成（布尔） | 扫描阶段结束后 |

内建分区名称（由引擎根据轮廓自动识别）：

| 分区名 | 说明 |
|---|---|
| `roof` | 车顶区域 |
| `windshield_front` | 前挡风玻璃 |
| `windshield_rear` | 后挡风玻璃 |
| `mirror_left` | 左后视镜 |
| `mirror_right` | 右后视镜 |
| `trunk` | 车尾行李舱区域 |
| `hood` | 引擎盖区域 |

### 7.4 通用位置函数与内建宏

当车体与设备存在相对运动时，常见判断可以分为两类：判断某个当前位置是否落在已测得的车身区间内，或判断持续移动的车身是否覆盖某个固定机构位置。引擎内建以下函数 / 宏简化表达：

`front` / `rear` 参数为位置引用对象，必须提供 `.position` 和 `.valid`，可传入 `axes.<id>`（如追踪轴）或 `markers.<id>`（如锁存标记）。位置参数 `pos` / `P` 为数值。

| 函数 / 宏 | 展开式 | 前提条件 | 含义 |
|---|---|---|---|
| `body_span_ready(front, rear)` | `front.valid AND rear.valid` | 无方向要求 | 车头 / 车尾两个位置是否都已获得 |
| `body_contains(pos, front, rear)` | `body_span_ready(front, rear) AND min(front.position, rear.position) <= pos AND pos <= max(front.position, rear.position)` | 无方向要求 | 位置 pos 是否位于已测车身区间内 |
| `body_front_at(P, front)` | `front.valid AND front.position >= P` | `front.position` 沿运动方向单调递增 | 车头位置是否已到达 / 经过 P |
| `body_rear_at(P, rear)` | `rear.valid AND rear.position >= P` | `rear.position` 沿运动方向单调递增 | 车尾位置是否已到达 / 经过 P |
| `body_covers(P, front, rear)` | `body_front_at(P, front) AND NOT body_rear_at(P, rear)` | `front.position` 和 `rear.position` 沿运动方向单调递增 | 持续移动的车身当前是否覆盖固定位置 P |

如果实际编码器方向相反，应先通过轴 `direction` 或派生轴统一为递增工艺坐标。`body_covers` 主要用于 `tracked` 轴这类持续变化的位置引用；锁存标记形成的静态车身区间应使用 `body_contains(pos, front, rear)`。`rear.valid == false` 时表示车尾尚未被观测到，`body_covers` 会按车尾尚未经过位置 P 处理。

示例：

```yaml
# 龙门移动扫描：当前龙门位置是否位于已锁存的车头 / 车尾之间
active_while: "body_contains(axes.gantry.position, markers.car_front, markers.car_rear)"

# 隧道单向通过：车身是否覆盖固定泡沫机构位置
active_while: "body_covers($foam_pos, axes.car_front, axes.car_rear)"
```

## 9. 完整配置示例

以下两个示例分别演示移动机构扫描车辆、输送带推动车辆通过固定机构两种配置方式。两者都使用同一套位置源、事件、标记和表达式抽象。

### 9.1 示例一：机构往返移动（龙门式洗车机，三趟精洗）

龙门带动刷具往返，车辆静止。龙门位置由编码器直接读取；洗车过程中，龙门架对射光电在遮挡 / 释放瞬间锁存车头和车尾坐标，后续阶段基于实测车身区间控制刷具、水阀和风机。

本示例同时使用两类条件：`WATER_PRESSURE_OK`、`TOP_BRUSH_CONTACT`、`AIR_PRESSURE_OK` 表示设备状态或工艺条件传感器的实时状态，适合水阀、顶刷、风机等只依赖当前检测状态的动作；`body_contains(...)` 表示当前龙门位置位于已锁存的车头 / 车尾区间内，适合侧刷避让、分区控制等依赖车身坐标的动作。

```yaml
program:
  schema_version: "1.0"
  id: gantry_premium_3pass
  name: 龙门精洗三趟

  params:
    gantry_length: 2000           # mm，行程总长

  axes:
    gantry:
      type: physical
      encoder: GANTRY_ENCODER_PULSE
      unit: mm
      pulse_per_mm: 10.5

  markers:
    car_front:
      type: latch
      axis: gantry
      on: {signal: GANTRY_BEAM, edge: falling}

    car_rear:
      type: latch
      axis: gantry
      on: {signal: GANTRY_BEAM, edge: rising}

  interlocks:
    - id: estop
      condition: "ESTOP == 1"
      action: halt_all
      priority: 0
      reset_condition: "ESTOP == 0"
      auto_reset: false

    - id: bumper_hit
      condition: "BUMPER_LEFT == 1 OR BUMPER_RIGHT == 1"
      action: halt_all
      priority: 1
      reset_condition: "BUMPER_LEFT == 0 AND BUMPER_RIGHT == 0"
      auto_reset: false

    - id: top_brush_collision
      condition: "TOP_BRUSH_COLLISION == 1"
      action: halt_phase
      priority: 2
      reset_condition: "TOP_BRUSH_COLLISION == 0"
      auto_reset: true

  templates:
    side_brush_avoidance:
      type: control
      active_while: "body_contains(axes.gantry.position, markers.car_front, markers.car_rear)"
      value_expr: >
        profile.in_zone('mirror', axes.gantry.position, default=false) ? 0 : 1

  phases:

    # ── 归位：龙门回后限位，顶刷升起 ────────────────────────────────────
    - id: homing
      name: 归位
      direction: none
      entry_guard: "true"
      exit_guard: "GANTRY_REV_LIMIT == 1 AND LIFT_UP_LIMIT == 1"
      timeout_ms: 30000
      on_timeout: halt_phase
      on_enter:
        - reset_marker: {marker: car_front}
        - reset_marker: {marker: car_rear}
      on_exit:
        - io_set: {channel: GANTRY_REV, value: 0}

      lanes:
        - id: gantry_home_lane
          steps:
            - id: gantry_to_home
              type: event
              trigger: {type: condition, expr: "GANTRY_REV_LIMIT == 0"}
              actions:
                - io_set: {channel: GANTRY_FWD, value: 0}
                - io_set: {channel: GANTRY_REV, value: 1}
              done: {type: signal, signal: GANTRY_REV_LIMIT, state: 1}
              on_error: halt_phase

        - id: top_brush_home_lane
          steps:
            - id: top_brush_to_up
              type: event
              trigger: {type: condition, expr: "LIFT_UP_LIMIT == 0"}
              actions:
                - io_set: {channel: TOP_BRUSH_ACT, value: 1}
              done: {type: signal, signal: LIFT_UP_LIMIT, state: 1, timeout_ms: 10000}
              on_error: halt_phase

    # ── 第一趟：去程，喷泡沫 + 顶刷扫描轮廓 ──────────────────────────────
    - id: pass1_foam_scan
      name: 第一趟-泡沫扫描
      direction: forward
      entry_guard: "axes.gantry.position <= 50"
      exit_guard: >
        axes.gantry.position >= $gantry_length - 50 AND
        body_span_ready(markers.car_front, markers.car_rear)
      timeout_ms: 90000
      on_timeout: halt_phase
      on_exit:
        - io_set: {channel: GANTRY_FWD, value: 0}
        - io_set: {channel: WATER_FOAM, value: 0}

      lanes:
        - id: gantry_lane
          steps:
            - id: gantry_forward
              type: event
              trigger: {type: condition, expr: "true"}
              actions:
                - io_set: {channel: GANTRY_HIGH_SPEED, value: 0}
                - io_set: {channel: GANTRY_REV,        value: 0}
                - io_set: {channel: GANTRY_FWD,        value: 1}
              done: {type: trigger_exit}
              on_error: halt_phase

        - id: foam_lane
          steps:
            - id: foam_on
              type: control
              active_while: "WATER_PRESSURE_OK == 1"
              output: WATER_FOAM
              value_expr: "1"

        - id: top_brush_lane
          steps:
            - id: top_brush_follow_pass1
              type: control
              active_while: "TOP_BRUSH_CONTACT == 1 AND LIFT_UP_LIMIT == 0"
              output: TOP_BRUSH_ACT
              value_expr: >
                TOP_BRUSH_OVERLOAD == 1 ? 0 : 1
              on_error: halt_phase

    # ── 第二趟：回程，主刷洗车（轮廓已完成，启用分区避让） ───────────────
    - id: pass2_main_wash
      name: 第二趟-主刷
      direction: backward
      entry_guard: "axes.gantry.position >= $gantry_length - 50"
      exit_guard:  "axes.gantry.position <= 50"
      timeout_ms: 90000
      on_timeout: halt_phase
      on_enter:
        - io_set: {channel: WATER_BRUSH, value: 1}
      on_exit:
        - io_set: {channel: GANTRY_REV,     value: 0}
        - io_set: {channel: SIDE_BRUSH_FWD, value: 0}
        - io_set: {channel: WATER_BRUSH,    value: 0}

      lanes:
        - id: gantry_lane
          steps:
            - id: gantry_backward
              type: event
              trigger: {type: condition, expr: "true"}
              actions:
                - io_set: {channel: GANTRY_HIGH_SPEED, value: 0}
                - io_set: {channel: GANTRY_FWD,        value: 0}
                - io_set: {channel: GANTRY_REV,        value: 1}
              done: {type: trigger_exit}
              on_error: halt_phase

        - id: brush_left_lane
          steps:
            - id: brush_left_ctrl
              use: side_brush_avoidance
              output: SIDE_BRUSH_FWD
              on_error: degrade

        - id: top_brush_lane
          steps:
            - id: top_brush_follow_pass2
              type: control
              active_while: "TOP_BRUSH_CONTACT == 1 AND LIFT_UP_LIMIT == 0"
              output: TOP_BRUSH_ACT
              value_expr: >
                TOP_BRUSH_OVERLOAD == 1 ? 0 : 1
              on_error: halt_phase

    # ── 第三趟：去程，高压冲洗 + 吹风（挡风玻璃处减速） ─────────────────
    - id: pass3_dry
      name: 第三趟-冲洗吹风
      direction: forward
      entry_guard: "axes.gantry.position <= 50"
      exit_guard:  "axes.gantry.position >= $gantry_length - 50"
      timeout_ms: 90000
      on_timeout: halt_phase
      on_exit:
        - io_set: {channel: GANTRY_FWD,     value: 0}
        - io_set: {channel: WATER_HIGHPRES,  value: 0}
        - io_set: {channel: FAN_START,       value: 0}

      lanes:
        - id: gantry_lane
          steps:
            # 挡风玻璃区域低速（不置位 HIGH_SPEED），其余高速
            - id: gantry_dry_speed
              type: control
              active_while: "true"
              output: GANTRY_HIGH_SPEED
              value_expr: >
                profile.in_zone('windshield_front', axes.gantry.position, default=false) OR
                profile.in_zone('windshield_rear',  axes.gantry.position, default=false)
                ? 0 : 1

            - id: gantry_dry_fwd
              type: event
              trigger: {type: condition, expr: "true"}
              actions:
                - io_set: {channel: GANTRY_REV, value: 0}
                - io_set: {channel: GANTRY_FWD, value: 1}
              done: {type: trigger_exit}
              on_error: halt_phase

        - id: highpres_lane
          steps:
            - id: highpres_ctrl
              type: control
              active_while: "WATER_PRESSURE_OK == 1"
              output: WATER_HIGHPRES
              value_expr: "1"

        - id: fan_lane
          steps:
            - id: fan_ctrl
              type: control
              active_while: "AIR_PRESSURE_OK == 1"
              output: FAN_START
              value_expr: "1"
```

### 9.2 示例二：车辆单向通过（隧道式洗车机，标准洗）

车辆随输送带匀速通过固定机构。车体位置由入口光电事件配合输送带编码器推算，单一阶段覆盖全程。

```yaml
program:
  schema_version: "1.0"
  id: tunnel_standard
  name: 隧道标准洗

  params:
    foam_pos:    200          # mm，各机构距入口光电的距离
    brush_pos:   500
    rinse_pos:  1200
    blower_pos: 1800

  axes:
    conveyor:
      type: physical
      encoder: CONVEYOR_ENCODER_PULSE
      unit: mm
      pulse_per_mm: 8.0
    car_front:
      type: tracked
      driven_by: conveyor
      zero_on: {signal: ENTRY_BEAM, edge: falling}
      valid_after: zero_on
    car_rear:
      type: tracked
      driven_by: conveyor
      zero_on: {signal: ENTRY_BEAM, edge: rising}
      valid_after: zero_on

  interlocks:
    - id: estop
      condition: "ESTOP == 1"
      action: halt_all
      priority: 0
      reset_condition: "ESTOP == 0"
      auto_reset: false

  templates:
    tunnel_ctrl:
      type: control
      value_expr: "1"

  phases:
    - id: wash
      name: 洗车
      direction: none
      entry_guard: "axes.car_front.valid"
      exit_guard: "axes.car_rear.valid AND axes.car_rear.position >= $blower_pos + 600"
      timeout_ms: 300000
      on_timeout: halt_phase
      on_exit:
        - io_set: {channel: FOAM_VALVE,      value: 0}
        - io_set: {channel: BRUSH_LEFT_FWD,  value: 0}
        - io_set: {channel: BRUSH_RIGHT_FWD, value: 0}
        - io_set: {channel: RINSE_VALVE,     value: 0}
        - io_set: {channel: BLOWER_START,    value: 0}

      lanes:
        - id: foam_lane
          steps:
            - id: foam_ctrl
              use: tunnel_ctrl
              active_while: "body_covers($foam_pos, axes.car_front, axes.car_rear)"
              output: FOAM_VALVE

        - id: brush_left_lane
          steps:
            - id: brush_left_ctrl
              use: tunnel_ctrl
              active_while: "body_covers($brush_pos, axes.car_front, axes.car_rear)"
              output: BRUSH_LEFT_FWD
              on_error: degrade

        - id: brush_right_lane
          steps:
            - id: brush_right_ctrl
              use: tunnel_ctrl
              active_while: "body_covers($brush_pos, axes.car_front, axes.car_rear)"
              output: BRUSH_RIGHT_FWD
              on_error: degrade

        - id: rinse_lane
          steps:
            - id: rinse_ctrl
              use: tunnel_ctrl
              active_while: "body_covers($rinse_pos, axes.car_front, axes.car_rear)"
              output: RINSE_VALVE

        - id: blower_lane
          steps:
            - id: blower_ctrl
              use: tunnel_ctrl
              active_while: "body_covers($blower_pos, axes.car_front, axes.car_rear)"
              output: BLOWER_START
```

## 10. 引擎实现职责边界

配置文件声明"做什么"，引擎负责"怎么做"。以下逻辑固化在引擎中，不通过配置暴露：

| 引擎职责 | 说明 |
|---|---|
| IO 通道注册 | 启动时由硬件层批量注册所有 DI/DO 枚举名，使配置可引用；注册实现由项目自定义 |
| 信号去抖滤波 | 由硬件层处理，不在 YAML 中配置 |
| 联锁监控 | 最高优先级，独立于阶段/步骤循环 |
| 轮廓构建 | 传感器采样 → 高度记录 → 分区识别算法 |
| 追踪轴管理 | 监听 `zero_on` 事件，维护各追踪轴的 position / valid |
| 标记管理 | 监听 `markers.<id>.on` 事件，锁存指定轴的位置并维护 valid |
| 表达式求值 | 运行时解析和求值配置中所有 Expression 字段 |
| 步骤调度 | 并行通道管理，独立触发器监控，`after` 依赖检查 |
| Phase 退出处理 | 停止 control 步骤输出，执行 `on_exit` 动作列表 |
| 错误处理 | 按 `on_error` 策略执行，记录诊断日志 |
| 超时监控 | 对每个 Phase 和 `wait_signal` 动作维护独立计时器 |
| schema 校验 | 加载时验证 `schema_version` 与解析规则兼容 |

以下行为由配置文件决定，引擎不硬编码：

- 各阶段的进入/退出条件及进退场动作
- 各机构的激活时机和约束条件
- 错误降级策略
- 轮廓分区的查询与使用方式
- 方案参数（速度、位置等）
- 位置来源、事件锁存、追踪轴和派生坐标的组合方式

引擎不得硬编码“龙门式 / 隧道式”等机型分支；同一调度逻辑应只依赖配置声明的轴、标记、信号、表达式和阶段结构。

## 附录 A：两种典型配置方式对比

两种典型机械结构的差异体现在配置如何声明位置来源，而不是引擎分支：

| 维度 | 移动机构扫描车辆 | 车辆通过固定机构 |
|---|---|---|
| 典型机型 | 龙门式洗车机 | 隧道式洗车机 |
| 移动对象 | 机构本身移动，车辆静止 | 车辆随输送带通过，机构固定 |
| 物理轴 | 龙门编码器 | 输送带编码器 |
| 车辆位置来源 | 对射光电事件锁存龙门当前位置，形成 `markers.car_front` / `markers.car_rear` | 入口光电事件清零追踪轴，形成 `axes.car_front` / `axes.car_rear` |
| 位置触发语义 | 当前机构位置是否位于实测车身区间内 | 当前车身是否覆盖固定机构位置 |
| 常用表达式 | `body_contains(axes.gantry.position, markers.car_front, markers.car_rear)` | `body_covers($brush_pos, axes.car_front, axes.car_rear)` |
| 阶段数量 | 通常多趟（Phase 列表描述每趟行程） | 通常单次通过（一个 Phase 覆盖全程） |
| 归位阶段 | 需要（机构回原点、升起）| 通常不需要 |
| 轮廓扫描 | 可在第一趟扫描并锁存车身范围，后续趟使用数据 | 可按固定工位触发，也可不需要 |
| direction 字段 | 有意义（`forward`/`backward`） | 通常填 `none` |
| 引擎是否需要识别机型 | 不需要 | 不需要 |

## 附录 B：IO 枚举名引用规范

YAML 配置中引用 IO 枚举名的完整规则：

| 用途 | YAML 字段 | 示例 |
|---|---|---|
| 表达式中读取 DI 状态 | `condition` / `active_while` / `guard` 等 | `"ESTOP == 1"` |
| 动作中写入 DO 状态 | `io_set.channel` | `{channel: GANTRY_FWD, value: 1}` |
| 等待 DI 信号 | `wait_signal.signal` | `{signal: LIFT_UP_LIMIT, state: 1}` |
| 追踪轴清零事件 | `zero_on.signal` | `{signal: ENTRY_BEAM, edge: falling}` |
| 锁存标记事件 | `markers.<id>.on.signal` | `{signal: GANTRY_BEAM, edge: falling}` |
| 触发器监听信号 | `trigger.signal` | `{type: signal, signal: TOP_BRUSH_PRESSURE_HIGH, edge: rising}` |
| 物理轴编码器 | `encoder` | `encoder: GANTRY_ENCODER_PULSE` |
| 追踪轴跟随源 | `driven_by` | `driven_by: conveyor` |
