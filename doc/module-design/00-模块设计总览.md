# 模块设计总览

**版本**：v1.0  
**状态**：已落地（通用框架核心 + Demo 接入 + 可选 provider）  
**最后同步代码**：2026-07-12  
**适用范围**：`common/`、`runtime/`、`domain/`、`application/`、`ports/`、`adapters/`、`services/`、`cloud/`、`demo/`  
**架构基线**：DDD 分层 + Ports & Adapters + 事件驱动运行时  
**关键词**：通用洗车机框架、六边形架构、事件总线、命令网关、洗车引擎、HAL provider、项目 wiring

---

## 1. 文档定位

本文档是 `wash-device-framework` 当前代码实现的总体设计说明，负责回答：

- 当前通用框架由哪些层组成。
- 各层承担什么职责，依赖方向如何约束。
- 已落地的核心模块如何协作。
- 项目接入时应在哪些边界做配置、绑定和适配。
- 哪些能力属于通用框架，哪些能力应留在具体项目中。

本文档不是单个机型的完整项目设计，不包含 M8 或其他项目的 IO 表、云端物模型表、报警码目录、水路拓扑表、洗车方案资产和真机 wiring。上述内容应由项目仓库或项目目录提供。

框架的核心目标是：

- 业务规则与硬件、云端、存储、线程、部署配置解耦。
- 同一套领域模型可复用于多类洗车机。
- 真机、仿真和外部 SDK 通过端口与适配器替换。
- 外部命令、运行模式、安全报警和洗车流程有明确边界。
- 项目扩展优先新增配置、绑定和 provider，不修改框架核心逻辑。

## 2. 架构原则

### 2.1 框架与项目分离

当前仓库提供通用框架和一个最小 Demo。通用框架目录不得依赖具体项目或机型。

| 归属 | 当前路径 | 内容 |
|------|----------|------|
| 通用框架 | `common/`、`runtime/`、`domain/`、`application/`、`ports/`、`adapters/`、`services/`、`cloud/` | 可跨项目复用能力 |
| Demo | `demo/` | 最小 wiring、最小报警目录、sim 接入示例 |
| 项目资产 | 项目仓库或项目目录 | IO 表、报警码表、云物模型、真机 wiring、方案文件 |
| 测试 | `tests/` | 当前框架单元测试与少量闭环验证 |

基本规则：

- 通用框架不得出现具体项目名、机型名、硬件点位、云平台产品字段或设备地址。
- 项目通过 `project_hooks`、端口注册和 provider 开关接入。
- 机型绑定、真机 IO 映射、云端点位表、报警码目录和洗车方案资产属于项目侧。
- 某项项目能力确认跨项目复用后，才沉淀为通用抽象或 helper。

### 2.2 DDD 分层

当前代码采用以下分层：

```text
common       公共基础层：错误码、日志、时间、CRC/FIFO、事件类型、点表编解码
runtime      运行时层：启动编排、事件总线、线程注册、周期任务、安全线程
domain       领域层：洗车引擎、命令模式、安全报警、设备控制模式、状态快照
application  应用层：命令网关、模式桥接、编排器、投影、恢复/自检/急停处理
ports        端口层：入站/出站契约
adapters     适配器层：HAL、存储、云端、runtime provider、仿真后端
services     共享服务层：参数服务、设备上下文组合读模型
cloud        云端物模型核心：点位、模型注册、变更检测
demo         Demo 接入层：最小 main、wiring、project hooks
```

依赖方向原则：

```text
adapters / demo / 项目 wiring
        ↓
ports / application
        ↓
domain
        ↓
common

runtime 负责启动和调度，可调用各层 init，但不承载业务规则。
```

### 2.3 Ports & Adapters

入站方向表示外部如何驱动系统：

```text
Cloud / CLI / UI / Sim / Test
        ↓
adapters/inbound
        ↓
ports/inbound
        ↓
application
```

出站方向表示系统如何访问外部资源：

```text
application / domain
        ↓
ports/outbound
        ↓
adapters/outbound
        ↓
HAL / Storage / Cloud SDK / Safety IO / Project Machine
```

端口只定义契约，不包含 SDK 类型、Modbus 地址、IO 编号、MQTT Topic、项目云字段或机型动作表。

### 2.4 稳定逻辑与变化因素分离

稳定逻辑放入框架：

- 事件总线、线程注册、周期任务。
- 命令网关、运行模式矩阵、副作用路由。
- 报警注册表、安全姿态、状态投影。
- 洗车方案模型、表达式引擎、profile 查询接口、JSON 加载器、模板展开、运行时 tick。
- 设备控制通用模式，如双向运动、连续旋转、槽位互锁、流体路径。
- HAL / cloud / storage 端口契约和可选 provider。

变化因素放入项目：

- IO 点位、信号极性、设备地址和真机 wiring。
- 云端物模型点位、Topic、产品凭证。
- 报警编码表、detector、项目 ON_MOTION binding 表。
- 机型机构 API、水路拓扑、设备安全输出表。
- 洗车方案 JSON 和 manifest。
- 部署配置与运行期参数默认值。

### 2.5 当前领域语言

| 中文 | 代码术语 | 说明 |
|------|----------|------|
| 洗车方案 | `engine_program_t` | 可加载的阶段/通道/步骤模型 |
| 洗车会话 | Wash session | `wash_orchestrator` 管理的一次洗车执行 |
| 阶段 | `engine_phase_t` | 串行推进的流程段 |
| 通道 | `engine_lane_t` | 同一阶段内并行扫描的步骤集合 |
| 步骤 | `engine_step_t` | event 或 control 型动作单元 |
| 联锁 | `engine_interlock_t` | tick 内高优先级安全/流程条件 |
| 运行模式 | `operational_mode_t` | 设备业务模式，命令矩阵的状态轴 |
| 设备命令 | `dev_cmd_t` | 云端、CLI、仿真等统一入站命令 |
| 报警定义 | `alarm_def_t` | 报警静态目录项 |

| 设备上下文 | `device_context_t` | operational/safety/wash/cloud 组合只读视图 |
| 运行参数 | `param_store` / `svc_param` | 可写 KV 与带语义访问层 |
| 部署配置 | `deploy_store` | 只读部署期配置 |

## 4. 基础与运行时

### 4.1 common

`common/` 放跨层公共基础能力。

| 模块 | 职责 |
|------|------|
| `sw_error.h` | 统一错误码 |
| `log.h` | 日志宏 |
| `time_util.*` | 当前时间、测试注入时间 |
| `event_types.h` | 事件类别、事件 ID、`event_t` |
| `io_handle.*` | IO 句柄抽象 |
| `pulse_out.*` | 脉冲输出 helper |
| `util_crc.*` | CRC 工具 |
| `util_fifo.*` | FIFO 工具 |
| `point_table/` | 通用点位 JSON 编解码、查找、apply 结果 |

`common/` 不承载设备业务规则，不依赖 HAL、云端 SDK 或项目配置。

### 4.2 runtime

`runtime/` 是框架运行骨架。

| 模块 | 职责 |
|------|------|
| `bootstrap/` | `bootstrap_run()` 启动编排、project hooks |
| `event_bus/` | 事件发布、订阅、优先级队列、dispatch loop |
| `scheduler/` | 线程注册、周期任务注册、统一 start |
| `platform/` | 安全线程、设备安全执行、panic/fatal 边界 |
| `config/` | 线程周期、优先级、容量等编译期配置 |

启动顺序由 `runtime/bootstrap/bootstrap.c` 固化：

```text
bootstrap_init_infra()
    time_util_init()
    event_bus_init()
    wiring()
    svc_param_init()

project_safety_init()

bootstrap_init_application()
    project_machine_setup()
    alarm_registry_init()
    safety_posture_init()
    project_alarm_catalog_init()
    alarm_event_bridge_init()
    safety_thread_init()
    operational_mode_init()
    command_gateway_init()
    self_check_service_init()
    op_mode_bridge_init()
    wash_orchestrator_init()
    recovery_service_init()
    emergency_handler_init()
    projections init

bootstrap_init_adapters()
    param/deploy/cloud/HAL provider init

bootstrap_start_threads()
    event_dispatch
    project_start_threads()
    scheduler_start_all()
```

详见 `doc/module-design/runtime/Runtime模块设计.md`、`doc/module-design/runtime/EventBus模块设计.md`。

### 4.3 services

`services/` 放跨模块共享的软件服务。

| 模块 | 职责 |
|------|------|
| `services/param/` | `svc_param`，运行参数的带语义访问层 |
| `services/dev_ctx/` | `dev_ctx_snapshot()`，组合 operational/safety/wash/cloud 只读上下文 |

约束：

- `svc_param` 通过 `param_store` 访问存储，不直接操作 JSON 文件。
- `dev_ctx` 组合 snapshot 与 cloud link 状态，不修改领域事实源。
- 业务裁决不放在 `services/`，应归属 `domain` 或 `application`。

## 5. 领域层

### 5.1 domain/wash

`domain/wash/` 是洗车方案与控制引擎上下文。

| 子模块 | 职责 |
|--------|------|
| `model/engine_model.*` | program/phase/lane/step/action/interlock 数据结构 |
| `model/engine_program_validate.*` | 方案语义校验 |
| `model/engine_program_manifest.*` | JSON 方案 manifest 校验 |
| `engine/engine.*` | 运行时创建、装载、启动、tick 推进 |
| `engine/engine_expr.*` | 表达式编译、clone、求值 |
| `engine/engine_io.*` | IO ops/catalog 注册与读取 |

设计原则：

- 洗车流程由 `engine_program_t` 描述，不在 C 代码中硬编码项目流程。
- 领域引擎只通过 `engine_io_ops_t` 读 signal/axis、写 output。
- 车辆轮廓通过 `engine_profile_provider_t` 查询，扫描算法和分区数据留在项目侧。
- JSON loader 只构建和校验模型，不执行流程；`program.templates` 仅在加载期展开。
- tick 由 `wash_orchestrator` worker 驱动，engine 自身不创建线程。

详见 `doc/module-design/domain/洗车引擎模块设计.md`。

### 5.2 domain/command_gateway

`domain/command_gateway/` 定义外部命令词汇、运行模式和裁决结果。

| 子模块 | 职责 |
|--------|------|
| `device_command.h` | `dev_cmd_t`、命令种类、来源、载荷 |
| `command_decision.h` | 裁决结果与副作用枚举 |
| `command_receipt.h` | 同步回执状态 |
| `op_mode_types.h` | 拒绝原因、洗车中止原因、恢复结果 |
| `operational_mode.*` | 模式矩阵、状态转移、事件发布 |

设计原则：

- 所有外部控制请求统一进入 `device_command_port.submit()`。
- `operational_mode` 只做裁决和模式状态维护，不调用 HAL 或 orchestrator。
- 副作用由 `application/side_effect_router` 执行。
- 异步生命周期事件由 `application/op_mode_bridge` 喂入 `op_mode_on_*`。

详见 `doc/module-design/domain/命令网关模块设计.md`。

### 5.3 domain/safety

`domain/safety/` 是报警与安全姿态上下文。

| 子模块 | 职责 |
|--------|------|
| `model/alarm_types.h` | 报警码、等级、清除策略、实例、域事件 |
| `model/safety_types.h` | 安全姿态类型 |
| `alarm_registry/` | 报警目录、活跃池、pending 事件、PostWash 查询 |
| `safety_posture/` | 订阅报警事件并聚合 `NOMINAL` / `LOCKOUT` |

设计原则：

- `alarm_registry` 是活跃报警事实源。
- detector 经 `alarm_binding_port` 接入，不直接写 registry 静态状态；通用边沿转发可复用 `alarm_detector_helper`。
- 报警事件先进入 registry pending 队列，再由 `alarm_event_bridge` 发布到 event bus。
- ON_MOTION 重评估经 `alarm_reeval_bridge` 查项目 binding 表后调用 registry 分组清除。
- 项目报警码目录、detector、ON_MOTION binding 表不放入通用框架。
- 报警编码规范可以沉淀为通用宏和校验 helper，但具体码表属于项目。

详见 `doc/module-design/domain/报警系统模块设计.md`。

### 5.4 domain/device_control

`domain/device_control/` 提供与机型无关的设备控制模式。

| 模式 | 职责 |
|------|------|
| `motion_lifecycle` | 运动生命周期选项 |
| `bidirectional_motion` | 双向运动封装 |
| `continuous_rotary` | 连续旋转封装 |
| `interlocked_slots` | 多槽互锁 |
| `fluid_path` | 流体路径掩码、引用计数、阀泵时序、急停关闭 |

设计原则：

- 通用模式可进入框架，命名机构 API 留在项目侧。
- `fluid_path` 校验通用拓扑一致性、路径上限和未知路径 mask；具体水路拓扑、DO 到 path 的映射、泵阀点位属于项目配置。
- 电机控制通过 `hal_motor_exec_port` 抽象，不绑定 MCC SDK。

详见 `doc/module-design/domain/设备控制模式模块设计.md`。

### 5.5 domain/telemetry

`domain/telemetry/snapshot/` 定义只读快照模型。

| Snapshot | 来源 |
|----------|------|
| `operational_snapshot` | `operational_projection` |
| `safety_snapshot` | `safety_projection` |
| `wash_snapshot` | `wash_projection` |

设计原则：

- snapshot 是读模型，不是事实源。
- 写侧由 `application/*_projection` 订阅事件后刷新。
- `dev_ctx` 组合多个 snapshot 和 cloud link 状态。

详见 `doc/module-design/domain/状态投影与设备上下文模块设计.md`。

## 6. 应用层

`application/` 负责用例编排、异步桥接和跨上下文协调。

| 模块 | 职责 |
|------|------|
| `command_gateway.*` | `device_command_port` 实现、队列、唤醒、同步回执 |
| `side_effect_router.*` | 将允许的命令副作用路由到 orchestrator、报警或 machine ops |
| `op_mode_bridge.*` | 订阅 WASH/SAFETY/ALARM/HW 事件，调用 `op_mode_on_*` |
| `alarm_event_bridge.*` | registry pending 事件转 `EVT_ALARM_*` |
| `operational_projection.*` | 模式事件转 operational snapshot |
| `safety_projection.*` | 报警事件转 safety snapshot |
| `wash_projection.*` | 洗车事件转 wash snapshot |
| `recovery_service.*` | 恢复请求处理 |
| `self_check_service.*` | 自检最小服务 |
| `safety_deferred_stop.*` | 安全延后停机 |
| `orchestrators/wash_orchestrator.*` | 洗车方案加载、engine 生命周期、worker tick |
| `orchestrators/emergency_handler.*` | 安全锁定/急停后的中止处理 |
| `orchestrators/report_scheduler.*` | 云端周期/事件上报调度 |

应用层约束：

- 不定义项目点位、云字段或机型硬件地址。
- 不绕过 domain 聚合直接改运行模式或报警事实。
- 不把 provider SDK 类型暴露给 domain 或 ports。
- 副作用执行必须经端口、orchestrator 或 machine ops。

## 8. 适配器层

### 8.1 HAL 适配器

当前 HAL 适配器包括：

- `adapters/outbound/hal/sim/`：仿真 IO、VFD、voice、engine IO 后端。
- `adapters/outbound/hal/providers/mcc/`：MCC 电机执行器 provider。
- `adapters/outbound/hal/providers/snack/io_exp/`：Snack IO 扩展 provider。
- `adapters/outbound/hal/providers/snack/modbus/`：Snack Modbus VFD / voice provider。

provider 通过 CMake 选项可选启用，默认不污染通用框架核心。

详见 `doc/module-design/ports-adapters/HAL端口与适配器模块设计.md`。

### 8.2 存储适配器

当前存储适配器包括：

- `json_param_store`：运行期参数 JSON KV。
- `json_deploy_store`：部署期只读配置。
- `engine_program_json`：洗车方案 JSON 加载器。
- `engine_program_manifest`：方案资产 size + SHA256 校验。

详见 `doc/module-design/ports-adapters/Storage端口与方案资产模块设计.md`。

### 8.3 云端适配器

云端分为三层：

| 层 | 模块 | 职责 |
|----|------|------|
| 物模型核心 | `cloud/cloud_point_*`、`cloud/cloud_model.*` | 点位校验、JSON 编解码、语义 dispatch、watcher |
| 调度 | `application/orchestrators/report_scheduler.*` | 周期/事件上报策略 |
| provider | `adapters/**/cloud/providers/snack/` | Snack MQTT link、property、report 适配 |

完整云物模型表属于项目侧。框架只提供点位模型、端口和 provider 接入方式。

详见 `doc/module-design/ports-adapters/CloudModel模块设计.md`。

### 8.4 runtime provider

`adapters/runtime/snack/` 提供 Snack 平台 runtime 对接，如 CLI、BLE、日志 sink 等。此类 provider 不应进入 domain 或 application 的核心依赖链。

## 9. 事件与线程模型

### 9.1 事件总线

事件总线是跨模块异步通知骨干。

核心约束：

- `event_t.param` 为 `uint32_t` 标量，不传递指针或复杂结构。
- 安全关键事件走高优先级队列。
- handler 在 `event_dispatch` 线程内执行，应避免长阻塞。
- 复杂状态通过领域查询接口或 snapshot 获取。

典型事件链：

```text
command_gateway submit
    → EVT_CMD_GATEWAY_WAKE
    → command_gateway_drain
    → EVT_OP_MODE_CMD_HANDLED

alarm_registry trigger
    → alarm_event_bridge_drain
    → EVT_ALARM_TRIGGERED
    → safety_posture / op_mode_bridge / safety_projection

wash_orchestrator
    → EVT_WASH_SESSION_STARTED / DONE / ABORTED
    → op_mode_bridge / wash_projection
```

### 9.2 线程与周期任务

当前线程治理由 `thread_registry` 和 `periodic_task` 统一管理。

已知线程/周期任务类型：

- `event_dispatch`：事件分发与 command gateway 唤醒处理。
- `safety_thread`：硬件急停快速轮询。
- `wash_worker`：洗车引擎 tick。
- `cloud_report`：云链路 poll、watcher poll、周期上报。
- Demo `alarm_bridge`：周期 drain 报警 pending 事件。

线程新增规则：

1. 框架线程在 init 阶段 `thread_register()`。
2. 固定周期逻辑优先用 `periodic_task_register()`。
3. 项目线程通过 `project_start_threads()` 或项目 hook 接入。
4. 不在 domain 模块内创建线程。

详见 `doc/module-design/runtime/Runtime模块设计.md`。

## 10. 项目接入模型

项目接入建议按以下顺序完成。

### 10.1 Storage

- 注册 `param_store` 和 `deploy_store`。
- 定义运行期参数键名、默认值和保存策略。
- 提供洗车方案 JSON 与 manifest。
- 注册 `engine_program_loader_port`。

### 10.2 HAL

- 注册真机 `hal_io`、`hal_sensor`、`hal_vfd`、`hal_voice`、`hal_motor_exec`。
- 注册 `engine_io_ops_t`，把方案中的 signal/output/axis 名称映射到真实硬件。
- 实现安全切断与急停输入端口。

### 10.3 Domain / Application

- 组合 `device_control/patterns` 形成项目命名机构 API。
- 通过 `machine_ops_port` 注册 `home_device`、`execute_manual_actuator`、`stop_all_outputs` 等。
- 定义报警目录并调用 `project_alarm_catalog_init()` 加载。
- 实现 detector，按需用 `alarm_detector_helper` 将归一化故障状态转发到 `alarm_binding_port`。
- 提供项目 `alarm_reeval_binding_t` 表，把动作完成或流程检查点绑定到项目 `reeval_group`。

### 10.4 Cloud

- 定义项目 `cloud_point_entry_t[]` 物模型表。
- 定义 `report_policy_entry_t[]` 上报策略。
- 注册 `cloud_model_bundle_t`。
- 将 `DEVICE_CMD` 点位通过 submit 回调接到 `device_command_port`。
- 选择并初始化云 provider。

### 10.5 Runtime

- 实现 `wiring()` 和 `project_hooks_*`。
- 决定哪些 provider 在构建期开启。
- 注册项目周期任务或线程。
- 验证 `bootstrap_run()` 的启动顺序满足项目依赖。

详见 `doc/module-design/integration/Demo与项目接入模块设计.md`。
