# 模块设计总览

**版本**：v1.1  
**状态**：已落地（通用框架核心 + Demo 接入 + 可选 provider）  
**最后同步代码**：2026-08-05  
**适用范围**：`common/`、`runtime/`、`domain/`、`application/`、`adapters/`、`services/`、`observability/`、`demo/`  
**架构基线**：DDD 分层 + Ports & Adapters + 事件驱动运行时  
**关键词**：通用洗车设备框架、六边形架构、事件总线、命令网关、方案引擎、HAL provider、项目 wiring

---

## 1. 文档定位

本文档是 `wash-device-framework` 当前代码实现的总体设计说明，负责回答：

- 当前通用框架由哪些层组成。
- 各层承担什么职责，依赖方向如何约束。
- 已落地的核心模块如何协作。
- 项目接入时应在哪些边界做配置、绑定和适配。
- 哪些能力属于通用框架，哪些能力应留在具体项目中。

本文档不是单个机型的完整项目设计，不包含任何具体机型的 IO 表、云端物模型表、报警码目录、水路拓扑表、洗车方案资产和真机 wiring。上述内容应由项目仓库或项目目录提供。

框架的核心目标是：

- 业务规则与硬件、云端、存储、线程、部署配置解耦。
- 同一套领域模型可复用于多类洗车机。
- 真机、仿真和外部 SDK 通过端口与适配器替换。
- 外部命令、运行模式、安全报警和洗车流程有明确边界。
- 项目扩展优先新增配置、绑定和 provider，不修改框架核心逻辑。

## 2. 架构原则

### 2.1 框架与项目分离

当前仓库提供通用框架和一个最小 Demo。通用框架目录不得依赖具体项目或机型。

| 归属 | 当前路径 | 内容 |
|------|----------|------|
| 通用框架 | `common/`、`runtime/`、`domain/`、`application/`、`adapters/`、`services/`、`observability/` | 可跨项目复用能力 |
| Demo | `demo/` | 最小 wiring、最小报警目录、sim 接入示例 |
| 项目资产 | 项目仓库或项目目录 | IO 表、报警码表、云物模型、真机 wiring、方案文件 |
| 测试 | `tests/` | 当前框架单元测试与少量闭环验证 |

基本规则：

- 通用框架不得出现具体项目名、机型名、硬件点位、云平台产品字段或设备地址。
- 项目通过 `project_hooks`、端口注册和 provider 开关接入。
- 机型绑定、真机 IO 映射、云端点位表、报警码目录和洗车方案资产属于项目侧。
- 某项项目能力确认跨项目复用后，才沉淀为通用抽象或 helper。

### 2.2 DDD 分层

当前代码采用以下分层：

```text
common        公共基础层：错误码、日志、时间、CRC/FIFO、事件类型、点表模型、追踪上下文
runtime       运行时层：启动编排、事件总线、线程注册、周期任务；`runtime/ports` 装配
domain        领域层：方案引擎、运行模式、安全报警、设备控制模式、遥测快照、云物模型；`domain/ports/outbound` 出站契约
application   应用层：命令网关、模式桥接、编排器、投影、恢复/自检、资产契约；`application/ports` 入站与云出站契约
adapters      适配器层：HAL、存储、云端、序列化、runtime provider、仿真后端
services      共享服务层：参数服务
observability 旁路诊断设施：观测记录发布、故障黑匣子
demo          Demo 接入层：最小 main、wiring、project hooks
```

依赖方向（include）——无顶层 `ports/` 业务层：

```text
adapters / demo / 项目 wiring
        ↓
application / services
        ↓
domain ──► domain/ports/outbound
        ↓
common
```

完整规则见 `doc/architecture/01-分层架构与依赖边界.md`。

### 2.3 Ports & Adapters

| 路径 | 语义所有权 |
|------|------------|
| `domain/ports/outbound/**` | 出站契约树（domain 锥；含 HAL/storage 等共享出站，详见 `architecture/01` §2.3） |
| `application/ports/inbound/**` | 入站用例 |
| `application/ports/outbound/cloud/**` | 应用云出站 |
| `runtime/ports/**` | 注册表与契约校验 |
| `application/bridges/alarm_binding_bridge.*` | 入站绑定到 `alarm_registry` |

### 2.4 稳定逻辑与变化因素分离

稳定逻辑放入框架：

- 事件总线、线程注册、周期任务。
- 命令网关、运行模式矩阵、副作用路由。
- 报警注册表、安全姿态、状态投影。
- 洗车方案模型、表达式引擎、profile 查询接口、JSON 加载器、模板展开、运行时 tick。
- 设备控制通用模式：单轴运动、流体路径。
- HAL / cloud / storage 端口契约和可选 provider。

变化因素放入项目：

- IO 点位、信号极性、设备地址和真机 wiring。
- 云端物模型点位、Topic、产品凭证。
- 报警编码表、detector、项目 ON_MOTION binding 表。
- 机型机构 API、水路拓扑、设备安全输出表。
- 洗车方案 JSON 和 manifest。
- 部署配置与运行期参数默认值。

| 中文 | 代码术语 | 说明 |
|------|----------|------|

| 联锁 | `engine_interlock_t` | tick 内高优先级安全/流程条件 |
| 运行模式 | `operational_mode_t` | 设备业务模式，命令矩阵的状态轴 |
| 设备命令 | `dev_cmd_t` | 云端、CLI、仿真等统一入站命令 |

## 4. 基础与运行时

### 4.1 common

`common/` 放跨层公共基础能力。

| 模块 | 职责 |
|------|------|
| `sw_error.h` | 统一错误码 |
| `log.h` | 日志宏 |
| `time_util.*` | 当前时间、测试注入时间 |
| `event_types.h` | 事件类别、事件 ID、`event_t`、param 编解码 |
| `io_handle.h` | IO 句柄抽象 |
| `pulse_out.*` | 脉冲输出 helper |
| `sw_mutex.*` | 互斥量封装，含优先级继承初始化 |
| `trace_context.*` | 追踪上下文（详见 `common/横切基础设施模块设计.md`） |
| `asset_version.*` | 语义化版本解析与兼容判定（同上） |
| `util_crc.*` | CRC 工具 |
| `util_fifo.*` | FIFO 工具 |
| `point_table/` | 通用点位表模型、查表、apply 结果（不含序列化） |

`common/` 不承载设备业务规则，不依赖 HAL、云端 SDK 或项目配置，也不依赖任何外部格式库。点位表的 JSON 编解码在 `adapters/outbound/serialization/json/`，因此 `common/` 不引入 cJSON——否则「domain 不解析序列化格式」会因 domain 依赖 common 而失去基础。

### 4.2 runtime

`runtime/` 是框架运行骨架。

| 模块 | 职责 |
|------|------|
| `bootstrap/` | `bootstrap_run()` 启动编排、`wiring()` 与 project hooks 契约 |
| `event_bus/` | 事件发布、订阅、优先级队列、dispatch loop、容量配置 |
| `scheduler/` | 线程注册、周期任务注册、统一 start |
| `config/` | 线程栈、周期、实时优先级等编译期配置 |

启动顺序由 `runtime/bootstrap/bootstrap.c` 固化，共 7 个阶段（钩子仍按细粒度调用）：

```text
bootstrap_register()
    time_util_init()
    event_bus_init() + event_bus_set_fatal_cb()
    wiring()
    project_hooks_register()
    thread_register("event_dispatch", ...)

bootstrap_load_storage()
    project_configure_storage()
    svc_param_init()
    deploy_store.load()

bootstrap_configure()
    project_configure_hal()
    project_configure_safety()
    project_configure_adapters()

bootstrap_bind()
    project_bind_hal()
    project_bind_machine()
    alarm_registry_init()
    project_bind_alarm_catalog()
    project_validate()

bootstrap_init_hal()
    hal_io / hal_vfd / hal_voice init
    project_init_hal()
    project_init_machine()
    project_init_safety()

bootstrap_init_services()
    alarm_bridge_init()
    operational_mode_init()
    command_gateway_init()
    recovery_service_init()
    safety_session_coordinator_init()
    op_mode_bridge_init()
    telemetry_projection_init()
    project_init_adapters()
    project_register_runtime_tasks()

bootstrap_start()
    hal_io.start()
    project_start_runtime()
    scheduler_start_all()
```

两项由项目在 `project_init_adapters()` 中显式选择启用，bootstrap 不引用：急停轮询适配器（`estop_poll_thread_init()`）与可观测事件桥（`observation_event_bridge_init()`）。原因是同一物理输入或同一事件若被两条通路各处理一次，会产生重复事件源或重复记录，该选择只有项目知道。

`bootstrap_run()` 返回非 `SW_OK` 时调用方必须终止进程：启动序列没有回滚路径，重试会造成队列重置与线程重复登记。

详见 `doc/module-design/runtime/Runtime模块设计.md`、`doc/module-design/runtime/EventBus模块设计.md`。

### 4.3 services

`services/` 放跨模块共享的软件服务，当前只有参数服务。

| 模块 | 职责 |
|------|------|
| `services/param/` | `svc_param`，运行参数的带语义访问层 |

约束：

- `svc_param` 通过 `param_store` 访问存储，不直接操作 JSON 文件。
- 业务裁决不放在 `services/`，应归属 `domain` 或 `application`。
- `services/` 不得依赖 `adapters/` 或 `application/`。

### 4.4 observability

`observability/` 是与业务无关的旁路诊断设施，只依赖 `common/`：

| 模块 | 职责 |
|------|------|
| `core/observation.*` | 非阻塞观测记录发布（事件、日志、状态、趋势、故障快照五类，普通与关键双队列） |
| `recorder/blackbox_recorder.*` | 循环采样缓冲，故障发生时冻结现场供事后取回 |

它不参与任何业务判定，也不回调其他层；记录如何落盘或外发由项目决定。框架侧唯一接入点是 `application/bridges/observation_event_bridge.*`，由项目选择是否启用。

详见 `doc/module-design/observability/可观测性模块设计.md`。

## 5. 领域层

### 5.1 domain/program_engine

`domain/program_engine/` 是洗车方案与控制引擎上下文。

| 子模块 | 职责 |
|--------|------|
| `model/engine_model.*` | program/phase/lane/step/action/interlock 数据结构、释放、clone |
| `model/engine_program_validate.*` | 方案语义校验 |
| `engine/engine.*` | 运行时创建、装载、启动、tick 推进 |
| `engine/engine_expr.*` | 表达式编译、clone、求值 |
| `engine/engine_var.*` | 变量解析 |
| `engine/engine_io.*` | IO ops/catalog 注册与读取 |
| `engine/engine_actuator.*` | 机构意图提交 ops/catalog 注册 |
| `engine/engine_profile.*` | 车辆轮廓 provider 注册与查询 |

设计原则：

- 洗车流程由 `engine_program_t` 描述，不在 C 代码中硬编码项目流程。
- 领域引擎只通过 `engine_io_ops_t` 按名读 signal/axis，通过 `engine_actuator_ops_t` 提交机构意图。
- 车辆轮廓通过 `engine_profile_provider_t` 查询，扫描算法和分区数据留在项目侧。
- JSON loader 只构建和校验模型，不执行流程；`program.templates` 仅在加载期展开。
- tick 由调用方驱动，engine 自身不创建线程；框架提供 `application/engine_session/` 作为通用会话 worker。
- 方案资产的反序列化与 manifest 校验在 `adapters/outbound/storage/json/`，不在 domain。

详见 `doc/module-design/domain/方案引擎模块设计.md`。

### 5.2 domain/op_mode

`domain/op_mode/` 定义外部命令词汇、运行模式和裁决结果。

| 子模块 | 职责 |
|--------|------|
| `device_command.h` | `dev_cmd_t`、命令种类、来源、载荷 |
| `command_types.h` | 裁决结果、副作用枚举、同步回执状态 |
| `op_mode_types.h` | 运行模式八态、拒绝原因、洗车中止原因、恢复结果、事件 param 编解码 |
| `operational_mode.*` | 命令矩阵、状态转移、事件发布 |

设计原则：

- 所有外部控制请求统一进入 `device_command_port.submit()`。
- `operational_mode` 只做裁决和模式状态维护，不调用 HAL 或 orchestrator。
- 副作用由 `application/side_effect_router` 执行。
- 异步生命周期事件由 `application/bridges/op_mode_bridge` 喂入 `op_mode_on_*`。
- 多字段事件 param 一律经 `op_mode_types.h` 的 encode/decode 收口，禁止在调用点手写移位。

详见 `doc/module-design/domain/命令网关模块设计.md`。

### 5.3 domain/safety

`domain/safety/` 是报警与安全姿态上下文。

| 子模块 | 职责 |
|--------|------|
| `model/alarm_types.h` | 报警码、等级、清除策略、实例、域事件、`safety_posture_t`、容量常量 |
| `model/safety_matrix.h` | 等级与清除策略的行为属性单一事实源 |
| `alarm_registry/` | 报警目录、活跃池、session journal、pending 事件 |

设计原则：

- `alarm_registry` 是活跃报警事实源；等级语义：MINOR 只记、MAJOR 禁开洗/洗中不停/洗后评估、CRITICAL→LOCKOUT。
- 等级与清除策略的判定统一查 `safety_matrix.h`，registry 内不写 `level >= MAJOR` 这类内联判断。
- detector 经 `alarm_binding_port` 接入，不直接写 registry 静态状态。
- 报警事件先进入 registry pending，再由 `alarm_bridge` 发布到 event bus，并在同桥内做姿态边沿（`EVT_SAFETY_*`）。
- ON_MOTION 重评估经 `alarm_bridge` 查项目 binding 表后调用 registry 分组清除。
- 项目报警码目录、detector、ON_MOTION binding 表不放入通用框架。
- 报警编码规范可以沉淀为通用宏和校验 helper，但具体码表属于项目。

详见 `doc/module-design/domain/报警系统模块设计.md`。

### 5.4 domain/device_control

`domain/device_control/` 提供与机型无关的设备控制模式。

| 模块 | 职责 |
|------|------|
| `model/actuator_events.*` | 机构完成、流程检查点生命周期事件 |
| `patterns/motion_lifecycle.h` | 运动生命周期选项注入（机构 ID + 过程故障回调） |
| `patterns/motor_axis.*` | 单轴运动：正反向运行、到位运动、回原、恢复、状态查询 |
| `patterns/fluid_path.*` | 流体路径掩码、引用计数、阀泵时序、急停关闭 |

设计原则：

- 通用模式可进入框架，命名机构 API 留在项目侧。
- `fluid_path` 校验通用拓扑一致性、路径上限和未知路径 mask；具体水路拓扑、DO 到 path 的映射、泵阀点位属于项目配置。
- 电机控制通过 `hal_motor_exec_port` 抽象，不绑定 MCC SDK。
- 模式层不触发 `alarm_registry`，只暴露 `on_process_fault` 回调或发布生命周期事件，由项目映射报警。
- 领域层不创建线程：`fluid_path_poll()` 需由调用方登记为周期任务。

详见 `doc/module-design/domain/设备控制模式模块设计.md`。

### 5.5 domain/telemetry

`domain/telemetry/device_snapshot.h` 统一定义只读快照模型，四个子域内联在同一结构中。

| 子域 | 内容 |
|------|------|
| `operational_snapshot_t` | 运行模式、运营总开关、急停标志 |
| `safety_snapshot_t` | 安全姿态、blocking 标志、最高报警码、活动报警表 |
| `wash_snapshot_t` | 最近一次会话启动的洗车模式 |
| `connectivity_snapshot_t` | 云连接状态 |

设计原则：

- 快照是读模型，不是事实源。
- 四子域共用一把互斥量，`device_snapshot_get()` 一次加锁返回整体副本，跨子域一致由结构保证而非调用顺序。
- 写侧统一由 `application/telemetry_projection` 订阅事件后刷新；写入口只在 `device_snapshot_internal.h`。
- 云连接状态由 application 层投影从 `cloud_link_port` 读取后写入，domain 不依赖云端口。

详见 `doc/module-design/domain/状态投影与设备快照模块设计.md`。

### 5.6 domain/cloud

`domain/cloud/` 是云端物模型核心子域：点位元模型、登记期校验、下行语义 dispatch、`ON_CHANGE` 变更检测。它复用 `common/point_table/` 的查表能力，但不解析 JSON——属性 JSON 编解码与 `property_port` 安装在 `adapters/outbound/cloud/`。

详见 `doc/module-design/ports-adapters/CloudModel模块设计.md`。

## 6. 应用层

`application/` 负责用例编排、异步桥接和跨上下文协调。

| 模块 | 职责 |
|------|------|
| `command_gateway.*` | `device_command_port` 实现、队列、唤醒、drain、同步回执 |
| `side_effect_router.*` | 已裁决命令的副作用路由（含自检判定） |
| `telemetry_projection.*` | 订阅模式/报警/安全/洗车/云事件，刷新设备快照 |
| `asset_contract.*` | 必需资产启动期校验（报警目录、云物模型、引擎 IO 目录是否就位） |
| `bridges/op_mode_bridge.*` | 订阅 WASH/SAFETY/ALARM/HW/OP_MODE 事件，调用 `op_mode_on_*` |
| `bridges/alarm_bridge.*` | pending→`EVT_ALARM_*`、姿态边沿、会话 journal、可选 ON_MOTION reeval |
| `bridges/observation_event_bridge.*` | 框架事件转观测记录（项目可选启用） |
| `engine_session/engine_session.*` | 通用方案会话：worker 线程驱动 engine tick、启动、中止、忙判定 |
| `orchestrators/recovery_service.*` | Recover：复位已恢复的锁存告警 + 异步归位 + 阻塞告警验证 |
| `orchestrators/safety_session_coordinator.*` | 急停/LOCKOUT 切断与中止归位 |
| `orchestrators/report_scheduler.*` | 云端周期/事件上报调度 |
| 项目洗车/归位编排器 | 选方案 + 发用例事件（**不在 framework**，经 `machine_ops` 接入） |

应用层约束：

- 不定义项目点位、云字段或机型硬件地址。
- 不绕过 domain 聚合直接改运行模式或报警事实。
- 不把 provider SDK 类型暴露给 domain 或 ports。
- 副作用执行必须经端口或框架服务；`side_effect_router` 只调 `machine_ops`（自检在 side_effect_router 内完成）。
- 不依赖 `adapters/` 或 `services/`。

### 7.3 端口注册与契约

端口注册器按域拆成四个文件：`runtime/ports/port_registry_hal.c`、`port_registry_safety.c`、`port_registry_cloud.c`、`port_registry_infra.c`，统一声明在 `runtime/ports/port_registry.h`。

`runtime/ports/port_contract.*` 提供启动期必需端口校验：项目按 `PORT_REQ_*` 位声明自己依赖哪些端口，`port_contract_validate()` 在 validate 阶段一次性给出完整缺失清单。这是最干净的失败点——此时尚未初始化硬件、也未启动线程。它与 `application/asset_contract.*` 互补：**port_contract 答「函数表是否注册」，asset_contract 答「数据是否就位」**。

详见 `doc/module-design/runtime/启动契约校验模块设计.md`。

## 8. 适配器层

### 8.1 HAL 适配器

当前 HAL 适配器包括：

- `adapters/outbound/hal/sim/`：仿真 IO、voice、engine IO、engine actuator 后端。
- `adapters/outbound/hal/components/`：与 vendor 无关的组合件（ADC 门控、DI 滤波、VFD manager）。
- `adapters/outbound/hal/providers/mcc/`：MCC 电机执行器 provider。
- `adapters/outbound/hal/providers/snack/io_exp/`：Snack IO 扩展 provider。
- `adapters/outbound/hal/providers/snack/modbus/`：Snack Modbus VFD / voice provider。

vendor provider 通过 CMake 选项（`WDF_ENABLE_*`）可选启用，默认不污染通用框架核心。

详见 `doc/module-design/ports-adapters/HAL端口与适配器模块设计.md`。

### 8.2 存储适配器

当前存储适配器包括：

- `json_param_store`：运行期参数 JSON KV。
- `json_deploy_store`：部署期只读配置。
- `engine_program_json`：洗车方案 JSON 加载器。
- `engine_program_manifest`：方案资产 size + SHA256 校验。

manifest 校验放在适配层而非 domain：它读取文件原始字节并解析 manifest JSON，两者都是 domain 明确不做的事。

详见 `doc/module-design/ports-adapters/Storage端口与方案资产模块设计.md`。

### 8.3 云端适配器

云端按职责分为四处：

| 层 | 模块 | 职责 |
|----|------|------|
| 物模型核心 | `domain/cloud/cloud_point_*`、`cloud_model.*` | 点位校验、语义 dispatch、watcher |
| 序列化 | `adapters/outbound/cloud/cloud_point_json.*`、`cloud_model_json.*` | 属性 JSON 编解码、`property_port` 安装 |
| 调度 | `application/orchestrators/report_scheduler.*` | 周期/事件上报策略 |
| provider | `adapters/**/cloud/providers/snack/` | Snack MQTT link、property、report 适配 |

`property_port` 的契约参数是 JSON 载荷，实现它必须解析 JSON，因此安装动作 `cloud_model_json_install()` 在适配层，不在 `cloud_model_register()` 内。

完整云物模型表属于项目侧。框架只提供点位模型、端口和 provider 接入方式。

详见 `doc/module-design/ports-adapters/CloudModel模块设计.md`。

### 8.4 runtime provider

`adapters/runtime/snack/` 提供 Snack 平台 runtime 对接，如 CLI、BLE、日志 sink 等。此类 provider 不应进入 domain 或 application 的核心依赖链。

## 9. 事件与线程模型

### 9.1 事件总线

事件总线是跨模块异步通知骨干。

核心约束：

- `event_t.param` 为 `uint32_t` 标量，不传递指针或复杂结构。
- 安全关键事件走高优先级队列。
- handler 在 `event_dispatch` 线程内执行，应避免长阻塞。
- 复杂状态通过领域查询接口或 snapshot 获取。

典型事件链：

```text
command_gateway submit
    → EVT_CMD_GATEWAY_WAKE
    → command_gateway_drain
    → EVT_OP_MODE_CMD_HANDLED

alarm_registry trigger
    → alarm_bridge_drain
    → EVT_ALARM_TRIGGERED / EVT_SAFETY_*
    → op_mode_bridge / telemetry_projection

wash session
    → EVT_WASH_SESSION_STARTED / DONE / ABORTED
    → op_mode_bridge / alarm_bridge / telemetry
```

### 9.2 线程与周期任务

当前线程治理由 `thread_registry` 和 `periodic_task` 统一管理。

已知线程/周期任务类型：

- `event_dispatch`：事件分发与 command gateway 唤醒处理（bootstrap 无条件登记）。
- `alarm_bridge`：50ms 周期 drain 报警 pending 事件并算姿态边沿（`alarm_bridge_init()` 登记）。
- 会话 worker：方案引擎 tick，名称与栈由 `engine_session` 调用方配置。
- `cloud_report_<period>ms`：云链路 poll、watcher poll、周期上报，每种周期一个任务。
- `hal_sensor_poll` / `vfd_manager_poll`：HAL 组合件周期推进。
- `estop_poll`：硬件急停轮询，项目选择性接入的入站适配器。

周期任务以绝对截止时间推进，回调耗时不累加进下一拍，超时的拍被跳过而非追赶。

线程新增规则：

1. 框架线程在 init 阶段 `thread_register()`，创建统一延后到 `scheduler_start_all()`。
2. 固定周期逻辑优先用 `periodic_task_register()`。
3. 项目周期任务通过 `project_register_runtime_tasks()` 接入，无法纳入 scheduler 的项目线程才通过 `project_start_runtime()` 接入。
4. 不在 domain 模块内创建线程；需要周期推进的领域函数（如 `fluid_path_poll`）由调用方登记。

详见 `doc/module-design/runtime/Runtime模块设计.md`。

## 10. 项目接入模型

项目接入建议按以下顺序完成。

### 10.1 Storage

- 注册 `param_store` 和 `deploy_store`。
- 定义运行期参数键名、默认值和保存策略。
- 提供洗车方案 JSON 与 manifest。
- 注册 `engine_program_loader_port`。

### 10.2 HAL

- 注册真机 `hal_io`、`hal_sensor`、`hal_vfd`、`hal_voice`、`hal_motor_exec`。
- 注册 `engine_io_ops_t`，把方案中的 signal/output/axis 名称映射到真实硬件。
- 实现安全切断与急停输入端口。

### 10.3 Domain / Application

- 组合 `device_control/patterns` 形成项目命名机构 API。
- 通过 `machine_ops_port` 注册 `start_wash`、`abort_wash`、`home_device`、`abort_home`、`execute_manual_actuator`、`stop_all_outputs`、`is_wash_entry_ready`。
- 洗车/归位编排由项目实现：框架提供 `engine_session` 作为通用会话 worker，选方案与机构动作由项目在 `machine_ops` 中承接。
- 定义报警目录并调用 `project_bind_alarm_catalog()` 加载。
- 实现 detector，经 `alarm_binding_port` 触发/清除。
- 提供项目 `alarm_reeval_binding_t` 表，把动作完成或流程检查点绑定到项目 `reeval_group`。

### 10.4 Cloud

- 定义项目 `cloud_point_entry_t[]` 物模型表，经 `cloud_model_bundle_t` 注册。
- 在 `project_validate()` 调 `cloud_model_validate()`，在 `project_init_adapters()` 调 `cloud_model_init()` 与 `cloud_model_json_install()`。
- 定义 `report_policy_entry_t[]` 上报策略，在 `project_register_runtime_tasks()` 经 `report_scheduler_register()` 注册（策略直接交给调度器，不经 `cloud_model` 转发）。
- 将 `DEVICE_CMD` 点位通过 `cloud_point_set_device_cmd_submit()` 回调接到 `device_command_port`。
- 选择云 provider，在 `project_configure_adapters()` 配置，在 `project_init_adapters()` 初始化。

### 10.5 Runtime

- 实现 `wiring()` 与 `project_hooks_register()`，填满 `project_hooks_t` 的 15 个函数指针（空实现也要提供）。
- 决定哪些 provider 在构建期开启，以及 link 哪些 `wdf_*` 分层目标。
- 决定是否接入急停轮询适配器与可观测事件桥（在 `project_init_adapters()` 中）。
- 在 `project_register_runtime_tasks()` 注册项目周期任务。
- 仅将无法纳入 scheduler 的项目线程放入 `project_start_runtime()`。
- 验证 `bootstrap_run()` 的启动顺序满足项目依赖；返回失败时必须终止进程。

详见 `doc/module-design/integration/Demo与项目接入模块设计.md`。

## 12. 后续可沉淀方向

以下能力来自旧规格或项目实践，其中只有通用抽象适合进入框架：

| 能力 | 建议归属 | 说明 |
|------|----------|------|
