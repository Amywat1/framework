## 1. 设计目标与核心理念

命令网关是外部控制请求的**唯一业务入口**：云端、CLI、仿真等来源解析为 `dev_cmd_t` 后，经端口提交，在独立 **`cmd_control`** 线程完成模式裁决与副作用执行。主路径为异步入队；同步提交仅为适配。软全停（`STOP_ALL`）相对普通命令优先，且可合并/抢占。

### 1.1 设计目标

- **统一入站契约**：所有外部命令走 `device_command_port`；主 API 为 `submit_async`，`submit_sync` 为阻塞适配。
- **控制面隔离**：命令 drain 在 `cmd_control`，与 `event_dispatch` 上的重业务 handler 隔离。
- **软停止优先**：`DEV_CMD_STOP_ALL_OUTPUTS` 优先 drain；队列满时可抢占非优先槽；连续 async STOP 合并。
- **裁决与执行分离**：domain 层 `operational_mode` 做权限与模式转移；application 层 `side_effect_router` 调 orchestrator/HAL。
- **完成通知**：统一发布 `EVT_OP_MODE_CMD_HANDLED`；sync 额外经 sem 取回 `dev_cmd_receipt_t`。
- **可观测**：裁决拒绝、模式变更、命令处理完成经 `event_bus` 广播。

### 1.2 核心理念

| 原则 | 规定 |
|------|------|
| 命令词汇在 domain | `dev_cmd_kind_t`、`dev_cmd_t` 定义于 `device_command.h`；port 只引用 |
| 表驱动权限 | `k_cmd_matrix[kind][mode]` 静态矩阵 + 条件分支（急停、报警、service_enabled） |
| 裁决与执行分离 | domain 只做许可与模式转移；application 按 `kind` + 裁决前模式执行同步 HAL |
| 模式单线程 | `operational_mode` 不订阅 event；外部生命周期通过显式 `op_mode_on_*` 钩子驱动 |
| 唤醒不经事件总线 | `cmd_control` 用专用 `sem_wait`；命令载荷保存在网关队列 slot |
| STOP 优先 | `STOP_ALL` 先于普通命令 drain；满队列可抢占非优先槽；async STOP 可合并 |

### 1.3 处理流水线

```text
  CLI / Cloud / Sim
        │
        ├─ submit_async(cmd, &request_id)     ← 主路径：入队即返回
        └─ submit_sync(cmd, receipt, timeout) ← 适配：入队 + 阻塞等待
        │
        ├─ 分配 queue slot（STOP_ALL 可合并/抢占）
        └─ sem_post(cmd_control wake)
                    │
                    ▼
  cmd_control 线程：sem_wait → command_gateway_drain()
        │  （先 STOP_ALL，再普通命令）
        ├─ decision = op_mode_handle_command(cmd)  ← 锁内带出 mode_before
        │       └─ ALLOWED → side_effect_router_run(cmd, decision.mode_before)
        ├─ publish EVT_OP_MODE_CMD_HANDLED
        └─ async 释槽 / sync sem_post
```

### 2.2 依赖方向

```text
adapters / CLI / cloud submit 回调
        │ device_command_port
        ▼
   application/command_gateway
        ├── domain/op_mode/operational_mode
        ├── application/side_effect_router
        │       ├── side_effect_router（含自检）
        │       └── device_ops_port
        └── runtime/event_bus
```

**依赖禁令**：

- `operational_mode` 不得调用 `side_effect_router` 或 HAL；只产出裁决与模式转移（进态异步事件可在 domain 发布）。
- `side_effect_router` 不得做命令权限判断（假设 gateway 已裁决 ALLOWED）；按 `kind` 执行。
- port 层不得包含业务裁决逻辑。
- 除 `command_gateway` 外，模块不得直接写 `operational_mode` 内部静态状态（须走 `op_mode_on_*` API）。

## 4. 数据模型

### 4.1 设备命令（dev_cmd_t）

```c
typedef struct {
    dev_cmd_meta_t meta;   /* request_id, source */
    dev_cmd_body_t body;   /* kind + payload union */
} dev_cmd_t;
```

**命令种类（dev_cmd_kind_t，闭集）**

| 枚举 | 载荷 | 说明 |
|------|------|------|
| `DEV_CMD_START_WASH` | `start_wash.mode` | 启动洗车（仅 IDLE，且无阻塞报警；IDLE 蕴含总开关已开） |
| `DEV_CMD_STOP_WASH` | 无 | 手动中止洗车会话 |
| `DEV_CMD_STOP_OPERATION` | 无 | 停运：关闭运营总开关并落到 STOPPED（非自动化态：STOPPED/IDLE/WASH_DONE；洗车/自检/恢复/清障中拒绝） |
| `DEV_CMD_RESUME_OPERATION` | 无 | 重新授权运营（除 INIT 外任意模式；已开则幂等；不改模式） |
| `DEV_CMD_MANUAL_ACTUATOR` | `act_id`, `param` | 手动点动（仅 STOPPED；急停激活时拒绝）；项目须非阻塞下发，见 `device_ops` 契约 |
| `DEV_CMD_START_SELF_CHECK` | 无 | 启动自检（仅 STOPPED；急停激活时拒绝；LOCKOUT/blocking 允许） |
| `DEV_CMD_RECOVER` | 无 | 设备恢复：STOPPED 进入 RECOVERING 并发布 `EVT_OP_MODE_RECOVERY_REQUESTED`；IDLE 幂等成功；需运营总开关开启且无急停 |
| `DEV_CMD_STOP_ALL_OUTPUTS` | 无 | 手动全停：切断全部输出、中止洗车（不清障）、收敛到 STOPPED（除 INIT） |

**命令来源（dev_cmd_source_t）**：`CLOUD` / `CLI` / `SIM` / `TEST`（元数据，不参与矩阵）。

### 4.2 运行模式（operational_mode_t）

| 模式 | 含义 |
|------|------|
| `OP_MODE_INIT` | 初始化前占位（`operational_mode_init` 调用前） |
| `OP_MODE_STOPPED` | 停机（总开关开时可归位进运营；关则禁止归位）；**上电默认态且总开关开** |
| `OP_MODE_IDLE` | 运营待机（可接单；不变量：总开关开且无急停；`set_mode` 进 IDLE 时强制） |
| `OP_MODE_WASHING` | 洗车会话执行中 |
| `OP_MODE_ABORT_HOMING` | 中止归位中（停洗清障后进入 STOPPED） |
| `OP_MODE_WASH_DONE` | 洗车完成，等待客户离场（离场后进入 IDLE） |
| `OP_MODE_SELF_CHECK` | 自检中 |
| `OP_MODE_RECOVERING` | 恢复中（`recovery_service`：锁存告警复位 + 异步归位 + 阻塞告警验证） |

故障（急停 / blocking / LOCKOUT）由旗标与安全快照表达，**不设**独立故障模式；带故障停机时模式仍为 `STOPPED`。

聚合内还维护：

- `s_estop_active`：急停标志（影响 CONDITIONAL：START_WASH / MANUAL_ACTUATOR / START_SELF_CHECK / RECOVER@STOPPED）
- `s_service_enabled`：运营总开关（关则禁止 RECOVER；`STOP_OPERATION` 关并切 STOPPED；`RESUME_OPERATION` 仅重新授权）

### 4.3 裁决结果（dev_cmd_decision_t）

```c
typedef struct {
    op_cmd_result_t    verdict; /* ALLOWED / DENIED */
    op_reject_reason_t reason;
    operational_mode_t mode_before; /**< 裁决前模式（与 verdict 原子） */
} dev_cmd_decision_t;
```

许可结果含锁内快照的 `mode_before`；gateway 交给 `side_effect_router_run(cmd, decision.mode_before)`，避免钩子插入导致过期。

**拒绝原因（op_reject_reason_t）**

| 枚举 | 典型场景 |
|------|----------|
| `OP_REJECT_WRONG_MODE` | 矩阵 DENIED 或 START_WASH 有 blocking 报警 |
| `OP_REJECT_ESTOP_ACTIVE` | CONDITIONAL 命令且急停有效 |
| `OP_REJECT_SERVICE_DISABLED` | RECOVER 且 service_enabled=false（典型在 STOPPED；IDLE 不变量已蕴含总开关开，该原因不可达） |
| `OP_REJECT_VEHICLE_NOT_READY` | START_WASH 但机型 `is_wash_entry_ready` 返回 false |
| `OP_REJECT_UNKNOWN_CMD` | kind 非法 |

### 4.4 回执（dev_cmd_receipt_t）

| status | 含义 | submit 返回 |
|--------|------|-------------|
| `DEV_CMD_STATUS_ACCEPTED` | 裁决通过且副作用 SW_OK | `SW_OK` |
| `DEV_CMD_STATUS_REJECTED` | 裁决 DENIED | `SW_ERR_STATE` |
| `DEV_CMD_STATUS_FAILED` | ALLOWED 但副作用失败 | `effect_error` |
| `DEV_CMD_STATUS_TIMEOUT` | sem 等待超时 | `SW_ERR_TIMEOUT` |
| `DEV_CMD_STATUS_BUSY` | 队列满或未入队 | `SW_ERR_BUSY` |

### 4.5 同步副作用（按 kind）

`side_effect_router` 按 `cmd->body.kind` 执行；`mode_before` 仅 STOP_ALL 需要。

| 命令 | router 行为 |
|------|-------------|
| `START_WASH` | `device_ops.start_wash(mode)` |
| `STOP_WASH` | `device_ops.abort_wash(WASH_ABORT_MANUAL)` |
| `START_SELF_CHECK` | 自检判定并发布 `SELF_CHECK_COMPLETED` |
| `MANUAL_ACTUATOR` | `execute_manual_actuator()`（须立即返回；不得等待点动结束） |
| `STOP_ALL_OUTPUTS` | `stop_all_outputs()`；若 `mode_before == WASHING` 再 `abort_wash(STOP_ALL)` |
| `STOP_OPERATION` / `RESUME_OPERATION` / `RECOVER` | 空操作（模式/旗标与 `RECOVERY_REQUESTED` 已在 domain 处理） |

### 4.6 相关事件

| 事件 | 发布方 | `param` 编码 |
|------|--------|--------------|
| `EVT_OP_MODE_CHANGED` | operational_mode | `(from << 8) \| to` |
| `EVT_OP_MODE_CMD_HANDLED` | command_gateway drain | `(kind << 16) \| (status << 8) \| reason` |
| `EVT_OP_MODE_RECOVERY_REQUESTED` | RECOVER 命令 | 0 |
| `EVT_OP_MODE_RECOVERY_COMPLETED` | recovery_service | `recovery_result_t` |
| `EVT_OP_MODE_HOME_COMPLETED` | 项目归位编排器 | 1=成功，0=失败 |
| `EVT_ABORT_HOME_REQUESTED` | operational_mode（进入 ABORT_HOMING 时） | 0 |
| `EVT_OP_MODE_CONTEXT_SYNC` | service_enabled / estop_active 变更 | 0 |
| `EVT_ABORT_HOME_DONE` | safety_session_coordinator（中止归位完成后） | 0 |
| `EVT_WASH_CUSTOMER_GONE` | 传感器/超时服务（客户已离场） | 0 |

## 5. 核心模块行为契约

### 5.1 command_gateway

**队列参数**

| 常量 | 值 | 说明 |
|------|-----|------|
| `CMD_GATEWAY_QUEUE_SIZE` | 4 | 最大在途命令（async/sync 共用） |
| `CMD_GATEWAY_WAIT_MS` | 5000 | `submit_sync` 且 `timeout_ms==0` 时的默认等待 |

**submit_async 行为**

1. 分配空闲 slot（`waiting=false`）；`STOP_ALL` 可合并已有 async 同类（不占新槽）。
2. 队列满且为 `STOP_ALL` → 抢占非优先槽（被抢占者 `CMD_HANDLED` status=BUSY）。
3. 队列满且非优先 → `SW_ERR_BUSY`。
4. `sem_post` 唤醒 `cmd_control`；立即返回 `request_id`。

**submit_sync 行为**

1. 若在 `cmd_control` 线程内调用 → 立即 `SW_ERR_STATE`。
2. 分配/挂接 slot（`waiting=true`）并唤醒 control。
3. `sem_timedwait`；超时或 generation 不匹配 → `SW_ERR_TIMEOUT`。
4. 拷贝 receipt，映射 `sw_err_t`。

**command_gateway_drain 行为**

- 在 **`cmd_control` 线程**执行（生产由 `scheduler_start_all` 启动登记线程）。
- 先处理全部 `STOP_ALL`，再处理其余：裁决 → 副作用 → `CMD_HANDLED`。
- async 由 drain 释槽；sync 由等待者释槽。

### 5.2 operational_mode — 命令矩阵

矩阵值：`OP_PERM_DENIED` / `OP_PERM_ALLOWED` / `OP_PERM_CONDITIONAL`。

**CONDITIONAL 附加规则**：若 `s_estop_active`，拒绝并返回 `OP_REJECT_ESTOP_ACTIVE`。

**业务附加规则**

| 命令 | 附加条件 |
|------|----------|
| `DEV_CMD_START_WASH` | 无 blocking 报警；若已注册则 `is_wash_entry_ready()` 为 true |
| `DEV_CMD_RECOVER` | `service_enabled`（总开关关时禁止正常归位和故障恢复） |
| `DEV_CMD_RESUME_OPERATION` | 无附加拒绝；已开则幂等（不改模式） |

**允许时的模式转移**

| 命令 | 模式/标志变更 |
|------|---------------|
| `DEV_CMD_START_SELF_CHECK` | → `OP_MODE_SELF_CHECK`（完成后一律回 STOPPED） |
| `DEV_CMD_RECOVER` | STOPPED → RECOVERING 并发布恢复请求；IDLE 不变 |
| `DEV_CMD_STOP_OPERATION` | → `OP_MODE_STOPPED` 且 `service_enabled = false` |
| `DEV_CMD_RESUME_OPERATION` | `service_enabled = true`（已开则幂等；模式不变） |
| `DEV_CMD_STOP_ALL_OUTPUTS` | → `OP_MODE_STOPPED`（不改总开关；按前态选择切断 / 切断+abort） |

> **观测窗口（有意取舍）**：`STOP_ALL` 在副作用执行前先 `set_mode(STOPPED)` 并发布 `EVT_OP_MODE_CHANGED`，因此存在短暂窗口——快照/遥测已显示 STOPPED，而 `stop_all_outputs` 尚未执行、输出可能仍带电。这样安排是为了让随后的 `abort_wash(STOP_ALL)` 到达时模式已非 WASHING，从而不会误入 `ABORT_HOMING` 清障。硬件急停走 `safety_cutout_execute()`，不受此窗口影响。离开 `RECOVERING` 后的归位等待由 `recovery_service` 订阅 `EVT_OP_MODE_CHANGED` 自行取消；迟到的 `HOME_COMPLETED` 在模式已非 RECOVERING 时忽略。

**外部生命周期钩子（非命令路径）**

| API | 触发场景 | 状态转移 |
|-----|----------|----------|
| `op_mode_on_wash_session_started` | IDLE | → WASHING |
| `op_mode_on_wash_session_completed` | WASHING | 无 blocking → WASH_DONE；仍有 MAJOR+ → STOPPED |
| `op_mode_on_wash_session_aborted(cause)` | WASHING | → ABORT_HOMING + 发布 ABORT_HOME_REQUESTED（急停/STOP_ALL 已先切 STOPPED 则忽略） |
| `op_mode_on_wash_customer_gone` | WASH_DONE | → IDLE |
| `op_mode_on_home_done()` | ABORT_HOMING | → STOPPED（仅 `EVT_ABORT_HOME_DONE`；运营归位不经本钩子） |
| `op_mode_on_self_check_completed(land_fault)` | SELF_CHECK | 一律 → STOPPED（`land_fault` 仅影响日志） |
| `op_mode_on_blocking_alarm` | 接单/自检等 | → STOPPED；WASHING/ABORT_HOMING/RECOVERING 保持当前流程 |
| `op_mode_on_estop(true)` | 任意 | → STOPPED，标志置位，发布 CONTEXT_SYNC |
| `op_mode_on_estop(false)` | 任意 | 标志清除，发布 CONTEXT_SYNC（不自动进 IDLE） |
| `op_mode_on_recovery_completed(result)` | RECOVERING | IDLE 结果 → IDLE；否则 → STOPPED |

**日志设计**

| 事件 | 级别 | 格式示例 |
|------|------|---------|
| 正常状态转移 | INFO | `op_mode: STOPPED -> RECOVERING` |
| 进入 ABORT_HOMING | WARN | `op_mode: WASHING -> ABORT_HOMING (critical)` |
| 命令被拒绝 | WARN | `op_mode: cmd 1 rejected (reason=2, mode=STOPPED)` |

### 5.3 side_effect_router

- 按 `cmd->body.kind` 分支；`STOP` / `RESUME` / `RECOVER` 直接 `SW_OK`。
- HAL 类命令：`device_ops_get()` 为 NULL 或函数指针 NULL → `SW_ERR_NOT_INIT`。
- `STOP_ALL`：先由 domain 切到 STOPPED；router 仅当 `mode_before == WASHING` 时再 `abort_wash(STOP_ALL)`。归位取消不在 router，由 `recovery_service` 监听模式变更。

### 5.4 op_mode_bridge — 事件驱动模式转移

`operational_mode` **不订阅** event_bus；异步生命周期由 `op_mode_bridge` 在 dispatch 线程调用 `op_mode_on_*` 完成。

**订阅表**

| 事件 | handler 行为 |
|------|--------------|
| `EVT_WASH_SESSION_STARTED` | `op_mode_on_wash_session_started` |
| `EVT_WASH_DONE` | `op_mode_on_wash_session_completed`（洗后评估） |
| `EVT_WASH_ABORTED` | 解码 cause → `op_mode_on_wash_session_aborted(cause)` → ABORT_HOMING |
| `EVT_WASH_CUSTOMER_GONE` | `op_mode_on_wash_customer_gone` → IDLE |
| `EVT_ALARM_TRIGGERED` | 存在 blocking 时调用 `op_mode_on_blocking_alarm`（急停码跳过，旗标只认 `EVT_HW_ESTOP_*`） |
| `EVT_HW_ESTOP_ON` | `op_mode_on_estop(true)` → STOPPED + CONTEXT_SYNC |
| `EVT_HW_ESTOP_OFF` | `op_mode_on_estop(false)` → 清标志 + CONTEXT_SYNC |
| `EVT_OP_MODE_RECOVERY_COMPLETED` | `op_mode_on_recovery_completed(param)` |
| `EVT_OP_MODE_SELF_CHECK_COMPLETED` | `op_mode_on_self_check_completed(param!=0)` |
| `EVT_ABORT_HOME_DONE` | `op_mode_on_home_done()` → STOPPED（ABORT_HOMING 路径） |

### 5.5 safety_session_coordinator — 安全会话

| 触发事件 | 行为 |
|----------|------|
| `EVT_HW_ESTOP_ON` | `safety_deferred_stop()` + `device_ops.abort_wash(WASH_ABORT_ESTOP)`；不跑 abort_home |
| `EVT_SAFETY_LOCKOUT` | `device_ops.abort_wash(WASH_ABORT_CRITICAL)`（不立即 deferred_stop；归位由 ABORT_HOMING 路径触发） |
| `EVT_ABORT_HOME_REQUESTED` | 启动 `device_ops.abort_home()`（异步）；`EVT_ABORT_HOME_DONE` 由项目在清障结束后发布 |

不订阅 `EVT_HW_ESTOP_OFF`：清急停标志由 `op_mode_bridge` 独占。

### 5.6 recovery_service — 故障恢复

位于 `application/orchestrators/`。订阅 `EVT_OP_MODE_RECOVERY_REQUESTED`（STOPPED 下 RECOVER 发布此事件），以及 `EVT_OP_MODE_HOME_COMPLETED` / `EVT_OP_MODE_CHANGED`。触发后：

1. `alarm_registry_reset_all()` 清除故障条件已经消失的锁存告警
2. 若仍为 LOCKOUT，则恢复失败且禁止归位
3. `device_ops.home_device()`
4. 归位完成后再次 `alarm_registry_reset_all()`，覆盖归位期间消失的故障条件
5. 归位成功且无 blocking 告警 → 发布 `EVT_OP_MODE_RECOVERY_COMPLETED(RECOVERY_RESULT_IDLE)`
6. 归位失败或仍有 blocking 告警 → 发布 `EVT_OP_MODE_RECOVERY_COMPLETED(RECOVERY_RESULT_FAILED)`

离开 `RECOVERING`（任意原因）时取消归位等待；模式已非 `RECOVERING` 时忽略迟到的 `HOME_COMPLETED`。

项目须在发布 `HOME_COMPLETED(成功)` 之前证明目标姿态（已在原点被跳过的 ON_MOTION 只 `clear` 条件）。`alarm_registry_reset_all()` 仅清除 `condition_active=false` 的可复位报警。

### 5.7 device_command_port API

```c
sw_err_t (*submit_async)(const dev_cmd_t *cmd, uint64_t *request_id);
sw_err_t (*submit_sync)(const dev_cmd_t *cmd,
                        dev_cmd_receipt_t *receipt,
                        uint32_t timeout_ms);
```

| API | 条件 | 返回值 |
|-----|------|--------|
| async | 已入队 | `SW_OK`（业务结果看 `EVT_OP_MODE_CMD_HANDLED`） |
| async | 队列/事件错误 | `SW_ERR_BUSY` 等 |
| sync | 已完成业务流水线 | `SW_OK`（receipt 内可能是 REJECTED/FAILED） |
| sync | 在 cmd_control 线程调用 | `SW_ERR_STATE` |
| sync | 队列/超时等 | `SW_ERR_BUSY` / `SW_ERR_TIMEOUT` 等 |
| 共用 | ops 未注册 | 调用方应检查 `device_command_port_get_ops() == NULL` |

项目云/面板接线优先 `submit_async`；CLI/产测可用 `submit_sync`。

## 6. 与云端模块的衔接

云端物模型 `CLOUD_KIND_COMMAND` 经 wiring 的 `cloud_json_install()` 登记 `cloud_point_set_device_cmd_submit()`，内部构造 `dev_cmd_t` 并调用本 port。云端脉冲命令通常只有 `kind`，无 `start_wash.mode` 等载荷；带载荷命令（如 START_WASH）须在 submit 回调中按云平台协议填充 `body.payload`。

详见 `doc/module-design/ports-adapters/CloudModel模块设计.md` §6。

## 7. 与事件总线的衔接

| 角色 | 说明 |
|------|------|
| 串行化 | submit 线程与 dispatch 线程解耦；模式状态只在 dispatch 线程变更 |
| 唤醒 | `cmd_control` 专用信号量；命令载荷在网关槽位，不经 event param |
| 广播 | 模式变更、拒绝、处理完成供上报、日志等订阅 |
| 非命令事件 | 洗车/急停/报警等经 **`op_mode_bridge`** 调用 `op_mode_on_*`，不经过 command_gateway 队列 |

`operational_mode` **不订阅** event_bus；`op_mode_bridge` 须与 `safety_session_coordinator`、`recovery_service` 同处于 dispatch 线程语义下初始化（见 §2.3）。

## 8. 完整接入示例

> **示例（单元测试 / 完整框架，仅供参考）**

```c
/* 启动 */
operational_mode_init();   /* → STOPPED */
command_gateway_init();
alarm_bridge_init();
op_mode_bridge_init();
/* 启动 event_dispatch 线程 */

/* 恢复设备并进入 IDLE */
dev_cmd_t recover_cmd = dev_cmd_make_simple(DEV_CMD_RECOVER);
dev_cmd_receipt_t receipt;
device_command_port_get_ops()->submit_sync(&recover_cmd, &receipt, 1000U);
/* HOME_COMPLETED → recovery_service → RECOVERY_COMPLETED → IDLE */

/* 提交洗车（项目侧亦可用 submit_async + 订阅 CMD_HANDLED） */
dev_cmd_t wash_cmd = dev_cmd_make_start_wash(WASH_MODE_STANDARD);
device_command_port_get_ops()->submit_sync(&wash_cmd, &receipt, 1000U);
/* ret==SW_OK && receipt.status==DEV_CMD_STATUS_ACCEPTED */
```

## 附录 A：命令矩阵速查

> 完整逻辑以 `operational_mode.c` 中 `k_cmd_matrix` 为准。下表为该矩阵的完整转录（8 命令 × 8 状态），列顺序与代码一致。

| 命令 \\ 模式 | INIT | STOPPED | IDLE | WASHING | ABORT_HOMING | WASH_DONE | SELF_CHECK | RECOVERING |
|--------------|------|---------|------|---------|--------------|-----------|------------|------------|
| START_WASH | D | D | C | D | D | D | D | D |
| STOP_WASH | D | D | D | A | D | D | D | D |
| STOP_OPERATION | D | A | A | D | D | A | D | D |
| RESUME_OPERATION | D | A | A | A | A | A | A | A |
| MANUAL_ACTUATOR | D | C | D | D | D | D | D | D |
| START_SELF_CHECK | D | C | D | D | D | D | D | D |
| RECOVER | D | C | A | D | D | D | D | D |
| STOP_ALL_OUTPUTS | D | A | A | A | A | A | A | A |

图例：A=ALLOWED，C=CONDITIONAL（急停有效时拒绝），D=DENIED。

矩阵之外的运行期附加条件（与矩阵值正交，即使矩阵为 A 也会检查）：

| 命令 | 附加条件 | 不满足时的拒绝原因 |
|------|----------|--------------------|
| START_WASH | 无 blocking 报警 | `WRONG_MODE` |
| START_WASH | 已注册时 `is_wash_entry_ready()` 为真 | `VEHICLE_NOT_READY` |
| RECOVER | `service_enabled` | `SERVICE_DISABLED` |

`START_WASH` 仅 IDLE 为 C：正常路径下急停/关总开关都会离 IDLE，C 的急停检查今日不可达，但作为开洗准入的防御保留；进 IDLE 时 `set_mode` 另强制 `service_enabled && !estop`，破坏则降级 STOPPED。`RECOVER` 在 IDLE 下矩阵为 A 且仍检查总开关，该态下恒成立；真正可观测的 `SERVICE_DISABLED` 发生在 STOPPED 且总开关关。`CONDITIONAL` 本身只查急停，不查运营开关。

`STOP_OPERATION` 与 `RESUME_OPERATION` 矩阵不对称是有意的：停运会关总开关并强制切到 STOPPED，故洗车/自检/恢复/清障中拒绝；恢复运营只翻开关、无硬件副作用，故除 INIT 外各态允许（已开则幂等）。读者勿把两行当成镜像填表。

`bootstrap` 完成后的初始态是 `OP_MODE_STOPPED` 且 `service_enabled == true`：此时可用的命令包括 `STOP_OPERATION`（关总开关）、`MANUAL_ACTUATOR`、`START_SELF_CHECK`、`RECOVER`、`STOP_ALL_OUTPUTS`、`RESUME_OPERATION`（幂等成功）。
