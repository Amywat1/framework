## 1. 设计目标与核心理念

报警子系统把硬件/流程/通讯异常转化为**可分级、可清除、可查询**的活跃报警实例，并通过事件总线驱动安全姿态与运行模式收敛。

### 1.1 设计目标

- **单一事实源**：活跃报警列表、会话 journal、pending 域事件均由 `alarm_registry` 维护。
- **端口隔离**：项目 detector 经 `alarm_binding_port` 触发/清除，不直接 `#include` registry 实现。
- **异步广播**：registry pending 经 `alarm_bridge`（50ms 周期 drain）转为 `EVT_ALARM_*`，并在边沿发布 `EVT_SAFETY_*`。
- **重评估桥接**：ON_MOTION 清除经生命周期事件与项目 binding 表映射到 `reeval_group`。
- **与运行模式解耦**：等级语义在报警域；模式转移由 `op_mode_bridge` / `operational_mode` 消费。

### 1.2 三条独立轴（等级驱动行为）

| 轴 | 回答问题 | 权威模块 |
|----|----------|----------|
| 报警等级 `alarm_level_t` | 严重度 + 运行时处置 | `safety_matrix.h` 行为属性表 |
| 安全姿态 `safety_posture_t` | 是否 LOCKOUT | `alarm_registry_safety_posture()`（CRITICAL 推导） |
| 运行模式 `operational_mode_t` | 允许哪些命令 | `operational_mode` |

等级语义：

| 等级 | 行为 |
|------|------|
| `MINOR` | 仅记录，不挡开洗 |
| `MAJOR` | blocking：禁开洗；洗中不中断；洗完仍活跃 → `STOPPED` |
| `CRITICAL` | LOCKOUT：立刻停机（经 `EVT_SAFETY_LOCKOUT`） |

清除策略仍独立：`AUTO_STATIC` / `ON_MOTION` / `MANUAL_RESET`。

上述两组语义都以**行为属性**表达，单一事实源是 `domain/safety/model/safety_matrix.h`；`alarm_registry` 的全部等级与策略判定都查这张表，不再各处写 `level >= MAJOR` 这类内联判断。未知等级取最严格值、未知策略不自动清除——漏配置若默认放行，现场表现是"有报警却照常开洗"或"安全状态被未定义行为解除"，比误停机危险得多。完整格点见 `doc/architecture/05-安全与报警架构.md` §3。

### 1.3 端到端事件链

```text
  项目 detector / HAL / CommWatchdog
        │ alarm_binding_port.trigger/clear
        ▼
  alarm_registry（活跃列表 + session journal + pending）
        │ alarm_bridge_drain()（50ms 周期）
        ▼
  EVT_ALARM_TRIGGERED / CLEARED
        ├─► 姿态边沿 → EVT_SAFETY_LOCKOUT / NOMINAL（同桥内）
        ├─► telemetry_projection
        └─► op_mode_bridge → op_mode_on_*

  命令 / 会话路径（正交）：
  START_WASH           → 存在 blocking 报警则拒绝
  WASH 正常结束        → 仍 blocking 则 STOPPED，否则 WASH_DONE
  DEV_CMD_RECOVER      → 复位已恢复的锁存告警 + home + blocking 验证
```

## 2. 分层归属与依赖方向

### 2.1 模块落位

| 层次 | 路径 | 职责 |
|------|------|------|
| **领域聚合** | `domain/safety/alarm_registry/` | catalog、active 池、journal、pending |
| **类型契约** | `domain/safety/model/alarm_types.h` | 码值、等级、清除、实例、域事件、`safety_posture_t` |
| **事件桥** | `application/bridges/alarm_bridge.*` | pending → `EVT_ALARM_*` + 姿态边沿 → `EVT_SAFETY_*` |
| **重评估桥** | `application/bridges/alarm_bridge.*` | lifecycle → `reevaluate_group` |
| **会话生命周期** | `application/bridges/alarm_bridge.*` | 洗车会话起止开关 journal |
| **入站端口** | `application/ports/inbound/safety/alarm_binding_port.h` | trigger/clear/load_catalog |
| **出站端口** | `domain/ports/outbound/safety/safety_port.h` | 急停码识别（项目注册 `safety_ops_t`） |

### 2.2 依赖方向

```text
项目 detector / watchdog（项目仓库）
        │ alarm_binding_port
        ▼
   domain/safety/alarm_registry
        │ pull_events
        ▼
   application/bridges/alarm_bridge → event_bus
        │
        ├─► EVT_SAFETY_*（桥内边沿）
        └─► op_mode_bridge / telemetry_projection
```

**依赖禁令**：

- `alarm_registry` 不得依赖 MQTT、云端或 `operational_mode`。
- `alarm_bridge` 不得解析机型业务，只做 pending 映射与姿态边沿。
- detector 不得绕过 port 直接写 registry 静态状态。

### 2.3 启动顺序契约

```text
bootstrap_bind()
    alarm_registry_init()           → 注册 alarm_binding_port
    project_bind_alarm_catalog()    → load_catalog + reeval_bridge_init
    ↓
bootstrap_init_services()
    alarm_bridge_init()       → 登记 50ms drain 周期任务（含姿态边沿）
    operational_mode_init()
    …
    alarm_bridge_init()
    op_mode_bridge_init()
    telemetry_projection_init()
    project_init_adapters()         → DI 防抖 / CommWatchdog
    ↓
bootstrap_start()
    project_start_runtime()         → alarm poll 线程等
    scheduler_start_all()
```

## 4. 数据模型

### 4.1 报警定义（alarm_def_t）

| 字段 | 说明 |
|------|------|
| `code` | 6 位报警码（`ALARM_CODE_MAKE`） |
| `level` | MINOR / MAJOR / CRITICAL |
| `clear` | AUTO_STATIC / ON_MOTION / MANUAL_RESET |
| `reeval_group` | ON_MOTION 重评估分组；非 ON_MOTION 填 `ALARM_REEVAL_GROUP_NONE` |
| `desc` | 描述 |

### 4.2 报警码编码

```text
报警码 = 大类 category(1) + 编号 index(3) + 性质 nature(2)
```

范围：category `1..9`，index `0..999`，nature `0..99`。  
通用大类/性质常量见 `alarm_types.h`；具体码表由项目目录提供。

### 4.3 域事件

| kind | 桥接为 |
|------|--------|
| `ALARM_DOMAIN_EVT_TRIGGERED` | `EVT_ALARM_TRIGGERED`（param=code） |
| `ALARM_DOMAIN_EVT_CLEARED` | `EVT_ALARM_CLEARED` |

实际删除活动告警时，对每条告警发独立 `CLEARED`，无 `BATCH_CLEARED`。

待发队列满时域事件会被丢弃——清除路径是批量操作（`reevaluate_group` /
`reset_all`），没有可以返回错误的单一调用方，无法像活跃池那样硬失败。改为累计
丢弃条数，由 `pull_events` 的 `dropped_out` 与本批事件**同锁**交出（分两次取会让
中间新产生的丢弃被当成已上报而清掉）。`alarm_bridge` 拿到非 0 即发
`EVT_ALARM_RESYNC`（param=丢弃条数，仅供诊断，不承载哪一条被丢的信息）。

凡按 `EVT_ALARM_*` 边沿维护派生状态的订阅者都必须订阅 `RESYNC` 并重读 registry
全量状态。框架内两处：`op_mode_bridge` 重判阻塞报警收敛，`telemetry_projection`
重刷安全快照。`observation_event_bridge` 按 INCIDENT/ERROR 记录，便于事后定位。

### 4.4 安全姿态

| 值 | 推导 |
|----|------|
| `SAFETY_POSTURE_NOMINAL` | 无 CRITICAL 活跃 |
| `SAFETY_POSTURE_LOCKOUT` | 存在 CRITICAL 活跃 |

由 `alarm_registry_safety_posture()` 计算；`alarm_bridge` 在 drain 后检测边沿并发布 `EVT_SAFETY_LOCKOUT` / `EVT_SAFETY_NOMINAL`。

### 4.5 容量与满池

| 宏 | 默认 | 说明 |
|----|------|------|
| `ALARM_CATALOG_MAX` | 64 | 静态目录 |
| `ALARM_ACTIVE_MAX` | 32 | 活跃池 |
| `ALARM_PENDING_EVENT_MAX` | 32 | pending |
| `ALARM_SESSION_JOURNAL_MAX` | 16 | 洗车会话 journal |

活跃池满时：打日志并返回 `SW_ERR_OVERFLOW`（无元告警、无驱逐）。
pending 满时：无法返回错误（见 §4.3），累计丢弃计数并经 `EVT_ALARM_RESYNC` 让
下游重读全量状态。

### 4.6 会话 journal

洗车会话期间触发的 MAJOR+ 码记入 journal，供后续云/CLI/业务消费；**不参与**洗后停机布尔判定（判定用当前 `alarm_registry_has_blocking_active()`）。

## 5. 核心模块行为契约

### 5.1 alarm_registry

下表 API 名省略 `alarm_registry_` 前缀，实际符号为 `alarm_registry_<名>`。

| API | 行为要点 |
|-----|----------|
| `load_catalog` | 逐条校验目录（码合法且唯一、等级与策略已定义、`ON_MOTION` ⇔ 非 NONE 分组），任一条不合法即整表拒绝 `SW_ERR_PARAM`；装载成功则清空 active / journal / pending |
| `trigger` | 表示故障条件成立；未知码 `SW_ERR_PARAM`；已 active 时刷新条件状态；池满 `SW_ERR_OVERFLOW` |
| `clear` | 表示故障条件消失；AUTO_STATIC 立即删除，MANUAL_RESET 保持锁存，ON_MOTION 等待重评估 |
| `reset_all` | 仅删除故障条件已消失的 MANUAL_RESET / ON_MOTION；条件仍成立时复位无效 |
| `reevaluate_group` | 对匹配的 ON_MOTION 告警确认条件消失并删除 |
| `has_blocking_active` | 存在 level ≥ MAJOR |
| `get_session_journal` | 拷贝本会话 MAJOR+ 码列表 |
| `copy_safety_view` | 一次持锁读出活动表 + blocking + 最高码 + 姿态；需要多项时一律走此接口 |
| `pull_events` | 取出 pending（FIFO），并同锁交出丢弃计数后清零 |
| `on_wash_session_started/ended` | 开关 journal 窗口 |

活动实例插入时即缓存 `level` / `clear` / `reeval_group`，目录在运行期不变
（`load_catalog` 会同时清空活动表），因此 `clear` / `reset_all` /
`reevaluate_group` 都只扫活动表一趟、不回查目录。遍历中删除时倒序扫描，
因为删除会前移后续条目。`has_blocking_active` 与 `safety_posture` 也复用
`copy_safety_view` 的同一次扫描，「MAJOR 阻塞开洗」「CRITICAL 进 LOCKOUT」
这两句判定在实现里各只出现一次。

### 5.2 alarm_bridge

| API | 行为 |
|-----|------|
| `init` | 注册 50ms 周期 drain |
| `drain` | `pull_events` → 发布 `EVT_ALARM_*`；丢弃计数非 0 则补发 `EVT_ALARM_RESYNC`；有变更则重算姿态边沿 |

drain 的排空轮次有上限（`ALARM_DRAIN_MAX_ROUNDS`）：待发队列可被上游持续写入，
无上界排空会让周期任务在报警抖动时长时间不返回。超出的事件留到下一拍，不会丢。

`drain` 由桥内互斥量串行化，可安全地被周期任务与项目 wiring 并发调用（demo 就在
主线程调它做同步验证）。锁整个 drain 而非只锁边沿判定：后者仍允许两个线程以相反
顺序发布 LOCKOUT/NOMINAL，对安全事件而言顺序倒置比多发一次更糟。锁序 bridge →
event_bus，无 handler 回调 drain，不成环。

这条串行化对应 ALRM-19，由 `test_alarm_event_bridge` 的并发用例验证：临界区内停留
钩子拉大窗口后断言重叠计数为 0；一次 CRITICAL 双线程 drain 只发一条 LOCKOUT。

### 5.3 alarm_bridge

项目提供 `alarm_reeval_binding_t` 表；桥接订阅 `EVT_COMP_MOTION_COMPLETED` / `EVT_WASH_CHECKPOINT_REACHED`，查表后 `reevaluate_group`。

### 5.4 alarm_bridge

订阅 `EVT_WASH_SESSION_STARTED` / `DONE` / `ABORTED`，调用 registry 会话起止 API。

### 5.5 alarm_binding_port

```c
typedef struct {
    sw_err_t (*trigger)(uint32_t alarm_code);
    sw_err_t (*clear)(uint32_t alarm_code);
    sw_err_t (*load_catalog)(const alarm_def_t *defs, unsigned count);
} alarm_binding_ops_t;
```

### 5.6 急停码判定（safety_port）

`op_mode_alarm_port_is_estop(code)`：由项目注册的 `safety_ops_t.alarm_is_estop` 回答（例如项目的急停 DI 报警码）；
供 `op_mode_bridge` 识别急停报警，与 `EVT_HW_ESTOP_*` 硬件路径并存。报警编码表属项目资产，故由项目实现。

注册安全端口时同时把 `estop_is_active` 绑到 `safety_output_hold`。机构「别再写输出」
不读电机绑定表里的第二根 DI，见 `doc/module-design/domain/机构控制模式模块设计.md`。

### 5.7 通讯 cutout（项目）

周期通讯丢失：若该条目 `level == CRITICAL`，watchdog 在 trigger 前同步 `safety_cutout_execute()`（不再单独配置 cutout 列）。

## 6. 与运行模式的衔接

| 衔接点 | 说明 |
|--------|------|
| START_WASH | `alarm_registry_has_blocking_active()` 则拒绝 |
| 洗车正常完成 | `op_mode_on_wash_session_completed`：仍 blocking → `STOPPED`，否则 → `WASH_DONE` |
| LOCKOUT | `EVT_SAFETY_LOCKOUT` → abort 洗车 + `op_mode_on_critical_alarm`（WASHING 中不立刻切模式，走中止/ABORT_HOMING） |
| Recover | 清可恢复告警 + 异步归位 → IDLE / STOPPED |
| 自检 | 查 LOCKOUT 与 blocking |

急停旗标只认 `EVT_HW_ESTOP_*`。DI 急停报警仍可投影为急停报警并进入 LOCKOUT，但不再置 `estop_active`，以免报警采样绕过采集器确认滤波。

## 8. 扩展指南

### 8.1 新增报警码

1. 在项目 config 表追加目录项（level / clear / reeval_group）。
2. `load_catalog` 加载——码须合法且全表唯一，`ON_MOTION` 须配非 NONE 分组、
   其余策略须配 `ALARM_REEVAL_GROUP_NONE`，否则整表被拒。
3. detector / 调用点经 `alarm_binding_port` 触发。
4. 按等级语义评估对开洗、洗中、洗后的影响。

### 8.2 新增 ON_MOTION 绑定

1. 定义 `reeval_group`。
2. 目录项 `clear=ON_MOTION` 并填 group。
3. wiring 提供 binding 表并 `alarm_bridge_reeval_init`。

### 8.3 新增 `EVT_ALARM_*` 订阅者

若订阅者按事件边沿维护派生状态（而非每次重读 registry），必须同时订阅
`EVT_ALARM_RESYNC` 并在收到时重读全量状态。否则待发队列溢出丢事件后，
该派生状态会静默停在旧值。

### 8.4 禁止

- detector 直接依赖 registry 实现文件。
- 在 bridge 内硬编码机型分支。
- 用事件 param 传递指针。
- 重新引入与等级重复的「响应策略」枚举，除非有可交叉的真实语义。
