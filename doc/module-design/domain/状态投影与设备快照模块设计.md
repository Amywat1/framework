# 状态投影与设备快照模块设计

**版本**：v2.0  
**状态**：已落地（统一快照 + 单一遥测投影；已接入 `bootstrap_run()`）  
**最后同步代码**：2026-08-20（`domain/telemetry/device_snapshot.*`、`application/telemetry_projection.*`）
**适用范围**：`domain/telemetry/`、`application/telemetry_projection.*`  
**架构基线**：事件驱动投影 + 单锁原子只读快照  
**关键词**：telemetry、device_snapshot、projection、read model、event_bus

---

## 1. 设计目标与核心理念

状态投影层把分散在运行模式、报警、安全姿态、洗车会话和云连接中的状态收敛成一个可查询的只读快照。写侧仍由各领域聚合维护事实源，读侧只保存事件驱动的投影副本，供云端上报、CLI、UI 或诊断读取。

### 1.1 设计目标

- **读写分离**：领域聚合是事实源，快照是只读缓存。
- **单锁原子读取**：四个子域存放在同一个静态结构中，由同一把互斥量保护；调用方一次加锁拿到全部子域的副本。
- **事件驱动刷新**：投影订阅事件后从事实源拉取最新状态，不在事件载荷中传递复杂结构。
- **跨子域一致**：读侧看到的运行模式、安全姿态、洗车模式和云连接状态来自同一时刻。
- **不承载业务决策**：快照只表达状态，命令裁决仍在 `operational_mode` / `command_gateway`。

### 1.2 为什么合并成单一快照

早期版本把三个子域拆成三个独立快照模块，各带一把锁，再由一个组合层分别读取后拼装。那种做法无法保证跨子域一致：拼装期间某个子域可能被投影刷新，读侧会看到"运行模式已进 EXCEPTION、安全姿态仍是 NOMINAL"这类自相矛盾的组合，而这恰好是诊断安全降级路径时最需要看清的时刻。

当前把四个子域并入 `device_snapshot_t` 并共用一把锁，`device_snapshot_get()` 一次加锁返回整体副本，一致性由结构本身保证，不再依赖调用顺序。

### 1.3 数据流

```text
领域事实源
  ├─ operational_mode
  ├─ alarm_registry
  ├─ 洗车会话事件发布方
  └─ cloud_link_port
        │ publish event
        ▼
event_bus dispatch
        │ telemetry_projection handler
        ▼
domain/telemetry/device_snapshot（单锁四子域）
        │ device_snapshot_get()
        ▼
云端上报 / CLI / 诊断
```

## 2. 分层归属与依赖方向

### 2.1 模块落位

| 层次 | 路径 | 职责 |
|------|------|------|
| **读模型 domain** | `domain/telemetry/device_snapshot.{h,c}` | 四子域快照存储、单锁读接口、派生判断 helper |
| **内部更新接口** | `domain/telemetry/device_snapshot_internal.h` | 投影专用写入口与测试复位 |
| **遥测投影** | `application/telemetry_projection.{h,c}` | 订阅模式/报警/安全/洗车/云事件，刷新快照 |
| **事件骨干** | `runtime/event_bus/` | 投影 handler 的串行触发机制 |

### 2.2 依赖方向

```text
application/telemetry_projection
        ├─ event_bus subscribe
        ├─ 读取领域事实源（operational_mode / alarm_registry）
        ├─ 读取 cloud_link_port
        └─ 调用 device_snapshot_internal 写接口

调用方（云上报 / CLI / 诊断）
        └─ device_snapshot_get()
```

**依赖禁令**：

- 公开头文件不得暴露更新接口；写入口只放在 `device_snapshot_internal.h`。
- `domain/telemetry` 不得依赖 `application/ports/outbound/cloud`；云连接状态由 application 层投影读取后写入。
- 投影 handler 不得长时间阻塞，不得执行网络上报。
- `device_snapshot_reset_for_test()` 不得在生产路径调用。

## 4. 快照数据模型

### 4.1 完整快照

```c
typedef struct {
    operational_snapshot_t  op;
    safety_snapshot_t       safety;
    wash_snapshot_t         wash;
    connectivity_snapshot_t connectivity;
} device_snapshot_t;

device_snapshot_t device_snapshot_get(void);
```

`device_snapshot_get()` 内部只加一次锁，返回整体副本。

### 4.2 运行模式子域

```c
typedef struct {
    operational_mode_t mode;
    bool               service_enabled;
    bool               estop_active;
} operational_snapshot_t;
```

| 字段 | 来源 |
|------|------|
| `mode` | `op_mode_get_current()` |
| `service_enabled` | `op_mode_is_service_enabled()` |
| `estop_active` | `op_mode_is_estop_active()` |

派生判断（`static inline`，入参为已取到的快照副本，不再自行读锁）：

| API | 语义 |
|-----|------|
| `operational_snapshot_is_stopping(s)` | 总开关关，或模式为 INIT/STOPPED/ABORT_HOMING/SELF_CHECK/RECOVERING |
| `operational_snapshot_is_standby(s)` | 模式为 IDLE（运营待机；蕴含总开关已开） |

### 4.3 安全/报警子域

```c
typedef struct {
    safety_posture_t posture;
    bool             blocking_active;
    uint32_t         top_alarm_code;
    unsigned         active_alarm_count;
    alarm_instance_t active_list[ALARM_ACTIVE_MAX];
} safety_snapshot_t;
```

四项数据由 `alarm_registry_copy_safety_view()` 一次持锁读出，因此活动表与安全姿态必然来自同一时刻。

告警态由 `device_snapshot_get().safety.blocking_active` 读出。

### 4.4 洗车会话子域

```c
typedef struct {
    wash_mode_t mode;
} wash_snapshot_t;
```

当前只记录最近一次 `EVT_WASH_SESSION_STARTED` 中的洗车模式。

### 4.5 连接性子域

```c
typedef struct {
    bool cloud_connected;
} connectivity_snapshot_t;
```

云连接状态本身不是领域事实，但读侧需要它与运行模式、安全状态在同一次读取中保持一致，因此并入快照。取值由 `telemetry_projection` 在云连接边沿事件到达时从 `cloud_link_port` 读取后写入；未注册云端口时按未连接处理。领域层不依赖任何云端口。

### 4.6 唯一读入口

读侧只有 `device_snapshot_get()` 一个入口，取回完整快照后按需读子域字段。

原先另有 `operational_snapshot_get()` / `safety_snapshot_get()` / `wash_snapshot_get()` 三个单子域包装，已删除。删除的理由不只是「无生产调用方」：包装看似便宜，实际每次都在持锁期间整体拷贝一份完整快照，而快照的大头是 `active_list[ALARM_ACTIVE_MAX]`（32 项，约 1KB）——为读 12 字节的运行模式拷 1KB，且这个代价从函数名上看不出来。留着它就等于给后来者留一个「读一个字段却拷全表」的入口，而 `device_snapshot.c` 一旦进入切断链路，这 1KB 就落在持锁区间内。

单入口同时消除了「分别调用三个包装取到不同时刻状态」这类误用：跨子域一致本就是本模块存在的理由。

## 5. 投影行为

`telemetry_projection` 是唯一的写侧，订阅表如下：

| 事件 | 行为 |
|------|------|
| `EVT_OP_MODE_CHANGED` | 从 `operational_mode` 拉取 mode/service/estop，刷新运行模式子域 |
| `EVT_OP_MODE_CONTEXT_SYNC` | 同上，用于 service_enabled / estop_active 等上下文同步 |
| `EVT_ALARM_TRIGGERED` | 刷新安全子域（活动表、blocking、最高码、姿态） |
| `EVT_ALARM_CLEARED` | 同上 |
| `EVT_SAFETY_LOCKOUT` | 同上 |
| `EVT_SAFETY_NOMINAL` | 同上 |
| `EVT_WASH_SESSION_STARTED` | 由 `wash_session_started_mode(param)` 解出洗车模式写入 |
| `EVT_CLOUD_CONNECTED` | 从 `cloud_link_port.is_online()` 刷新连接状态 |
| `EVT_CLOUD_DISCONNECTED` | 同上 |

两点订阅约束：

- **安全姿态边沿必须单独订阅**。`posture` 由 CRITICAL 告警驱动，但姿态事件与告警事件是两条独立发布路径；只订阅 `EVT_ALARM_*` 会让 LOCKOUT/NOMINAL 切换后快照里的 `posture` 滞后。
- **报警事件的 `param` 只用于事件语义**，投影刷新一律以 registry 当前状态为准，不从 param 推导快照内容。

当前**未订阅** `EVT_WASH_DONE` / `EVT_WASH_ABORTED`，因此洗车子域只表达最近一次启动的模式，不表达 busy/done/abort 状态。

`telemetry_projection_init()` 订阅成功后立即执行一次全量同步（运行模式、安全、云连接），确保初始读模型与当前聚合状态一致；同时注册 1000 ms 周期重建任务。周期任务调用公开的 `telemetry_projection_sync_all()`，并在事件总线 `dropped_count` 增长时记录诊断。因此可重建子域的最大滞后为一次 1000 ms 周期加调度延迟。

洗车子域例外：当前只表达最近一次启动模式，事实仅来自 `EVT_WASH_SESSION_STARTED`，没有可供拉取的独立会话事实源。`telemetry_projection_sync_all()` 不修改该子域，也不对其承诺事件丢失后的自动重建。

## 6. 初始化与启动边界

`bootstrap_init_services()` 已直接调用 `telemetry_projection_init()`，项目无需在 hook 中重复调用。调用点位于 `op_mode_bridge_init()` 之后，前置条件由启动序列保证：

| 前置 | 原因 |
|------|------|
| `event_bus_init()` | 订阅表需要总线已初始化 |
| `operational_mode_init()` | 初始同步要读运行模式聚合 |
| `alarm_registry_init()` + 报警目录已加载 | 初始同步要读安全投影 |

云端口是可选前置：未注册时初始同步把连接状态写为 `false`，后续注册并发出连接事件后自动刷新。

完整启动序列见 `doc/module-design/runtime/Runtime模块设计.md`。

## 7. 线程安全与一致性

| 对象 | 策略 |
|------|------|
| `device_snapshot_t` 全部子域 | 单一静态实例 + 单一 mutex |
| `device_snapshot_get()` | 一次加锁拷贝整体，跨子域原子 |
| 单子域兼容包装 | 各自一次加锁；多次调用之间不保证一致 |
| 投影 handler | 在 `event_dispatch` 线程串行执行 |

快照没有 init 入口，靠加载期零初始化。`device_snapshot_reset_for_test()` 供单元测试在 setUp 中消除用例间残留，避免断言绝对值时隐式依赖执行顺序。

## 8. 当前边界与扩展指南

### 8.1 已落地边界

- 四子域统一快照与单锁原子读取。
- 单一 `telemetry_projection` 覆盖运行模式、报警安全、安全姿态边沿、洗车启动模式、云连接边沿。
- 已接入 `bootstrap_run()`，不再需要项目显式初始化。

### 8.2 待项目或后续决定

- 是否扩展洗车子域，加入 busy、current phase、abort cause、direction 等字段。
- 是否把快照作为云物模型 get 回调的统一来源。

### 8.3 新增子域或字段

1. 先确认领域事实源和触发事件。
2. 在 `device_snapshot.h` 追加子域类型与字段，在 `device_snapshot_internal.h` 追加对应写入口。
3. 在 `telemetry_projection.c` 订阅事件并从事实源拉取状态，不在事件 `param` 中塞指针或复杂结构。
4. 派生判断写成入参为快照副本的 `static inline`，不要在 helper 内部再读一次锁。
5. 补充投影单元测试，覆盖初始同步和事件刷新两条路径。
