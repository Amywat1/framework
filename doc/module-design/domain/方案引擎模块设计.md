## 1. 设计目标与核心理念

通用方案控制引擎负责把“洗车方案”从硬编码流程拆成可配置的阶段、通道、步骤和动作。领域层只解释方案模型并按 tick 推进状态，不直接依赖具体 IO 板、变频器、电机 SDK 或文件系统。

### 1.1 设计目标

- **流程配置化**：洗车过程由 `engine_program_t` 描述，运行时只读方案模型。
- **硬件解耦**：引擎通过 `engine_io_ops_t` 按名称读 DI/轴；通过 `engine_actuator_ops_t` 提交机构意图（`resource/cmd/dir/gear/...`）。
- **表达式驱动**：进入/退出条件、触发条件、联锁条件与 `active_while` 等均由 `engine_expr` 编译并重复求值。
- **模板复用**：JSON 加载期支持 `program.templates` + step `use`，展开后进入统一运行模型。
- **轮廓查询解耦**：表达式可查询 `profile.*`，但车辆轮廓数据来源和分区算法由项目 provider 注入。
- **tick 推进**：外部固定周期调用 `engine_tick(dt_ms)`，引擎不创建线程。
- **加载与执行分离**：JSON 加载器只负责解析、编译表达式和语义校验；运行时只接收已构建的 `engine_program_t`。
- **安全优先**：每个 tick 先扫描 interlock，再推进 phase/step；`halt_all` 调用执行机构后端停机。

### 1.2 核心理念

| 原则 | 规定 |
|------|------|
| domain 不碰外设 | `engine.c` 只调用 `engine_io_get_ops()` / `engine_actuator_get_ops()`，不 include HAL/SDK |
| 方案内存所有权清晰 | `engine_load_program()` 接管 `engine_program_t`，`engine_destroy()` 释放 |
| 表达式预编译 | JSON 加载期将字符串编译为 `engine_expr_t`，tick 内只求值 |
| 模板只在加载期展开 | `templates` 不进入 runtime 模型；运行时只看展开后的 `engine_step_t` |
| profile 只定义查询契约 | `engine_profile` 不采集、不识别轮廓；项目 provider 决定数据来源 |
| 阶段串行、通道并行 | phase 按数组顺序串行推进；同一 phase 内 lane/step 每 tick 全量扫描 |
| 联锁高优先级 | `engine_tick()` 中 markers → interlocks → phase，联锁可中断后续流程 |
| IO/资源名校验可选 | 注册 `engine_io_catalog_t` / `engine_actuator_catalog_t` 时加载期校验；未注册时跳过 |

### 1.3 端到端数据流

```text
YAML（人维护）→ yaml2json → JSON 方案文件
        │
        ▼
engine_program_json
        ├─ cJSON 解析 program
        ├─ templates/use 展开
        ├─ engine_expr_compile()
        ├─ engine_program_validate()  ← 对照项目注册的 IO/执行机构目录
        └─ engine_program_t*
                │
                ▼
engine_load_program(engine, program)
                │
                ▼
engine_start()
                │
                ▼
周期调用 engine_tick(dt_ms)
        ├─ markers_tick()       ← engine_io.read_signal/read_axis
        ├─ interlocks_tick()    ← condition / reset_condition
        └─ phase_tick()
             ├─ entry_guard / on_enter
             ├─ lanes steps
             │    ├─ event step: trigger → actions(act/wait_time) → done
             │    └─ control step: active_while → actuator.submit(intent)
             └─ exit_guard / on_exit / advance phase
```

### 2.2 依赖方向

```text
application / orchestrator
        │ engine_program_loader_port / engine API
        ▼
   domain/program_engine/engine
        ├── domain/program_engine/model
        └── engine_io ops
                ▲
                │ engine_io_register()
   adapters/outbound/hal/sim/engine_io_sim

   adapters/outbound/storage/json/engine_program_json
        ├── domain/program_engine/model
        ├── domain/program_engine/engine/engine_expr
        ├── engine_program_validate
        └── third_party/cJSON
```

**依赖禁令**：

- `domain/program_engine/engine` 不得 include `adapters/`、文件系统或具体 HAL 头文件。
- `engine_program_loader_port` 不得依赖 JSON 适配器实现。
- `engine_program_json` 不得执行洗车流程，只构建模型并校验。
- `engine_io_sim` 仅用于仿真/测试，不应成为真机 wiring 的默认后端。

### 2.3 推荐启动顺序

框架提供 `application/engine_session/` 作为通用会话：它持有 engine 实例、登记 worker 线程、按周期调 `engine_tick()`，并暴露 start / abort / is_busy。**选哪个方案、何时启动、完成后发什么用例事件属于项目编排职责**，框架不提供 `wash_orchestrator`；项目通过 `machine_ops.start_wash` / `abort_wash` 接入命令链路。

项目层装配顺序：

```text
wiring()
    ├── engine_io_sim_register() / 真机 engine_io 后端 register
    ├── engine_actuator 后端 register
    ├── engine_program_json_register_loader()
    └── 其他 ports/adapters

项目编排器 init
    └── engine_session_init(storage, cfg)     // 配置 worker 线程名、栈、tick 周期

machine_ops.start_wash(mode)
    ├── 选方案 → engine_program_manifest_verify()
    ├── engine_program_load(path, err, errsz)
    └── engine_session_start(storage, run)    // 内部 engine_load_program + engine_start

会话 worker 周期
    └── engine_tick(engine, dt_ms)
```

## 4. 数据模型

### 4.1 顶层方案

```c
typedef struct {
    char schema_version[ENGINE_VERSION_MAX];
    char id[ENGINE_NAME_MAX];
    char name[ENGINE_DISPLAY_MAX];

    engine_param_t     *params;       unsigned param_count;
    engine_axis_t      *axes;         unsigned axis_count;
    engine_marker_t    *markers;      unsigned marker_count;
    engine_interlock_t *interlocks;   unsigned interlock_count;
    engine_phase_t     *phases;       unsigned phase_count;
} engine_program_t;
```

当前 JSON loader 支持 `schema_version == "1.0"`。

### 4.2 阶段、通道、步骤

```text
program
  └── phases[]                  串行
        ├── entry_guard
        ├── exit_guard
        ├── on_enter / on_exit
        └── lanes[]             phase 内并行扫描
              └── steps[]       lane 内按数组扫描
                    ├── event step
                    └── control step
```

**phase 字段**：

| 字段 | 含义 |
|------|------|
| `id` / `name` | 阶段标识与显示名 |
| `direction` | `none` / `forward` / `backward` |
| `entry_guard` | 阶段进入条件；未满足时停留等待 |
| `exit_guard` | 阶段退出条件；满足后执行 on_exit 并进入下一阶段 |
| `timeout_ms` | 阶段最大时长；校验要求非 0 |
| `on_timeout` | 超时策略：`stop` / `halt_phase` / `skip` / `degrade`；默认 `halt_phase` |
| `on_enter` / `on_exit` | 阶段进入/退出即时动作（`act` / `wait_time`） |
| `keep` | 可选：阶段退出时不自动释放的执行机构资源名数组 |
| `lanes` | 通道数组（必需、非空） |

### 4.3 event step

event step 是一次性动作步骤，状态流如下：

```text
WAIT_AFTER → ARMED → RUNNING → WAIT_DONE → DONE
                  │
                  └──────── actions_complete ───────→ DONE
```

| 字段 | 含义 |
|------|------|
| `trigger` | `condition`（`expr`）或 `signal`（`signal` + `edge`） |
| `guard` | 可选触发后守卫，失败则保持 ARMED |
| `actions` | 顺序动作，仅支持 `{act:{...}}` 与 `{wait_time:{ms}}` |
| `done` | 完成条件：`actions_complete` / `trigger_exit` / `signal` / `timeout` |
| `after` | 同 phase 内前置 step id，最多 `ENGINE_AFTER_MAX` 个 |
| `on_error` | done 超时或表达式失败时的策略 |

### 4.4 control step

control step 是持续机构意图输出：`active_while` 为真时提交 `intent`，为假时释放该资源。

| 字段 | 含义 |
|------|------|
| `active_while` | 为真时保持提交 `intent` |
| `intent` | `{resource, cmd, dir?, gear?, paths?}`，由项目 `engine_actuator` 解释 |
| `on_error` | 表达式求值失败时的策略，默认 `halt_phase` |

每个 tick 中：

```text
active_while == true  → actuator.submit(intent)
active_while == false → actuator.release(resource)（阶段切换时另按 keep 策略）
```

### 4.5 interlock

```c
typedef struct {
    char id[ENGINE_NAME_MAX];
    engine_expr_t *condition;
    engine_interlock_action_t action;
    engine_action_t *actions;
    unsigned action_count;
    int priority;
    engine_expr_t *reset_condition;
    bool auto_reset;
} engine_interlock_t;
```

| action | 行为 |
|--------|------|
| `halt_all` | 调用 `engine_actuator.halt_all()`，状态转 `ENGINE_STATE_HALTED` |
| `halt_phase` | 执行当前 phase on_exit、停 control 输出，状态转 `ENGINE_STATE_PHASE_HALTED` |
| `custom_action` | 立即执行 interlock actions，不改变运行状态 |

扫描顺序按 `priority` 升序。校验要求存在 id 为 `estop` 的 interlock。

### 4.6 marker 与 axis

marker 用于在 DI 边沿到达时锁存 axis 位置：

```text
marker.signal edge 命中
    └── engine_io.read_axis(marker.axis)
          ├── position → markers.<id>.position
          └── valid    → markers.<id>.valid
```

表达式可引用：

- `axes.<id>.position`
- `axes.<id>.speed`
- `axes.<id>.valid`
- `markers.<id>.position`
- `markers.<id>.valid`

## 5. 表达式系统

### 5.1 支持语法

| 类别 | 支持项 |
|------|--------|
| 算术 | `+`、`-`、`*`、`/`、一元负号 |
| 比较 | `>`、`<`、`>=`、`<=`、`==`、`!=` |
| 逻辑 | `AND`、`OR`、`NOT` |
| 三目 | `cond ? a : b` |
| 常量 | 数字、字符串、`true`、`false` |
| 变量 | `$param`、DI 名、axis、marker、phase 变量 |
| 函数 | `body_contains`、`body_covers`、`profile.height_at`、`profile.in_zone` |

除零返回 `0.0`，不会直接报错。未知变量会使本次求值 `ok=false`。

### 5.2 变量解析

运行时 `engine_resolve()` 解析变量：

| 变量形态 | 来源 |
|----------|------|
| `$name` | `engine_program_t.params` |
| `axes.<id>.position/speed/valid` | `engine_io_ops_t.read_axis` |
| `markers.<id>.position/valid` | engine 内部 marker runtime |
| `phase.elapsed_ms` | 当前 phase 累计时间 |
| `phase.direction` | `forward=1.0`、`backward=-1.0`、`none=0.0` |
| **其它标识符**（如 `GANTRY_FWD_LIMIT`） | **按 DI 信号名**调用 `engine_io_ops_t.read_signal(name)` |

框架**不内置**具体信号枚举表。方案里出现的 `GANTRY_FWD_LIMIT`、`LIFT_UP_LIMIT` 等名字：

1. **加载期**：作为表达式字符串由 `engine_expr_compile` 解析出变量；`engine_program_validate` 对照项目注册的 `engine_io_catalog_t.signals` 做存在性检查（catalog 未注册则跳过）。
2. **运行期**：`engine_resolve` 走「其它标识符 → `read_signal`」；项目 engine_io 后端用自己的信号名映射表把字符串映射到真实 DI。

以一个限位信号名 `GANTRY_FWD_LIMIT` 为例，四个环节各自的职责：

| 环节 | 位置 | 行为 |
|------|------|------|
| 方案文本 | 方案资产的 `active_while` / `exit_guard` | 仅是表达式字符串的一部分 |
| 编译 | `engine_expr_compile` | 识别为变量名，不绑定硬件 |
| 校验 | `engine_program_validate` + 项目 catalog | 名须出现在项目注册的信号名表中 |
| 求值 | `engine_resolve` → 项目 `engine_io_ops_t.read_signal` | 项目内部查表映射到自己的信号枚举，读滤波后信号 |

信号名表、枚举和 DI 通道绑定全部是项目资产；框架只保证「名字 → `read_signal(name)`」这一层转接稳定。

机构间的协调控制（如顶刷跟随车顶轮廓）由项目在自己的资源实现内聚完成，**不**通过
假 DI 把机构间门控塞进方案表达式：表达式只回答「条件是否满足」，一旦承担控制律，
方案资产就获得了绕过命令裁决与安全矩阵的旁路。框架侧对应的落点是
`domain/device_control/patterns/` 的通用模式与 `application/` 的编排器。

执行机构名（`intent.resource` 如 `gantry` / `lift` / `roof_follow`）同理：加载期对照 `engine_actuator_catalog`；运行期由项目 `engine_actuator` 适配器解释，不在表达式 DI 路径里。

### 5.3 内建函数

| 函数 | 语义 |
|------|------|
| `body_contains(pos, a, b)` | `pos` 是否落在 `[min(a,b), max(a,b)]` 内 |
| `body_covers(fixed_pos, front, rear)` | 固定机构位置是否被车身前后边界覆盖 |
| `profile.height_at(pos, default)` | 查询指定位置高度；无 provider 或查询失败时返回 `default` |
| `profile.in_zone("zone", pos, default)` | 查询指定位置是否处于命名分区；无 provider 或查询失败时返回 `default` |

`body_*` 是纯数学 helper，不依赖 provider。`profile.*` 只调用 `engine_profile_provider_t`：

```c
typedef struct {
    bool (*height_at)(void *ctx, double pos, double default_value, double *out_height);
    bool (*in_zone)(void *ctx, const char *zone, double pos, bool default_value, bool *out_in_zone);
    void *ctx;
} engine_profile_provider_t;
```

框架不定义扫描算法、分区名称集合或轮廓存储格式；项目在 wiring 阶段按需 `engine_profile_register()`。

### 5.4 编译与 clone

- `engine_expr_compile(text)`：语法错误返回 `NULL`，可通过 `engine_expr_last_error()` 获取错误描述。
- `engine_expr_clone(expr)`：深拷贝 AST，供 `engine_program_clone()` 使用。
- `engine_expr_foreach_var()`：用于加载期语义校验，遍历变量名并去重。

## 6. 运行时行为契约

### 6.1 生命周期

| API | 行为 |
|-----|------|
| `engine_create()` | 分配实例，初始 `ENGINE_STATE_IDLE`，`cur_phase=-1` |
| `engine_load_program(e, prog)` | 接管 `prog`，构建 runtime tables 和 DO 通道集 |
| `engine_start(e)` | 复位 marker/interlock，进入第 0 个 phase |
| `engine_tick(e, dt_ms)` | 推进 marker、interlock、phase |
| `engine_recover(e)` | 从 `PHASE_HALTED` 恢复当前 phase |
| `engine_destroy(e)` | 释放 runtime tables 和接管的 program |

### 6.2 状态机

| 状态 | 含义 |
|------|------|
| `ENGINE_STATE_IDLE` | 未启动或仅装载方案 |
| `ENGINE_STATE_RUNNING` | 正在执行 |
| `ENGINE_STATE_PHASE_HALTED` | 当前阶段暂停，允许 `engine_recover()` |
| `ENGINE_STATE_HALTED` | 全局终止，不通过 `recover` 恢复 |
| `ENGINE_STATE_DONE` | 所有 phase 完成 |

### 6.3 tick 顺序

```text
engine_tick()
    ├── markers_tick()       // RUNNING / PHASE_HALTED 下执行
    ├── interlocks_tick()    // RUNNING / PHASE_HALTED 下执行
    ├── 若状态不是 RUNNING，返回
    └── phase_tick()
```

**注意**：`phase.elapsed_ms` 在 `phase_tick()` 末尾累加。因此某一拍内表达式看到的是进入本拍前的累计时间。

### 6.4 phase 推进

1. 若 phase 尚未 entered，先求 `entry_guard`。
2. `entry_guard` 为真后执行 `on_enter` 一次。
3. 扫描所有 lane/step。
4. 累加 `phase_elapsed += dt_ms`。
5. 若达到 `timeout_ms`，按 `on_timeout` 处理。
6. 若 `exit_guard` 为真，执行 `on_exit` 并进入下一 phase。
7. 最后一个 phase 退出后状态转 `ENGINE_STATE_DONE`。

### 6.5 step 推进

event step 在单拍内允许级联推进，例如 `WAIT_AFTER → ARMED → RUNNING → DONE` 可在同一次 tick 完成，减少固定一拍延迟。

`wait_time` 是跨拍动作：

- 遇到 `wait_time` 后设置 `waiting=true`。
- 后续 tick 按 `dt_ms` 扣减。
- 倒计时结束后继续执行后续 action。

### 6.6 halt 与 recover

`halt_all`：

- 遍历装载方案时收集到的所有 DO 通道。
- 对每个 DO 写 `0`。
- 状态置为 `ENGINE_STATE_HALTED`。

`halt_phase`：

- 停止当前 phase 内所有 control step 输出。
- 执行当前 phase `on_exit`。
- 状态置为 `ENGINE_STATE_PHASE_HALTED`。

`engine_recover()`：

- 仅 `ENGINE_STATE_PHASE_HALTED` 可调用。
- 清除 `halt_phase` 类联锁 active 标志。
- 将 `RUNNING` / `WAIT_DONE` 中途步骤回退到 `ARMED`。
- 重新执行 `on_enter`。
- 不重置 `phase_elapsed`，避免多次恢复扩展最大阶段时长。

## 7. JSON 加载器契约

### 7.1 入口

| API | 行为 |
|-----|------|
| `engine_program_load_json_string(json, err, errsz)` | 解析 JSON 字符串并返回 program |
| `engine_program_load_json_file(path, err, errsz)` | 读取文件后调用 string loader |
| `engine_program_json_register_loader()` | 注册到 `engine_program_loader_port` |
| `engine_program_load(path, err, errsz)` | 通过已注册 loader 加载；未注册返回 `NULL` 并填错 |

### 7.2 支持的 JSON 子集

权威实现：`adapters/outbound/storage/json/engine_program_json.c`。YAML 经 `yaml2json` 转成同等 JSON。未知字段静默忽略；必需字段缺失、枚举非法、表达式编译失败返回 `NULL`。

**顶层 `program`**

| 字段 | 必需 | 说明 |
|------|------|------|
| `schema_version` | 是 | 仅 `"1.0"` |
| `id` / `name` | 建议 | 标识与显示名 |
| `params` | 否 | 对象，值为 number；非 number 按 `0.0` |
| `templates` | 否 | 对象或数组，可复用 step 片段 |
| `axes` | 否 | 对象，仅 `type == "physical"`（`encoder` / `pulse_per_mm` / `direction`） |
| `markers` | 否 | 对象，仅 `type == "latch"`（`axis` + `on.signal` / `on.edge`） |
| `interlocks` | 否 | 数组：`halt_all` / `halt_phase` / `custom_action` |
| `phases` | 是 | 非空数组 |

**`phases[]`**：`id`、`entry_guard`、`exit_guard`、`timeout_ms`、`lanes` 必需；可选 `name`、`direction`、`on_timeout`、`on_enter`、`on_exit`、`keep`。

**`lanes[]`**：`id`、`steps`（非空）。

**步骤 `type`**

| 类型 | 必需字段 | 可选 |
|------|----------|------|
| `control` | `id`、`active_while`、`intent` | `on_error`、`use` |
| `event` | `id`、`trigger`、`done` | `guard`、`actions`、`after`、`on_error`、`use` |

**`intent` / `act`**：`resource`、`cmd` 必需；可选 `dir`、`gear`、`paths[]`。

**动作原语（仅）**：`{act:{...}}`、`{wait_time:{ms}}`。

**`trigger.type`**：`condition`（`expr`）/ `signal`（`signal` + `edge`：`rising`/`falling`/`high`/`low`）。

**`done.type`**：`actions_complete` / `trigger_exit` / `signal`（`signal`+`state`，可带 `timeout_ms`）/ `timeout`（`timeout_ms`）。

**错误策略枚举**：`stop` / `halt_phase` / `skip` / `degrade`。

**步骤模板**：`use` 引用 `templates`；当前 step 除 `use` 外字段覆盖模板。

### 7.3 模板展开规则

模板是 JSON 加载期能力，不改变 `engine_program_t` 数据模型：

```json
{
  "templates": {
    "lift_hold_up": {
      "type": "control",
      "active_while": "LIFT_UP_LIMIT == 0",
      "intent": {"resource": "lift", "cmd": "move", "dir": "up", "gear": 1}
    }
  },
  "steps": [
    {"id": "lift_a", "use": "lift_hold_up"},
    {"id": "lift_b", "use": "lift_hold_up", "active_while": "true"}
  ]
}
```

规则：

| 规则 | 行为 |
|------|------|
| 模板表形态 | 对象 `{ "name": { ... } }`，或数组且每项带 `id` |
| 引用 | step 中 `use` 必须能找到模板 |
| 覆盖 | 当前 step 除 `use` 外的字段覆盖模板同名字段 |
| 校验时机 | 展开后再走 `build_step()` 与 `engine_program_validate()` |
| runtime | 模板不进入运行时；`engine.c` 无感知 |

### 7.4 加载期语义校验

`engine_program_validate()` 当前检查：

| 检查项 | 失败条件 |
|--------|----------|
| program 非空 | `prog == NULL` |
| phases | `phase_count == 0` 或 `phases == NULL` |
| phase id | 重复 |
| estop interlock | 缺少 id 为 `estop` 的 interlock |
| marker axis | 引用未知 axis |
| marker signal | catalog 存在且 signal 不在 catalog |
| phase timeout | `timeout_ms == 0` |
| expression vars | 未知 `$param`、axis、marker、DI（对照 IO catalog） |
| intent.resource / paths | catalog 存在且资源/水路路径不在执行机构 catalog |
| trigger/done signal | catalog 存在且 DI 不在 catalog |
| after | 引用当前 phase 内不存在的 step |
| keep | catalog 存在且资源名不在执行机构 catalog |

### 7.5 manifest 校验

`engine_program_manifest_verify(json_path, manifest_path, err, errsz)`：

- 读取 JSON 文件并计算 SHA256。
- 读取 manifest JSON。
- 比对 manifest 中记录的 hash 与 size。
- 成功返回 `SW_OK`，不一致返回 `SW_ERR_CRC`，文件/格式问题返回 `SW_ERR_PARAM`。

`engine_program_manifest_path_from_json()` 将 `xxx.json` 推导为 `xxx.manifest.json`。

## 8. 仿真 IO 后端

### 8.1 后端行为

`engine_io_sim` 是内存表实现：

| 类型 | 测试注入 API | 未设置时 |
|------|--------------|----------|
| DI | `engine_io_sim_set_signal(name, value)` | 读 0 |
| Axis | `engine_io_sim_set_axis(name, pos, speed, valid)` / `engine_io_sim_get_axis_pos(name)` | 位置 0、速度 0、valid=false |

`engine_io_sim_register()` 同时注册 `engine_io_ops_t` 与 `engine_io_catalog_t`；`engine_io_sim_reset()` 清空两张表，供用例间隔离。

### 8.2 容量限制

| 宏 | 值 | 说明 |
|----|-----|------|
| `ENGINE_IO_SIM_NAME_MAX` | 48 | 单个名称最大长度 |
| `ENGINE_IO_SIM_SIGNAL_CAP` | 128 | DI 名条目上限 |
| `ENGINE_IO_SIM_AXIS_CAP` | 16 | 轴条目上限 |

容量满时新名称写入会被忽略；已有名称仍可读写。三项均定义在 `engine_io_sim.c` 内部，不对外暴露。

`engine_io_sim` 只提供 DI 与轴：机构输出走 `engine_actuator_ops_t`，其仿真后端是独立的 `engine_actuator_sim.*`，不在本表内。

## 10. 当前边界与项目接入

### 10.1 已落地边界

- 已具备配置模型、表达式、profile 查询接口、运行时、JSON loader、模板展开、loader port、仿真 IO 与仿真执行机构。
