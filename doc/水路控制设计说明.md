# 水路控制规格说明

版本：1.0  
适用范围：各类洗车机泵阀水路控制系统

---

## 1. 概述

### 1.1 设计目标

本文档定义一套**通用水路控制模型**，通过路径掩码与拓扑配置驱动泵阀输出，实现：

- 上层只声明「哪些逻辑水路应开启」，不逐个操作阀泵，也不处理共享泵协调
- 同一套机制支持不同阀泵布局的洗车机，机型差异收敛到配置表与 bindings
- 多路水路可并行开启，共享泵由引用计数自动管理
- 阀泵开关顺序与延时等待由机制统一保证，不阻塞洗车流程线程

### 1.2 适用场景

本规格适用于满足以下特征的泵阀水路控制：

**多路并行**  
幕布水、泡沫水、高压水等逻辑水路可同时或独立请求开启；每次请求表达为路径集合，而非单个 DO 翻转。

**共享泵**  
多台水阀共用一台或少数几台泵；泵的生命周期由所有活跃水路的引用共同决定，上层无需显式协调。

**阀泵时序**  
开启顺序为阀 → 延时 → 泵；关闭顺序为泵 → 延时 → 阀。延时参数由机型配置注入。

**非阻塞请求**  
路径切换请求立即返回；时序等待由 `periodic_task` 周期推进（`fluid_path_poll`，默认 10ms），洗车流程线程不得阻塞等待阀泵到位。

**机型可配置**  
路径数量、路径与执行器的依赖关系、引脚映射、时序毫秒值因机型而异；控制规则保持不变。

### 1.3 核心概念一览

```text
路径（Path）
  ├── 路径索引 path_idx（无名字编号）
  ├── 路径掩码 mask（目标态：哪些 path 请求开启）
  └── 拓扑 deps[]（该 path 依赖的执行器列表）

执行器（Actuator）
  ├── 通道索引 channel（无名字编号）
  ├── 槽位类型 slot（泵 / 水阀 / 气阀）
  └── 引用计数 ref（被多少条 path 共同使用）

映射与输出
  ├── 拓扑表（path → deps）
  ├── 引脚表（channel + slot → DO）
  └── 引擎 IO 聚合（工艺 DO 名 → path mask）
```

## 2. 映射层

水路控制分三层，各司其职：

| 层次 | 载体 | 内容 |
|------|------|------|
| **逻辑路径层** | domain 类型 + 项目拓扑表 | 路径索引、路径掩码、`path → deps` |
| **执行器层** | domain 类型 + 项目引脚表 | `(channel, slot)` 坐标；slot 类型跨机型通用 |
| **硬件引脚层** | 项目 bindings | `io_do_t`；仅 bindings 查表写 HAL |

上层（洗车引擎 IO 适配、应用编排）只操作**路径掩码**。  
domain 机制负责引用计数、阀泵时序与目标态收敛。  
bindings 负责引脚查找与 `hal_io` 输出。

配置与命名分工：

| 内容 | 归属 |
|------|------|
| 路径索引、通道索引的**语义命名** | `projects/<proj>/config/*_water_table.h` |
| 路径拓扑表、执行器引脚表 | `projects/<proj>/config/*_water_table.h` |
| 阀开 / 泵停延时 | `projects/<proj>/config/*_machine_config.h` |
| 工艺 DO 名 → path mask | `projects/<proj>/bindings/engine_io_*.c` |
| 路径掩码、引用、时序规则 | `framework/domain/device_control/patterns/fluid_path.*` |

`framework/domain/` 不得出现机型名、工艺名或 IO 引脚宏。

## 3. 逻辑路径（Path）

### 3.1 路径索引与掩码

路径用无名字索引 `0 .. N-1` 编号。路径掩码 `mask` 为 `uint32_t`：bit N 为 1 表示路径 N **请求开启**。

```c
typedef uint32_t fluid_path_mask_t;
#define FLUID_PATH_MASK(idx)  (1u << (unsigned)(idx))
```

一次调用可表达并行组合，例如 `mask = FLUID_PATH_MASK(0) | FLUID_PATH_MASK(2)` 表示同时请求路径 0 与路径 2。

路径索引上限受掩码位宽约束：建议不超过 31 条逻辑路径。

### 3.2 路径拓扑

每条路径在机型拓扑表中声明为 `fluid_path_def_t`：

```c
typedef struct {
    uint8_t                      path_idx;
    const fluid_path_actuator_key_t  *deps;
    uint8_t                      dep_count;
} fluid_path_def_t;

typedef struct {
    fluid_path_channel_idx_t ch;
    fluid_path_slot_t        slot;
} fluid_path_actuator_key_t;
```

| 字段 | 说明 |
|------|------|
| `path_idx` | 与掩码 bit 位置一致 |
| `deps` | 开启该路径需要涉及的执行器；可含阀、泵、气阀等 |
| `dep_count` | 依赖项数量 |

多条路径可共享同一 `deps` 项（典型：共用主泵）。共享关系在拓扑表中声明，不由上层代码判断。

> **示例（M8，仅供参考）** — 幕布水路拓扑：
>
> ```c
> /* path_idx = M8_WATER_PATH_CURTAIN */
> deps[] = {
>     { M8_WATER_CH_CURTAIN, FLUID_PATH_SLOT_WATER_VALVE },
>     { M8_WATER_CH_SHARED,  FLUID_PATH_SLOT_PUMP },
> };
> ```
>
> M8 共 5 条逻辑路径，均依赖共享主泵 `M8_WATER_CH_SHARED + FLUID_PATH_SLOT_PUMP`。

### 3.3 目标态与稳定态

机制维护两组路径掩码：

| 态 | 含义 |
|----|------|
| **目标态** | 上层最近一次请求的路径集合（`fluid_path_set` 写入） |
| **稳定态** | 阀泵时序已完成、确认到位的路径集合 |

上层只写目标态；稳定态由机制异步收敛。  
当目标态与稳定态不一致时，机制按差量规则切换，**先关后开**：

```text
to_close = stable & ~target
to_open  = target & ~stable
```

## 4. 执行器（Actuator）

### 4.1 通道与槽位

```c
typedef uint8_t fluid_path_channel_idx_t;

typedef enum {
    FLUID_PATH_SLOT_PUMP = 0,
    FLUID_PATH_SLOT_WATER_VALVE,
    FLUID_PATH_SLOT_AIR_VALVE,
    FLUID_PATH_SLOT_COUNT,
} fluid_path_slot_t;
```

| 概念 | 说明 |
|------|------|
| `channel` | 执行器归属通道，无名字索引，由项目配置赋值 |
| `slot` | 执行器类型，跨机型通用；时序分组为「泵类」（`PUMP`）与「阀类」（`WATER_VALVE`、`AIR_VALVE` 槽位） |

### 4.2 引用计数

每个 `(channel, slot)` 维护引用计数 `ref`，表示当前有多少条**已纳入稳定态或正在切换中**的路径依赖该执行器。

| 操作 | 规则 |
|------|------|
| 开启路径 | 遍历该路径 `deps`，逐项 `ref++`；仅 `ref` 从 0→1 时，该执行器纳入本次「打开」输出 |
| 关闭路径 | 遍历该路径 `deps`，逐项 `ref--`；仅 `ref` 从 1→0 时，该执行器纳入本次「关闭」输出 |

共享泵：路径 A、B 同时开启时，泵 `ref = 2`，只打开一次；关闭 A 后 `ref = 1`，泵保持运行；全部关闭后 `ref = 0`，泵才关闭。

### 4.3 执行器引脚表

引脚表将 `(channel, slot)` 映射到 `io_do_t`，仅供项目 bindings 查表，domain 不感知引脚。

| 列 | 说明 |
|----|------|
| `channel` | 通道索引 |
| `slot` | 槽位类型 |
| `pin` | DO 句柄 |

引脚表应覆盖拓扑表中出现的所有 `(channel, slot)` 组合。无效引脚（`IO_HANDLE_NULL`）不得静默忽略。

## 5. 阀泵时序

### 5.1 顺序规定

关闭与开启使用相反顺序；延时参数来自机型配置：

| 方向 | 顺序 |
|------|------|
| **关闭** | 关泵类 → `pump_stop_delay_ms` → 关阀类 |
| **开启** | 开阀类 → `valve_open_delay_ms` → 开泵类 |

延时为 0 时跳过等待，同步执行下一步。

```c
typedef struct {
    uint32_t valve_open_delay_ms;
    uint32_t pump_stop_delay_ms;
    uint8_t  channel_count;
} fluid_path_cfg_t;
```

| 字段 | 说明 |
|------|------|
| `valve_open_delay_ms` | 开阀后至开泵的等待（ms） |
| `pump_stop_delay_ms` | 关泵后至关阀的等待（ms） |
| `channel_count` | 机型通道数，不得超过 `FLUID_PATH_CHANNEL_MAX`（16） |

### 5.2 时序状态

| 状态 | 说明 |
|------|------|
| `IDLE` | 无延时等待；可接受新的差量切换 |
| `WAIT_CLOSE_PUMP` | 已关泵，等待泵停延时后关阀 |
| `WAIT_OPEN_VALVE` | 已开阀，等待阀开延时后开泵 |

时序推进由 `fluid_path_poll` 周期任务负责（`periodic_task_register`，周期 `THD_FLUID_PATH_POLL_PERIOD_MS`，默认 10ms）。`fluid_path_set` 与 `fluid_path_all_off` **不得阻塞**等待时序完成。

### 5.3 全关抢占

`fluid_path_all_off()` 置全关标志并清空目标态。机制下次推进时**绕过**差量与时序流程，直接调用 `all_off()` 关闭全部水路 DO，并重置内部状态。

应用层在洗车结束、急停等场景调用 `fluid_path_all_off()`；机制不感知设备 FSM。

## 6. 对外接口语义

上层通过以下接口与水路机制交互；语义由 domain 保证，与机型无关。

| 接口 | 语义 |
|------|------|
| `fluid_path_init(cfg, ops, paths, count)` | 加载拓扑与时序；初始化全关；注册 `fluid_path_poll` 周期任务 |
| `fluid_path_set(mask)` | 设置目标路径集合；非阻塞；覆盖式更新 |
| `fluid_path_all_off()` | 全关抢占；非阻塞 |

单元测试（`FLUID_PATH_UNIT_TEST`）额外提供 `fluid_path_poll(now_ms)` 与 `fluid_path_is_settled()`，由测试用例主动推进时序，不注册周期任务。

输出回调 `fluid_path_actuator_ops_t` 由项目 bindings 实现：

| 回调 | 语义 |
|------|------|
| `slot_set(ch, slot, on)` | 驱动单个执行器输出 |
| `all_off()` | 关闭本机型所有水路相关 DO |

bindings **不得**实现引用计数或阀泵时序。

## 7. 与洗车引擎的衔接

洗车引擎以 **DO 枚举名** 表达水路步骤输出（如 `io_set: {channel: WATER_CURTAIN, value: 1}`）。  
引擎配置**不出现**引脚号；引脚由 bindings 引脚表解析。

项目 IO 适配层（`engine_io_<proj>.c`）负责：

1. 维护各水路 DO 的状态缓存；
2. 在相关 DO 变化时，聚合为 `fluid_path_mask_t`；
3. 调用 `fluid_path_set(mask)`。

规则：

| 规则 | 说明 |
|------|------|
| 聚合而非直驱 | **不得**在 IO 适配层对每个 DO 直接调用 `slot_set` |
| 映射可合并 | 多个 DO 可映射到同一路径；一个 DO 也可对应一条路径 |
| 引擎无 path 概念 | 引擎只认识 DO 名；path 是机构层的抽象 |

> **示例（M8，仅供参考）** — 引擎 DO 到路径的聚合：
>
> | 引擎 DO 名 | 路径 |
> |------------|------|
> | `WATER_CURTAIN` | `M8_WATER_PATH_CURTAIN` |
> | `WATER_TOP_FOAM` | `M8_WATER_PATH_FOAM` |
> | `WATER_BUTTOM_FOAM` | `M8_WATER_PATH_BOTTOM_FOAM` |
> | `WATER_HIGHPRES_TOP` / `WATER_HIGHPRES_BOTTOM` | `M8_WATER_PATH_HIGHPRES` |
>
> `apply_water()` 通过静态映射表 `s_water_do_map[]` 将各 DO 状态变量聚合为 mask，再调用 `fluid_path_set()`：
>
> ```c
> static const struct {
>     const int        *p_state;
>     fluid_path_mask_t path_bit;
> } s_water_do_map[] = {
>     { &s_water_curtain,  M8_WATER_PATH_MASK(M8_WATER_PATH_CURTAIN)     },
>     { &s_water_top_foam, M8_WATER_PATH_MASK(M8_WATER_PATH_FOAM)        },
>     { &s_water_btm_foam, M8_WATER_PATH_MASK(M8_WATER_PATH_BOTTOM_FOAM) },
>     { &s_water_hp_top,   M8_WATER_PATH_MASK(M8_WATER_PATH_HIGHPRES)   },
>     { &s_water_hp_btm,   M8_WATER_PATH_MASK(M8_WATER_PATH_HIGHPRES)   },
> };
> ```

## 8. 完整配置示例

> **示例（M8，仅供参考）**

### 8.1 路径与通道命名

命名与拓扑、引脚表统一放在 `m8_water_table.h`：

```c
/* projects/m8/config/m8_water_table.h */
typedef enum {
    M8_WATER_PATH_CURTAIN = 0,
    M8_WATER_PATH_FOAM,
    M8_WATER_PATH_BOTTOM_FOAM,
    M8_WATER_PATH_BRUSH,
    M8_WATER_PATH_HIGHPRES,
} m8_water_path_id_t;

typedef enum {
    M8_WATER_CH_SHARED = 0,
    M8_WATER_CH_CURTAIN,
    M8_WATER_CH_FOAM,
    /* … */
} m8_water_channel_t;

#define M8_WATER_PATH_MASK(id)  FLUID_PATH_MASK(id)
```

### 8.2 拓扑表与引脚表（节选）

```c
/* 拓扑 */
{ M8_WATER_PATH_CURTAIN, m8_deps_curtain, 2 },
{ M8_WATER_PATH_FOAM,    m8_deps_foam,    2 },
/* … 共 5 条路径 */

/* 引脚 */
{ M8_WATER_CH_SHARED,  FLUID_PATH_SLOT_PUMP,        M8_IO_DO_WATER_PUMP },
{ M8_WATER_CH_CURTAIN, FLUID_PATH_SLOT_WATER_VALVE, M8_IO_DO_WATER_CURTAIN },
/* … */
```

### 8.3 时序参数

```c
#define CFG_WATER_VALVE_OPEN_DELAY_MS    200U
#define CFG_WATER_PUMP_STOP_DELAY_MS     300U
```

### 8.4 并行与共享泵行为（语义样例）

| 时刻 | 请求 mask | 稳定结果 |
|------|-----------|----------|
| T0 | `CURTAIN` | 幕布阀开，主泵开 |
| T1 | `CURTAIN \| FOAM` | 幕布阀 + 泡沫阀开，主泵保持（ref=2） |
| T2 | `FOAM` | 幕布阀关，泡沫阀开，主泵保持（ref=1） |
| T3 | `0` | 全关，主泵关 |

## 9. 实现职责边界

项目配置声明「哪些路径依赖哪些执行器」，机制负责「怎么安全地协调输出」。

### 9.1 固化在 domain 中

| 职责 | 说明 |
|------|------|
| 目标态 / 稳定态管理 | 接收 mask，维护差量 |
| 引用计数 | 按拓扑展开 deps，决定执行器实际开关 |
| 阀泵时序状态机 | 关泵→延时→关阀；开阀→延时→开泵 |
| 全关抢占 | `fluid_path_all_off` 绕过差量逻辑 |
| 周期 tick | `fluid_path_poll` 经 `periodic_task` 推进时序，不阻塞调用方 |
| 槽位类型分组 | 泵类 / 阀类时序分组 |

### 9.2 由项目配置 / bindings 决定

| 职责 | 说明 |
|------|------|
| 路径数量与命名 | `*_water_table.h` |
| 路径拓扑 | `*_water_table.h` 拓扑表 |
| 引脚映射 | `*_water_table.h` 引脚表 |
| 时序毫秒值 | `*_machine_config.h` |
| 引擎 DO → path 聚合 | `engine_io_*.c`（表驱动映射） |
| HAL 输出 | `*_water_setup.c` 中 `slot_set` / `all_off` |

### 9.3 硬性约束

- 不得为每条水路增加项目级 `xxx_on()` 硬编码 API；一律通过 `fluid_path_set(mask)`。
- 不得在 domain 硬编码机型名、工艺名或引脚。
- 不得硬编码「幕布机 / 隧道机」等分支；同一机制只依赖拓扑表与掩码。
- bindings 不得包含引用计数或时序逻辑。

代码落位（简要）：`framework/domain/device_control/patterns/fluid_path.{h,c}` 为实现载体；项目侧为 `*_water_table.h`、`*_water_setup.c`、`engine_io_*.c`。

## 附录 B：扩展场景

### B.1 新增机型

1. 新增 `*_water_table.h`：路径与通道命名、拓扑表、引脚表。
2. 新增 `*_water_setup.c`：`slot_set` / `all_off` + `fluid_path_init()`。
3. 在 `engine_io_*.c` 实现 DO → mask 表驱动聚合。
4. 在 machine setup 中调用 `*_water_setup()`（`hal_io` register 之后）。

**不改** `framework/domain/device_control/patterns/fluid_path.{h,c}`。

### B.2 新增一条逻辑水路

1. 在 `*_water_table.h` 分配 `path_idx`。
2. 拓扑表增加一行 `fluid_path_def_t`。
3. 若 deps 含新 `(ch, slot)`，引脚表增加对应行。
4. 引擎 IO 适配在 `s_water_do_map[]` 增加 DO → 该 path 的映射行。

**不改** domain API 与时序状态机结构。

### B.3 新增执行器槽位类型

1. 在 `fluid_path_slot_t` 增加枚举（domain 变更）。
2. 明确该 slot 归属泵类或阀类时序分组。
3. 项目拓扑表与引脚表引用新 slot。
